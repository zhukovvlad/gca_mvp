## 1. Что сделано по задачам

**Задача 1** (`ca67122`, правка п. 8 — `09b9a01`) — `backend/tests/conftest.py`:

* `worker_database_url(url, worker_id)` — три явные ветки: `master` → URL как
  есть; `^gw\d+$` → имя базы `gca_test` → `gca_gw<N>_test` (суффикс, не
  приставка); иное — громкий `RuntimeError`. Идентификатор — из штатной
  session-фикстуры `worker_id` pytest-xdist;
* `test_database_refusal_reason(url)` — вынесенное решение барьера (b); отказ
  остаётся `pytest.skip` на вызывающей стороне;
* `_create_worker_database(url)` — `CREATE DATABASE` через
  `psycopg.sql.Identifier`, подключением к служебной `postgres` в autocommit,
  только на gw-пути: master-путь ведёт себя как раньше;
* порядок в `db_engine` — по плану: worker URL → resolve + барьер (a) →
  барьер (b) → `ensure_mutation_allowed` → `CREATE DATABASE` → engine /
  `DROP SCHEMA` / миграции;
* +16 тестов в `tests/unit/test_worker_database.py` (дельта плана +13…16);
  в `test_db_guard_wiring.py` три вызова `db_engine.__wrapped__()` получили
  явный `"master"` (строки 149, 177, 196), утверждения не ослаблены.

**Задача 2a** (`7a2f4c7`) — рецепт `test-backend-parallel n` с обязательным
`n`; `ci` на этом шаге остался серийным.

**Задача 3** — замеры, реестр снятий (§3 ниже), этот devlog.

**Задача 2b** (`e0df7e8`) — default `n=12` из замера; `ci` переключён на

## 2. Замеры

### 2.1. Число собранных — дельта плана сошлась

База: 1416 passed / 6 skipped. После задачи 1: **1432 passed / 6 skipped**
(+16 при обещанных +13…16; 16, а не меньше, потому что п. 4 плана
параметризован пятью посторонними входами). Правленых существующих — три,
как и обещано. Число skipped — ровно 6 во всех прогонах, серийных и
параллельных.

### 2.2. Изоляция под xdist — работает

Первый же полный прогон `-n 8`: **1432 passed / 6 skipped / 0 errors**
(до правки на общей базе было 416 errors). Все восемь баз `gca_gw0..7_test`
созданы воркёрами самостоятельно, схема в них — head `0010`, 25 таблиц
(проверено `psql` после прогона — это же доказательство пункта DoD
«integration исполнились, а не пропустились», вместе со счётом skipped = 6).

### 2.3. Ускорение — замерено, и оно скромнее нижней границы спеки

Одно железо (16 ядер), тёплые базы воркёров, `--dist load`:

| Прогон | Время |
|---|---|
| серийно (эта сессия) | 291,6 с |
| `-n 4` | 194,0 с |
| `-n 8` | 173,1 с (дважды; холодный первый — 247,4 с) |
| `-n 12` | 151,0 с; повтор 140,6 с |

Default поставлен **12**. Итоговое ускорение backend-шага ~2,1× (291,6 →
~141–151 с), `just ci` целиком — см. §2.6.

**76,7 с из §1.2 спеки не подтвердились, и спека это предсказывала**: тот
замер снят с прогона, где 416 integration-тестов падали на setup, не сделав
ни одного запроса к БД. Куда девается время, разобрано замером по слоям:

* unit-слой: серийно 62,6 с → `-n 8` всего 50,5 с. Пол держат неделимые
  module-scoped фикстуры: разбор трёх реальных оферт — 22,6 с setup на одном
  воркёре (и он повторяется на каждом воркёре, которому достались тесты этого
  модуля, — цена `--dist load`, названная в спеке §3 п. 2);
* integration-слой: серийно 242,3 с → `-n 8` 92,8 с (2,6×) — БД-работа
  параллелится, но восемь воркёров на одном кластере контендятся (setup
  `db_engine` растёт с ~6 до 9–12 с на воркёра);
* сумма слоёв по отдельности (50,5 + 92,8 = 143 с) меньше полного прогона
  `-n 8` (173 с): в смешанном прогоне тяжёлые module-фикстуры размазываются
  по воркёрам ещё хуже.

### 2.4. Контрольный замер `--dist loadfile` — расходится с основанием спеки

Спека §3 п. 2 отвергла `loadfile` сравнением его пола (116 с тяжёлого файла)
с 76,7 с — числом, которое не подтвердилось. Контрольный замер на
исправленном наборе: **`-n 8 --dist loadfile` — 146,3 с**, то есть *лучше*
`-n 8 --dist load` (173 с) и вровень с `-n 12 --dist load`. Причина понятна
из §2.3: loadfile не дублирует module-scoped фикстуры по воркёрам.

Решение спеки не пересматривалось — ship идёт на `--dist load` с `n=12`,
как зафиксировано гейтами. Но замер записан здесь именно потому, что
основание того отвержения оказалось ложным: если возникнет желание дожать
ещё ~10 с или снизить число баз, `loadfile` — готовый кандидат с уже снятым
числом, решение за пользователем.

### 2.5. Ускорение проверено «снятием» по определению

Прогон без правки — это серийный `just test-backend-local`: 291,6 с на том же
железе в тот же день. Оба числа из реальных прогонов, не пересказ.

### 2.6. `just ci` целиком

До фичи ~330 с (§1.1 спеки, при backend-шаге 251 с). Финальный прогон после
переключения `ci` на `test-backend-parallel` — **251,2 с** (`time just ci`,
4 м 11 с, зелёный целиком): выигрыш ~80 с против базовой суммы спеки, и он
целиком за счёт backend-шага. Оговорка о разбросе: серийный backend в *этой*
сессии шёл 291,6 с (спека даёт разброс 251…307), так что против серийного
прогона того же дня выигрыш ближе к ~120 с. Стенд `gca_dev` не участвовал ни
в одной команде; `db-test-check` остался на одной `gca_test`.

## 3. Реестр негативных проверок — все десять, лично

Метод — [verifying-guards](../insights/verifying-guards.md), все восемь
слоёв: перед каждым снятием контрольный зелёный прогон (23 теста:
16 новых + 7 wiring); снятие метится маркером `СНЯТИЕ N` и проверяется
`grep -c` (слой 2); восстановление — побайтовой копией с сверкой sha256
(`24916a38…` до и после каждого снятия); ожидаемое число собранных сверялось
в каждом прогоне — ни один прогон не собрал ноль.

| № | Что снималось | Ожидалось | Получено |
|---|---|---|---|
| 1 | master получает перестроенный URL | красный п. 1, gw-ветка зелёная | ✓ ровно `test_master_returns_url_unchanged`, 22 зелёных |
| 2 | приставка `gca_test_gw0` (unit-уровень) | красный п. 3 | ✓ пп. 2, 3, 5 красные; пп. 10–11 ушли в **skip** через живой барьер — та самая тихая феноменология, см. ниже |
| 3 | валидация входа убрана | красный п. 4 | ✓ все 5 параметров п. 4 |
| 4 | `RuntimeError` → `pytest.skip` | красный п. 4, **не** skipped | ✓ 5 failed, 0 skipped — ловушка `pytest.raises(BaseException)` + `isinstance` сработала; с наивным `pytest.raises(RuntimeError)` тест ушёл бы в skipped и снятие прошло бы тихо |
| 5 | URL пересобран без порта и пароля | красный п. 5 | ✓ ровно п. 5; п. 11 остался зелёным (все четыре точки видят одинаково сломанный URL — потоку данных перестановки нет) |
| 6 | барьер (b): функция всегда `None` | красные пп. 6 и 8 | ✓ ровно пп. 6 и 8. Прогон п. 8 прошёл мёртвый барьер и упал на **заведомо несуществующей** базе-пробнике — реальная мутация исключена конструкцией теста |
| 7 | приставка при ЖИВОМ барьере, end-to-end | skipped 6 → сотни, прогон «зелёный» | ✓ integration `-n 8`: **23 passed, 675 skipped, 0 failed, код возврата 0** — прогон выглядит зелёным, не проверив ничего; ловит только проверка «skipped ровно 6» |
| 8 | `CREATE DATABASE` раньше guard'а | красные пп. 9 и 10 | ✓ двумя под-перестановками: 8a (перед guard) — п. 10 красный, п. 9 зелёный; 8b (перед барьером (a)) — п. 9 красный. Одна перестановка не роняет оба: п. 9 и п. 10 стерегут разные звенья порядка |
| 9 | перестройка URL после барьеров | красный п. 11, п. 7 зелёный | ✓ падение дословно предсказанное: «точки цепочки видели РАЗНЫЕ URL: {…gca_test, …gca_gw0_test}»; п. 7 отдельным прогоном — зелёный |
| 10 | guard получает исходный URL | красный п. 11 — **и только он** | ✓ 1 failed, 22 passed: п. 10 (порядок отказа) зелёный — дыра, которую ловит только четырёхточечный тест потока данных |

Два наблюдения сверх плана:

* **снятие 2 показало тихий пропуск и на unit-уровне**: пп. 10–11 при
  сломанном имени не падают, а скипаются живым барьером (b) — Skipped не
  ловится `pytest.raises(RuntimeError/_Sentinel)` и уносит тест в пропуск.
  Красные пп. 2/3/5 это компенсируют, но само поведение — иллюстрация того,
  почему счёт skipped обязан проверяться везде;
* **строка 6 реестра — это на самом деле две защиты** (слой 8): решение
  (чистая функция) и его обвязка (skip в `db_engine`). Снятие «функция всегда
  `None`» роняет п. 8 только потому, что п. 8 подаёт плохое имя через подмену
  генератора, а причину считает настоящей функцией — первая редакция теста
  стабила саму функцию, и снятие 6 её не роняло. Поймано до пуша, исправлено
  `09b9a01`; это четвёртый-бис случай того же класса, что и кандидат в инсайт.

## 5. Отступления от плана и находки

1. **Дельта +16 — верхняя граница вилки** (+13…16): параметризация п. 4
   пятью входами. Не расхождение, но названо.
2. **П. 8 переписан после первой редакции** (см. §3, строка 6) — стаб
   переехал с функции-решения на генератор имени. Без этого снятие 6 не
   доказывало бы живость барьера.
3. **Один тест добавлен сверх перечня плана**: gw-ветка с базой без суффикса
   `_test` → `RuntimeError` (`test_non_test_base_name_is_loud_runtime_error`).
   Тихие альтернативы (передать имя как есть → skip на каждом воркёре;
   дописать суффикс → воркёры проходят барьер, который серийный прогон не
   проходит) обе хуже громкого отказа — Global Constraint 4 плана.
4. **Ускорение скромнее нижней границы спеки** — разобрано замером, §2.3;
   основание отвержения `loadfile` оказалось ложным — контрольный замер
   записан, решение не пересматривалось, §2.4.
5. **cwd уезжал один раз** (`cd backend` при уже действующем `backend/`) —
   пойман на месте `pwd`, ни один замер от этого не пострадал; урок из памяти
   сессии подтверждён.

## 6. Названные границы

Без изменений против спеки §3: тяжёлый `test_import_fixture_e2e.py` (рычаг
module-scope импорта — отдельная фича, решение пользователя); `DROP SCHEMA`
остаётся; базы воркёров после прогона не удаляются; `db-test-check` на одной
`gca_test`; frontend не тронут. Новое знание к первой границе: под `load`
этот файл ещё и дублирует разбор fixture по воркёрам — module-scope импорта
дал бы двойной эффект (см. §2.3–§2.4).

Отдельно: `-n 12` в CI-воркфлоу согласован с локальным рецептом по букве DoD,
но раннер GitHub (`ubuntu-latest`) имеет 4 vCPU — его собственное оптимальное
`n` может отличаться. Замерить это можно только прогоном в CI; первый прогон
PR это покажет, порог `timeout-minutes: 20` оставлен с запасом.

## 7. Кандидат в инсайт — подтверждён реализацией
