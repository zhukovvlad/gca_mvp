Смысл колонки блока подрядчика теперь выводится из пары «тип группы + подпись
шапки», а не из числа колонок (`colspan`). Контракт парсера поднят до
`4.0.0` (мажор: у файлов ширины 10 из позиций исчезает ключ
`total_cost_for_organizer_quantity` и появляется `comment_contractor`).

Этот файл заводится задачей 6 (регрессия по четырём классам спеки §7 и
независимый замер сводной таблицы) и дописывается задачей 7 (финал ветки,
`just ci`, PR).

### Классификация: `compare_parse_snapshots.py before after`

Правила классификации — зеркало четырёх непересекающихся классов спеки §7
(`backend/scripts/compare_parse_snapshots.py`, функция `classify`). Прогон
дал ровно то, что заложено эталоном `EXPECTED_COUNTS`, без единого
`VIOLATION`:

| Класс | Файлов | Смысл |
|---|---:|---|
| **class1** | 18 | ширина 11, «Комментарий участника» последней колонкой — JSON **побайтно тот же** |
| **class2** | 3 | ширина 10, «Комментарий участника» последней колонкой — исправляющая дельта: `comment_contractor` появился, `total_cost_for_organizer_quantity` исчез, ложные предупреждения «значение не число» пропали |
| **class3** | 1 | сводная таблица (блоки 8 + 11 с «% от р/с» + 12×3) — раньше отказ на ширине 12, теперь разбирается |
| **class4** | 5 | не смета ГП в ожидаемом формате — отказ и до, и после, с тем же текстом ошибки |

`18 + 3 + 1 + 5 = 27`, `VIOLATION = 0`; `class1 + class2 = 21` совпадает с
`ok` снимка `before`, `class3 + class4` — с `error` снимка `before` (6);
`class1 + class2 + class3 = 22` совпадает с `ok` снимка `after`, `class4` — с
его `error` (5). Три числа (счётчики снимков и результат сравнения) сходятся
между собой независимо друг от друга.

Команда и код возврата:

```
cd backend && PYTHONIOENCODING=utf-8 uv run python -m scripts.compare_parse_snapshots before after
echo $?
```

`echo $?` — отдельной командой, не через конвейер (`docs/insights/silent-test-runs.md`):
успех этого прогона обязан читаться по коду возврата одной команды.

### Независимый замер сводной таблицы (class3): `verify_summary_sheet.py`

Единственный файл класса 3 (дайджест `74e53bdfc43b…`) — сводная таблица,
которая раньше отвергалась на ширине 12 и теперь разбирается. Итоговый JSON
после постобработки не несёт всего, что нужно проверить (пустой блок
«Расчетная стоимость» заменяется заглушкой, отклонения подрядчиков
вычищаются), поэтому замер — в два этапа.

**Этап A (до `normalize_lots_json_structure`)** сверяет пять физических
блоков подрядчика (базовый + четыре предложения) поколоночно: JSON против
сырого чтения листа по литеральным координатам замера плана (`col_start`
10/19/31/44/57, `header_row` 11, первая строка данных 13) — независимо от
того, правильно ли `resolve_contractor` разметил колонки блока.

**Этап B (после `parse_estimate`)** утверждает внутри самого прогона пять
предпосылок задачи 6, а не принимает их на веру:

1. `proposals` — ровно `contractor_1..4`;
2. `baseline_proposal["title"]` равен `postprocess.BASELINE_MISSING_TITLE`;
3. `vat_rate == "22"` у всех четырёх предложений;
4. `deviation_from_baseline_cost` отсутствует на позициях (колонка на листе
   есть — её вычистило правило «нет валидной базы», спека §2.8);
5. предупреждения содержат «найдено 5» (число блоков подрядчика с базовым).

Команда:

```
cd backend && PYTHONIOENCODING=utf-8 uv run python -m scripts.verify_summary_sheet
```

**Отступление от плана (задача 6, этап A).** План требовал записать ключи
колонок каждого из пяти блоков литеральными кортежами. Скрипт вместо этого
держит канонические кортежи, измеренные при планировании (`KEYS_8`,
`KEYS_TENDER_11`, `KEYS_12`), и выбирает нужный по ШИРИНЕ блока, прочитанной у
`read_contractors`. Независимость эталона от проверяемого при этом
сохраняется: `read_contractors` фича не меняла, а сами кортежи — замер плана,
а не вывод `resolve_contractor`. Ширины 8/11/12/12/12 в этом файле дают
однозначное соответствие, и `col_start` пяти блоков скрипт всё равно сверяет с
литералами 10/19/31/44/57, так что подмена файла или сдвиг блоков будут
замечены.

Пункт 2 — не молчаливое допущение (`docs/insights/false-test-premises.md`):
скрипт утверждает и печатает фактическую форму заглушки; что бы ни оказалось
по факту прогона, это записывается сюда без ослабления проверки задним

### Отступления от плана

| Что | Почему |
|---|---|
| Задача 2: два эскизных теста чистили ярус через `ws.cell(..., value=None)` | В openpyxl это **не операция**: тело `Worksheet.cell` — `if value is not None: cell.value = value`. Ярус не очищался, и обе проверки `TestHeaderTiers` были бы пустыми. Заменено на `ws.cell(...).value = None`; исходник модуля не тронут |
| Задача 3: удалён неиспользуемый импорт `BlockLayout` в `test_resolve_contractor.py` | Пришёл из эскиза плана и валил `ruff` (F401 + I001), то есть DoD 9 |
| Задача 4, снятие 1: план предсказывал, что `TestMeasuredLayouts` останется зелёным | Не остался: из пяти измеренных раскладок покраснели четыре. Иначе и быть не могло — подставная таблица и ЕСТЬ канон ГП-11, с которым остальные раскладки не совпадают. Предсказание неверное, доказательство — нет: снятие покрасило свои целевые тесты, а лишняя краснота лишь подтверждает, что и эти пять стерегут «смысл по месту» |
| Задача 6: эталон этапа A выбирается по ширине блока, а не задан литералами на каждый блок | Записано выше, в разделе независимого замера |

### Найденные грабли

Обе — про инструмент, а не про домен; в devlog фичи, потому что план их не
предвидел, а следующая фича на них наступит.

1. **`Worksheet.cell(row=, column=, value=None)` в openpyxl ничего не пишет.**
   Очистить ячейку так нельзя — только `ws.cell(row=, column=).value = None`.
   Тест, который «очищает» ячейку первым способом, проверяет не то, что
   написано в его докстроке, и зелёным будет по совершенно другой причине.
2. **Переписывание файла целиком из Python переводит его в LF, и `git status`
   считает файл изменённым при пустом `git diff`.** Рабочее дерево здесь CRLF.
   Само по себе безобидно — но `snapshot_parse_samples.py` пишет в манифест
   флаг `dirty`, читая `git status --porcelain -- backend/parser`, а
   `compare_parse_snapshots.py` отказывается сравнивать грязный снимок. То
   есть правка докстроки скриптом могла отменить регрессионное сравнение с
   формулировкой, которая ни на что не намекает. Правки в существующих файлах
   — точечным редактированием, не перезаписью.

Обе выглядят кандидатами в `AGENTS.md` §11, но план такой правки не
предусматривал, и §11 — документ инвариантов: решение за пользователем.

### Границы

- **Импорт многоподрядного файла не входит в фичу** (спека §4): сводная
  таблица теперь РАЗБИРАЕТСЯ и предупреждает о числе подрядчиков, но что
  делать с `contractor_2..N` при импорте, решает фича 2.
- **Запись `deviation_from_baseline_cost` в `position_items`** — тоже фича 2,
  вместе с ревизией `AGENTS.md` §4. Здесь ключ доезжает до JSON и не дальше.
- Ни одна проверка не осталась выводом вместо прогона. Третий пункт дельты
  класса 2 — исчезновение ложных «значение не число» — исполнен настоящим
  `import_estimate` до `ImportOutcome.warnings` и сохранённого `PositionItem`
  (`TestWidthTenReachesImportCleanly`, integration, прогон на живом кластере),
  а не выведен из формы JSON.
