# 2026-07-20 — Локальный тестовый Postgres: backend-тесты за ~30 сек вместо 6–8 мин

**Ветка:** `main` (прямой коммит, код приложения не менялся — только justfile и docs)
**Метод:** systematic-debugging (root cause → сверка с CI и соседними проектами → замеры до/после)

## Задача

Интеграционные тесты локально шли очень долго (полный `just test-backend` —
6–8 минут). Выяснить корневую причину и ускорить, по возможности так же, как
это решалось в соседних проектах.

## Диагноз

- `TEST_DATABASE_URL` указывает на Neon eu-central-1 (Франкфурт) через pooler.
  Замер: **~43 мс RTT на каждый SQL-запрос**, ~1.4 с на установку соединения.
- 324 интеграционных теста × ~25 запросов × 43 мс ≈ 6 минут чистой сети.
  Контрольный файл `test_invoices.py` (59 тестов) — **63 с**.
- CI эту проблему уже не имеет: `backend-tests.yml` поднимает
  `pgvector/pgvector:pg16` service-container на раннере (~0.1 мс/запрос,
  полный прогон ~1 мин).
- Сверка с соседями: **Vendors** остались на Neon (перенесли к себе наш же
  паттерн session-scoped engine + savepoint, остаточный RTT приняли осознанно —
  у них БД источник истины: вьюхи/функции/триггеры); **CIW** — in-memory фейки
  без БД, интеграция skip по умолчанию. Готового чужого рецепта нет —
  правильный путь для UDP = повторить локально собственную CI-схему.

## Что сделано

1. **Портативный PostgreSQL 16.14 + pgvector 0.8.3** (conda-forge, micromamba) —
   целиком в `%LOCALAPPDATA%\Programs\udp-pgtest`, порт 5433, auth trust,
   без службы Windows, **без админ-прав и без Docker** (на машине нет ни Docker,
   ни WSL; VS Build Tools стоят без Windows SDK, поэтому MSVC-сборка pgvector
   из исходников невозможна — conda-forge оказался единственным бинарным
   каналом с pgvector под win-64).
2. **justfile:** `pg-test-start` / `pg-test-stop`, `test-int-local`,
   `test-int-local-k`, `test-backend-local`; `test-backend` (а значит и
   `just test`) теперь **авто-выбирает БД** — локальный PG, если установлен
   (`.../udp-pgtest/data` существует), иначе Neon из `.env` как раньше.
   `.env` не тронут: локальный URL передаётся инлайн-переменной
   (шелл-переменная имеет приоритет над dotenv внутри pytest — проверено).
3. **docs/testing.md:** раздел «Локальный тестовый Postgres» — зачем, что
   установлено, инструкция установки с нуля на новой машине, грабли с локалью.
4. **AGENTS.md:** новые команды в списке.

## Верификация

- `test_invoices.py`: 63.2 с (Neon) → **9.7 с** (localhost), ~6.5×.
- Полный backend через `just test-backend` (авто-маршрут на локальный PG):
  **579 passed, 6 skipped за ~30 с** (было 6–8 мин).
- `just lint` (ruff + eslint) чист, frontend 206 passed, `tsc` чист.
- Neon-путь (`just test-backend-integration`) не менялся и остаётся
  финальной проверкой перед PR; CI не затронут (гоняет `pytest` напрямую).

## Решения и нюансы

- **Грабли: `initdb --locale=C` ломает pg_trgm на кириллице.** В C-локали
  кириллица не классифицируется как alnum → триграммы пустые → similarity=0 →
  падал `test_duplicates_finds_similar_names`. Кластер пересоздан с
  `--locale="en-US"` (на Windows PostgreSQL использует wide-char CRT-функции,
  кириллица фолдится корректно). ICU в conda-forge win-64 сборке не собран.
- Порт 5433 — чтобы не конфликтовать с возможным системным Postgres.
- Сервер не автостартует после перезагрузки — его поднимает `just pg-test-start`
  (автозависимость всех `*-local`-рецептов), при отсутствии установки рецепт
  даёт понятную ошибку со ссылкой на docs/testing.md.
- pgvector в коде пока не используется (только `CREATE EXTENSION` в миграции
  `4424d8ac3601`), но расширение поставлено настоящее — когда появятся
  vector-колонки, локальный прогон их переживёт.
