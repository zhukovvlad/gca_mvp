# Бэкенд-набор: 80 % времени уходит в установку фикстур, а не в тесты

**Статус: предложение, в работу не поставлено.** Замеры сделаны 2026-09-02 на
16 ядрах, ветка `main` (8673a2b).

**Связанное:** `justfile`, рецепты `test-backend-parallel` и `ci`;
[`TECH_DEBT.md`](../TECH_DEBT.md) (запись про `max_locks_per_transaction` на
n=12); `tests/integration/conftest.py`.

---

## 1. Проблема с замерами

`just ci` целиком — 576 с серийно. Из них **бэкенд-набор 408–414 с, то есть
71 %**. Всё остальное (лок, ruff, alembic check, eslint, tsc, vitest) — 168 с.
После того как цепочки `ci` разведены параллельно, бэкенд-набор становится
единственным, что определяет время гейта §9.3.

Набор — 2401 теста (969 unit, 1481 integration, 6 skipped) на 8 воркёрах
xdist. Комментарий в `justfile` называл 154–157 с — это замер от 2026-08-12 на
1497 тестах, он устарел: тестов стало на 60 % больше, а время выросло в 2,7 раза.

Профиль `--durations=30` (то же прогон, 414 с):

| Категория | Сумма по топ-30 |
|---|---|
| `setup` (установка фикстур) | ~411 с |
| `call` (тела тестов) | ~91 с |
| `teardown` | ~15 с |

**80 % самых дорогих записей — установка фикстур, а не тела тестов.** Наверху
списка:

| с | Фаза | Тест |
|---|---|---|
| 89,19 | setup | `test_import_fixture_e2e::test_fixture_parses_without_any_vat_rate_warning` |
| 42,92 | call | `test_tenders_api::TestRoundUpload::test_upload_creates_round_job_and_all_estimates` |
| 36,34 | setup | `unit/parser/test_estimate::TestParseEstimateOnRealSamples` |
| 34,75 | setup | `test_tenders_api::TestRights::test_member_can_read` |
| 23,46 | setup | `test_import_fixture_e2e::TestFullPipelineOnFixture::test_upload_to_done` |
| 17,75 | setup | `unit/parser/test_estimate::TestParseEstimateOnFixture` |
| 17,41 | setup | `test_category_overrides_api::test_missing_raw_data_is_404` |

Показательны не они, а те, что ниже:

| с | Тест | Что проверяет |
|---|---|---|
| 10,61 | `test_admin::test_admin_endpoints_forbidden_for_member` | код ответа 403 |
| 10,61 | `test_contracts_api::test_empty_note_becomes_null_not_empty_string` | пустая строка → NULL |
| 11,74 / 11,34 / 11,06 | три теста `test_estimate_vat_api` | форма ответа и права |

Проверка того, что `member` получает 403, платит **10,6 с установки**. Значит
она висит на цепочке фикстур, которая проводит настоящий импорт сметы:
`openpyxl` читает книгу, `spacy`+`pymorphy3` лемматизируют каждое наименование,
каскад матчинга ходит в БД. Отдельный замер это подтверждает: чистый разбор
фикстуры **без БД** (юнит-тест `TestParseEstimateOnFixture`) — 17,75 с.

Тот же разбор повторяется в каждом модуле, у которого своя module-scoped
фикстура, и в каждом воркёре xdist заново. Модель «одна транзакция на тест с
rollback» (`tests/conftest.py::db_session`) экономит на очистке БД, но не на
подготовке состояния: состояние готовится импортом.

## 2. Выбранный вариант

**Разделить «разобрать файл» и «положить разобранное в БД», и кэшировать первое
на процесс.**

1. Разбор фикстуры — за `lru_cache` по хэшу содержимого файла, в тестовом
   хелпере. Один разбор на воркёр вместо одного на модуль. Результат парсера
   — обычный JSON (`raw_data`), он неизменяем и уже так и хранится
   (`estimate_raw_data`), поэтому кэш не меняет наблюдаемого поведения.
2. Фикстуры, которым нужна **импортированная смета**, а не сам импорт, получают
   её из этого кэша: вставка строк в БД по готовому `raw_data` без парсера,
   лемматизации и матчинга.
3. Тесты, которые проверяют **сам конвейер импорта** (`test_import_fixture_e2e`,
   `test_estimates_api::TestUploadHappyPath`, `TestRoundUpload`), продолжают
   гонять его целиком — там это и есть предмет проверки.

Ожидание по замеру: снимается основная часть тех ~411 с установки, где импорт
— не предмет теста, а способ получить состояние. Точная цифра неизвестна до
реализации, поэтому она и не называется.

## 3. Отвергнутые альтернативы

1. **Больше воркёров xdist.** Закрыто замером и записано в `justfile`:
   на n=12 прогон разваливается на `DROP SCHEMA public CASCADE` с
   `OutOfMemory: out of shared memory / increase max_locks_per_transaction`,
   3 падения из 4 прогонов. Причина не найдена (`TECH_DEBT.md`), n=8 — потолок.
   Кроме того, узкое место не в числе воркёров, а в том, что каждый повторяет
   один и тот же разбор.
2. **Template-база Postgres** (`CREATE DATABASE ... TEMPLATE imported`).
   Убирает вставку, но НЕ убирает разбор — а замер показывает, что разбор и есть
   дорогая часть (17,75 с без всякой БД). Плюс требует отдельного шага
   подготовки шаблона до `-n 8` и ломает нынешнюю схему «база на воркёра,
   создаётся фикстурой сама».
3. **Кэш разобранного на ДИСК между прогонами.** Дал бы больше, но вносит
   класс ошибки «тест зелёный на устаревшем кэше»: `PARSER_VERSION` и версии
   `spacy`/`pymorphy3` определяют результат нормализации (§11), и протухший
   кэш скрыл бы именно ту регрессию, для которой набор и существует. Кэш на
   процесс этой опасности не несёт — он живёт минуты.
4. **Уменьшить фикстуру.** Обезличенная смета — единственный вход, на котором
   проверяется реальная структура (§9.4 фаза 0). Урезать её значит перестать
   проверять то, ради чего она есть.
5. **Пометить медленные тесты маркером и не гонять их в `ci`.** Набор
   перестанет быть гейтом. Отвергнуто по определению §9.3.

## 5. Чем проверяется, что сработало

- `pytest -n 8 --durations=30` до и после: доля `setup` в топ-30 и общее время
  прогона. Ожидание — общее время ниже 250 с, доля `setup` ниже половины.
- **Обязательная негативная проверка:** кэш не должен скрывать регрессию
  парсера. Прогон с намеренно изменённым `PARSER_VERSION` (или подменённым
  байтом фикстуры) обязан оставить набор красным ровно так же, как без кэша.
  Без этой проверки предложение не считается выполненным: иначе замер покажет
  ускорение, а набор перестанет ловить то, для чего написан.
