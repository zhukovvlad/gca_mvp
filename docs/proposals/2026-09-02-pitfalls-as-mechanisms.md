## 1. Проблема с замерами

`AGENTS.md` — 120 274 символа, примерно 40 000 токенов, и `CLAUDE.md`
предписывает читать его в начале каждой сессии. Разбивка по разделам:

| Раздел | Символов | Когда нужен |
|---|---|---|
| §11 Известные грабли | 30 205 | ситуативно |
| §12 Выстраданные правила | 16 710 | ситуативно |
| §7 Экраны фронтенда | 13 218 | при работе с фронтом |
| §4 Доменная модель | 10 602 | при работе со схемой |
| §10 Definition of Done | 8 217 | всегда |
| §9 Процесс разработки | 7 744 | всегда |
| §5 Пайплайн импорта | 7 274 | при работе с парсером |
| §1–3, §6, §8 + шапка | 25 929 | §1–3 всегда |

§11 — крупнейший раздел документа: 46 пунктов, 30 205 символов, около
10 000 токенов в каждой сессии независимо от темы работы.

Но объём — не главное. Главное в том, **чем эти правила держатся.** Правило в
прозе действует, только если его вспомнят в нужный момент; часть пунктов §11
при этом описывает вещи, которые машина проверяет сама. Примеры из списка:

| Пункт §11 (сокращённо) | Чем может держаться вместо прозы |
|---|---|
| «Деньги: Decimal end-to-end; в JSON — строки» | тест по OpenAPI: все денежные поля `type: string` (после [типизации контракта](2026-09-02-typed-api-contract.md)) |
| «`npx vitest` из КОРНЯ репозитория поднимает другой vitest» | удалить `node_modules/` в корне — он там лежит с 11.08 и не нужен |
| «Случайный `npx <инструмент>` из каталога БЕЗ этого инструмента» | рецепты `just` уже есть; пункт описывает обход рецептов |
| «Перезапись файла целиком из Python переводит его в LF» | `.gitattributes` с явными `eol` |
| «Два прогона pytest против одной тестовой БД одновременно» | уже закрыто: база на воркёра (`test-backend-parallel`) — пункт устарел |
| «Один uvicorn worker — не дефолт, который можно поменять» | assert на старте приложения |
| «`npx tsc --noEmit` во фронтенде проверяет НОЛЬ файлов» | рецепт `typecheck-frontend` уже использует `tsc -b`; пункт описывает ручной обход |

Остальные пункты §11 механизму не поддаются и прозой останутся: «печатную
раскладку А4 проверяет только замер в браузере», «`Decimal.//` усекает частное
к нулю», «выравнивание не сходится, пока у ячеек строки разные шрифты» — это
знание о внешнем мире, а не инвариант кода.

Второй замер того же класса: `docs/TECH_DEBT.md` — 1133 строки, 27 записей,
слово «закрыт» встречается 33 раза. Файл читают при триаже, а больше половины
его объёма — уже закрытые долги, чья история и без того есть в devlog и в git.

## 2. Выбранный вариант

**Пройти §11 по пунктам и каждый либо закрепить механизмом и удалить из прозы,
либо оставить прозой осознанно.** Три исхода на пункт:

1. **Механизм** — тест, хук, конфиг, assert, удаление источника проблемы.
   Пункт уходит из §11; в тесте/конфиге остаётся ссылка на то, чем он выстрадан.
2. **Устарел** — проблема закрыта другим решением. Пункт уходит, причина смерти
   записывается там, где она пережила пункт.
3. **Остаётся прозой** — механизма нет. Пункт живёт в §11.

Одновременно §11 и §12 переезжают из `AGENTS.md` в `docs/reference/` (либо в
скиллы `.claude/skills/`), а в ядре остаётся указатель. Ядро — §1–3, §9, §10 —
около 45 000 символов вместо 120 274.

**Порядок важен: сначала механизмы, потом переезд.** Если сначала переехать,
исчезнет стимул разбирать пункты — они просто станут невидимыми, оставшись
такими же ненадёжными.

## 3. Отвергнутые альтернативы

1. **Только переезд §11/§12 в отдельные файлы.** Сокращает контекст, но
   оставляет 46 правил, каждое из которых держится на памяти читателя. Хуже
   того: правило, вынесенное из документа, который читают всегда, в файл,
   который читают иногда, становится СЛАБЕЕ, а не сильнее.
2. **Ничего не трогать, полагаясь на память модели.** Замер против: §11 растёт
   (46 пунктов) и уже содержит устаревшее (пункт про две базы pytest).
3. **Сократить §11 выкидыванием «мелких» пунктов.** Критерия «мелкий» нет.
   Пункт про `openpyxl`, который «ничего не пишет» при `value=None`, короткий
   и стоил отдельного круга отладки.
4. **Автоматически проверять всё §11.** Часть пунктов — про наблюдаемое только
   глазом (печать А4, теснота в браузере). Требование механизма для каждого
   пункта заставило бы имитировать проверку там, где её нет.

## 4. Что придётся изменить

- `AGENTS.md`: §11 разобрать по трём исходам; §11 и §12 вынести в
  `docs/reference/pitfalls.md` и `docs/reference/insights.md`, оставив в ядре
  указатель и правило «новый пункт сначала пробуют закрепить механизмом».
- Удалить `node_modules/` в корне репозитория (пункт §11 про «другой vitest»).
- Добавить `.gitattributes` (пункт про LF).
- Добавить assert на один worker при старте приложения.
- Снять пункт про две базы pytest как устаревший.
- `docs/TECH_DEBT.md`: закрытые записи вынести в `docs/TECH_DEBT-closed.md`
  либо удалить со ссылкой на devlog; в рабочем файле оставить только открытое.
- `CLAUDE.md`: указатель на ядро, а не на весь документ.

## 5. Чем проверяется, что сработало

- Размер `AGENTS.md` в символах: ожидание — ниже 50 000 против 120 274.
- Число пунктов §11: ожидание — меньше 30, и каждый из оставшихся имеет
  пометку «механизма нет, потому что…».
- **Негативная проверка на каждый закреплённый пункт:** механизм обязан падать,
  если правило нарушить. Пункт, для которого такая проверка не написана,
  считается НЕ закреплённым и остаётся в прозе. Иначе получится худший из
  исходов: правило удалили из документа, а механизм его не ловит.
