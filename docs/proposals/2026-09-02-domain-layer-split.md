## 1. Проблема с замерами

Размер слоёв бэкенда:

| Слой | Строк |
|---|---|
| `crud/` | 11 910 |
| `services/` | 7 595 |
| `routers/` | 3 254 |
| `parser/` | 3 312 |
| `money/` | 440 |

Крупнейший слой называется `crud`, но содержит не чтение-запись сущностей.
`crud/comparison.py` — 2542 строки, и в нём: разрешение инфляции
(`resolve_inflation`, `InflationPlan`), выбор налоговой оси, медианы и бакеты
(`_split_buckets`, `_MedianResult`), построение объединения строк
(`_collect_union_nodes`, `build_rows`), состояния ячеек (`_resolve_cell`,
`cell_net`). Это доменные алгоритмы; БД в них не участвует.

Тот же разрыв в `crud/project_passport.py` (1887), `crud/analytics.py` (1263),
`crud/reports.py` (1023), `crud/dashboard.py` (830). При этом `services/`
занят импортом и оркестрацией — то есть имена слоёв разошлись с содержимым в
обе стороны.

Следствие замеряется в тестах: **integration — 1481 тест против 969 unit**.
Доменная арифметика проверяется через HTTP и настоящий Postgres, потому что
живёт в функции, у которой первый аргумент `db: Session`. Цена этого:
integration-набор идёт 408 с (профиль — в связанном предложении), а чистый
юнит-путь того же набора — около 10 с на 967 тестов.

Второй следствие — размер файлов. Каждая новая аналитическая поверхность
(`stage_summary`, `position_drilldown`, `round_unallocated`) добавляет свой
модуль в `crud/`, и самый старый из них уже 2542 строки.

## 2. Выбранный вариант

**Три слоя вместо двух, по признаку «нужна ли сессия».**

- `backend/domain/` — чистые функции и датаклассы, **без `Session` в
  сигнатурах**: `comparison` (ячейки, оси, медианы, бакеты), `passport`,
  `rollup`, `inflation`. Вход — строки-DTO и `Decimal`, выход — те же
  датаклассы, что сейчас.
- `backend/repos/` — только загрузчики: `select`, VIEW, батчи. Возвращают
  row-DTO, ничего не считают.
- `crud/` остаётся тем, что называется: чтение-запись сущностей.

Переезд механический, потому что **шов уже есть в самом файле**.
`crud/comparison.py` разделён комментарными секциями: загрузчики
`_load_categories` / `_load_estimates` / `_load_declared_rates` /
`_load_view_rows` — строки 254–334; всё, что ниже 337, — накопление и свёртка
без БД. Разделение проводится по этой границе, а не заново.

Порядок: сперва один модуль (`comparison`), с ним переносятся его тесты из
`tests/integration` в `tests/unit`; остальные — по одному, в темпе фич,
которые их всё равно открывают.

## 3. Отвергнутые альтернативы

1. **Переименовать `crud/` в `services/` и слить.** Имя перестанет врать, но
   зависимость домена от `Session` останется, а с ней и невозможность
   тестировать арифметику без Postgres — то есть главная измеренная цена.
2. **Разрезать только по размеру файла** (`comparison.py` → три файла по 800
   строк). Уберёт симптом и оставит причину: новые поверхности продолжат
   приносить смешанный код, просто в новые файлы.
3. **Вводить слой сразу целиком, одной веткой.** `comparison` — самый
   деликатный модуль проекта (§6 зафиксирована семантика матрицы). Массовый
   перенос лишает возможности сверять поведение по одному модулю.
4. **Оставить как есть, ускоряя integration-набор.** Это соседнее предложение,
   и оно нужно независимо. Но оно не отменяет того, что арифметика
   проверяется через HTTP: цена останется, просто станет меньше.

## 4. Что придётся изменить

- Завести `backend/domain/` и `backend/repos/`; перенести `crud/comparison.py`
  по существующей границе (строки 254–334 → `repos/comparison.py`, остальное →
  `domain/comparison.py`).
- `crud/comparison.py` остаётся точкой сборки: загрузить → посчитать.
- `crud/comparison.py::net_of` — снять обёртку, домен зовёт
  `money.vat.gross_to_net` напрямую (обёртка заведена ради словаря модуля,
  своей арифметики не несёт).
- Перенести доменные тесты `comparison` из `tests/integration` в `tests/unit`.
- `finance.py` (одна функция `money_round`) — свернуть в `money/`: сейчас у
  округления денег два дома.
- `AGENTS.md` §4 — назвать три слоя и правило «в `domain/` нет `Session`».

## 5. Чем проверяется, что сработало

- **Поведение не меняется ни на йоту.** Единственный допустимый результат
  переноса — тот же ответ API при том же входе. Проверяется существующим
  набором ДО правки тестов: сначала перенос кода при нетронутых
  integration-тестах, только потом перенос тестов в unit.
- Механическая проверка слоя: в `backend/domain/` нет ни одного вхождения
  `Session`, `db.` и `select(`. Это тест, а не соглашение.
- Соотношение unit/integration на следующих двух фичах: ожидание — новые
  доменные правила приходят с юнит-тестами, а integration остаётся за
  контрактом эндпоинта и правами.
