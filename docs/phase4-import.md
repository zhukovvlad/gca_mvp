Результат фазы 4 (AGENTS.md §9.4). Документ фиксирует три решения, которые фаза
обязана была принять явно (`docs/phase4-start.md` §6), отступления от Go-референса,

Читать вместе с AGENTS.md §5 (пайплайн — источник истины) и
`docs/phase2-schema.md` (объекты схемы, на которые опирается матчинг).

## 2. Три решения фазы (docs/phase4-start.md §6)

### 2.1. Несколько подрядчиков в файле — отказ

Принята рекомендация брифинга: файл, в котором в лоте больше одного блока
подрядчика, **не импортируется**. `EstimateImportError` с текстом «Смета ГП с
несколькими подрядчиками не поддерживается…», перечисляющим найденные названия;
задание уходит в `error`, домен не тронут.

Обоснование — не только §4 («ровно одно предложение на лот», закреплено
`uq_proposals_lot_id`). Договор ГП заключён с одним подрядчиком, и **какой из
блоков договорной, из файла не определить**. Импортировать первого значит выбрать
за человека вслепую и получить смету, которая выглядит правильной. Отказ с
названиями блоков даёт человеку ровно ту информацию, которая нужна для решения.

Парсер при этом продолжает разбирать все блоки и предупреждать
(`layout.check_estimate_layout`) — его поведение фаза 4 не меняла: предупреждение
там сознательно не обещает судьбу импорта.

Тот же отказ выдаётся, если в лоте **ноль** предложений: смета без расценок
подрядчика бессмысленна.

### 2.2. Формулы без кэша — предупреждение

Реализована эвристика брифинга: **есть позиции, но ни у одной не заполнена ни
одна денежная колонка → warning** с инструкцией пересчитать файл (F9) и загрузить
повторно.

Проверяются восемь полей каждой позиции (`unit_cost.*`, `total_cost.*`), а не
только `total`: файл без пересчёта даёт NULL везде, а смета с незаполненным
`total` при заполненных составляющих — нормальная ситуация.

Именно предупреждение, а не отказ: при `data_only=True` парсер не отличает «файл
сохранён без пересчёта» от «смета действительно без расценок», а импорт
нерасценённой сметы — законная операция (в матрицу такие строки не попадут, §6
исключает `unit_cost_total IS NULL`). Отказ здесь запретил бы допустимое.

### 2.3. Неизвестная единица измерения — `unit_id = NULL` + предупреждение

Выбран **вариант (б)** брифинга. Неизвестный текст единицы даёт `unit_id = NULL`,
`unit_norm = ''` — то есть трактуется так же, как «единицы в файле нет», — плюс
агрегированное предупреждение (одно на уникальный текст, с числом позиций).
Новая единица **не создаётся**.

Почему не вариант (а) «get-or-create новой единицы», как делал tenders-go:

* в tenders-go таблица `units` была списком названий, и создать строку стоило
  одного INSERT. Здесь `units_of_measure` — курируемый справочник **физических
  размерностей**: `dimension NOT NULL` с CHECK по шести значениям,
  `base_unit_id`, `to_base_multiplier`. Размерность произвольной строки из ячейки
  неизвестна, и её пришлось бы выдумать — то есть записать в справочник ложь;
* у системы уже есть штатное лечение: алиас — это **данные** (`unit_aliases`), а
  не код. Оператор добавляет алиас и перезагружает смету. Автосоздание единиц
  обошло бы этот механизм и наполнило справочник мусором из опечаток.

Цена решения названа честно: неизвестная единица и отсутствие единицы дают одну
каталожную идентичность. Две **разные** неизвестные единицы при одном названии
работы схлопнутся в одну каталожную строку. Это ограничение принято сознательно:

* правило одно и то же во всех трёх местах (каталог, точное совпадение,
  `cache_key`) — никаких вторых представлений строки, чего и требует §4;
* такая строка всегда попадает в `TO_REVIEW`, то есть на глаза оператору;
* предупреждение называет текст единицы и число позиций.

Альтернатива «хранить исходный текст неизвестной единицы в `cache_key`» была
отвергнута: она развела бы ключ кэша и каталожную идентичность (пара по
`unit_id = NULL` всё равно одна), то есть создала бы второе представление строки
при неизменной сути проблемы.

На обезличенном fixture все 8 встречающихся единиц разрешаются алиасами фазы 1,
предупреждений нет.

## 3. Отступления от Go-референса (`tenders-go@121718bf45df`)

Перенесена структура обхода `ImportFullTender`: тендер → лоты → предложение →
позиции/итоги → raw JSON, одной транзакцией, с откатом всей транзакции при любой
ошибке. Отступления — все продиктованы AGENTS.md, как и предписывал брифинг §3:

1. **`GetOrCreateObject` / `GetOrCreateContractor` / `GetOrCreateExecutor` не
   переносятся** (§3). `contract_id` приходит в запросе; объект и подрядчик берутся
   из карточки. Реквизиты из шапки только сверяются → `import_jobs.warnings`.
   `proposals.contractor_id` заполняется из `contract.contractor_id`, а не из
   файла — закреплено тестом.
2. **UPSERT → INSERT.** Повторную загрузку регулирует эндпоинт (§5), поэтому
   внутри транзакции смета либо новая, либо только что удалённая replace-ом.
3. **Baseline не импортируется.** Парсер всегда отдаёт заглушку; непустой
   baseline даёт warning, но предложение всё равно одно.
4. **Каскад матчинга — по §5, а не по Go-коду.** В Go ключ кэша —
   `sha256(StandardJobTitle)` без единицы, а промах писал новую каталожную строку
   в `draft_catalog_id` как fallback для RAG-воркера. Здесь единица **обязательна**
   в ключе, RAG и векторов нет, промах даёт очередь ручного матчинга.
5. `comment_organazier` → `comment_organizer` (опечатка в источнике).
6. **Итоги** (`proposal_summary_lines`) берутся из блока `total_cost`, как в Go;
   `unit_cost` в итоговых строках не используется.

`article_smr` из парсера не имеет колонки в `position_items` (её не было и в
tenders-go) и остаётся только в `estimate_raw_data.raw_data` — закреплено тестом.

## 4. Транзакционная модель: что сделано дословно, а что уточнено

Дословно по §5:

* **сессия A** — переходы `pending→parsing→importing→matching`, короткие
  транзакции с немедленным commit (проверено тестом: пока работает парсер, из
  независимой сессии виден статус `parsing`);
* **сессия B** — домен, матчинг и **финальный `done` со счётчиками** одной
  транзакцией. Состояния «смета в БД, а job не `done`» не существует: тест
  роняет `finalize_done` и проверяет, что не осталось ни сметы, ни позиций, ни
  TO_REVIEW-строк каталога;
* статус `error` пишет сессия A **после** откатa домена и потому его переживает.

### 4.1. Уточнение §5: доменные предупреждения пишет сессия B

**Согласовано с пользователем и внесено в AGENTS.md v6.2.** Прежняя редакция §5
относила запись `warnings` к сессии A целиком. Предупреждения разделены по смыслу:

| Что | Кто пишет | Почему |
|---|---|---|
| предупреждения парсера | сессия A, сразу после разбора | относятся к файлу; обязаны переживать откат домена и быть видны во время прогресса |
| замена сметы, расхождение шапки, неизвестные единицы, эвристики, нечитаемые значения | сессия B, вместе с доменом | **описывают** доменное состояние |

Аргумент тот же, которым §5 требует атомарности `done` со счётчиками:
предупреждение «заменена смета estimate_id=N» не должно существовать, если
замены не произошло. Дописывание в оба конца делается SQL-конкатенацией
(`warnings || :items`), а не «прочитать-изменить-записать»: иначе одна сессия
теряла бы то, что дописала другая.

### 4.2. Сессия A пишет статус при открытой транзакции B

Переход в `matching` происходит внутри транзакции B. Блокировки нет и это не
случайность: вставка сметы взяла на строке задания `FOR KEY SHARE` (это FK-ссылка
`estimates.import_job_id`), а UPDATE неключевых колонок берёт
`FOR NO KEY UPDATE`; в PostgreSQL эти режимы совместимы.

### 4.3. Статус `error` не пишется силой

Если в момент отказа недоступна и сессия A, задание останется в незавершённом
статусе — и его вылечит startup-recovery при следующем запуске. Поэтому
исключение внутри `StatusWriter.fail` только логируется: второй барьер уже есть,
а наверху пайплайна его никто не ждёт. Закреплено тестом, который глушит запись
`error` и потом лечит задание recovery.

Оборотная сторона этого рассуждения — **recovery обязан работать**, иначе второго
барьера нет вовсе. Именно на этом и поймало первое ревью (§12.1).

### 4.4. Мягкий таймаут

Проверка прошедшего времени **на границах этапов** (§3), без прерывания: тест
подтверждает, что медленный этап доводится до конца и только потом задание
падает. `IMPORT_SOFT_TIMEOUT_MINUTES=0` отключает проверку.

## 5. Матчинг

### 5.1. Каскад по группам, а не по строкам

Каскад — чистая функция пары (нормализованное название, единица), поэтому позиции
сначала группируются по паре, и на группу приходится один проход. На обезличенном
fixture это 1830 позиций против ~1100 уникальных пар; вместо ~7000 запросов
получается 5 партий (кэш, точный поиск, get-or-create, запись кэша, привязка
позиций). Семантика §5 не меняется — счётчики считаются по позициям, а не по
группам.

Следствие, названное явно: разные исходные тексты одной единицы («м2» и «кв.м»)
попадают в одну группу, и в `matching_cache.unit_text` сохраняется первый
встретившийся. Колонка нужна для перевыпуска ключей при инкременте
`norm_version`, и любой алиас даёт при перевыпуске тот же `unit_norm`.

### 5.2. `norm_version = 1` и `cache_key`

`cache_key = sha256(norm_version || '|' || normalized_title || '|' || unit_norm)`,
константа `NORM_VERSION = 1` — рядом с функцией ключа, `AUTO_CACHE_TTL_DAYS = 30`.
`unit_norm` — `units_of_measure.code` разрешённой единицы либо `''`.

Время TTL считается в Python (`utils.utcnow_aware`), а не через SQL `now()`:
только так freezegun может подменить его в тесте «ручное решение переживает
истечение auto-TTL».

Записи с чужой `norm_version` матчинг не видит — закреплено тестом.

### 5.3. Разрешение алиаса — в свою единицу, не в базовую

`crud.units.load_alias_map` резолвит алиас до базовой единицы размерности
(кг → т). Это правильно для пересчёта величин и **неправильно** для
идентичности: «кладка, кг» и «кладка, т» — разные расценки. Поэтому
`services/unit_resolution.py` строит свою карту, где алиас ведёт в СВОЮ единицу.

### 5.4. Инвариант «кэш никогда не указывает на `TO_REVIEW`»

Кэш пишется только в ветке 2, в не-POSITION ветках шага 3 и при ручных решениях.
Инвариант закреплён двумя тестами (после импорта и после слияния) — он же условие
безопасности `DELETE` TO_REVIEW-строки: FK `matching_cache.catalog_position_id`
объявлен `ON DELETE CASCADE`, и запись на TO_REVIEW была бы снесена молча.
Обнаруженное нарушение логируется как `ERROR`, а не как предупреждение.

Второй барьер удаления даёт схема: FK `position_items.catalog_position_id` **без**
каскада, поэтому забытая ссылка не даст удалить строку — БД не пустит.

### 5.5. Найденный дефект: арбитр `ON CONFLICT` со связанным параметром

`sa.func.coalesce(CatalogPosition.unit_id, -1)` рендерится как
`coalesce(unit_id, %(coalesce_1)s)`. Пока запрос исполняется без подготовки,
PostgreSQL сворачивает параметр в константу и находит
`uq_catalog_positions_norm_unit`. Но psycopg3 готовит повторяющийся запрос после
`prepare_threshold = 5`, и у подготовленного плана параметр остаётся параметром:

```
psycopg.errors.InvalidColumnReference: there is no unique or exclusion
constraint matching the ON CONFLICT specification
```

Замерено: партия из 1, 2, 3, 5 вставок проходит, из 10 — падает. То есть дефект
проявлялся **не** на маленькой смете, а на настоящей — ровно там, где хуже всего.
Нашёлся на первом же прогоне полного конвейера на fixture; ни один из 33 тестов
матчинга его не видел, потому что все партии были меньше порога.

Исправление — `sa.literal_column("-1")`, то же выражение, что в индексе. Регрессия
закрыта двумя тестами, и проверено, что оба её ловят:

* `tests/unit/test_matching_sql.py` — форма отрендеренного SQL;
* `test_matching.py::test_batch_larger_than_the_prepare_threshold` — партия из 12
  промахов, то есть через порог подготовки.

Урок для следующих фаз: **любое обращение к трём raw-SQL объектам схемы
(`docs/phase2-schema.md` §2) должно тестироваться партией, а не одной строкой.**

## 6. Эндпоинты и правила повторной загрузки

`POST /api/v1/estimates/upload` (multipart: файл, `contract_id`, `amendment_no?`,
`replace?`), `GET /api/v1/import-jobs/{id}`, `GET /api/v1/import-jobs/{id}/file`.
Префикс `/api/v1/...` взят из §5 дословно и потому отличается от более ранних
роутеров (`/api/auth`, `/api/admin`, `/api/units` — без версии). Это расхождение
внутри проекта названо здесь специально: выравнивать префиксы задним числом —
отдельное решение, а не побочный эффект фазы 4.

Права: загрузка — `member`, `replace=true` — `admin` (§3, §5).

Валидация до создания задания: договор существует (404), `amendment_no > 0` (422),
размер ≤ `UPLOAD_MAX_SIZE_MB` (413), расширение `.xlsx`/`.xlsm` и ZIP-магия внутри
(400). Проверка магии нужна: `.xls`, переименованный в `.xlsx`, иначе доехал бы
до парсера и дал бы невнятную ошибку в задании.

### 6.1. Уточнение §5, правило 1: идемпотентность по текущей смете

**Согласовано с пользователем и внесено в AGENTS.md v6.2.** Прежняя редакция §5
говорила: «уже есть `done`-job с тем же `file_sha256` → идемпотентно вернуть
существующий job». Реализована **более узкая** проверка: текущая смета этой пары
загружена **именно этим** файлом (`estimate.import_job_id` → задание, у него тот
же sha256 и статус `done`).

Причина: буквальное правило ломается после замены. Загрузили файл A, затем файл B
с `replace=true`, затем снова A — в БД лежит смета из B, а `done`-job с sha256
файла A существует. Буквальное правило ответило бы «уже загружено», и человек
остался бы с уверенностью, что загружена A. Узкая проверка в этом случае идёт по
правилу 2 и требует `replace=true`.

### 6.2. Файл остаётся только у реально созданного задания

§5 требует удалять сохранённый файл на всех путях, где задание не создано.
Реализовано сильнее: проверки идемпотентности и 409 выполняются **до** сохранения
файла (для sha256 достаточно прочитать байты, сохранять их не нужно), поэтому
удалять нечего. Единственный путь удаления — ошибка создания задания. Инвариант
закреплён тестами: после 409 и после идемпотентного ответа набор файлов в
хранилище не меняется.

### 6.3. Явный 409 на незавершённое задание пары

Лок пары держит частичный уникальный индекс `uq_import_jobs_active_pair`.
Эндпоинт проверяет его сам, чтобы отдать понятный текст вместо `IntegrityError`.
Блокируется **пара**, а не договор: параллельная загрузка разных допсоглашений
одного договора разрешена — закреплено тестом.

## 7. Хранилище и ретенция (§8)

`Storage` — `save(bytes) -> key`, `get(key) -> BinaryIO`, `delete`, `exists`.
`get` отдаёт поток, а не путь: S3-реализация не должна ломать вызывающие места,
поэтому выдача файла — `StreamingResponse`, не `FileResponse`.

* ключ — `uuid4().hex`, проверяется регуляркой **перед любым обращением к ФС**:
  это последний барьер между строкой из внешнего мира и путём (тест на обход
  пути включён);
* запись через временное имя + `os.replace`: недописанный файл никогда не виден
  под своим ключом, иначе импорт мог бы прочитать половину XLSX;
* оригинальное имя — только в `import_jobs.filename`; в выдаче — RFC 5987
  (`filename*=UTF-8''…`), потому что имена кириллические.

**Ретенция.** Файлы `error`-заданий старше `ERROR_JOB_FILE_RETENTION_DAYS`
удаляются при старте приложения — то есть при первом запуске после истечения
срока, как и написано в §8. Запись задания ретенцию переживает (аудит) — уносит
её только удаление самого договора (`AGENTS.md` v6.7, ревизия 2026-08-16;
на момент фазы 4 удаления договора не существовало вовсе). Факт
удаления файла дописывается в `warnings`. Отсюда следствие для API: у выдачи
файла есть третий ответ — **410 Gone** («удалён по ретенции»), отличный и от 404
(нет задания), и от 200. Повторные запуски предупреждение не дублируют.

## 10. Решения по значениям и границам

* **Деньги** — `Decimal(строка)` напрямую: парсер отдаёт десятичные строки, все
  литералы ошибок Excel уже погашены. Нечисловой мусор в денежной колонке →
  `NULL` + предупреждение, а не падение: ронять импорт 2,5-тысячной сметы из-за
  одной ячейки нельзя, а `NULL` — штатное представление «стоимости нет» (§3).
  Поток однотипных предупреждений ограничен десятью плюс агрегирующая строка.
* **Количества** — `Decimal(str(v))`. Контракт парсера (числа) не менялся: это
  потребовало бы инкремента `PARSER_VERSION` и правки принятых артефактов фазы 3,
  а выигрыша нет — `str()` от `float` даёт кратчайшее представление, то есть
  ровно то же значение, что и перевод количеств в строки на стороне парсера.
  Логическое значение вместо количества → `NULL` + предупреждение
  (`Decimal(True)` дал бы `1` молча).
* **Пустое наименование работы**: строка сохраняется (`job_title_in_proposal = ''`,
  колонка NOT NULL), но к каскаду не допускается и **в `positions_total` не
  входит** — у неё нет идентичности работы. То же для наименований, которые после
  нормализации становятся пустыми (например `«---»`). В обоих случаях —
  предупреждение с количеством. Формулировка §10 («позиции, допущенные к каскаду»)
  этому соответствует.
* **`data_prepared_on_date`** — `NULL` в сметах ГП норма
  (`docs/phase3-parser.md` §4.1); нераспознанная дата даёт предупреждение и
  фолбэк на `contracts.signed_date`.
* **Адрес и аккредитация подрядчика из файла** с карточкой не сверяются: в
  карточке их заводит человек в свободной форме, расхождение здесь — норма, а не
  сигнал. Полностью они остаются в `raw_data`. Сверяются объект, адрес объекта,
  название подрядчика и ИНН; сравнение нечувствительно к пунктуации и регистру.
* **`catalog_positions.status`** новых TO_REVIEW-строк — `na`. Значение
  `pending_indexing` обслуживает векторную индексацию, а она вне MVP (§5).

## 12. Первое внешнее ревью: четыре дефекта

Ревью (Codex) фазу не приняло. Все четыре замечания подтверждены на фактах,
исправлены, и для каждого проверено, что новый тест **ловит регрессию** — правка
временно откатывалась, тест падал.

### 12.1. Recovery мог не выполниться, а приложение всё равно поднималось

`lifespan` гасил любое исключение обслуживания логом. Незавершённые задания
оставались активными и держали `uq_import_jobs_active_pair`: повторная загрузка
той же пары получала бы `409` до следующего перезапуска — прямое нарушение
инварианта §5. Хуже того, recovery и ретенция шли **одной** транзакцией, поэтому
недоступное хранилище откатывало и recovery.

Исправлено: recovery выполняется своей транзакцией, его исключение уходит наружу
и роняет старт (громкий отказ честнее сервиса, вечно отвечающего «импорт уже
идёт»); ретенция — своей транзакцией и best-effort. Инвариант внесён в AGENTS.md
§5 отдельным абзацем.

Моя исходная мотивировка («приложение обязано подняться даже при недоступной БД,
иначе не починить конфигурацию») не выдерживает проверки: конфигурация правится на
диске, а не через поднятое приложение.

Тесты: `test_retention_failure_does_not_roll_back_recovery`,
`test_recovery_failure_propagates`, `test_app_startup_fails_when_maintenance_fails`.

### 12.2. Канонические единицы считались неизвестными

`UnitResolver` строил карту **только** из `unit_aliases`, хотя текст
предупреждения обещал проверку «ни среди канонических, ни среди алиасов». Замер
на засеянном справочнике:

| форма | было |
|---|---|
| `SET`, `MON` (коды) | `unknown`, `unit_id = NULL` |
| «Килограмм», «Кв. метр», «Куб. метр», «Метр», «Штука», «Литр» (названия) | `unknown`, `unit_id = NULL` |

То есть валидная единица молча теряла `unit_id` — а единица входит в идентичность
каталожной работы. Отдельно: `unit_norm_for_id` тоже строился по алиасам, поэтому
единица без алиасов вернула бы `''`, то есть **чужую** идентичность «без
единицы». На засеянном справочнике это ещё не проявлялось (у всех девяти единиц
есть алиасы), но первая же единица без алиаса схлопнула бы пары.

Исправлено: карта строится из `code`/`name`/`symbol` всех единиц плюс алиасов;
обратное отображение — по справочнику.

Тесты: `tests/integration/test_unit_resolution.py` — в том числе проверка «каждая
`code`/`name`/`symbol` каждой единицы справочника резолвится в свою единицу», то
есть новые единицы в справочнике проверяются автоматически.

### 12.2.1. Политика конфликта форм: первая заявка побеждает

Первая правка §12.2 накладывала алиасы **поверх** канонических форм с мотивировкой
«алиас заведён человеком, значит авторитетнее». Второе ревью показало, что это
несостоятельно, и было право:

* оно противоречило соседнему тесту, обещающему «каждая `code`/`name`/`symbol`
  резолвится в свою единицу», — два теста в одном файле кодировали
  взаимоисключающие политики;
* алиас «Кв. метр» → `M3` делал `M2` **недостижимой по собственному имени**, и
  позиции в квадратных метрах молча уезжали бы в кубические. `unit_id` входит в
  идентичность каталожной работы (§4), то есть цена ошибки — испорченный каталог;
* человек, заводящий алиас, не может знать, что отнимает имя у другой строки
  справочника: последствие ему невидимо.

Ключевое соображение: **приоритет вообще имеет значение только в конфликте, а
конфликт здесь по определению дефект справочника.** Правильный ответ на дефект —
не «выбрать сторону молча», а отказать и сказать вслух. Поэтому вместо двух
правил (одно для канонических форм, другое для алиасов) действует одно:

> Первая заявка на нормализованную форму побеждает; конфликтующая заявка **не
> применяется** и логируется как дефект справочника. Порядок регистрации
> детерминирован: канонические формы (по `id` единицы), затем алиасы (по `id`
> алиаса) — поэтому каноническая форма всегда сильнее алиаса чужой единицы.

Повторная заявка ТОЙ ЖЕ единицы конфликтом не считается: алиас «м2» при символе
«м²» — одна форма, а не спор.

Правило заодно накрыло случай, которого не было ни в ревью, ни в первой правке:
`unit_aliases.raw_text` уникален по **сырому** тексту, а не по нормализованному
ключу, поэтому «квм» и «КВМ» — две законные строки, способные указывать на разные
единицы. Раньше поздняя молча выигрывала.

Лог теперь проверяется тестами — через собственный хендлер, а не `caplog`
(он в проекте ненадёжен, `docs/phase3-parser.md` §4.4; в первой правке `caplog`
был передан в тест, но фактически не проверялся — справедливое замечание ревью).

Проверено снятием защиты: с политикой «алиас поверх» падают три теста
(`test_alias_cannot_steal_a_canonical_form_of_another_unit`,
`test_two_aliases_differing_only_by_case_do_not_silently_swap`,
`test_canonical_forms_survive_any_alias_table`).

**Задача фазы 5:** CRUD единиц должен отклонять добавление алиаса, чья
нормализованная форма уже занята другой единицей, — чтобы дефект не попадал в
справочник вовсе, а не только гасился на чтении.

### 12.3. Конкурентная загрузка одной пары давала 500

Проверка активного задания отделена от `INSERT`, поэтому два одновременных
запроса могли оба её пройти; второго останавливал частичный уникальный индекс, и
`IntegrityError` уходил клиенту как 500. Данные были защищены, контракт API — нет.

Исправлено: нарушение `uq_import_jobs_active_pair` отличается по имени индекса и
переводится в тот же `409`, что и синхронная проверка; файл проигравшего
удаляется. Гонка воспроизводится детерминированно — соперник создаётся из
независимой сессии в момент сохранения файла, то есть между проверкой и вставкой
(`test_concurrent_upload_of_the_same_pair_is_409_not_500`).

### 12.4. Ручные решения Review не были сериализованы

Источник читался без `FOR UPDATE`. Исправлено: источник и цель блокируются одним
запросом с `ORDER BY id` (единый порядок захвата исключает взаимную блокировку),
проверка состояния идёт **после** захвата, плюс проверка «удалена ровно одна
строка».

**Отдельно стоит записать, чему научил этот пункт.** Первая версия тестов
конкуренции проходила и **без** `FOR UPDATE`: второй оператор всё равно упирался в
замки самих записей (`UPDATE position_items`, `UPDATE catalog_positions`), а
проверка удаления не давала закоммитить решение по исчезнувшему источнику. То есть
тесты «доказывали» блокировку, которой не было. Разница проявляется только в
сценарии с настоящей конкуренцией: два решения `set_kind` с разными `kind` —
без блокировки второй читает `kind = TO_REVIEW`, ждёт на записи и после коммита
первого применяет своё решение поверх, **молча теряя** решение первого. Этот
сценарий вынесен в отдельный тест на потоках
(`test_lost_update_of_a_kind_decision_is_refused`); он ждёт, пока второй backend
действительно встанет на ожидание замка (`pg_stat_activity.wait_event_type`), а не
спит «на глазок». Без `FOR UPDATE` он падает ровно с описанным симптомом:
`applied: TRASH` поверх `POSITION`.

Урок общий: **тест на гонку обязан быть проверен снятием защиты.** Иначе он
фиксирует не механизм, а совпадение.

### 12.5. Что ревью подтвердило

Целевые тесты фазы, `lint`, отсутствие дрейфа схемы, исправление подготовленного
`ON CONFLICT` (§5.5), откат домена, атомарный `done`, TTL, replace-аудит и
инвариант кэша. Полный прогон 600 тестов ревьюер не дождался; после правок он
занимает 1,5–2 мин (629 тестов), из них ~15 с — однократный разбор fixture.

## 13. Внутреннее ревью после приёмки внешним

После того как у внешнего ревью замечаний не осталось, проведено собственное
ревью всего кода фазы. Найдено два дефекта (оба проверены снятием защиты) и
внесены две защитные меры, которые снятием защиты проверить нельзя — это
сказано прямо, а не спрятано.

### 13.1. Выдача файла не закрывала хендл хранилища

`GET /api/v1/import-jobs/{id}/file` отдавал в `StreamingResponse` сырой файловый
объект. Это две проблемы разом: Starlette итерирует такой объект **построчно**
(двоичный ZIP резался на чанки по случайным байтам `0x0A`), а `close()` не
вызывает никогда — хендл жил до сборщика мусора. На Windows открытый хендл
блокирует удаление файла, то есть незакрытая выдача мешала бы ретенции §8 в этом
же процессе. Содержимое ответа при этом было корректным — потому дефект и
пережил все прогоны.

Исправлено в два круга — и второй круг поучителен сам по себе.

**Первая правка была неполной.** Генератор с чтением по 64 КиБ и `close()` в
`finally` закрыл штатный путь, но не аварийный: при разрыве соединения `send()`
падает, Starlette перестаёт потреблять генератор и хранит его в
`body_iterator` — `finally` генератора не выполняется, пока жив объект ответа.
То есть на аварийном пути закрытие по-прежнему доставалось сборщику мусора —
ровно то, от чего правка уходила. Нашло внешнее ревью прямым ASGI-вызовом с
падающим `send`; воспроизведено и здесь: `closed_while_response_alive = False`,
`closed_after_gc = True`.

**Вторая правка** поднимает закрытие на уровень `Response.__call__`
(`ClosingStreamingResponse`): его `finally` выполняется при любом исходе —
полное чтение, разрыв, отмена; `close()` файла идемпотентен.

Тесты — три, каждый со своей ролью: (1) вызов `close()` после полного
скачивания через шпион-обёртку (полный стек); (2) разрыв соединения при
**живом** объекте ответа — без удержания объекта локальной переменной
refcounting закрыл бы брошенный хендл сразу, и тест не отличал бы починку от
везения; (3) эндпоинт возвращает именно `ClosingStreamingResponse` — иначе
возврат к голому `StreamingResponse` прошёл бы незамеченным: тест полного
скачивания закрытие увидел бы и так. Тест (2) проверен снятием защиты: без
`finally` уровня `__call__` он падает, а тест полного чтения проходит — что и
доказывает, что первая правка закрывала только штатный путь.

### 13.2. Один испорченный `file_key` обрывал всю ретенцию

`storage.exists()` на невалидном ключе поднимает `StorageKeyError`, и цикл
ретенции умирал на первом же таком задании: файлы всех остальных error-заданий
копились бы до ручного вмешательства. Best-effort-обёртка из §12.1 защищала
recovery, но не остальные задания того же прогона ретенции.

Исправлено изоляцией ошибок по заданиям (`StorageKeyError`, `OSError` — лог и
`continue`). Тест ставит задание с плохим ключом по `id` раньше хорошего и
проверяет, что хорошее всё равно вычищено. Проверено снятием защиты.

### 13.3. Защитная мера: канонический порядок массовых записей матчинга

§4 разрешает параллельный импорт разных допсоглашений, и `BackgroundTasks`
выполняет их в разных потоках. Две executemany-партии (`ON CONFLICT` в
get-or-create, `DO UPDATE` в записи кэша), захватывающие пересекающиеся строки в
разном порядке, — классический сценарий взаимной блокировки. Партии теперь
отсортированы (пары — по `(normalized_job_title, unit)`, кэш — по `cache_key`):
единый порядок захвата исключает дедлок по построению.

Честные границы: (а) дедлок не воспроизводился — интерливинг внутри
executemany снаружи не управляется, поэтому теста «снятием защиты» здесь нет и
не будет, это упорядочение по построению; (б) одиночному UPDATE в
`_extend_auto_ttl` порядок захвата не навяжешь (его выбирает планировщик) —
остаточный риск принят: цена дедлока — abort одной транзакции и job в `error`,
повторная загрузка законна, порчи данных нет.

### 13.4. Защитная мера: сериализация вызовов spaCy

spaCy не документирует потокобезопасность `Language`-объекта (общие
`Vocab`/`StringStore` мутируют на новых строках), а лемматизация при
параллельных импортах зовётся из разных потоков. Стресс — 8 потоков × 320
уникальных фраз против последовательного эталона — расхождений **не показал**,
поэтому дефектом это не объявлено. Замок вокруг `nlp()` в `_lemmatize` добавлен
как защита недокументированного контракта: цена нулевая (лемматизация держит
GIL, реального параллелизма замок не отнимает; `lru_cache` оставляет попадания
без замка), а ставка в случае ошибки — детерминизм `normalized_job_title`, то
есть идентичность каталога (§11). `PARSER_VERSION` не менялся: поведение
функции не изменилось.

### 13.5. Проверено и признано чистым

* совместимость замков сессий A и B на строке задания (`FOR KEY SHARE` от
  FK-вставки против `FOR NO KEY UPDATE` от UPDATE неключевых колонок);
* `_write_cache DO UPDATE` не может перетереть живую manual-запись: живая даёт
  hit в ветке 1, а другой `norm_version` означает другой ключ;
* группировка матчинга эквивалентна паре идентичности: `unit_id` ↔ `unit_norm`
  взаимно-однозначны после правки §12.2;
* конкатенация `warnings` в SQL корректна и для не-ASCII (`json.dumps`-эскейпы
  разбираются jsonb), порядок дописываний A → B последовательный;
* пути 409/идемпотентности/replace не оставляют файлов-сирот; ключ хранилища
  валидируется до любого обращения к ФС (обход пути закрыт тестом);
* `IntegrityError` внутри пайплайна (гонка replace-загрузок одной пары) даёт
  общий текст «непредвиденная ошибка» — приемлемо: штатный путь перехватывает
  конфликт на эндпоинте до пайплайна.

Замечено и оставлено осознанно:

* **приложение теперь не стартует без мигрированной БД** (recovery делает
  UPDATE по `import_jobs`) — следствие §12.1; README и так требует
  `just db-dev-init` до первого запуска;
* **осиротевшие TO_REVIEW-строки после replace**: у заменённой сметы позиции
  удаляются каскадом, а созданные ею TO_REVIEW-строки остаются (обычно их тут же
  переиспользует новый импорт тех же пар). Строка без единой позиции в очереди
  Review — вопрос гигиены экрана фазы 5, не целостности.
