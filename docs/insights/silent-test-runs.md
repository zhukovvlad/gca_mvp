# Прогон, который молчит вместо того чтобы упасть

**Правило.** Успех прогона читается по числу **прошедших** тестов, а не по коду
возврата и не по отсутствию красного. Пропущенный, несобранный и неподнявшийся
тест выглядят как успех.

## Чем выстрадано

**Файл без маркера выпадает из выборки** (фаза 5,
`docs/phase5-crud-review.md` §13.4). Два integration-файла не объявляли
`pytestmark = pytest.mark.integration`. На CI это не влияло — там гоняется весь
`pytest`, — но точечный прогон по маркеру собирал 279 тестов из 813 и **молча
пропускал 65**. После добавления маркера выборка выросла до 344.

**Integration-тесты без `TEST_DATABASE_URL` пропускаются молча.** Наступали
дважды: план Ф1 предупреждал об этом заранее, и в самой сессии Ф1 прогон дал
`17 skipped` вместо `18 passed`, потому что `DATABASE_URL` указывала на ту же
базу и conftest отказался работать по рабочей БД. Обе цифры выглядят как «команда
отработала».

**Составная команда прячет падение** (фаза 5, `docs/phase5-crud-review.md` §13.8).
Три шага фронтенд-CI (eslint, tsc, vitest) в одной локальной команде с `&&` и
`grep` — падение типизации не было видно. CI гоняет их отдельными шагами; локально
надо так же.

**Раннер, который не поднимается** (фаза 6, `docs/phase6-analytics.md` §4). Из
Python-подпроцесса `vitest` не стартует вовсе, и все пробы возвращались красными
независимо от кода. Обратная сторона той же монеты: прогон, который всегда
красный, так же бесполезен, как всегда зелёный.

**Логи, которых нет** (фаза 3, `docs/phase3-parser.md:384`). `caplog` в проекте
ненадёжен: `setup_logging()` делает `root.handlers.clear()` и сносит хендлер
фикстуры. Проверка «в логе есть предупреждение» молча проходила бы мимо. Ловить
лог собственным хендлером.

**`try/finally` в PowerShell маскирует падение дочернего процесса** (Ф4б фазы 7,
гейт 3 плана — `docs/superpowers/plans/2026-08-08-vat-rate.md`, Global
Constraints). Замерено в PowerShell 5.1: нативная команда внутри `try` вернула
`3`, `finally` отработал успешно, и **после блока `$?` стал `True`** при
`$LASTEXITCODE = 3` — потому что `$?` отражает последнюю операцию, а ею был
`finally`. Цепочка через `if ($?)` пошла бы дальше по упавшему шагу. А блок
`try/finally` там стоял не для красоты: им возвращается подменённая
`DATABASE_URL`, то есть шаблон обязательный. Стоило круга гейта 3 — план
переписывался трижды, и в последний раз именно из-за этого.

**Как теперь:** после **каждой** нативной команды внутри `try` —
`if ($LASTEXITCODE -ne 0) { throw "<что> failed: $LASTEXITCODE" }`. Проверено, что
`throw` уходит наружу, а `finally` всё равно восстанавливает переменную.

Обратная сторона того же: `rg` без совпадений возвращает `1`. Блок, где все
значения верны, завершается кодом `1`, если последним отработал `rg` с нулём
совпадений, — то есть **код возврата блока врёт в обе стороны**. Вердикт читается
по напечатанным числам (`21`, `0`, `passed`), а не по `$?`.

## Как теперь

- Читай итоговую строку целиком: `N passed`, и сверяй N с ожидаемым. `skipped`
  в интеграционных прогонах — сигнал разобраться, а не фон.
- Новому integration-файлу — `pytestmark = pytest.mark.integration`.
- Точечный прогон integration: `TEST_DATABASE_URL` обязателен, а `DATABASE_URL`
  на ту же базу — снимать (`env -u DATABASE_URL`; в PowerShell —
  `Remove-Item Env:DATABASE_URL` с возвратом в `finally`).
- В PowerShell успех нативной команды читается по `$LASTEXITCODE`, а не по `$?`:
  внутри `try/finally` последний равен `True` даже после падения.
- Шаги CI гонять по отдельности и в той же форме, что CI.
- Прежде чем верить прогону, убедись, что раннер вообще стартовал.
- **Не заворачивать прогон в конвейер.** `just ci 2>&1 | tail -40` возвращает код
  `tail`, а не `just`: падение бэкенда пришло как `exit code 0` и было прочитано
  как успех — поймалось только чтением хвоста лога, где стояло `269 errors`.
  Писать в файл и проверять код отдельно: `just ci > log 2>&1; echo $?`. Тот же
  дефект у `| grep`, `| head`, `| jq`. Родня уже описанным `&&` и
  PowerShell-овскому `$?`: везде код возврата подменяется соседним звеном.

## Чего это правило не ловит

Тест, который исполнился и прошёл, но ничего не стережёт — это
[verifying-guards.md](verifying-guards.md).
