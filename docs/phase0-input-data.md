# Фаза 0 — входные данные и сверка семантики

Результат фазы 0 (AGENTS.md §9). Документ фиксирует, на каких данных проверены
допущения брифа и какие из них остались непокрытыми.

## Полученные образцы

| Файл | Статус |
|---|---|
| `samples/Оферта_ООО 'ПОДРЯДЧИК'_NNN-ТУ_лот №1.xlsx` | единственный полученный реальный образец |

**Ограничение, принятое осознанно.** Бриф (§9) требует 2–3 реальные сметы;
получен один. Фазы 1–2 от этого не зависят (инфраструктура и схема БД), фаза 3
стартует на нём же, но покрытие форматов ограничено одним источником —
**до пилотной приёмки парсера дополнительные образцы обязательны**.

Полученный файл — оферта участника по лоту генподряда. Структурно это ровно то,
что бриф называет сметой ГП (§4: «смета к договору ГП структурно = тендерная
таблица, но с одним подрядчиком, без колонки „Расчётная стоимость“ и с
заполненным `suggested_quantity`»): один подрядчик, baseline-колонки нет,
«Предлагаемое количество» заполнено. **Подтвердить у заказчика**, что сметы к
подписанным договорам ГП приходят в этом же макете, а не в другом.

## Сверка quantity vs suggested_quantity (§6)

Бриф требует до начала работ проверить, какое поле несёт вес позиции для
средневзвешенной ставки. Замер по единственному образцу (1830 строк с единицей
измерения):

| Соотношение колонок H («Общее кол-во») и J («Предлагаемое количество») | Строк |
|---|---|
| H ≠ J | 1287 |
| H = J | 541 |
| J пусто, H заполнено | 2 |

В подавляющем большинстве строк H равно `1` (заглушка), а фактический объём
лежит в J: например, «Бетонная подготовка … 100мм» — H=1, J=1000 м², и
`Стоимость всего` = `цена за ед.` × J. Формула `w = COALESCE(suggested_quantity,
quantity)` из §6 подтверждена; останавливаться и спрашивать не потребовалось.

Прочие наблюдения по структуре файла:

- шапка: предмет тендера (D2), объект (D3), адрес (D4), контрагент (J6), ИНН (J7), адрес контрагента (J8);
- строка заголовков таблицы — 9-я, подзаголовки — 10-я, данные с 11-й;
- колонки: A №, B № раздела, C статья СМР, D наименование, F комментарий, G ед. изм., H общее кол-во, J предлагаемое кол-во, K–N цена за единицу (материалы/СМР/косвенные/всего), O–R стоимость всего, S стоимость за объёмы заказчика, T комментарий участника;
- единицы измерения в образце: м2 (1058), компл (310), шт (231), м3 (127), м (78), т (13), мес (11), кг (2) — отсюда обязательность алиасов «м2»/«кв.м»/«м²» (§4);
- в конце листа — строка «ИТОГО, руб. с учетом НДС» и блок «Дополнительная информация» (6 строк), которые парсер обязан не принимать за позиции.

## Обезличенный fixture

`fixtures/gp_estimate_fixture.xlsx` — обезличенная копия образца для тестов
(реальные файлы не коммитятся, §9).

Проверено после генерации: количество строк (2600), позиций с наименованием
(2576), объединённых диапазонов (2613) и гистограмма типов ячеек
(8926 str / 14214 float / 9652 int) совпадают с оригиналом; контрольные строки
14/43/61/2586 идентичны по значениям.

Что изменено относительно оригинала:

1. **Семь ячеек шапки** — контрагент, его ИНН и адрес, наименование объекта,
   предмет тендера, адрес объекта, название лота. Структура, типы данных,
   объединённые ячейки и все 2571 позиции сохранены.
2. **Метаданные книги** (`creator`, `lastModifiedBy`, даты, custom docProps)
   очищены: в исходнике они содержали имя реального автора.
3. **Формулы материализованы в значения.** Это осознанное решение, а не потеря
   данных: парсер открывает книгу с `data_only=True` и формул не видит в
   принципе — он читает те же кэшированные значения. Fixture поэтому подаёт
   парсеру ровно тот вход, который он получил бы из реального файла. Побочный
   эффект: fixture непригоден для проверки поведения на *формулах* — если такой
   тест понадобится, его нужно строить на синтетическом файле.
4. **Размерность листа сузилась** `A1:XFD2600` → `A1:X2600`: openpyxl при
   сохранении пересчитывает dimension по фактическим данным. Следствие важное —
   **на этом fixture нельзя воспроизвести риск `XFD` (см. ниже)**; тест
   производительности обязан использовать файл с искусственно раздутой
   размерностью.

### Синтетические fixtures (задача фазы 3)

Одного образца мало для покрытия граничных случаев. В фазе 3 к нему добавляются
синтетические файлы: без baseline-блока, с пустыми стоимостями (`NULL`, не `0` —
§3), с разными алиасами единиц, с формулами вместо материализованных значений,
с отсутствующими необязательными колонками.

## Риск производительности: dimension `A1:XFD2600`

Лист образца заявляет размерность до последней колонки Excel (`XFD`, 16384) —
форматированием задействована вся ширина, хотя данные заканчиваются на колонке
20. Замер на реальном файле:

- `load_workbook(data_only=True)` — 2.8 с;
- скан `read_contractors.py` (`iter_rows(min_row=4, max_row=10, max_col=ws.max_column)`) — 0.28 с, 114 688 ячеек.

Катастрофы нет: единственный полноширинный скан ограничен семью строками.
Опасность — гипотетическая: обход всех строк на полной ширине дал бы 42.6 млн
ячеек. **Задача фазы 3:** при адаптации парсера не вводить полностраничных
обходов, ограничивать сканы фактической шириной данных и закрепить это тестом
производительности. Тест нужно строить на синтетическом файле с раздутой
размерностью — обезличенный fixture этот дефект не воспроизводит (см. п. 4 выше),
а реальный файл в репозиторий не коммитится.
