# Фаза 0 — входные данные и сверка семантики

Результат фазы 0 (AGENTS.md §9). Документ фиксирует, на каких данных проверены
допущения брифа и какие из них остались непокрытыми.

## Полученные образцы

| Образец | Статус |
|---|---|
| «реальный образец №1» — оферта участника по лоту генподряда, лежит в локальном `samples/` | единственный полученный |

Имя файла здесь намеренно не приводится: в нём фигурирует контрагент, а этот
документ — отслеживаемый. Само правило «реальные данные не коммитить» (§9)
распространяется и на документацию, не только на сам XLSX.

**Ограничение, принятое осознанно.** Бриф (§9) требует 2–3 реальные сметы;
получен один. Фазы 1–2 от этого не зависят (инфраструктура и схема БД), фаза 3
стартует на нём же, но покрытие форматов ограничено одним источником —
**до пилотной приёмки парсера дополнительные образцы обязательны**.

Полученный файл — оферта участника по лоту генподряда. Структурно это ровно то,
что бриф называет сметой ГП (§4: «смета к договору ГП структурно = тендерная
таблица, но с одним подрядчиком, без колонки „Расчётная стоимость“ и с
заполненным `suggested_quantity`»): один подрядчик, baseline-колонки нет,
«Предлагаемое количество» заполнено.

Заказчик подтвердил (2026-08-02): сметы к подписанным договорам ГП приходят в
том же формате. Макет фазы 3 строится по этому образцу.

## Сверка quantity vs suggested_quantity (§6) — ВЫВОД

Бриф требует до начала работ проверить, какое поле несёт вес позиции для
средневзвешенной ставки, и остановиться, если авторитетно другое.

**Вывод: авторитетен `suggested_quantity` — колонка J «Предлагаемое количество».
Формула `w = COALESCE(suggested_quantity, quantity)` из §6 подтверждена, развилка
закрыта.** Вывод перенесён в AGENTS.md §4 и §6.

### Терминология: «Предлагаемое», а не «Предполагаемое»

Реальный заголовок ячейки `J10` — **«Предлагаемое количество»**, то есть
количество, *предложенное подрядчиком*. Ранние редакции брифа называли его
«Предполагаемое количество» — это пересказ, расходящийся с файлом на одну букву
и по смыслу. Словарь самого парсера совпадает с файлом: в `app/constants.py`
`suggested_quantity` описан как «Количество, предложенное участником», а
`quantity` — как «Количество согласно тендерной документации (объем
организатора)». **Константы детекции шапки в фазе 3 писать по реальному
заголовку.**

### Чем доказано

Замер по 1828 расценённым строкам образца (`N` = цена за единицу «Всего»,
`R` = «Стоимость всего, RUB», `S` = «Стоимость всего за объемы заказчика»):

| Проверка | Совпало |
|---|---|
| `R = N × J` (Предлагаемое количество) | **1828 / 1828** |
| `R = N × H` (Общее кол-во) | 557 |
| `S = N × H` | **1828 / 1828** |
| `S = N × J` | 557 |
| строк, где `H ≠ 1` **и** `H ≠ J` | **0** |

Читается однозначно: деньги договора считаются по J, а H питает только
справочную колонку «за объемы заказчика». Совпадения в 557 строках — это те,
где H = J, поэтому обе формулы дают один результат.

Отдельно проверено, что `COALESCE` безопасен: строк, где `quantity` одновременно
осмыслен (не `1`) и отличается от `suggested_quantity`, **нет ни одной** — H либо
заглушка `1`, либо равен J. То есть фолбэк на `quantity` не может подменить вес
чужим числом.

Схема типичной строки (числа синтетические — реальные расценки в отслеживаемую
документацию не выносятся): единица «м²», «Общее кол-во» = 1, «Предлагаемое
количество» = 1000, цена за единицу «Всего» = 2000 ₽, «Стоимость всего» =
2 000 000 ₽ = 2000 × 1000, «Стоимость всего за объемы заказчика» = 2000 ₽ =
2000 × 1. Проверять надо именно это соотношение.

**Ограничение:** проверено на одном образце (см. выше). Замер стоит повторить,
когда появятся сметы других объектов и лет.

Прочие наблюдения по структуре файла:

- шапка: предмет тендера (D2), объект (D3), адрес (D4), контрагент (J6), ИНН (J7), адрес контрагента (J8);
- строка заголовков таблицы — 9-я, подзаголовки — 10-я, данные с 11-й;
- колонки: A №, B № раздела, C статья СМР, D наименование, F комментарий, G ед. изм., H общее кол-во, J предлагаемое кол-во, K–N цена за единицу (материалы/СМР/косвенные/всего), O–R стоимость всего, S стоимость за объёмы заказчика, T комментарий участника;
- единицы измерения в образце: м2 (1058), компл (310), шт (231), м3 (127), м (78), т (13), мес (11), кг (2) — отсюда обязательность алиасов «м2»/«кв.м»/«м²» (§4);
- в конце листа — строка «ИТОГО, руб. с учетом НДС» и блок «Дополнительная информация» (6 строк), которые парсер обязан не принимать за позиции. **В этом блоке колонка J содержит текст** («Представлено», «К обсуждению», «Будет направлено до подписание Договора») — если досрочный выход по merged-ячейке (§11) когда-нибудь сломается, парсер попытается разобрать эти строки как количество. Годится как негативный тест для фазы 3.

## Обезличенный fixture

`fixtures/gp_estimate_fixture.xlsx` — обезличенная копия образца для тестов
(реальные файлы не коммитятся, §9).

Проверено после генерации: количество строк (2600), позиций с наименованием
(2576), объединённых диапазонов (2613) и гистограмма типов ячеек
(8926 str / 14214 float / 9652 int) совпадают с оригиналом; контрольные строки
14/43/61/2586 идентичны по значениям.

Что изменено относительно оригинала:

1. **Семь ячеек шапки** — контрагент, его ИНН и адрес, наименование объекта,
   предмет тендера, адрес объекта, название лота. Структура, типы данных,
   объединённые ячейки и все позиции сохранены (числа — в проверке выше).
2. **Метаданные книги** (`creator`, `lastModifiedBy`, даты, custom docProps)
   очищены: в исходнике они содержали имя реального автора.
3. **Формулы материализованы в значения.** Это осознанное решение, а не потеря
   данных: парсер открывает книгу с `data_only=True` и формул не видит в
   принципе — он читает те же кэшированные значения. Fixture поэтому подаёт
   парсеру ровно тот вход, который он получил бы из реального файла. Побочный
   эффект: fixture непригоден для проверки поведения на *формулах* — если такой
   тест понадобится, его нужно строить на синтетическом файле.
4. **Потеряны пустые стилизованные ячейки за пределами данных.** Тонкий момент,
   важный для теста производительности (см. ниже). Объявленная в XML строка
   `<dimension ref="A1:XFD2600">` перенеслась в fixture дословно, но при
   сохранении openpyxl отбросил пустые стилизованные ячейки, и крайняя правая
   реальная ячейка сдвинулась с `XFD9` на `X329`:

   | | реальный образец | fixture |
   |---|---|---|
   | `<dimension ref>` в XML | `A1:XFD2600` | `A1:XFD2600` |
   | самая правая ячейка `<c>` | `XFD9` (16384) | `X329` (24) |
   | всего элементов `<c>` | 196 423 | 54 628 |
   | `ws.max_column`, обычный режим | 16384 | **24** |
   | `ws.max_column`, `read_only=True` | 16384 | **16384** |

   **Расхождение по режимам открытия принципиально.** В обычном режиме — том,
   в котором работает парсер (`load_workbook(path, data_only=True)`) — openpyxl
   игнорирует строку `<dimension>` и считает `max_column` по фактическим
   ячейкам, отсюда 24. В `read_only=True` он, наоборот, берёт размерность прямо
   из XML, и `max_column` равен 16384 даже у fixture.

   Следствия два. **Первое:** для текущего парсера fixture риск `XFD` не
   воспроизводит — тест производительности нужен на отдельном файле. **Второе:**
   если в фазе 3 парсер переведут в `read_only` ради скорости на больших файлах
   (естественная оптимизация — сейчас так открывает книгу `file_validation.py`),
   полноширинные сканы станут дорогими снова, и вот тогда fixture начнёт
   воспроизводить проблему. Смена режима открытия — это изменение, требующее
   перепроверки замеров, а не безобидная оптимизация.

### Синтетические fixtures (задача фазы 3)

Одного образца мало для покрытия граничных случаев. В фазе 3 к нему добавляются
синтетические файлы: без baseline-блока, с пустыми стоимостями (`NULL`, не `0` —
§3), с разными алиасами единиц, с формулами вместо материализованных значений,
с отсутствующими необязательными колонками.

## Риск производительности: `ws.max_column` = 16384

В реальном образце есть пустая стилизованная ячейка `XFD9` — крайняя правая
колонка Excel, хотя данные заканчиваются на колонке 24. Из-за неё
`ws.max_column` равен 16384, а парсер в одном месте подставляет его в скан:
`read_contractors.py:72` — `iter_rows(min_row=4, max_row=10, max_col=ws.max_column)`.

Замеры:

| | реальный образец | fixture |
|---|---|---|
| `load_workbook(data_only=True)` | 2.8 с | — |
| скан `read_contractors` | 114 688 ячеек / 0.28 с | 168 ячеек / 0.00 с |

Катастрофы нет: единственный полноширинный скан ограничен семью строками.
Опасность гипотетическая — обход всех строк на полной ширине стоил бы 42.6 млн
ячеек.

**Задача фазы 3:** не вводить полностраничных обходов, ограничивать сканы
фактической шириной данных и закрепить это тестом производительности.
Тест нужен на отдельном файле: при обычном режиме открытия fixture этот дефект
**не** воспроизводит (`max_column` = 24, см. п. 4 выше), а реальный образец в
репозиторий не коммитится. Достаточно синтетического файла на 2–3 строки с одной
пустой стилизованной ячейкой в `XFD` — этого хватает, чтобы `max_column` стал
16384. Если же парсер переведут в `read_only=True`, замеры надо переснять:
в этом режиме `max_column` берётся из XML и равен 16384 у любого из файлов.
