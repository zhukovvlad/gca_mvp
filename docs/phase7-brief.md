## 1. Скоуп v1 — что делаем и что сознательно НЕ делаем

Цель: **базовый паспорт проекта по исходной смете договора** — шапка с ТЭП,
свод, таблица по статьям фиксированного классификатора компании с руб/м².

За скобками v1 (зафиксировано пользователем, не пересматривать молча):

1. **Допсоглашения и их статусы** — паспорт v1 считает только исходную смету
   (`amendment_no IS NULL`). Никаких колонок «ДС подписанные / на рассмотрении»,
   никакого `estimates.status`. Миграция статуса — потом, поверх готовой оси.
2. **LLM-контур ключевых объёмов** — не строится. Колонка «объём» в паспорте
   скрыта или пустая. Весь §4 старого брифа — бэклог.
3. **Привязка позиций → статьи через каталожные работы** — отложена ещё в
   старом брифе, остаётся отложенной.
4. **Очередь подтверждения привязок** — в v1 не строится. Разделы без статьи
   видны в паспорте как «Нераспределённое» — этого достаточно; ручной override
   и Review-слой — следующая итерация.
5. **Обновление справочника из шаблона (админский слой с diff-превью)** — бэклог.
6. **Предзаполнение коммерческих условий договора** — бэклог; уточнение против
   старого брифа: аванс % и банковская гарантия уже доезжают до
   `proposal_additional_info` из блока «Дополнительная информация» оферты, так
   что предзаполнение возможно **детерминированно, без LLM** — записать в
   бэклог именно так.

## 2. Ключевая находка и проверенные факты

В офертах/сметах ГП есть колонка C **«Статья СМР»** — привязка разделов сметы к
**фиксированному классификатору компании** прямо в файле. Канонический источник
классификатора — корпоративный шаблон `samples/Шаблон.xlsx`. Следствия:

- Маппинг раздел → статья в v1 **детерминированный, из файла**
  (`category_source='file'`). LLM для маппинга не нужен.
- Классификатор — таблица `work_categories`, сидируется снапшотом шаблона в
  миграции. Отдельной таблицы «шаблон» НЕ заводить: один источник истины.

Факты, проверенные скриптом на реальных файлах (закладывать в код и тесты):

- **Шаблон**: один лист, одна колонка, ровно **362 строки** формата
  `(код.) Название`; уровней три (21 / 127 / 214 статей); дублей кодов и сирот
  нет; **родитель всегда раньше ребёнка** (резолв `parent_code` при вставке
  корректен без сортировки); **22 корзины** с кодом `99`/`x.99`, включая
  верхнеуровневую `99`; в строке 64 код с пробелом — `(6.6 .)` — парсер сида
  обязан быть к этому терпим.
- В офертах формат значения — `<код>. Название` (без скобок, код с завершающей
  точкой: `14.99. Прочее (MR Base)`); резолв по коду покрывает оба формата.
- **Все коды всех трёх оферт находятся в шаблоне**: 138 (159-ТУ), 168 (42-ТУ),
  222 (449-ТУ) строки со статьёй — неизвестных кодов ноль. Обработка
  неизвестного кода — защитная: раздел без привязки + warning; **автосоздание
  статей запрещено**.
- **Названия статей в сметах бывают с опечатками** относительно шаблона —
  ровно 10 уникальных кодов расхождений на 3 файла («внутреняя/внутренняя»,
  «в тч.» против «в тч», регистр, слитные скобки). Резолв — **строго по коду**
  (префикс до первого пробела, формат `^\d+(\.\d+)*\.?`, завершающую точку и
  пробелы срезать). Название сверяется в нормализованной форме (casefold,
  схлопнутые пробелы); расхождение — warning в `import_jobs.warnings`, не блок.
- **Статья проставлена не на всех строках-разделах.** Структурные группировки
  («Корпус 1», «Секция 2», «Стилобат») идут без статьи — и над статейным
  уровнем, и под ним. Правило резолва: раздел получает свою статью, иначе —
  ближайшего объемлющего раздела **по порядку файла** (см. §5); позиции
  наследуют от своего раздела.
- **Настоящие пробелы существуют.** Такие разделы остаются без привязки —
  «Нераспределённое». Это НЕ ошибка импорта.

  **Правка факта по итогам замера Ф3** (спека Ф3 §1.2; прежняя редакция называла
  здесь «4.3 Металлоконструкции» в 159-ТУ). `4.3` — **не** пробел: своей статьи у
  него действительно нет, но она есть у родителя `4`, поэтому `4.3` наследует «4»
  и её позиции ложатся в статью «4». Настоящие пробелы 159-ТУ — строка лота, `10`
  и `10.4`, и у всех трёх **ноль прямых позиций**, то есть по деньгам
  «Нераспределённое» в 159-ТУ и 42-ТУ пусто. Пробел с деньгами есть в 449-ТУ и в
  fixture: `14 SHELL & CORE` со всем поддеревом и `15 Рабочая документация` —
  39 разделов, 38 позиций.
- **Нумерация разделов (колонка B) бита систематически, не в порядке
  исключения.** В 159-ТУ — 10 дублей номеров на уровнях с 1-го по 5-й, и у
  дублей бывают **разные** статьи: два раздела «4.1.2.2» несут статьи 4.1.2 и
  4.1.3, два «7.3» — статьи 7.2 и 7.3, два «5.1.2» — статьи 5.1 и 5.2; дубли
  «7.3.1»–«7.3.3» без своей статьи стоят под разными родителями. В 42-ТУ —
  дубль «9.1.6». Дубль номера «1» есть **во всех трёх файлах**: строка самого
  лота несёт «1» в «№ раздела». Следствия: каноническая ось — статья, не номер
  раздела; принадлежность строки разделу определяет **только порядок строк
  файла**; SQL-join по номеру раздела в денежной логике **запрещён** — при
  дублях он даёт fan-out, деньги считаются дважды и ложатся в обе статьи.

## 3. Миграции

Стиль — как 0001–0004: деньги/проценты `Numeric` без точности, CHECK на всё
непредставимое, raw SQL через `op.execute` там, где Alembic не выражает,
литералы строками (миграция неизменна во времени), явный downgrade, круговой
рейс `downgrade base → upgrade head` — проверяется, а не объявляется.

### 0005 — классификатор (ЗАМЕНЕНО спекой Ф1)

Схема и сид классификатора здесь **больше не описываются**: актуальный источник —
`docs/superpowers/specs/2026-08-05-work-categories-schema-design.md`. Прежний
черновик схемы удалён, чтобы в репозитории не лежало двух разных `work_categories`
(история — в git). Что изменилось по существу после замеров:

- `is_bucket` — **generated column**, а не хранимый флаг с DEFAULT;
- точка в регулярке — `[.]`, а не `\.` (замер: при
  `standard_conforming_strings=off` обычный литерал молча принимает код `1x2`);
- добавлены `UNIQUE (sort_order)`, запрет быть своим родителем и
  **локале-независимый** запрет пустого названия (точное определение — спека
  §2.1.2; выражение здесь не дублируется намеренно);
- `parent_id` **не резолвится при вставке** из `parent_code`, а выводится из
  самого кода одним UPDATE — топологичность шаблона перестала быть допущением;
- промежуточный `work_categories_seed.csv` **не создаётся и не коммитится**: одно
  представление, литерал в миграции, генератор — сниппет спеки §6.

Осталось в силе: `level` в таблицу не класть (производное от дерева); парсер
шаблона терпим к пробелам и завершающей точке в коде (`(6.6 .)` — реальная
строка).

На `position_items` четыре колонки (**внимание: не в 0005.** Нарезка изменена —
эти колонки едут миграцией **0006** в Ф3, вместе с кодом, который их заполняет;
авторитетно — `docs/phase7-frame.md` и спека Ф1 §5):

```
smr_article_raw   Text NULL                   -- сырая «Статья СМР», только на строках-разделах
work_category_id  BigInteger NULL FK work_categories   -- только на строках-разделах
category_source   Text NULL CHECK (category_source IN ('file','llm','manual'))
chapter_item_id   BigInteger NULL FK position_items.id ON DELETE RESTRICT
                  -- физический родитель по порядку файла: у позиции — её
                  -- строка-раздел, у раздела — родительский раздел, у верхнего
                  -- уровня — NULL
CHECK (is_chapter OR (smr_article_raw IS NULL AND work_category_id IS NULL AND category_source IS NULL))
CHECK ((work_category_id IS NULL) = (category_source IS NULL))
```

`'llm'` в CHECK — зарезервировано, в v1 не используется. Статья живёт **только
на строках-разделах**; позиции несут `chapter_item_id` — ссылку на конкретную
физическую строку-раздел, а не копию статьи и не номер. Это одновременно:
аудит («найти концы»: позиция → строка-раздел → её сырой номер, сырая статья,
резолв, source), защита от дублей номеров (FK указывает на одну строку) и
дешёвый будущий ручной override (UPDATE одной строки-раздела меняет статью
всем её позициям через join). Инвариант «`chapter_item_id` указывает на строку
с `is_chapter=true`» CHECK-ом в PostgreSQL не выразить (подзапросы в CHECK
запрещены) — держится кодом импорта и закрепляется тестом. Индексы частичные:
по `work_category_id` и по `chapter_item_id`, оба `WHERE ... IS NOT NULL`.

`ON DELETE RESTRICT` на self-FK — сознательно: легитимного сценария точечного
удаления строки-раздела нет, сметы умирают только целиком через каскад
`proposals → position_items` (replace-флоу). RESTRICT этому не мешает —
**проверено экспериментом на PG 16.14**: каскад от `proposal_id` удаляет все
строки одним оператором, self-FK-проверка выполняется по его завершении;
одиночный DELETE, сносящий раздел вместе с его позициями, тоже проходит. А вот
точечное удаление раздела, на который ссылаются строки, — громкая ошибка FK
вместо тихого каскадного уноса позиций и подразделов. Та же философия
непредставимых состояний, что в 0002–0004.

Колонка **уже читается**: `get_lot_positions` забирает C на всех строках в поле

Существующие тесты парсера не трогать; новые — на файл с корректным заголовком,

## 5. Импорт (Session B)

После вставки позиций, **в той же транзакции, что домен и `done`** (правило
атомарности из фазы 5 — крэш-окно не открывать): один проход по строкам каждого
proposal **в порядке файла** (порядок вставки = порядок парсера, ключи «1..N»):

1. Ведётся **стек текущих разделов** по фактической вложенности в файле —
   принадлежность определяет положение строки, не номер (§2, дубли). Правило
   глубины — фиксированное, не на усмотрение реализации: глубина строки-раздела
   = число сегментов её «№ раздела»; раздел глубины N вытесняет из стека всё
   с глубиной ≥ N. Дубль «1» от строки лота при этом естественно вытесняется
   первым настоящим разделом «1».
2. Раздел со своим `smr_article_raw`: код префиксом до первого пробела
   (`^\d+(\.\d+)*\.?`; завершающую точку и пробелы срезать) → поиск в
   `work_categories` по `code`; название сверить в нормализованной форме →
   расхождение — warning.
3. Раздел без кода → статья ближайшего объемлющего раздела **из стека**
   (не «родителя по номеру»: у дублей типа «7.3.1» правильный родитель — тот,
   под которым строка физически стоит).
4. Материализация: на разделах — `work_category_id` + `category_source='file'`;
   на **всех** строках — `chapter_item_id` (позиция → её раздел, раздел →
   родительский раздел). Реализационно self-FK требует знать id раздела в
   момент простановки — либо вставка по ходу прохода, либо второй UPDATE-проход
   в той же транзакции.
5. Деградация: неизвестный код или нет предка со статьёй → NULL + warning;
   падать нельзя. Автосоздание статей запрещено.

Warnings в `import_jobs.warnings` — **с сырьём**: неизвестный код (сам код и
номер раздела), расхождение названия (оба варианта текста), отсутствующая
колонка, раздел без привязки (счётчик). Концы должны находиться без захода в БД.

Данные, импортированные до этой фазы (СТЕНД-Ф6-*), остаются без привязки — это
ожидаемо; перезаливка через существующий admin-only `replace=true` по желанию
пользователя, спросить перед демо.

  дополнительным работам»**, многострочное, формат строки:
  `<№ раздела этой сметы> <название> - <сумма> руб`
  (пример: `3.2.2 Гидроизоляция фундаментной плиты - 12 675 964,53 руб`).
  Суммы — с неразрывными пробелами (\xa0) и десятичной запятой — чистить в
  `Decimal`, float не появляется. Встречается строка с суммой **0 руб**
  (159-ТУ: «Подпорные стены и элементы геопластики - 0 руб») — валидна.
  **Подтверждено: текст уже доезжает до БД** — `get_additional_info` читает
  блок в `proposal_additional_info`, поэтому расшивка делается **на импорте**,
  парсер в этой части не дорабатывается.

Правила:

1. **Если в материалах/СМР агрегатной строки — «нет разбивки», хранить NULL,
   не 0** (иначе total ≠ materials + works и проверки согласованности лгут).
2. **Контрольная сумма:** сумма разобранных строк «Сведений» должна сходиться
   с «итого» агрегатной строки. Расхождение (в т.ч. из-за вариаций формата
   текста) — warning; нерасшитый остаток — отдельной записью в
   «Нераспределённое». Деньги не теряются даже при нечитаемом тексте.
3. Парсер обязан **распознать агрегатную строку по имени** в зоне перед ИТОГО
   и не споткнуться / не проглотить её молча (см. выше — сейчас глотает).
4. **Агрегатная строка не порождает `position_item`.** После распознавания её
   «итого» живёт только как контрольная сумма для «Сведений»; деньги допработ —
   единственно в `estimate_additional_works` (расшитые строки + нерасшитый
   остаток). Иначе двойной счёт: позиция с 12,7 млн плюс те же деньги в
   допработах — и инвариант §6 этого НЕ поймает, обе стороны равенства
   вырастут одинаково.

Хранение — отдельная таблица (НЕ position_items: нет единицы/количества/цены):

```
estimate_additional_works
  id               BigInteger PK
  estimate_id      FK estimates ON DELETE CASCADE
  chapter_ref_raw  Text NULL           -- '3.2.2'; NULL для нерасшитого остатка
  title            Text NOT NULL
  total_amount     Numeric NOT NULL CHECK (total_amount >= 0)
  work_category_id BigInteger NULL FK work_categories
  raw_line         Text NULL           -- исходная строка «Сведений», аудит
```

Резолв в статью: `chapter_ref_raw` → строки-разделы этой же сметы по
`chapter_number_in_proposal` → материализованный `work_category_id`. Правило
тотальное, с учётом дублей номеров: совпадений нет, ИЛИ совпало несколько
строк-разделов с **разными** статьями → NULL + warning → «Нераспределённое»;
несколько с одной статьёй — привязать. `v_category_totals` (§6) суммирует ОБА
источника: позиции + допработы; у допработ в разрезе материалы/СМР — NULL.

## 6. Агрегация и паспорт

- SQL-агрегация денег по статьям: позиции исходной сметы (`amendment_no IS
  NULL`, `is_chapter = false`) → их строка-раздел **по `chapter_item_id`**
  (FK на конкретную строку — точен при дублях номеров; join по номеру раздела
  запрещён, §2) → `work_category_id` раздела → свод по дереву статей с roll-up
  на родителей. Оформить как VIEW `v_category_totals` по образцу
  `v_position_deviations` (деньги только из `position_items`; сумма раздела =
  сумма его позиций, итогам из строк-разделов не верить). Второй источник —
  `estimate_additional_works` (§5a).
- **Инвариант, закрепить тестом:** сумма паспорта по всем статьям +
  «Нераспределённое» = сумма всех позиций исходной сметы + сумма допработ.
  Любой fan-out или потеря строк рвёт это равенство.
- Позиции разделов без привязки → строка «Нераспределённое» в паспорте:
  видимая, не размазанная. Корзины `is_bucket` показывать как обычные статьи,
  но UI вправе их подсвечивать.
- руб/м² = сумма / `objects.area_total`. Пустая `area_total` → паспорт
  показывает суммы без удельных с явным бейджем «нет ТЭП», колонку молча не
  прятать.
- Деньги end-to-end: `responses.decimal_json` и `MoneyCell` (§11 AGENTS.md),
  float не появляется нигде.

Экран паспорта v1 (`/contracts/:id/passport` — новая реализация):
шапка (объект, договор, ТЭП, аванс/гарантия/удержание), свод (итого + руб/м²),
таблица статей: код | название | итого | руб/м², иерархия сворачиваемая,
«Нераспределённое» внизу. Колонки «объём» нет. Если паспорт печатный —
проверка раскладки только через eyecheck-скрипт (playwright-core + системный
Chrome, `channel: "chrome"`); jsdom бесполезен.
