## 2. Решение

### 2.1. Что сдаёт 4а

1. Расчёт «нашей цены» строки КП по истории договоров: лестница, системы,
   состояния, суммы, ₽/м², НДС, ИПЦ — **на сервере** (§2.3–§2.10).
2. Сигнал «каталог ещё разбирает строки этапа» (§2.11).
3. Два эндпоинта чтения и третий для предпросмотра ступени (§2.12).
4. Экран этапа и экран разбора участника с панелью строки — только просмотр
   (§2.13, §2.14).
5. Входы: кнопка в панели этапа и пункт меню «⋯» ячейки КП (§2.13).
6. Справочник: `screens.md` §8 и `money-axes.md` (§2.16).

Миграций нет: 4а ничего не пишет в базу.

### 2.2. Термины

- **Строка КП** — `position_items` сметы оферты, `is_chapter = false`.
- **История** — строки последних смет договоров (§2.3).
- **Ключ строки** на уровне `v` / `p` / `f` — вариант / пара «семья, значение
  первого главного параметра» / семья (§2.5).
- **Охват** — `cls` (договоры класса тендера) или `all`.
- **Ступень** — пара (уровень, охват); шесть ступеней в порядке дизайна 3.4.

### 2.3. История и ставка договора

**Состав.** Последняя смета каждого договора — `latest_estimates()` с
отсечением `contract_id IS NULL`; договор, чей `object_id` равен объекту
тендера, не входит. Дата подписания договора состав не ограничивает: экран
живой, в истории — все договоры на момент открытия (моё решение).

**Строки истории.** Только строки с членством, чей контекст несёт вариант
(`work_variant_id IS NOT NULL`) и не архивирован; цена и вес проходят
предикаты (`is_price` / `_price_ok` на `unit_cost_total`, `is_weight` /
`_weight_ok` на `COALESCE(suggested_quantity, quantity)`); база НДС строки —
`COALESCE(estimates.vat_rate_base_override, proposals.vat_rate)`, как в VIEW;
строка с неизвестной базой в ставку не входит.

**Ставка договора по ключу** (работа, не система) — средневзвешенная нетто:
`Σ gross_to_net(unit_cost_total, база) · w / Σ w` по строкам договора с этим
ключом. **Система** — сумма нетто `total_cost_total` строк договора с этим
ключом, делённая на `area_total_sp` его объекта; без площади — договор в
ступень системы не входит.

**Ставка проходит предикат цены** (дизайн 3.4, круг 3 ревью): нефинитная или не
больше нуля ставка договора в ступень не входит и в число договоров не
считается. Промежуточного округления нет нигде (§2.9).

**Договоры с неизвестной базой.** Договор, у которого по ключу все строки
выпали из-за базы, на ступени не стоит; панель строки называет его отдельной
строкой «выпал: неизвестна база НДС» (дизайн 3.6).

### 2.4. Семантика строки

- **Контекст строки** — единственное членство (`context_members`), без
  оглядки на `CURRENT` / `STALE`: статья корзины для сравнения не нужна,
  статья берётся эффективная (ниже).
- **Вариант и семья** — `catalog_contexts.work_variant_id` /
  `work_family_id` (после слияний уже живые). Нет варианта — состояние
  «не разобрана в каталоге».
- **Вид** — `catalog_contexts.semantic_kind`; `SYSTEM` — система, всё
  остальное, включая `UNKNOWN`, — работа (моё решение: `UNKNOWN` ставит
  только человек, и строка без признака системы сравнивается за единицу).
- **Подпись варианта** — название семьи и значения активных главных
  параметров **действующей** (`frozen`) версии схемы в порядке номера, «не
  уточнено» для `value_id IS NULL`; второстепенные — из
  `context_parameter_values` контекста, в подсказке.
- **Первый главный параметр** — главный активный параметр действующей
  версии с наименьшим номером; уровень `p` есть, только если активных главных
  два и больше. Значение строки для него — `work_variant_values` её варианта
  по этому `parameter_id`. Вариант на недействующей версии схемы (после
  слияния семей) уровня `p` не получает и сравнивается на `v` и `f` (моё
  решение: значения разных версий несопоставимы по идентификатору).
- **Эффективная статья** — статья ближайшей главы, тем же соединением, что
  `v_category_totals` (`chapter_item_id` → `work_category_id`). Экран этапа
  и таблица статей группируют по **корню** дерева классификатора; строка без
  статьи — в «Нераспределённое».

### 2.5. Лестница

Шесть ступеней дизайна 3.4: `v·cls`, `v·all`, `p·cls`, `p·all`, `f·cls`,
`f·all` (ступени `p` — только у семей с двумя и более главными). **Авто** —
первая сверху ступень, где договоров не меньше двух; если такой нет — самая
узкая с одним договором; если ни на одной нет договоров — состояние «нет в
наших договорах».

**Наша расценка** — минимум ставок договоров класса тендера на выбранной
ступени; если на ступени договоров класса нет — минимум по всем, с признаком
`our_from_all_classes`. Класс тендера — `tenders.rate_class_id` (снимок на
дату тендера). Класс договора — `contracts.rate_class_id`.

**Ручной выбор ступени в 4а не сохраняется.** Панель строки показывает все
ступени с числом договоров; выбор другой ступени — **предпросмотр**: эндпоинт
§2.12 считает строку на выбранной ступени, плитки и суммы экрана остаются
автоматическими. Сохранение ручной ступени и её влияние на суммы — 4б
(правка, право `admin`).

### 2.6. Системы

Дизайн 3.4 (круг 1 ревью): **ступень у систем одна на семью внутри КП.**

1. Системные строки КП (вид `SYSTEM`, вариант есть, сумма проходит предикат)
   группируются по семье.
2. Для каждой ступени по порядку строки семьи делятся по ключу уровня
   ступени; у каждой группы — свои договоры этой ступени.
3. Авто — первая ступень, где у **каждой** группы не меньше двух договоров;
   иначе — первая, где у каждой хотя бы один; иначе — `f·all`.
4. Цена группы КП — сумма нетто строк группы / площадь объекта тендера;
   строка получает долю `доля = нетто строки / нетто группы`; рубли разницы
   делятся по долям.
5. **Нулевая или непригодная сумма группы — состояние «нет цены»**, без
   деления (круг 2 ревью).
6. Предпросмотр ступени у системной строки — предпросмотр для всей семьи в
   этом КП.

Площади объекта тендера нет — системы КП не сравниваются, состояние «нет
площади объекта» (своя причина, деньги — в «не с чем сравнить»).

### 2.7. Состояния строки

Ровно одно, проверка сверху вниз:

| Код | Когда | Корзина |
|---|---|---|
| `in_progress` | строка ждёт каталог (§2.11) | «не с чем сравнить», своя подпись |
| `unknown_vat_base` | база НДС КП неизвестна | «не с чем сравнить», своя подпись |
| `no_price` | цена или вес строки КП не проходят предикат; у системы — сумма группы | «не с чем сравнить» |
| `no_area` | система, у объекта тендера нет площади | «не с чем сравнить» |
| `no_variant` | у строки нет варианта (нет членства, нет варианта у контекста) | «не с чем сравнить» |
| `no_history` | ни на одной ступени нет договоров | «не с чем сравнить» |
| `unit_mismatch` | цена КП / медиана ступени `> 5` или `< 0,2`, **или** ставка любого договора / медиана остальных договоров ступени `> 5` или `< 0,2` | своя плитка |
| `comparable` | остальное | суммы ниже |

`unknown_vat_base` КП: база — `COALESCE(estimates.vat_rate_base_override,`
единогласие `proposals.vat_rate`)` (своя копия правила `_rates_by_estimate`,
§1.2). Обычно база одна на КП, поэтому состояние — у всех его строк.

### 2.8. Суммы и ₽/м²

Все суммы — в нетто, `Decimal`, без промежуточного округления.

- **«Можно выторговать до нашей цены»** = `Σ max(0, (цена КП − наша
  расценка) · вес · доля)` по `comparable`.
- **«Ниже всего, что платили»** = `Σ (цена КП − минимум ступени) · вес ·
  доля` по `comparable` с ценой КП ниже минимума; число строк.
- **Положение** строки: `above` (выше максимума ступени), `in`, `below`.
- **«Разные единицы учёта»** — число строк и сумма нетто КП по ним.
- **«Не с чем сравнить»** — сумма нетто КП по остальным состояниям, разбивка по
  кодам.
- Вес строки КП — `COALESCE(suggested_quantity, quantity)`; у системы вместо
  веса — площадь объекта тендера (дизайн 3.13).

**₽/м² объекта** = сумма нетто по статьям сметы / `area_total_sp` (дизайн
3.13): у КП — его сметы и объекта тендера, у договора — последней сметы и его
объекта. **Источник сумм — `v_category_totals`** (`CATEGORY_TOTALS`,
`crud/project_passport.py:84`), как у паспорта и свода по этапам: строки-позиции
и допработы, по каждому предложению с его базой НДС, переведённые в нетто
`gross_to_net`. **Правило суммирования денег — не предикат цены:** VIEW
складывает все **конечные** `total_cost_total`, отрицательные тоже
(миграция `0012`, фильтр только на `NaN` и бесконечности), и спека его не
сужает — позиции `100` и `−20` дают `80`. Предикат цены «конечно и больше
нуля» остаётся правилом пригодности **расценки** строки (§2.3, §2.7) и к
суммам статьи не применяется. Предложение с неизвестной базой даёт нетто
`null`; сумма сметы, где такое есть, — не число, а состояние
`unknown_vat_base` (у КП) или выпадение договора из вилки ₽/м² (у истории).
По статье — то же внутри корня эффективной статьи (ключ VIEW —
`work_category_id` главы, корень — по дереву классификатора). Без площади —
`null` с причиной `no_area`.

Чем выстрадано (ревью Codex, круг 1 гейта 2): редакция 1 применяла к суммам
предикат `> 0` и выбрасывала отрицательные позиции — стоимость КП, вилка
истории и «статья целиком» расходились бы с паспортом и сводом по этапам.

**Статья целиком** = (₽/м² КП по статье − минимум ₽/м² договоров класса по
статье) × площадь объекта тендера; договоров класса со статьёй нет — `null`.

### 2.9. НДС

Дизайн 3.12 говорил «переключатель НДС пересчитывается на клиенте
множителем». **Спека это меняет** (§2.14): деньги в JS не перемножаются
(`AGENTS.md` §3, §10: «считает сервер, до агрегации», в JS нет `Decimal`).
Вместо этого **ответ несёт каждое денежное поле в двух видах**: `net` и
`shown` — в ставке КП (`net_to_gross(net, ставка КП)`), посчитанных на
сервере. Переключатель выбирает поле, без запроса и без лоадера.

- Ставка показа КП — его база НДС (§2.7); на экране этапа — у каждого
  участника своя, и подпись это называет (дизайн 3.12).
- **История на экране этапа — общая колонка, а ставки участников могут
  различаться** (ревью Codex, круг 1 гейта 2: 100 ₽ нетто — это 100 ₽ для
  участника с НДС 0 % и 122 ₽ для участника с 22 %). Поэтому:
  - всё, что относится к участнику (его ₽/м², ячейки статей, вилка и наша
    расценка в его строках, «статья целиком»), несёт `shown` **в его
    ставке** — поле внутри участника;
  - общая колонка «Наши договоры» несёт `shown` только тогда, когда у всех
    участников с известной базой ставка одна (`history_shown_rate`); если
    ставки разные или ни одной нет — `shown` общей колонки `null`, колонка
    в режиме «с НДС» остаётся в нетто с подписью «без НДС — ставки
    участников разные»;
  - в разборе участника участник один, и история там всегда в его ставке.
- База КП неизвестна — `shown` равен `null`, подпись «база НДС неизвестна».
- Договоры в `shown` пересчитываются по ставке КП, не по своей (дизайн 3.12).
- Округление — `quantize_money` один раз на поле ответа; ставки за единицу —
  без округления до копеек, строкой (§2.12): копеечные цены остаются ценами
  (круг 4 ревью, дизайн 3.13).

### 2.10. ИПЦ

- Параметры запроса `inflation_series_id` (необязательный) — без него ответ
  номинальный, и ключей приведения в нём нет (`AGENTS.md` §10).
- **Целевой месяц** — месяц `tender_rounds.held_on`; если даты нет — месяц
  `data_prepared_on_date` сметы КП; если нет обеих — отказ 422
  `inflation_target_missing` (дизайн 3.13).
- **Период договора** — правило `_estimate_period` (`crud/comparison.py:578`):
  исходная смета — `COALESCE(data_prepared_on_date, signed_date)`,
  допсоглашение — только `data_prepared_on_date`. **Последняя смета-ДС без
  даты подготовки — отказ 422 `amendment_date_missing`**, как в
  `resolve_inflation` (`crud/comparison.py:705-711`), с теми же контекстом
  (`estimate_ids`) и смыслом: подставлять дату исходного договора или молча
  выкидывать договор из истории нельзя — это поменяло бы вилку без подписи.
  Отказ проверяется до расчёта, по всем договорам истории запроса (ревью
  Codex, круг 1 гейта 2).
- **Приводятся только ставки истории** (ставки за единицу и ₽/м²
  договоров); КП — на целевую дату и не приводится; площадь не индексируется.
  Порядок — нетто → приведение → ставка показа.
- **Своё планирование на ядре `money/inflation.py`**: `resolve_inflation`
  не годится (только договоры и выбор месяца пользователем), его копия для
  договоров истории с тем же ядром, теми же отказами (404 ряда, 422
  `missing_inflation_years` с `missing_years`) и тем же видом подписи.
- **Ряд по умолчанию** на экране — первый активный ряд по `id` (на стенде —
  «Росстат, ИПЦ, декабрь к декабрю»); список активных — существующий
  `GET /api/v1/inflation-series` (`routers/inflation_series.py:109`, под
  `get_current_user`, открыт `member`). Дизайн 3.12 называл ряд по имени; выбор по `id` — моё
  решение, имя может меняться.
- **Отказ приведения не роняет экран — по образцу страницы сравнения**
  (`ComparePage.tsx:625-651`): при **любом из трёх** отказов приведения —
  422 `missing_inflation_years`, `amendment_date_missing`,
  `inflation_target_missing` — клиент делает **второй запрос того же
  эндпоинта без ряда** и показывает его номинальные цифры; над ними —
  `InflationRefusalBanner` (сообщение сервера дословно), в шапке — подпись
  «цены без приведения». Кнопка «Заполнить недостающие годы» — только у
  `missing_inflation_years` и только `admin`; у двух других кнопки нет: правка
  ряда их не лечит. Если упал и номинальный запрос — обычное состояние ошибки
  экрана, без пустого молчания. Наличие кеша клиента на это не влияет: прямая
  ссылка с выбранным рядом ведёт себя так же (ревью Codex, круги 1–2 гейта 2:
  в редакции 2 `inflation_target_missing` в возврат к номиналу не входил, а
  обе даты — `tender_rounds.held_on` и `estimates.data_prepared_on_date` —
  в схеме допускают `NULL`).
- **`InflationRefusalBanner` получает третью ветку текста** для
  `inflation_target_missing` — без кнопки, по образцу `amendment_date_missing`
  (`frontend/src/components/inflation/InflationRefusalBanner.tsx`, ветки по
  коду). Сообщение сервера называет, чего не хватает: «у этапа нет даты
  проведения, и у КП нет даты подготовки — приведение по ИПЦ не к чему
  привязать».

### 2.11. Сигнал «каталог ещё разбирает»

Строка КП — `in_progress`, если выполнено одно из:

1. у её контекста есть задание `family_suggestion` или `context_values` в
   `pending` или `running`;
2. у семьи её контекста есть задание `family_schema` в `pending` или
   `running`;
3. у контекста нет семьи, и для единицы её каталожной строки есть задание
   `family_discovery` в `pending` или `running`.

**Не** `in_progress`: `error`, `privacy_hold`, удержанная пачка, захват на
паузе — это «не разобрана в каталоге» с подписью «ждёт решения
администратора» (дизайн 3.13). Иначе плашка висела бы без конца.

Прогресс плашки — `(строки этапа − in_progress) / строки этапа` по всем КП
этапа; плашка видна, пока `in_progress > 0`. Экран опрашивает эндпоинт этапа
раз в 5 секунд, пока сигнал не погас (образец — условный `refetchInterval`,
`frontend/src/services/queries.ts`), и не опрашивает в фоне.

### 2.12. API

Все — `GET`, под `get_current_user` (чтение открыто `member`), ответ через
`decimal_json`; деньги и ставки — строки; даты — `iso`.

**`GET /api/v1/tenders/{tender_id}/rounds/{round_id}/our-price`**
`?inflation_series_id=` — экран этапа.

```
{
  tender: {id, title, object: {id, title, area_total_sp|null}, rate_class: {id, title}},
  round: {id, stage_no, label, held_on|null},
  progress: {lines_total, in_progress, waiting_admin},
  history: {contracts: [{id, number, object_title, year, rate_class, contractor_id, area|null}],
            shown_rate: rate|null,  /* одна ставка всех участников с известной базой, иначе null (§2.9) */
            per_sqm: [{contract_id, net, shown|null}]},
  inflation: {...как у сравнения...} | отсутствует,
  participants: [{offer_id, estimate_id|null, contractor: {id, title}, vat_rate|null,
                  state: "ok"|"no_estimate"|"unknown_vat_base",
                  per_sqm: {net, shown}|null, ours_with_contractor: int,
                  totals: {bargain, below, below_lines, unit_mismatch_lines, unit_mismatch_amount,
                           not_comparable: {total, by_state: {...}}}  /* каждое — {net, shown} */}],
  articles: [{work_category_id|null, code, title, sort_order,
              ours_class_per_sqm: {min, max}|null,           /* {net, shown|null} — shown по history.shown_rate */
              cells: [{offer_id, per_sqm, whole, unit_mismatch_lines,

```

**`GET /api/v1/tenders/{tender_id}/rounds/{round_id}/our-price/offers/{offer_id}`**
`?inflation_series_id=` — разбор участника: шапка как выше для одного
участника, таблица статей (`articles`) с суммами по статье и **все строки КП**:

```
lines: [{position_item_id, article_id|null, title, unit, quantity, section_ref,
         family|null, variant_label|null, secondary: [{name, value}],
         state, kind: "work"|"system",
         kp: {unit_price, total}  /* {net, shown} */,
         rung: {level, scope, auto: true, threshold_met: bool} | null,
         rungs: [{level, scope, contracts: int}],
         range: {min, max, median}|null, ours: {value, from_all_classes}|null,
         position: "above"|"in"|"below"|null,
         bargain, below  /* {net, shown} | null */,
         group: {lines: int, share}|null,
         unit_mismatch: {kp_ratio|null, contracts: [{contract_id, ratio}]}|null}]
```

**`GET …/our-price/offers/{offer_id}/lines/{position_item_id}?level=&scope=`**
`&inflation_series_id=` — панель строки и предпросмотр ступени: та же строка
на выбранной ступени (у системы — вся семья) и **договоры ступени**: объект,
номер, год, класс, подрядчик, ставка (`{net, shown}`), признак «нижняя
граница», признак «договор с этим подрядчиком», кратность расхождения, договоры,
выпавшие из-за базы НДС. Без `level`/`scope` — авто.

**Отказы** (`DomainError` → `{code, message, ...}`): 404 — тендер, раунд,
оффер или строка не найдены либо не принадлежат друг другу; 404 ряда; 422
`missing_inflation_years` (`missing_years`); 422 `amendment_date_missing`
(`estimate_ids`); 422 `inflation_target_missing`; 422 `unknown_rung` —
ступень, которой у строки нет. Тексты `missing_inflation_years` и
`amendment_date_missing` — те же, что у сравнения договоров;
`inflation_target_missing` — новый код с третьей веткой баннера (§2.10).

Строки разбора не пагинируются: 1 831 строка — один ответ; таблица на клиенте
раскрывается по статьям. Форма — интерфейс гейта 3, имена полей могут
уточниться планом, состав — нет.

**Маршрут** `/tenders/:tenderId/rounds/:roundId/our-price`, вне меню, вне

**Входы:**

### 2.14. Разбор участника

**Маршрут** `/tenders/:tenderId/rounds/:roundId/our-price/offers/:offerId`
(`?article=` раскрывает статью).

Раскладка «Воронка» (дизайн 3.3): путь с возвратом к этапу и переключателем
участников; плитки-фильтры; полоса ₽/м²; таблица статей с раскрытием строк;
колонки строк — дизайн 3.3, сортировка по всем; панель строки (`ui/sheet`)
— дизайн 3.5 **без блока «Для выгрузки»**: цены, лестница с числом договоров,
предпросмотр ступени, договоры ступени, плашка «разные единицы учёта».
Наша расценка — справкой.

**Расхождения спеки с дизайном:**
1. НДС — два поля в ответе вместо множителя на клиенте (§2.9).
2. Ручная ступень в 4а — предпросмотр без сохранения (§2.5); сохранение — 4б.
3. Ряд ИПЦ по умолчанию — по `id`, не по имени (§2.10).
4. Переключение НДС — без лоадера (нет запроса); серый слой — на смену ряда

   без глав» (§2.8).
6. Общая колонка истории на экране этапа в режиме «с НДС» — только при одной
   ставке участников, иначе нетто с подписью (§2.9).

### 2.17. Скорость

Цель дизайна 3.13: экран этапа на стенде (4 × 1 831 строка, история 10 100
строк) — **не дольше 3 секунд** ответа; разбор участника — не дольше 2 секунд.

Как достигается — **расчёт на запрос**: история читается одним проходом
SQL на все ключи всех строк этапа (не по строке), ставки договоров по ключам
считаются в Python один раз на запрос; кеша нет (моё решение: без кеша нечему
протухать при новых договорах и вариантах — дизайн 3.7). Если замер
приёмки покажет больше цели — кеш истории по отпечатку (последние сметы,
версии схем, время последнего назначения варианта) заводится отдельной
задачей, а не молча.

### 2.18. Чем держится каждое правило

| Правило | Чем держится |
|---|---|
| история — последние сметы договоров, без объекта тендера, без смет оферт и раундов | тест: смета оферты и договор объекта тендера в ставку не входят |
| ставка договора проходит предикат; копеечная — входит | тест: договор с ставкой `0`, `NaN` выпадает из ступени и числа договоров; ставка `0,0000001` — входит и даёт `unit_mismatch` |
| предикаты цены и веса совпадают с `money.price` | тест согласия SQL ↔ Python, как `test_price_predicate_sql.py` |
| строка с неизвестной базой не входит; КП с неизвестной базой — состояние | тесты обоих случаев |
| лестница: порог 2, класс раньше параметров, fallback 1, `no_history` | табличный тест чистой функции |
| системы — одна ступень на семью, одинаковый состав | тест: две системные строки семьи на разных ступенях по отдельности — расчёт сравнивает сумму всей семьи; повтор случая «Временные здания» |
| нулевая сумма группы — `no_price`, без деления | тест |
| `unit_mismatch` по КП и по договорам; не в суммах | тест |
| суммы «выторговать» и «ниже» | тест на числах |
| `net` и `shown` — сервер; `shown` по ставке КП | тест: договор с 20 % в `shown` пересчитан по 22 % КП |
| ₽/м² и суммы статей — `v_category_totals`: конечные, с отрицательными и допработами | тест: позиции `100` и `−20` дают `80`; допработа статьи входит в сумму; совпадение с суммой статьи свода по этапам на той же смете |
| общая колонка истории в режиме «с НДС» — только при одной ставке участников | тест: участники 0 % и 22 % — у общей колонки `shown = null`, у каждого участника своя `shown` |
| ИПЦ: цель — месяц этапа; приводится история; отказы | тесты: приведённая ставка = номинал × коэффициент ядра; 422 `missing_inflation_years` при дыре; 422 `amendment_date_missing` для последней сметы-ДС без даты подготовки — без подстановки даты договора |
| отказ ИПЦ → номинальный запрос и баннер | тест фронта на **каждый из трёх кодов**: прямой заход с рядом без кеша, сервер 422 → второй запрос без ряда, баннер своей ветки (кнопка — только `missing_inflation_years` у `admin`), подпись «без приведения»; номинальный тоже упал → состояние ошибки |
| `inflation_target_missing` | тест бэкенда: этап без `held_on` и КП без `data_prepared_on_date` с рядом → 422; без ряда → 200 с номинальными цифрами |
| без ряда — ключей приведения нет | тест |
| `in_progress` и «ждёт решения администратора» | тесты по каждому виду задания и статусу |
| `member` читает, эндпоинты не пишут | тест прав; тест «ни одной записи» (счётчики транзакции) |
| нет `float` в ответе | тест на типы JSON |
| скорость | замер на стенде при приёмке (DoD 12) |

## 3. Отвергнутые альтернативы
