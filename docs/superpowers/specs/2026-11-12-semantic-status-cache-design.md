## 1. Что есть (разведка кода 12.11.2026)

- `GET /api/v1/semantic/status` → `routers/semantic.py`, `queue_status_route`
  (право `admin`) → `crud/semantic_queue.py`, `queue_status(db)`. Дорогие
  части ответа: `stale_units` и `config_stale` из `_stale_scan(db)`;
  `releasable_open` = `len(current_proposals(db, family_ids=None, page=None))`
  (`services/releasable.py`). Остальные поля — `spent_24h_usd`,
  `daily_budget_usd`, `claim_paused`, `held_batches`, `zones_disputed`, пять
  счётчиков `_promotion_counters` — дешёвые (0,06 с на `gca_dev`).
- `get_db` (`database.py`) не коммитит: маршруты коммитят сами, внутри
  обработчика. Значит, к моменту, когда прослойка `@app.middleware("http")`
  получает ответ или исключение, коммит изменения уже сделан (или не сделан
  вовсе).
- Фоновые изменения каталога из HTTP — только импорт:
  `background.add_task(run_import_job, …)` в `routers/estimates.py`
  (загрузка сметы) и дважды в `routers/tenders.py` (договор из КП, файл
  раунда). `run_import_job` (`services/import_pipeline.py`) исключений наружу
  не выпускает.
- Прослойка `@app.middleware("http")` возвращает ответ раньше, чем фоновые
  задачи запроса завершатся, поэтому сброс по окончании запроса импорт не
  покрывает (ревью Codex гейта 1, замечание 1). Замер 12.11.2026 на FastAPI
  0.139.2 / Starlette 1.3.1: `finally` прослойки отработал раньше фоновой
  задачи, спавшей 0,3 с.
- `accept_all_proposals` (`services/releasable.py`) коммитит после каждой
  семьи; исключение не из `DomainError` выходит наружу после уже
  закоммиченных семей (замечание 2).
- Тесты читают сводку двумя путями: прямым вызовом `queue_status(db_session)`
  (`test_analog_releasable.py`, `test_catalog_discovery_systems.py`) и через
  `GET …/status` (`test_semantic_queue_api.py` — 28 мест, `test_analog_zone_job.py`,
  `test_work_variants_api.py`). Многие меняют данные **через crud, минуя
  HTTP**, между двумя чтениями и ждут свежий ответ — например,
  `test_unit_is_stale_exactly_when_its_reask_would_change_something`.

## 2. Решение

### 2.1. Что сдаёт фича

Ответ `GET /semantic/status` по составу и форме не меняется ни одним ключом.
Меняется только свежесть трёх полей — `stale_units`, `config_stale`,
`releasable_open`: они берутся из общего кэша в памяти процесса, пока он
действителен. Фронт не меняется.

### 2.2. Разделение расчёта

`crud/semantic_queue.py`:

- новая `heavy_status_parts(db) -> HeavyStatusParts` — считает три дорогих
  поля (`_stale_scan` и `current_proposals`), ничего не помнит;
- `queue_status(db, *, heavy: HeavyStatusParts | None = None)` — при
  `heavy=None` считает их сама через `heavy_status_parts` (поведение прямого
  вызова не меняется — им пользуются тесты и любой будущий внутренний
  вызывающий), иначе подставляет переданные; дешёвые поля считаются всегда.

`HeavyStatusParts` — `TypedDict` с ключами `stale_units`, `config_stale`,
`releasable_open`, типы — как у одноимённых полей `QueueStatus`.

Маршрут `queue_status_route` — единственное место, которое ходит в кэш:
`queue_status(db, heavy=status_cache.get(lambda: heavy_status_parts(db)))`.

### 2.3. Кэш

Новый модуль `services/status_cache.py`: класс `StatusCache` и общий экземпляр
`status_cache`. Интерфейс:

- `get(compute: Callable[[], T]) -> T` — действительное значение или
  результат пересчёта;
- `invalidate() -> None` — сброс;
- конструктор принимает `ttl_seconds: Callable[[], float]` (читается при
  каждом `get`, чтобы тест мог менять настройку) и `clock: Callable[[], float]`
  (по умолчанию `time.monotonic`).

Срок жизни — новая настройка `SEMANTIC_STATUS_CACHE_TTL_S: int = Field(300,
ge=0)` (`config.py`, строка-пояснение в `backend/.env.example`). `0` —
кэш выключен: каждый `get` вызывает `compute`, ничего не запоминая и не
беря замка.

Поведение (все правила — для `ttl > 0`):

1. **Действительность.** Значение действительно, если с конца его пересчёта
   прошло меньше срока и после начала пересчёта не было сброса.
2. **Поколение.** Каждый `invalidate()` увеличивает номер поколения и
   стирает значение. Пересчёт запоминает номер поколения при старте; если к
   концу пересчёта номер сменился, результат **не запоминается**.
3. **Один пересчёт.** Пересчитывает один вызов за раз. Пока он идёт:
   - вызов, у которого есть истёкшее, но не сброшенное значение текущего
     поколения, получает его сразу, не дожидаясь;
   - вызов, у которого значения нет (первый запуск или после сброса), ждёт
     окончания пересчёта; если тот запомнил результат текущего поколения —
     получает его, иначе (сброс во время пересчёта, исключение в `compute`)
     пересчитывает сам по тем же правилам.
4. **Результат, начатый до сброса, не отдаётся пришедшему после.** Вызов,
   начавшийся после сброса, не получает результат пересчёта, начатого до
   него, — ни из памяти, ни дожидаясь (следует из 2 и 3).
5. **Исключение** в `compute` уходит вызвавшему; признак «идёт пересчёт»
   снимается, ожидающие просыпаются (и пересчитывают по правилу 3); кэш
   остаётся без значения — истёкшее значение, которое до ошибки отдавалось
   по правилу 3, тоже стирается.
6. Значение отдаётся как есть; вызывающие его не изменяют.

Каждый пересчёт пишет в журнал строку уровня `INFO` с длительностью — по ней
проверяется работа кэша на стенде (§3, проверка 7).

### 2.4. Точки сброса

1. **Прослойка в `main.py`** — `@app.middleware("http")`: для методов
   `POST`, `PUT`, `PATCH`, `DELETE` (тот же список, что у
   `csrf_middleware`) вызывает `status_cache.invalidate()` по окончании
   обработки — при любом коде ответа и при исключении (`try/finally` вокруг
   `call_next`). Чтения (`GET`, `HEAD`, `OPTIONS`) кэш не трогают. Путь
   запроса не проверяется: сбрасывает любой запрос на изменение, в том числе
   не связанный с каталогом (вход, правка норматива) — это цена отказа от
   списка (дизайн §5).
2. **`run_import_job`** — `status_cache.invalidate()` в `finally` вокруг всего
   тела: при `done`, `error` и любом исключении, после коммита сессии B.
3. Фоновый исполнитель очереди и консольные команды кэш не сбрасывают —
   их изменения видны не позже срока жизни (дизайн §3, §5).

### 2.5. Тесты и настройка

Автоматическая фикстура в `backend/tests/conftest.py` ставит
`SEMANTIC_STATUS_CACHE_TTL_S = 0` и сбрасывает `status_cache` до и после
каждого теста. Действующие тесты проверяют расчёт сводки, а не кэш, и меняют
данные в обход HTTP (§1) — с включённым кэшем они проверяли бы прежнее
значение. Тесты кэша включают срок явно и подают свои часы. Числа
действующих тестов не меняются, правок в них нет.

Это не маскировка дефекта переменной окружения
(`docs/insights/environment-hygiene-masks-the-defect.md`): продуктовое
значение по умолчанию — 300, и каждое утверждение кэша проверяется тестом,
где он включён.

## 3. Проверки

Пять проверок дизайна (§3), проверка ошибки пересчёта (ревью Codex гейта 2)
и две проверки стенда. Уровень — где живёт дефект: правила кэша — модульные
тесты `StatusCache` с поддельными часами и потоками; точки сброса —
интеграционные, через `admin_client` и `run_import_job`. Каждое ожидание
потока или события в тестах ограничено по времени: снятие защиты не должно
вешать прогон, а должно его ронять.

1. **Срок.** Второй `GET /status` в пределах срока не вызывает
   `heavy_status_parts` (счётчик вызовов), но дешёвые поля считает заново:
   изменение, видимое только в дешёвом поле (например, остановка захвата
   через crud), отражается сразу; по истечении срока — пересчёт.
2. **Сброс запросом на изменение — при любом исходе.** После `POST` с ответом
   2xx, с ответом 4xx и с исключением в обработчике следующий `GET /status`
   пересчитывает; после `GET` другого маршрута — нет. Сценарий ревью:
   «принять всё» (`POST …/releasable-proposals/accept-all`), упавшее
   исключением после коммита первой семьи, — следующий `GET /status`
   показывает `releasable_open`, уменьшенный на принятые предложения первой
   семьи.
3. **Импорт.** Сводка, запрошенная во время импорта (из подставленного
   `parse` в `run_import_job`), запоминается; по окончании импорта — и при
   `done`, и при `error` — следующий `GET /status` пересчитывает.
4. **Пересечение со сбросом.** Пересчёт, начатый до `invalidate()` и
   законченный после, не запоминается; вызов, начавшийся после сброса и
   ждавший этого пересчёта, считает сам (модульный, потоки и события).
5. **Один пересчёт.** Два одновременных `get` при пустом кэше вызывают
   `compute` один раз и получают одно значение; при истёкшем значении второй
   вызов получает прежнее значение без ожидания (модульный).
6. **Ошибка пересчёта** (модульный, потоки и события):
   - при пустом кэше первый вызов начал `compute`, второй ждёт, первый
     выбрасывает исключение — первый получает исключение, второй
     завершается успешным новым пересчётом, третий вызов получает
     запомненное значение без пересчёта;
   - после истечения срока пересчёт выбрасывает исключение — истёкшее
     значение не остаётся: следующий вызов пересчитывает, а не получает его.
7. **Стенд, нагрузка.** На `gca_dev` с открытой вкладкой «Предложения» в
   журнале — не больше одной строки пересчёта за пять минут без действий;
   ответы `/status` между пересчётами — меньше 1 с (`backend/logs/app.log`).
8. **Стенд, свой результат.** После «Перезапросить единицу…» баннер единицы
   пропадает при первом же перечитывании шапки, без ожидания срока.

Проверки 2–6 — свойства конкурентности и сброса: ревьюер задачи предъявляет
каждую снятием защиты (убрать `finally`/сброс в прослойке, сброс в
`run_import_job`, проверку поколения, ожидание при пустом кэше; при
исключении в `compute` — снятие признака «идёт пересчёт», пробуждение
ожидающих, стирание истёкшего значения) — тест обязан покраснеть, а не
зависнуть.

## 4. Отвергнутые альтернативы

Сверх дизайна §5:

- **Кэш внутри `queue_status`.** Прямые вызовы в тестах и любой внутренний
  вызывающий получили бы прежнее значение после изменения через crud;
  граница кэша — маршрут, а не расчёт.
- **Чистая ASGI-прослойка вместо `@app.middleware("http")`** — она
  дожидается фоновых задач ответа и покрыла бы импорт без отдельного сброса.
  Отвергнута: правило держалось бы на устройстве Starlette, а не на коде
  проекта, и проверялось бы только через HTTP; сброс в `run_import_job` явен
  и проверяется без транспорта.
- **Включённый кэш в тестах со сбросом между тестами.** Не спасает тесты, что
  меняют данные через crud внутри одного теста (§1); править их — значит
  переписывать проверки расчёта под кэш.

## 5. Границы

- Не делается: инкрементальное устаревание, пакетный `current_proposals`,
  ускорение `/semantic/discovery/units` и `/semantic/releasable-proposals` —
  долг №57.
- Фронт, справочник (`docs/reference/`) и `AGENTS.md` не меняются: сводку
  справочник не описывает, инвариант §3 не правится.

## 6. Definition of Done

- Проверки 1–6 — тесты, зелёные; проверки 2–6 предъявлены снятием защиты,
  включая восстановление после исключения в `compute`.
- Затронутые наборы (`test_semantic_queue_api.py`, `test_analog_releasable.py`,
  `test_catalog_discovery_systems.py`, `test_analog_zone_job.py`,
  `test_work_variants_api.py`, тесты импорта) зелёные без правок; полный
  прогон — GitHub Actions.
- Проверки 7–8 — на стенде, с замером в devlog.
- `docs/devlog/2026-11-12-semantic-status-cache.md`: что сделано, замер
  стенда, тронутые области и прочитанные файлы граблей (`backend.md`,
  `runs.md`) — AGENTS §10.
