# Пересмотр привязок: ожидающее назначение, перезапрос привязанных, смена семьи

**Гейт 1 — общий с фичей 3а-1** ([дизайн](../design/2026-10-02-catalog-variants.md),
редакция 12, закрыт 02.10.2026). **Гейт 2 закрыт 03.10.2026** вместе с 3а-1: эта
спека выделена из [спеки 3а-1](2026-10-02-catalog-variants-design.md) решением
пользователя после того, как четыре круга ревью Codex не сошлись именно на
протоколе ожидающего назначения (10 → 11 → 3 → 2 → 5 замечаний, почти все —
о его пересечениях со слиянием семей, пачками и отменами). Содержание ниже —
результат тех кругов; история — коммиты файла 3а-1 и PR #57. Это **фича 3а-2
направления «семьи и контексты»**; она **стоит на смерженной 3а-1**: вариант,
схема семьи, три вида заданий, промоушен — её предпосылки, не предмет.

**Что меняет.** В 3а-1 привязанный контекст новых предложений не получает, а
смена семьи у контекста с вариантом снимает вариант до готовности новых
значений. Здесь: привязанные контексты пересматриваются перезапросом единицы;
смена семьи у контекста с вариантом двухшаговая — контекст держит прежние семью
и вариант, пока не готовы значения по новой семье; ошибка автопринятия
исправляется правилом, решение человека — только человеком; появляется очередь
«Смена семьи».

**Решения этой спеки сверх дизайна** (сверх решений 3а-1):

1. **предикат применимости фичи 2 больше не требует `work_family_id IS NULL`**:
   привязанный контекст тоже получает предложения, и это даёт перезапросу
   единицы «пересмотр привязок» без второго предиката; что делать с ответом,
   решает публикация по происхождению текущей семьи (§2.2);
2. **ожидающее назначение семьи хранится на контексте** (шесть колонок), а не
   отдельной таблицей: у контекста одно ожидание, второе его заменяет (§2.1);
3. **три новых решения предложения** — `auto_pending`, `auto_superseded` без
   автора и `accepted_pending` с автором: исполненное, вытесненное и отложенное
   человеком различимы в журнале (§2.1, §2.3);
4. **правило не вытесняет ожидание человека**: его предложение другой семьи
   идёт в очередь «смена семьи», ожидание `manual`/`suggestion` снимает только
   человек (§2.3);
5. **ожидаемая семья — живая привязка** для архивирования и смены единицы, и
   обработчик перепроверяет её при применении (§2.3, §2.5);
6. **одно новое событие журнала** `context_family_pending` с исходами `set` /
   `superseded` / `cancelled` / `applied` / `redirected` (§2.7).

Номер ревизии `AGENTS.md` здесь **намеренно не назван**: страж
(`check_agents_index.py`) не разрешает версию, которой ещё нет ни в преамбуле, ни
в архиве.

---

## 1. Проблема с замерами

### 1.1. Новая семья не забирает своих строк

Перезапрос единицы фичи 2 (§2.10 спеки 2) ставит задания только контекстам
**без семьи**: `is_applicable` требует `work_family_id IS NULL`
(`services/semantic_request.py:205`). Выдели из «Дверей» семью «Противопожарные
двери» — уже привязанные двери в ней не окажутся. При 12 привязках из 6 613
контекстов (дизайн §1) это незаметно; после автопринятия 3а-1 привязанными станут
тысячи, и каждая новая, более точная семья будет получать только новые строки
(дизайн §2.2, решение пользователя 02.10.2026).

### 1.2. Смена семьи с вариантом в 3а-1 оставляет дыру

Составной FK «семья варианта = семья контекста» (спека 3а-1 §2.4) не даёт сменить
семью, не сняв вариант. В 3а-1 вариант снимается сразу, и до готовности новых
значений (минуты при живой очереди, часы при `privacy_hold` или ошибке) контекст
— `POSITION` без варианта: матрица фичи 4 покажет его как «работа без варианта»,
а перезапрос сотен привязанных контекстов единицы разом обнулил бы столько же
вариантов. Отсюда двухшаговый протокол (§2.3).

### 1.3. Автоматика не должна отменять решение человека

`family_source` различает `manual`, `suggestion` (подтверждено человеком) и
`auto_suggestion` (3а-1). Перезапрос приносит привязанному контексту предложение
другой семьи; для автопривязки его вправе применить правило, для человеческой —
только человек (дизайн §2.2). Отсюда таблица публикации §2.2 и очередь «смена
семьи» §2.6.

## 2. Решение

### 2.1. Схема: миграция `0020`

```
catalog_contexts                  -- ожидающее назначение
  pending_family_id → work_families [RESTRICT] NULL, pending_family_source ('manual'|'suggestion'|'auto_suggestion') NULL,
  pending_suggestion_id → family_suggestions [RESTRICT] NULL, pending_by → users [RESTRICT] NULL,
  pending_threshold numeric NULL, pending_at NULL
  # CK_CONTEXT_PENDING — один тотальный предикат из двух полных ветвей:
  #   (pending_family_id IS NULL AND pending_family_source IS NULL AND pending_suggestion_id IS NULL
  #      AND pending_by IS NULL AND pending_threshold IS NULL AND pending_at IS NULL)
  #   OR (pending_family_id IS NOT NULL AND pending_family_source IS NOT NULL AND pending_at IS NOT NULL
  #      AND (pending_family_source = 'manual') = (pending_by IS NOT NULL)
  #      AND (pending_family_source <> 'manual') = (pending_suggestion_id IS NOT NULL)
  #      AND (pending_family_source = 'auto_suggestion') = (pending_threshold IS NOT NULL))
  #   -- цепочка равенств a = b = c пропускала бы строку с пустой семьёй и заполненными источником и временем
  #      (docs/insights/state-the-rule-as-an-equivalence.md)

family_suggestions                -- расширение решений
  decision ('accepted'|'rejected'|'other_family'|'family_created'|'auto_accepted'|'accepted_pending'|'auto_pending'|'auto_superseded')
  # accepted_pending — человек подтвердил, смена отложена ожиданием (decided_by NOT NULL); при применении → accepted, при отмене → rejected
  # ck_family_suggestions_decision_author_pair → (decided_by IS NULL) = (decision IS NULL OR decision IN ('auto_accepted','auto_pending','auto_superseded'))

semantic_events                   -- новый тип context_family_pending (§2.7)
```

Downgrade `0020` отказывает при любом контексте с `pending_family_id`, любом
предложении с тремя новыми решениями и любом событии нового типа — как 0019.

### 2.2. Предикат и таблица публикации

**Предикат применимости** (`is_applicable`) теряет условие
`work_family_id IS NULL` (решение 1). Остальное — без изменений. Следствие:
перезапрос единицы и точки инварианта фичи 2 ставят `family_suggestion` и
привязанным контекстам; пометка «список семей единицы изменён» считается по ним
же; оценка стоимости перезапроса растёт до размера единицы, формула не меняется.

**Публикация** (`record_result`) после вердикта фичи 2 и поверх строк 3а-1 (контекст
без семьи) — при опубликованном ответе со «своей» семьёй и заданном пороге:

| Контекст: семья | вариант | Предложенная семья | Уверенность | Исход |
|---|---|---|---|---|
| та же | любой | — | любая | `decision=auto_accepted`; семья и вариант не меняются; **висящее ожидание другой семьи с `pending_family_source=auto_suggestion` снимается**, его предложение → `auto_superseded`, задание значений по той семье отменяется сверкой — иначе более старое автоожидание отменило бы более новое решение; ожидание `manual` или `suggestion` ответ модели не трогает |
| другая, `auto_suggestion` | **нет** | ≠ текущей | ≥ порога | семья меняется **сразу** (`assign_family`; варианта, который надо беречь, нет), прежнее задание значений отменяется сверкой, ставится новое; `decision=auto_accepted` |
| другая, `auto_suggestion` | **есть** | ≠ текущей | ≥ порога | **ожидающее назначение** `pending_family_source=auto_suggestion`, `pending_threshold` = порог на момент решения, `decision=auto_pending`, задание значений по схеме новой семьи |
| другая, `auto_suggestion` | любой | ≠ текущей | < порога | опубликовано, очередь «смена семьи» |
| другая, `manual` или `suggestion` | любой | ≠ текущей | любая | опубликовано, очередь «смена семьи»; правило не трогает |

Для ожидания порог в событии `context_family_assigned` берётся из
`pending_threshold`, а не из настройки на момент переключения: настройка к тому
времени могла измениться.

### 2.3. Ожидающее назначение

Единая точка входа — `services/work_families.request_family_change(db, *, context_id, family_id, actor_id, source, suggestion_id=None) -> FamilyChangeOutcome`;
`assign_family` остаётся низкоуровневой операцией. Правила:

1. контекст **без варианта** получает семью сразу (`assign_family`) — есть у
   него семья или нет; прежнее задание значений, если было, отменяет сверка;
2. контекст **с вариантом** любую смену семьи — автопринятием, человеком
   («Другая семья…», переназначение на карточке), подтверждением из очереди
   «смена семьи» — получает как ожидание: `pending_*` заполняются,
   `work_family_id` и `work_variant_id` не меняются, ставится задание
   `context_values` по текущей схеме новой семьи (если текущей нет — задание
   появится с заморозкой); предложение человека получает
   `decision = accepted_pending` (семья ещё не сменилась), при применении →
   `accepted`, при отмене или вытеснении человеком → `rejected`. **Снятие
   варианта при смене семьи из 3а-1 этим правилом заменяется**: вариант больше
   не снимается до готовности нового;
3. по готовности значений **одной транзакцией** (обработчик 3а-1 §2.6, шаг 5):
   `work_family_id := pending_family_id`, `family_source := pending_family_source`,
   `family_by`, вариант по правилу, `pending_*` очищаются, события
   `context_family_assigned` с `from/to` и `context_variant_assigned`; старый
   вариант архивируется при нуле контекстов;
4. новое ожидание заменяет прежнее (одно на контекст) — **правило не вытесняет
   ожидание человека** (`manual`, `suggestion`): его предложение другой семьи
   идёт в очередь «смена семьи». Ожидание `auto_suggestion` вытесняется и
   правилом, и человеком. «Отменить ожидание» на карточке очищает колонки и
   отменяет задание (`cancelled/not_applicable`). Предложение, породившее
   ожидание, получает `auto_accepted`/`accepted` **только при фактическом
   переключении**; при отмене человеком — `rejected` с автором; при вытеснении
   — `auto_superseded` без автора, если вытеснило правило, и `rejected` с
   автором, если человек. Все исходы терминальны для своего отпечатка —
   отклонённое не воскресает (§2.9 спеки 2);
5. ошибка задания значений, задержка приватности, отсутствие схемы — ожидание
   висит и видно на карточке и в `/status`; контекст живёт прежним решением;
6. **ожидаемая семья — живая привязка**: `archive_family` и `set_unit`
   (`services/work_families.py:886`, `:789`) считают ссылки и по
   `pending_family_id`, отказывая теми же кодами; обработчик значений при
   применении ожидания **перепроверяет** под взятой блокировкой семьи, что она
   `active` и её единица равна единице строки контекста — иначе результат не
   применяется, ожидание снимается с `outcome = cancelled`, его предложение →
   `auto_superseded` без автора — отменило правило, а не человек, и для
   человеческого ожидания тоже (`rejected` требует автора); причина — в
   `reason` события; контекст живёт прежним решением.

Снятие семьи (`family_id=None`) снимает и вариант, и ожидание, и значения;
строка каталога не понижается (3а-1 §2.10).

### 2.4. Обработчик значений и слияние семей

- **Обработчик `context_values`** (3а-1 §2.6) берёт на шаге 0 **обе семьи —
  текущую и ожидаемую — `FOR UPDATE` по возрастанию `id`**: одной семьи мало —
  встречные ожидания A→B и B→A на двух контекстах держали бы по семье и по
  прежнему варианту и ждали бы целевой вариант друг друга; шаг 5 — переключение
  семьи из §2.3 п. 3 перед записью `work_variant_id`. Нулевая схема ожидаемой
  семьи идёт тем же путём — заданием без вызова модели.
- **Состав имён схемы** (3а-1 §2.3) включает предложения `auto_pending` и
  `accepted_pending` на эту семью при `pending_family_id` контекста, равном ей:
  оба ожидания — принятое членство, отложенное лишь до значений, и единственное
  подтверждённое человеком написание не должно выпасть из строящейся схемы цели.
- **Слияние семей** (3а-1 §2.9) получает шаг 2а: чужие контексты с
  `pending_family_id = источник` перенаправляются на цель
  (`pending_family_id := target`, событие `context_family_pending` с
  `outcome = redirected`), их задание значений отменяется сверкой как
  неприменимое и ставится заново по схеме цели; решение породившего предложения
  не меняется — его `family_id` уже стал целью в 3а-1.
- **Защищённые поля** архитектурного теста (3а-1 §2.7) дополняются
  `catalog_contexts.pending_family_id`; новая точка инварианта —
  `request_family_change`.

### 2.5. Массовое автопринятие

Protocol 3а-1 §2.12 расширяется на привязанные контексты: apply идёт по полной
таблице §2.2 строка за строкой; `preview_hash` считается по кортежам
`(suggestion_id, request_hash, эффективная семья предложения, рассчитанный
исход, work_family_id, family_source, work_variant_id, pending_family_id,
pending_family_source)` и по порогу — состояние контекста между preview и apply
меняет исход, и хэш обязан это поймать; блокировки — `FOR SHARE` семей по
возрастанию `id`, затем `FOR UPDATE` контекстов по возрастанию `id`.

### 2.6. Экран и API

- **Контексты** → карточка: блок «Ожидает семьи: … (кто, когда, порог)» с
  «Отменить»; пометка «ожидает значений по схеме цели» после слияния семей;
  «Другая семья…» — через `request_family_change`, ответ `assigned` / `pending`.
  Фильтр «ожидает».
- **Предложения** → четвёртая очередь **«Смена семьи»**: все опубликованные
  предложения другой семьи контексту **с семьёй**, которые правило не применило,
  — у ручных и подтверждённых человеком привязок любой уверенности и у
  автопривязок ниже порога (таблица §2.2, строки 4 и 5); группы «семья → семья +
  полоса»; «Подтвердить» ставит ожидание (или назначает сразу, если варианта
  нет), «Отклонить» — как в фиче 2; счётчик ожиданий в шапке.
- `screens.md` `## 9.` — абзац «Смена семьи».

| Метод | Путь | Что |
|---|---|---|
| POST | `/contexts/{id}/family` | **меняет смысл**: через `request_family_change`, отвечает исходом `assigned` / `pending` |
| DELETE | `/contexts/{id}/pending-family` | отменить ожидание |
| GET | `/suggestions?queue=change` | очередь «смена семьи» |
| POST | `/auto-accept/preview`, `/auto-accept` | кортеж `preview_hash` расширен состоянием контекста (§2.5) |
| GET | `/status` | счётчик ожиданий |

### 2.7. Журнал и ревизия документов

Новый `event_type` `context_family_pending` (предмет — контекст): `payload` —
`pending_family_id`, `source`, `suggestion_id`, `threshold` (при
`auto_suggestion`), `outcome` (`set` / `superseded` / `cancelled` / `applied` /
`redirected`), `reason` при `cancelled` правилом.

`AGENTS.md` §5: предложения получают и привязанные контексты; решение фичи 2
«автопривязки нет» и правило 3а-1 «смена семьи снимает вариант» заменяются
двухшаговым протоколом. `docs/reference/schema.md` §7 — колонки ожидания;
`screens.md` `## 9.` — абзац. Дорожная карта: «3а-2 сделана».

## 3. Отвергнутые альтернативы

- **Второй предикат применимости для привязанных** — две ветви сверки вместо
  одной таблицы публикации (решение 1).
- **Снятие варианта при смене семьи (правило 3а-1) как окончательное** —
  перезапрос единицы обнулял бы сотни вариантов разом (§1.2).
- **`suggestion` с пустым автором / `accepted` для отложенного подтверждения** —
  неразличимо в журнале; `accepted` до смены семьи попадал бы во вход схемы
  старой семьи (решение 3).
- **Удержанная пачка для массового автопринятия** — пачка хранит предметы
  заданий, а автопринятие — доменная смена семьи (3а-1 §2.12).

## 4. Границы

- Стоит на смерженной 3а-1; без неё не планируется.
- Системы — 3б; поверхности — фича 4.
- Ожидание человека автоматика не снимает ни при каком исходе модели.

## 5. Definition of Done

1. Миграция `0020`: `CK_CONTEXT_PENDING` доказан пробоем на всех частично
   заполненных комбинациях колонок ожидания (по входу на каждую колонку, пустую
   при заполненных остальных, и на каждое несоответствие источника автору,
   предложению и порогу); `accepted_pending` без автора — отказ; downgrade при
   ожидании, новом решении, новом событии — отказ (три входа).
2. Предикат без `work_family_id IS NULL`: привязанный контекст получает задание
   при перезапросе единицы и в точках инварианта; оценка preview перезапроса
   считает привязанные.
3. Таблица публикации §2.2 — каждая строка отдельным входом, в том числе «та же
   семья» при висящем автоожидании (снято, `auto_superseded`) и при ручном
   (не тронуто); порог ожидания в событии — из `pending_threshold`, а не из
   изменённой настройки.
4. Ожидающее назначение §2.3 — каждый из шести пунктов отдельным входом;
   переключение семьи и варианта одной транзакцией (снятие транзакционности
   делает тест красным); ошибка и `privacy_hold` оставляют прежние семью и
   вариант; исходы `auto_accepted` / `accepted` / `rejected` / `auto_superseded`
   терминальны; `accepted_pending` входит во вход схемы цели, `accepted`
   переназначенного вручную — нет; архивирование и смена единицы семьи с одними
   ожиданиями — отказ; архивированная в обход (гонка) семья при применении —
   результат не применён, ожидание снято.
5. Обработчик: встречные ожидания A→B и B→A параллельно — без deadlock
   (проверено снятием блокировки второй семьи); нулевая схема ожидаемой семьи —
   полное переключение тем же обработчиком.
6. Слияние семей: чужие ожидания на источник перенаправлены на цель с новым
   заданием и событием `redirected`.
7. Массовое автопринятие: ручная привязка, выдача варианта и слияние предложенной
   семьи между preview и apply — каждое меняет `preview_hash` (`409`); apply при
   работающем опросчике — без deadlock.
8. Экран: блок ожидания с отменой, очередь «Смена семьи», фильтр; `screens.md`
   дополнен; снимки против макета или перечня §2.6.
