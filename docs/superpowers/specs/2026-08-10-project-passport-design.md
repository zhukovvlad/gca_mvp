# Ф6: паспорт проекта по статьям классификатора — дизайн

**Ветка:** `feat/project-passport`.
**Рамка фазы:** [phase7-frame.md](../../phase7-frame.md), строка Ф6 — последняя фича фазы 7.
**Референс экрана:** [2026-08-09-project-passport-mockup.html](2026-08-09-project-passport-mockup.html)
(одобрен пользователем на гейте 1; файл датирован днём коммита).
**Гейт 1 закрыт** в диалоге; внешнее заключение — approved with minor clarifications,
архитектурных и бизнес-блокеров нет.

Ф6 превращает уже накопленное сырьё в форму, которой бизнес пользуется: позиции
смет (Ф3), допработы (Ф4), валовое ИТОГО (Ф4a), ставку НДС (Ф4б) и ТЭП с
коммерческими условиями (Ф5) — в один свод по статьям фиксированного
классификатора компании, с рублями на квадратный метр.

## 1. Замеры, на которых стоит дизайн

Числа сняты 2026-08-09 на живом стенде `gca_dev` и на реальных офертах из
`samples/`. Реальные суммы в код, тесты и сообщения коммитов не переносятся;
здесь они приведены как обоснование решений (политика `samples/` запрещает
перенос, а не упоминание в рассуждении — но и здесь их нет там, где можно
обойтись выводом).

### 1.1. База отсчёта

`main` = `3b01ccf`, backend **1337** собранных (1331 passed / 6 известных
skipped), vitest **206** в 20 файлах, обе базы кластера на `0009`,
`PARSER_VERSION` = `3.1.0`.

### 1.2. Главный инвариант фичи держится на всех трёх сметах стенда

Сумма «позиции (не-разделы) + допработы» совпадает с валовым ИТОГО файла
**до копейки**, дельта ноль у 159-ТУ, 42-ТУ и 449-ТУ. Это два независимых пути:
таблица считается из `position_items` и `estimate_additional_works`, а валовое
ИТОГО парсер читает из блока итогов в `proposal_summary_lines`. Именно
расхождением этих путей ловится двойной счёт, которого инвариант «статьи +
нераспределённое = позиции + допработы» не видит (обе стороны растут одинаково —
[devlog Ф4](../../devlog/2026-08-07-additional-works.md)).

«Нераспределённое» с деньгами существует: у 449-ТУ это 38 позиций под разделами
без статьи, около 2,3 % сметы. У двух других смет оно пусто.

### 1.3. Размер таблицы решает форму экрана

Непустых ветвей дерева: **103 / 117 / 178** строк по трём сметам. Статей
верхнего уровня в справочнике 21, деньги есть у 14–16. Нулевых строк (сумма ровно
ноль при существующих позициях) у 159-ТУ — **31 из 103**.

На один лист А4 входит порядка 45–50 плотных строк. Отсюда решение §2.11:
паспорт — экранный свод, печать многостраничная.

### 1.4. У статьи-родителя бывают свои деньги помимо детей

Четыре места на трёх сметах; самое крупное — «6 Фасадные работы» у 159-ТУ, где
дети не досчитывают до родителя заметную сумму. **Проверено по самому файлу:**
это не дефект. В файле есть строка-раздел с собственным номером и наименованием
«Прочее», у которой колонка «Статья СМР» пуста; правило Ф3 отдаёт ей статью
ближайшего объемлющего раздела — «6. Фасадные работы». Под ней шесть законных
позиций.

Три случая из четырёх набираются одним разделом файла, четвёртый — двумя, причём
у обоих статья своя. Значит служебную строку нельзя назвать именем раздела в
общем случае — отсюда решение §2.9 п. 6.

### 1.5. Нумерация разделов файла и коды классификатора — разные оси

В том же блоке 159-ТУ строка с номером раздела `6.4` несёт статью
`6.6 Система обслуживания фасадов`, а строка `6.2.1` — статью `6.4`. То есть
«6.5» из файла не имеет отношения к статье 6.5 справочника. Это подтверждает
запрет Ф3 на join по номеру раздела в денежной логике; принадлежность даёт
только `chapter_item_id`.

### 1.6. Разрез материалы / СМР / косвенные в колонки не берётся

Замерено: разрез заполнен у **100 %** позиций всех трёх смет, но сумма трёх
слагаемых расходится с итогом на копейки (порядка десятых и сотых рубля на
смету) — округление в самом файле. У допработ разреза нет вовсе (решение Ф4).
Колонка, которая на бумаге не сходится при сложении, в документе «для банка»
вреднее, чем её отсутствие.

### 1.7. Целевой образец и чего в схеме нет

Лист «Проекты» образца `samples/…rev1.xlsx` — источник формы. В его шапке есть
**РНВ** (планируемая сдача) и **полезная площадь** со своим руб/м². В схеме нет
ни того, ни другого: Ф5 завела только подземную, надземную и вычисляемую общую
(`area_underground_sp`, `area_aboveground_sp`, `area_total_sp`). Решение — §3 п. 1.

Из состава главной таблицы образца вне скоупа v1 остаются колонки «Объём» и

## 2. Решение

### 2.1. Единица, маршрут, судьба старого экрана

Паспорт строится **по договору**: деньги живут в смете договора, а ТЭП берутся у
объекта этого договора. Маршрут — `/contracts/:contractId/passport`, тот же, что
у экрана фазы 6: **новая реализация заменяет старую**, чтобы в системе не
существовало двух разных «паспортов» с разными числами.

`PassportPage.tsx`, `PassportPage.test.tsx`, хук `usePassport` и типы старого
ответа удаляются. Бэкенд фазы 6 (`/api/v1/analytics/passport` и его тесты) **не
трогается** — так требует бриф §7, и по нему же экраны фазы 6 позже вернутся
«нижним этажом».

### 2.2. Слой данных: VIEW `v_category_totals`, миграция 0010

Гранулярность — **прямые** суммы, без roll-up:

| колонка | тип | смысл |
|---|---|---|
| `estimate_id` | bigint | смета |
| `work_category_id` | bigint NULL | статья; **NULL = нераспределённое** |
| `source` | text | `'positions'` \| `'additional_works'` |
| `amount` | numeric NULL | сумма денег строк |
| `row_count` | integer | сколько строк сложилось |
| `rows_with_amount` | integer | из них с непустой суммой |

Ключ — `(estimate_id, work_category_id, source)`.

Почему прямые, а не свёрнутые: экрану нужны обе величины сразу — итог поддерева
и собственные деньги родителя (§1.4), — а выводить собственные разностью
«родитель минус дети» значит считать вычитанием то, что и так есть в источнике.
Roll-up делает Python (§2.7).

Деньги позиций: `position_items` с `is_chapter = false`, путь до статьи —
`chapter_item_id → строка-раздел → work_category_id`. **Join по номеру раздела
запрещён** (§1.5). Итогам, записанным в самих строках-разделах, не верим:
сумма статьи — это сумма её позиций.

Второй источник — `estimate_additional_works` через `proposal_id → lot_id →
estimate_id`, `source = 'additional_works'`.

**Фильтра по `amendment_no` в VIEW нет** — решение подтверждено на гейте 1.
VIEW с именем «итоги по статьям», молча игнорирующий половину смет, — тот же
класс ловушки, что `total_cost_with_vat` со значением «без НДС», за который
заплатила Ф4a. Выбор исходной сметы делает CRUD явным условием (§2.4).

В `work_category_id IS NULL` сливаются две разные причины: позиция под разделом
без статьи и позиция вовсе без `chapter_item_id` (строка вне структуры). Обе —
законно нераспределённое; различает их §2.9 п. 8.

### 2.3. Три состояния суммы, и «нет строк» отличается от «нет цены»

`SUM(x)` даёт `NULL` и когда строк нет, и когда у всех строк `x IS NULL`.
Опираться на `amount IS NULL` поэтому нельзя — состояния надо различать
счётчиками. `position_items.total_cost_total` **обнуляем по схеме**: §3
`AGENTS.md` требует «пустая стоимость в смете → `NULL`, не `0`».

Правило VIEW: строка появляется, если есть хотя бы одна исходная строка;
`row_count` считает все, `rows_with_amount` — только с непустой суммой;
`amount` равен `NULL` тогда и только тогда, когда `rows_with_amount = 0`.

Правило ответа API, по узлу дерева (см. §2.6):

| состояние | `total` | `rows` | `rows_priced` | как показывает экран |
|---|---|---|---|---|
| в поддереве нет ни одной строки | `null` | `0` | `0` | прочерк |
| строки есть, ни у одной нет цены | `null` | `> 0` | `0` | прочерк + подпись «цена не заполнена: N позиций» |
| строки есть, суммы нули | `"0.00"` | `> 0` | `> 0` | ноль |

То есть **`total = null` тогда и только тогда, когда `rows_priced = 0`**, а
различает два случая `rows`. Замерено: позиций без цены на стенде ноль, поэтому
второе состояние проверяется синтетикой — названо границей §5 п. 9.

Та же тройка состояний действует для собственных денег статьи, по `own`,
`own_rows` и `own_rows_priced`.

У ветки допработ `rows_with_amount` всегда равен `row_count`: `total_amount`
объявлен `NOT NULL` миграцией 0007. Колонка сохранена ради одной формы у обеих
веток; её третье состояние на этой ветке недостижимо — §5 п. 10.

### 2.4. Паспорт берёт исходную смету, и фильтр стоит в CRUD

Скоуп v1 считает только исходную смету (`amendment_no IS NULL`) — решение
пользователя, зафиксированное рамкой фазы. Фильтр применяется в CRUD, а не в
VIEW (§2.2).

Договор без сметы — **не** `404`: карточка заведена, файл ещё не загружен,
реквизиты уже есть что показать. В ответе тогда `estimate: null`, таблица пуста,
итог пуст. `404` остаётся за несуществующим договором.

### 2.5. Валовое ИТОГО, его агрегация по лотам и сверка

`proposal_summary_lines` висит на предложении, а у сметы предложений может быть
несколько (по одному на лот). Правило:

> **Валовое ИТОГО сметы** = сумма `total_cost_including_vat` по **всем**
> предложениям всех лотов исходной сметы.

Оно считается **неизвестным** (`null`), если выполнено хоть одно:

1. у сметы нет ни одного предложения;
2. хотя бы у одного предложения нет строки с ключом `total_cost_including_vat`;
3. хотя бы одно значение пусто или не `is_finite()`.

Пункт 3 — не перестраховка: `_money` пропускает `NaN`/`Infinity` в `numeric`,
это открытый хвост Ф4, и `SUM` по такой колонке даёт `NaN` молча.

При неизвестном валовом **сверка не проводится**: `delta_to_file_total = null`,
строка расхождения не показывается. Это принцип некаскадирования Ф4б §2.7:
недостающий вход гасит проверку, а не рождает неверный вердикт.

Иначе `delta = totals.amount − валовое`, сравнение точное, `Decimal` с
`Decimal`. Строка расхождения показывается **только при `delta ≠ 0`**.

Ставка НДС берётся тем же правилом единогласия: если все предложения исходной
сметы объявили одну и ту же ставку — она; если ставки различаются или хотя бы
одна `NULL` — `null`, и экран пишет «не заявлена в файле», а не ноль.

### 2.6. Эндпоинт и форма ответа

`GET /api/v1/analytics/project-passport/{contract_id}` — чтение, доступно
`member` (§3 `AGENTS.md`: аналитика — чтение). Весь ответ через
`responses.decimal_json`: деньги уезжают строками, `float` не появляется.

```
{
  contract:   { id, contract_number, title, signer, signed_date,
                object_id, object_title, contractor_title, rate_class_title,
                advance_pct, advance_note,
                bank_guarantee_pct, bank_guarantee_note,
                retention_pct, retention_note,
                object_contracts_count },
  object:     { id, title, area_underground_sp, area_aboveground_sp, area_total_sp },
  estimate:   null | { id, amendment_no, title, data_prepared_on_date,
                       parser_version, vat_rate },
  totals:     { amount, per_sqm,
                positions_rows, positions_rows_priced, additional_works_rows,
                file_total_including_vat, delta_to_file_total },
  categories: [ { id, code, title, parent_id, is_bucket, sort_order,
                  total, rows, rows_priced, share_pct, per_sqm,
                  own, own_rows, own_rows_priced,
                  extras: [ { title, amount } ] } ],
  unallocated:{ amount, rows, rows_priced, share_pct, per_sqm,
                chapters, rows_outside_structure }
}
```

`per_sqm` = сумма узла, делённая на `object.area_total_sp`; он `null`, когда
площадь `NULL` или когда `null` сама сумма. Деления на ноль не бывает: `CHECK`
Ф5 держит общую площадь строго положительной.

**`share_pct` считает сервер, а не браузер.** Знаменатель — `totals.amount`,
один и тот же для всех строк, включая «Нераспределённое»; значение `null`, если
`totals.amount` пуст или равен нулю. Вычисляется точным `Decimal`, округление —
только на слое представления: ровно то правило, которым §4 `AGENTS.md` уже
описал `deviation_pct`. Сумма долей всех корней плюс доля нераспределённого
равна 100 % с точностью округления представления, и это **не** утверждается
тестом как строгое равенство — округление до сотых на сотне строк даёт законный
дрейф последнего знака.

`unallocated.chapters` — число **различных** строк-разделов сметы, у которых нет
статьи и под которыми есть позиции. `rows_outside_structure` — позиции без
`chapter_item_id` вовсе; это другая причина того же следствия, и она считается
отдельно (§2.2).

`object_contracts_count` — число договоров у объекта; при значении больше
единицы экран показывает предупреждающий бейдж (обязательство 3, Ф5 §6 п. 3).

### 2.7. Roll-up считает сервер

Каждый узел приезжает с готовыми `total` (итог поддерева) и `own` (собственные
деньги статьи). Складывать десятичные строки в браузере нельзя: это ровно тот
промах, ради которого Ф5 писала `addDecimalStrings`, и сотня сложений на каждую
перерисовку туда не поедет. В Python сложение идёт `Decimal`-ом.

Инвариант, закрепляемый тестом: **для любого узла `total` = `own` + сумма
`extras` + сумма `total` детей**, а сумма `total` корней плюс `unallocated.amount`
равна `totals.amount`.

### 2.8. Состав статей в ответе

**Все 21 статья верхнего уровня присутствуют всегда**, даже отсутствующие в
смете: паспорта разных объектов должны иметь один каркас и класться рядом — в
этом смысл единого классификатора, а «ТХ — прочерк» есть факт, а не пропавшая
строка.

Глубже первого уровня узел попадает в ответ, только если в его поддереве есть
хотя бы одна строка. Нулевые попадают (у них `rows > 0`) и прячутся
переключателем на экране; отсутствующие не отдаются вовсе. По замеру §1.3 это
даёт около сотни узлов на смету, а не все 362.

### 2.9. Экран

Нормативный вид — [референс](2026-08-09-project-passport-mockup.html). Требования,
которые из него следуют:

1. **Четыре состояния у каждого блока данных**: загрузка, отказ, пусто,
   заполнено. Пустое состояние утверждает факт о данных («ТЭП не заведены»),
   которого при неудавшемся запросе мы не знаем, — путать их нельзя (урок Ф5 §4a).
2. **Шапка**: объект, номер договора, подрядчик, дата подписания, класс,
   подписант. Линейка показателей: общая площадь с раскладкой на подземную и
   надземную; стоимость по смете с НДС и ставка НДС подписью; стоимость за м²;
   аванс / гарантия / удержание.
3. **Нет ТЭП** — вместо чисел бейдж, вся колонка ₽/м² в прочерках. Ноль там
   читался бы как «бесплатно».
4. **Оговорки коммерческих условий** — свободный текст, зажимается по высоте
   (обязательство 2). Класс `block` рядом с `line-clamp` отменяет зажим вовсе —
   грабли §11 `AGENTS.md`.
5. **Таблица**: `Код | Статья классификатора | Итого, ₽ | Доля | ₽ / м²`.
   Иерархия сворачиваемая, **по умолчанию свёрнута полностью** — видны 21 статья
   верхнего уровня, «Нераспределённое» и итог. Наименование статьи зажимается по
   высоте (в справочнике есть названия до 181 символа).
6. **Служебная строка собственных денег статьи** появляется при раскрытии тогда и
   только тогда, когда у узла есть дети или допработы **и** `own_rows > 0`.
   Называется «Без подстатьи», если у узла есть дети, и «Позиции сметы», если
   детей нет и раскрытие вызвано только допработами. Подпись — какие разделы
   сметы туда попали.
7. **Допработы** — отдельной строкой с бейджем внутри своей статьи, сумма статьи
   их включает.
8. **«Нераспределённое»** — видимая строка внизу, амброй, с подписью «N разделов
   сметы без статьи классификатора». Если есть строки вне структуры, они названы
   отдельно: это другая причина того же следствия (§2.2).
9. **Корзины** (`is_bucket`) показываются как обычные статьи с бейджем.
10. **Строка сверки** с валовым ИТОГО появляется только при расхождении; молчание
    — нормальный вид (§2.5).
11. **Бейдж «у объекта N договоров»** при `object_contracts_count > 1`.
12. **Переключатель «показывать нулевые подстатьи»**, по умолчанию выключен.
13. Только примитивы shadcn/ui и токены темы; новые примитивы ставятся
    `npx shadcn add`, а не пишутся руками.

### 2.10. Кольцо структуры

Топ-8 статей верхнего уровня по сумме, плюс «Остальные статьи (N)», плюс
«Нераспределённое». Палитра — категориальный набор, **прошедший валидатор**
(полоса светлоты, порог цветности, разделимость соседних секторов при
дальтонизме, контраст к поверхности) в светлой и тёмной темах на поверхностях
проекта. Приглушённый набор в регистре документа проверку не проходит: соседняя
пара давала различимость на грани даже при нормальном зрении.

«Нераспределённое» вдобавок **заштриховано** — цвет не единственный носитель
смысла; это же снимает соседство с жёлтым слотом палитры. Легенда даёт
идентичность текстом, таблица ниже — полные числа; это и есть требуемое
подкрепление для секторов, у которых контраст к светлой поверхности ниже 3:1.

### 2.11. Печать и ревизия `AGENTS.md`

Паспорт — экранный свод; печать многостраничная, `Ctrl+P`. Требования печатной
раскладки: шапка таблицы повторяется на каждом листе, строка не рвётся посередине,
кольцо печатается, служебные элементы уходят.

Обязательство §11 `AGENTS.md` у Ф6 читается как «замером в браузере проверено,
что нет обрезки по правому краю и разрывов внутри строк», а не «один лист».
Замер обязателен и не заменяется ничем: `@media print` в jsdom не наблюдаем.

**Отсюда правка инварианта, которая делается этой же веткой.** Строка DoD §10
«Паспорт печатается на одну страницу А4 со всеми полями §1 пункт 2» перестаёт
описывать действующий экран, и §7.4 описывает состав экрана фазы 6. Обе правятся
здесь, а не откладываются на приёмку фазы: иначе с момента мержа документ-инвариант
противоречит коду, а §9.2 говорит, что при противоречии побеждает инвариант.
Верхняя граница `passport_top_n` (`CHECK` миграции 0004) в БД остаётся и в §7.4
упоминается как история — колонка не удаляется (§2.13).

### 2.12. Кэш

Корень `qk.passport` **переиспользуется**: старый экран удаляется вместе со своим
хуком, новый занимает тот же ключ. Этим обязательство 1, унаследованное от Ф5,
закрывается по построению — расширять список инвалидации `useUpdateObject` не
требуется, и это проверяется тестом на состав корней.

`useUpdateAppSettings` продолжает инвалидировать `qk.passport.all`; после Ф6 эта
инвалидация ничего осмысленного не обновляет, потому что новый паспорт от
`passport_top_n` не зависит. Она не удаляется вместе с настройкой (§2.13) и
названа хвостом.

### 2.13. Экраны фазы 6

Из `TopNav` уходят **«Матрица»**, **«Отчёты»** и **«Настройки»**. Маршруты,
компоненты, бэкенд-эндпоинты и все их тесты остаются живыми: фаза 6 вернётся
drill-down'ом из статьи, дерево `chapter_item_id` для этого уже есть.

«Настройки» уходят из навигации, потому что их единственное содержимое —
`passport_top_n`, число ключевых расценок экрана, который больше не открыть.
Экран, маршрут, эндпоинт и колонка **не удаляются**: это была бы миграция,
которой у Ф6 по рамке нет, и удаление рабочего админского экрана шире рамки.
Решение подтверждено на гейте 1.

## 3. Что сознательно НЕ делается

1. **РНВ и полезная площадь не показываются** — их нет в схеме, а Ф6 их не
   заводит. Отдельная фича после приёмки фазы. Паспорт на два поля беднее
   целевого образца, и это видно.
2. **Колонки «Объём» и «Стоимость за ед.»** — LLM-контур объёмов вне скоупа v1
   (рамка фазы).
3. **Допсоглашения** — считаем только исходную смету (рамка фазы).
4. **Разрез материалы / СМР / косвенные** — §1.6.
5. **Выгрузка в Excel** — рамка называет составом Ф6 VIEW, экран и скрытие
   экранов фазы 6; выгрузки там нет.
6. **Очередь подтверждения привязок и ручной override** — вне скоупа v1.
7. **Backfill и принудительный репарсинг** — не делаются, решение пользователя
   (хвост Ф4a, в силе).

## 4. Тесты

Списки поведенческие; конкретные имена и файлы — в плане. На финале строится
соответствие «требование §2 → тест» по тексту, требование за требованием
([replaying-new-rules](../../insights/replaying-new-rules.md), слой 3).

### 4.1. VIEW и схема

- состав колонок VIEW совпадает с объявленным отражением (сверка с
  `information_schema`, по образцу теста фазы 6);
- круговой рейс `downgrade base → upgrade head`; `downgrade` снимает VIEW;
- позиции-разделы (`is_chapter = true`) в суммы не входят;
- позиция под разделом без статьи попадает в `work_category_id IS NULL`;
- позиция без `chapter_item_id` попадает туда же, но считается отдельно;
- допработы попадают своим `source`, в том числе без статьи;
- **дубли номеров разделов не задваивают деньги** — вход с двумя разделами
  одного номера и разными статьями;
- `amount IS NULL` ⟺ `rows_with_amount = 0`; позиция с `total_cost_total IS NULL`
  даёт `row_count = 1`, `rows_with_amount = 0`;
- VIEW не фильтрует `amendment_no`: смета-ДС в нём присутствует.

### 4.2. Агрегация и ответ

- **инвариант суммы**: статьи + нераспределённое = позиции + допработы;
- **инвариант roll-up**: `own` + `extras` + дети = `total`, на всём дереве;
- **у договора есть исходная смета и ДС — паспорт берёт только исходную**
  (тест закрывает фильтр в CRUD, раз его нет в VIEW);
- все 21 статья верхнего уровня присутствуют; отсутствующая даёт
  `total = null, rows = 0`;
- узел, у которого все позиции без цены, даёт `total = null, rows > 0`;
- нулевая сумма даёт `"0.00"`, а не `null`;
- валовое ИТОГО суммируется по всем предложениям исходной сметы;
- нет ключа хотя бы у одного предложения → валовое `null`, сверка не проводится;
- негодное (`NaN`/`Infinity`) значение → валовое `null`, разбор не падает;
- ставка НДС: единогласие даёт значение, расхождение или `NULL` — `null`;
- заявленный `0 %` отличим от отсутствия;
- `per_sqm` пуст при `NULL`-площади, а не нулевой, — и у итога, и у каждой строки;
- `share_pct` считается от `totals.amount`, один знаменатель у всех строк
  включая «Нераспределённое»; при пустом или нулевом итоге — `null`;
- договор без сметы — `200` с `estimate: null`, несуществующий — `404`;
- деньги во всех ветвях ответа приходят строками (сырое тело, не `float`);
- `member` читает эндпоинт.

### 4.3. Экран

- четыре состояния блоков (загрузка / отказ / пусто / заполнено);
- «ТЭП не заведены» и прочерки в колонке ₽/м²;
- прочерк, «цена не заполнена», ноль — три разных вида;
- «Без подстатьи» есть тогда и только тогда, когда у статьи есть дети и свои
  деньги; у листа с допработами — «Позиции сметы»;
- строка допработ с бейджем внутри своей статьи;
- «Нераспределённое» видимо и названо;
- переключатель нулевых подстатей;
- бейдж «у объекта N договоров» при значении больше единицы;
- строка сверки появляется **только** при расхождении;
- состав корней инвалидации.

### 4.4. Замер в браузере

Обязателен и незаменим (§11 `AGENTS.md`): печатная раскладка на реальной смете
стенда — нет обрезки по правому краю, строки не рвутся, шапка таблицы
повторяется; узкий экран; тёмная тема; консоль чиста.

### 4.5. Негативные проверки

Снятием защиты, по всем восьми слоям
[verifying-guards](../../insights/verifying-guards.md), **делает оркестратор
лично**. Реестр — в плане; вход каждого негативного теста обязан нарушать ровно
одно ограничение.

## 5. Названные границы

1. **РНВ и полезная площадь** отсутствуют в схеме и на экране (§3 п. 1).
2. **«Объект = охват одного ГП» держится людьми.** При двух договорах на объекте
   два паспорта делят разные деньги на одну площадь; бейдж предупреждает, но не
   чинит (граница Ф5 №3 в силе).
3. **Опечатка в площади ничем не ловится** — общая вычисляется, сверять её не с
   чем, неверный знаменатель доедет до ₽/м² без признака ошибки (граница Ф5 №1).
4. **Сверка с валовым ИТОГО не ловит согласованно неверные данные** — если
   ошибка попала в оба пути одинаково, дельта останется нулевой (та же граница,
   что E2E Ф4 п. 4).
5. **Сметы, загруженные до Ф3 и Ф4**, выглядят в паспорте пустыми или неполными:
   у них нет привязок и записей допработ. Лечится перезагрузкой файла;
   принудительного репарсинга нет сознательно, и «всегда восстановимо
   перезагрузкой» обещать нельзя — файл может уйти по ретенции (§8 `AGENTS.md`).
6. **Кольцо показывает топ-8**; девятая статья и дальше видны только в таблице.
7. **Правило «партия больше пяти» неприменимо** — в Ф6 нет ни `ON CONFLICT`, ни
   COALESCE-уникальных и частичных индексов.
8. **Строки вне структуры недостижимы из файлов** при парсере `2.0.0` (граница
   Ф4 №2). Путь живой только для синтетических входов, поэтому проверяется
   синтетикой.
9. **Позиция без цены в корпусе не встречается** — замер даёт ноль таких на трёх
   сметах. Второе состояние §2.3 проверяется синтетикой; корпус умеет
   соглашаться с неверным правилом.
10. **`rows_with_amount` на ветке допработ всегда равен `row_count`** —
    `total_amount` объявлен `NOT NULL`. Колонка сохранена ради одной формы у
    обеих ветвей; её третье состояние там недостижимо и тестом не стережётся.
11. **Инвалидация `qk.passport.all` в `useUpdateAppSettings` становится
    бессмысленной** — новый паспорт от `passport_top_n` не зависит. Не удаляется,
    названа хвостом.
12. **Отсутствие Excel-выгрузки тестом не стережётся** — отсутствие кода тестом
    не проверяется.
13. **Печатная раскладка проверяется только замером** и только на тех данных, на
    которых замер сделан. О четвёртой смете он не говорит ничего.

## 6. Отвергнутые альтернативы

| Что отвергнуто | Почему |
|---|---|
| Строго один лист А4 с таблицей только по верхнему уровню | Теряются второй и третий уровни, а именно в них живёт разбивка фасада на СПК/НВФ и ВИС на механику с электрикой — то, что аналитик расписывает руками в целевом образце |
| Два лица: экран полный, печать свёрнутая до верхнего уровня | Печатный вид молча теряет то, что видно на экране, — ровно та «обрезка при печати», которую §7.4 `AGENTS.md` один раз уже запретил |
| Roll-up в браузере | Сложение десятичных строк в JS; промах `Number` выборочный и на доменной паре не проявляется (замер Ф5 §2.5) |
| `amendment_no IS NULL` внутри VIEW | Имя объекта перестало бы описывать его содержимое; тот же класс, что `total_cost_with_vat` со значением «без НДС» |
| Колонки «в т.ч. материалы / СМР / косвенные» | Три слагаемых не сходятся с итогом до копейки, а у допработ разреза нет вовсе (§1.6) |
| Приглушённая палитра кольца в регистре документа | Трижды не прошла валидатор: соседние сектора неразличимы при дальтонизме, одна пара — и при нормальном зрении |
| Строка «Без подстатьи» с именем раздела файла как заголовком | В одном из четырёх случаев разделов два, и у обоих статья своя (§1.4) — общего имени нет |
| Слить допработы в сумму статьи молча | Деньги разного происхождения стали бы неотличимы; именно на их двойном счёте фаза уже один раз чуть не погорела |
| Паспорт объекта вместо паспорта договора | При двух договорах пришлось бы либо складывать их сметы (вне скоупа v1), либо заводить выбор договора на самом экране |
| Показывать только статьи, которые есть в смете | Паспорта разных объектов получили бы разный набор строк, и «у этого объекта нет ТХ» стало бы неотличимо от «ТХ потерялись при импорте» |
| Удалить экран «Настройки», `passport_top_n` и колонку | Это миграция, которой у Ф6 по рамке нет, и удаление рабочего админского экрана шире рамки |
| Показывать строку сверки всегда | Технический бейдж в документе «для банка»; молчание при сходящихся числах информативнее |
