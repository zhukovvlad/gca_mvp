# Тендерный контур и импорт сводных таблиц раунда — дизайн

**Гейт 1 закрыт 26.08.2026.** Дизайн одобрен в диалоге по разделам; каждый раздел
прошёл внешнее ревью (codex) и правился по его замечаниям до фиксации. Решения,
принятые пользователем отдельно: расчётная стоимость — отдельная смета раунда
(§2.5); участники заводятся из файла, не руками (§2.7); граница фичи — без
команды «создать договор из раунда» (§4); каскад от пакета участника заменён
явной командой с подтверждением (§2.11).

Это **фича 2 из четырёх** [рамки тендерного контура](../../proposals/2026-08-25-tenders-model.md)
§4. Стоит на фиче 1 (парсер читает сводную таблицу, PR #32) и наполняет данными
фичу 3 (свод по этапам, [расчётный контракт](../../proposals/2026-08-25-stage-summary-contract.md)).
Рамка §3 даёт модель; здесь — то, что рамка оставила открытым и что показал код.

Дизайн **ревизует** действующие решения `AGENTS.md` — §3, §4, §5, §7, §8 — и
перечисляет каждую правку в §2.15. Он **не трогает** `backend/parser/`,
матчинг, каталог, единицы, паспорт, матрицу, сравнение.

---

## 1. Что показал код

Рамка §3 писалась по замерам файлов; дизайн проверен по коду, и пять фактов
изменили его форму.

### 1.1. `uq_proposals_lot_id` делает «N смет на раунд» буквальным

`proposals` объявлен «ровно одно на лот» и закреплён индексом (`models.py`).
Значит один `Estimate` **не может** держать N предложений раунда: N предложений
= N смет, каждая со своим `Lot` и `Proposal`. Это не цена дизайна, а его опора:
`_replace_existing`, паспорт, матрица, сравнение читают предложение через лот, и
все они остаются верны без правок.

### 1.2. `proposals.is_baseline` уже есть, `contractor_id NOT NULL` — тоже

Поле `is_baseline` сохранено «для задела на возврат тендеров» (§4). Но
`contractor_id NOT NULL` делает baseline-предложение непредставимым: у расчётной
стоимости подрядчика нет. Без правки схемы baseline получил бы фиктивного
подрядчика либо не вставился.

### 1.3. `postprocess` заглушает пустую базу и решает валидность ПО ЛОТАМ

`normalize_lots_json_structure` зовёт `_is_baseline_valid` на каждый лот
(`postprocess.py:164`): валидный блок остаётся `baseline_proposal` с вырезанным
`additional_info`, невалидный заменяется заглушкой `BASELINE_MISSING_TITLE`, а
`% от р/с` у участников этого лота вычищается. Единого факта «база валидна» у
файла нет. На измеренной сводной таблице (класс 3 фичи 1) база пуста во всех
лотах — то есть на сегодняшнем корпусе baseline-смета не возникнет ни разу.

### 1.4. `decide_owner` читает `additional_info` индексированием

`additional_works.py:364` берёт `proposal_data[JSON_KEY_CONTRACTOR_ADDITIONAL_INFO]`
без `.get`. Для baseline-проекции, где постобработка это поле вырезала, импорт
упал бы `KeyError` до первой позиции. Контур допработ для базы надо выключать
явно, а не полагаться на «пустой список».

### 1.5. У ИНН две канонические формы

`create_contractor` сравнивает `inn` как строку (`uq_contractors_inn`), сверка
шапки — через `_digits` (`estimate_import.py:287`). Заведение подрядчика из
файла по ИНН сделало бы «77 00…» и «7700…» двумя подрядчиками. При этом
`str.isdigit()` шире ASCII `[0-9]`: замер — строка из полноширинных, арабских и
надстрочных цифр даёт 6 символов через `isdigit` и 2 через `[^0-9]`. Канон,
записанный Python-ом, обязан совпадать с тем, что проверит PostgreSQL.

## 2. Решение

### 2.1. Схема

Четыре новых таблицы — рамка §3 с двумя структурными гарантиями, которых там не
было.

```
tenders           id, object_id NOT NULL → objects, title text NOT NULL,
                  tender_number text NOT NULL, rate_class_id NOT NULL → rate_classes,
                  notes, created_at, updated_at
                  CHECK btrim(title) <> '';  CHECK btrim(tender_number) <> ''
                  UNIQUE (tender_number)
tender_rounds     id, tender_id NOT NULL → tenders CASCADE,
                  stage_no int NOT NULL CHECK (stage_no > 0), label, held_on date NULL
                  UNIQUE (tender_id, stage_no);  UNIQUE (id, tender_id)
offer_packages    id, tender_id NOT NULL → tenders CASCADE,
                  contractor_id NOT NULL → contractors RESTRICT
                  UNIQUE (tender_id, contractor_id);  UNIQUE (id, tender_id)
offers            id, tender_id NOT NULL, round_id NOT NULL, package_id NOT NULL
                  FK (round_id, tender_id)   → tender_rounds (id, tender_id) CASCADE
                  FK (package_id, tender_id) → offer_packages (id, tender_id) RESTRICT
                  UNIQUE (round_id, package_id)
```

**`rate_class_id` тендера — снимок**, по правилу и причине `contracts.rate_class_id`
(§4): переклассификация объекта не меняет прошлое.

**Составные FK с продублированным `tender_id` — единство решётки как форма, а не
проверка.** `UNIQUE (round_id, package_id)` сам по себе не мешает связать раунд
тендера A с участником тендера B. `tender_id` в `offers` дублируется намеренно:
это делает ячейку одной решётки структурной правдой. Приём в проекте уже есть —
составной self-FK `fk_position_items_chapter` по `(proposal_id, id)` держит
раздел и позицию в одном предложении тем же способом. **`NOT NULL` на всех
колонках составных FK обязателен**: PostgreSQL проверяет составной FK в режиме
`MATCH SIMPLE`, и при `NULL` хотя бы в одной колонке проверка не выполняется
вовсе — ячейка без раунда прошла бы молча.

**Каскад от раунда, `RESTRICT` от пакета — осознанная асимметрия.** Раунд —
снимок решётки, без предложений он не хранит ничего своего; удаление раунда
уносит по одной смете у каждого участника. Пакет — участник со всей историей
торга; удаление пакета каскадом снесло бы предложения, сметы, позиции во всех
раундах из любого места, где кто-то удалит строку — миграции, SQL, будущего
CRUD. `RESTRICT` заставляет пройти через команду §2.11, которая умеет отказать и
посчитать. Архивирование пакета не заводится: участник, подавший предложение,
из истории тендера не исчезает по определению.

Правки существующих таблиц:

```
estimates     contract_id DROP NOT NULL
              + offer_id → offers CASCADE;  + round_id → tender_rounds CASCADE
              CHECK num_nonnulls(contract_id, offer_id, round_id) = 1
              CHECK (contract_id IS NOT NULL OR amendment_no IS NULL)
              uq_estimates_contract_amendment → частичный WHERE contract_id IS NOT NULL   (ОБЯЗАТЕЛЬНО)
              UNIQUE (offer_id) WHERE offer_id IS NOT NULL
              UNIQUE (round_id) WHERE round_id IS NOT NULL         -- одна baseline на раунд
proposals     contractor_id DROP NOT NULL
              CHECK ((is_baseline AND contractor_id IS NULL) OR (NOT is_baseline AND contractor_id IS NOT NULL))
import_jobs   contract_id DROP NOT NULL
              + round_id → tender_rounds CASCADE
              + parsed_data jsonb NULL;  + parser_version text NULL
              + estimates_created int NULL CHECK (estimates_created IS NULL OR estimates_created > 0)
              CHECK num_nonnulls(contract_id, round_id) = 1
              CHECK (contract_id IS NOT NULL OR amendment_no IS NULL)
              CHECK ((parsed_data IS NULL) = (parser_version IS NULL))
              uq_import_jobs_active_pair → частичный WHERE contract_id IS NOT NULL
              + UNIQUE (round_id) WHERE round_id IS NOT NULL AND status NOT IN (terminal)
              + ix_import_jobs_round_id                            -- история и каскад, не только active
contractors   CHECK (inn ~ '^[0-9]+$')
```

Три владельца сметы: договор, предложение, раунд. **`round_id` на смете и есть
признак baseline** — второго булева не нужно; `Proposal.is_baseline` при этом
отражает ту же правду и стережётся `CHECK`. Два владельца задания: договор,
раунд. `amendment_no` вне договора — бессмысленное состояние, и схема его
запрещает.

**Частичность `uq_estimates_contract_amendment` — условие работоспособности**
(рамка §3.1): индекс объявлен `NULLS NOT DISTINCT`, и при `contract_id IS NULL`
все сметы предложений схлопнулись бы в одну строку.

Индекс на каждом новом FK: PostgreSQL их не создаёт, и это уже правило проекта
(`ix_contracts_*`).

**Не заводятся** `contracts.awarded_offer_id` и `estimates.source_offer_id`:
обе колонки принадлежат команде «создать договор из раунда» (§4), и колонка,
которую никто не пишет и не читает, — обещание без кода.

### 2.2. Миграция 0015

Raw SQL для частичных индексов и `NULLS NOT DISTINCT`, как 0002. Выражения
`CHECK` продублированы константами в шапке и в `models.py`; parity-тесты
`test_schema_constraints.py`.

**Канонизация ИНН — миграция данных с отказом.** До добавления `CHECK`:
вычислить канон каждого подрядчика; **отказаться с диагностикой**, если канон
пуст либо два подрядчика схлопываются в один (назвать обоих по `id`); только
затем `UPDATE` и `CHECK`. На стенде все 6 ИНН уже канонические — миграция
пройдёт вхолостую, но защиту несёт всё равно: правило про представление, а не
про сегодняшние строки.

**`downgrade` отказывает** — как 0011, по трём счётчикам отдельно: строк в
`tenders`; `import_jobs` с `round_id IS NOT NULL`; `estimates` с
`contract_id IS NULL`. Одного счётчика недостаточно: round-job мог сохраниться и
упасть до создания смет, а после снятия `round_id` job с `contract_id = NULL` не
даст вернуть `NOT NULL`. Отказ обязан назвать, что именно держит откат.

### 2.3. Три факта об одном файле

Полный JSON из XLSX **не восстанавливается**: файл можно разобрать заново только
текущим парсером, а после его изменения результат отличается от того, по которому
job создал сметы. `parser_version` называет версию, но не возвращает старый код.

Поэтому у файла раунда три разных факта, а не две копии одного:

| Носитель | Что это | Кто пишет |
|---|---|---|
| `storage[import_jobs.file_key]` | исходный артефакт — XLSX | эндпоинт загрузки |
| `import_jobs.parsed_data` + `parser_version` | **точный `ParseResult.data` этого разбора** | сессия A, сразу после успешного парсинга, **независимо от исхода импорта** — failed-job честно показывает, какой разбор привёл к отказу |
| `estimate_raw_data` | **проекция под конкретную смету** — вход материализации и резолвера статей (`category_override.py` требует её неизменности) | сессия B, на каждую смету |

Contract-job тоже получает `parsed_data`: правило одно на оба владельца. Старые
jobs законно `NULL`. Докстрока `EstimateRawData` («полный JSON парсера») и
`AGENTS.md` §4 ревизуются: «проекция сметы».

### 2.4. Владельцы — два уровня

```
JobOwner      = ContractJobOwner(contract, amendment_no) | RoundJobOwner(round)

EstimateOwner = ContractEstimateOwner(contract, amendment_no)
              | OfferEstimateOwner(offer)
              | BaselineEstimateOwner(round)
```

`import_estimate` перестаёт принимать `contract: Contract` и принимает
`owner: EstimateOwner` и `truth: HeaderTruth`. Всё ниже — лоты, предложения,
позиции, матчинг — не меняется.

**`HeaderTruth`** — то, с чем сверяется шапка файла (`compare_header`, бывший
`compare_header_with_contract`; расхождения — warnings, не отказ):

| Владелец | Истина |
|---|---|
| договор | объект, адрес, подрядчик: название, ИНН, адрес, аккредитация — из карточки договора |
| предложение | объект, адрес — из карточки **тендера**; подрядчик: все карточные поля — из `offer.package.contractor` |
| baseline | объект, адрес — из карточки тендера; подрядчика нет |

Существующая карточка подрядчика **из XLSX не обновляется** — расхождение имени
или адреса идёт в warnings (§3 остаётся в силе там, где карточка есть).

### 2.5. Один файл → N offer-смет + опциональная baseline

Один загруженный файл → один `ImportJob(round_id)` → **один парсинг** → в
**одной транзакции сессии B**:

1. **Замена уровнем раунда, ДО цикла** (§2.6).
2. **Разбиение по каноническому ИНН через все лоты** (§2.7) → N проекций JSON, в
   каждой по одному предложению на лот.
3. На каждую проекцию: get-or-create `contractor` → `offer_package` → `offer`
   (§2.8) → `import_estimate(OfferEstimateOwner(offer), проекция)`.
4. Baseline (§2.9): `import_estimate(BaselineEstimateOwner(round), проекция)`,
   если есть хоть один валидный блок.
5. **Матчинг — один вызов** по объединённому списку позиций всех N+1 смет.
6. `estimates_created = N (+1)`, `done` — последней операцией той же транзакции.

Падение на четвёртом участнике откатывает трёх первых: атомарность §5 остаётся
атомарностью раунда.

**Расчётная стоимость — отдельная смета раунда** (решение пользователя,
рамка §5.1): хранится рядом с предложениями, но предложением не является —
ячейки решётки не занимает, в свод и матрицу не попадает. Отвергнуто:
предложение с флагом `is_baseline` на уровне смет — каждый запрос по участникам
обязан помнить про фильтр, и забытый фильтр тихо добавляет «участника» в свод и
медиану; колонка на позиции — теряет итоги и шапку блока, а при несопоставленных
позициях база расползается по строкам.

### 2.6. Замена — целиком, уровнем раунда

Поштучный `_replace_existing` по входящему владельцу здесь не годится: если
новый файл не содержит участника из предыдущего, до его старой сметы замена не
дойдёт, и получится смесь двух загрузок. До цикла:

```
SELECT tender FOR KEY SHARE   -- иерархия локов §2.11: тендер → раунды → пакет
SELECT round  FOR UPDATE
найти все offer-owned и round-owned сметы раунда
есть и replace = false  → отказ
replace = true           → удалить весь найденный набор
дальше — импорт нового набора без локальных replace
```

Удаляются **сметы**, не `Offer` и не `offer_package`: участник остаётся в
решётке, просто без сметы текущей загрузки (§2.13, состояние ячейки «предложение
было, сметы нет»). Предупреждения о снесённых ручных решениях по статьям
агрегируются по всем удалённым сметам — тем же счётом под тем же локом, что
сегодня в `_replace_existing`.

### 2.7. Разбиение — по каноническому ИНН через все лоты

`contractor_N` в JSON — локальный индекс внутри лота после постобработки, а не
идентичность участника. Проекции собираются по каноническому ИНН через все лоты.
**До записи** проверяется, и любое нарушение — отказ импорта, не предупреждение:

- у каждого блока непустой ИНН;
- один ИНН не встречается дважды в одном лоте;
- **наборы ИНН во всех лотах совпадают** — частичное участие как бизнес-правило
  никто не принимал, а выдумать его молча значит получить участников с разным
  составом смет и лот без предложения в `_validate_payload`;
- один ИНН → ровно одна offer-смета со всеми лотами.

**Канон ИНН — одна публичная `canonicalize_inn()`: только ASCII `[0-9]`**, без
проверки длины (прежнее решение о разных юрисдикциях сохраняется). Применяется в
`create_contractor`, `update_contractor`, импорте, сверке шапки **и в поиске
`list_contractors`** — иначе поиск по «77 00…» перестанет находить сохранённое
«7700…». `_digits` на `isdigit` заменяется ею: §1.5 — `isdigit` пропускает то,
что `CHECK` затем отвергнет, и отказ на вставке был бы необъяснимым.

### 2.8. Get-or-create — конкурентный контракт

Лок `round_id` не мешает двум разным раундам одновременно создавать одного
подрядчика или один пакет. Для `contractor` (по канону ИНН), `offer_package`
(по `(tender_id, contractor_id)`), `offer` (по `(round_id, package_id)`) —
`INSERT … ON CONFLICT DO NOTHING RETURNING` + повторный `SELECT`, без
`IntegrityError` в транзакции. Тот же приём, что у каталога (§5 шаг 4.3).

**Участники заводятся из файла** (решение пользователя): кто подал предложение —
тот участник. Новый ИНН → новый `contractor` (если нет в справочнике) и новый
пакет; заведение — в warnings поимённо. Через API участники не создаются и не
правятся. Это **расширение права `member`** — загрузка файла участником создаёт
строку справочника подрядчиков — и оно вносится в §3 явно.

### 2.9. Baseline — по лотам, без контура допработ

Baseline-смета создаётся из **валидных** baseline-блоков и содержит только их
лоты; лоты без базы называются в warning. Раунд без единого валидного блока —
без baseline-сметы, warning «расчётная стоимость в файле не заполнена». Это
сохраняет факты файла и не выбрасывает частично заполненную базу.

Проекция переносит `lot.baseline_proposal` в единственный элемент
`lot.proposals` — иначе `_validate_payload` увидит ноль предложений. Предложение
получает `is_baseline = true`, `contractor_id = NULL`.

Для `BaselineEstimateOwner` **весь контур допработ выключен** — и
`decide_owner`, и `_import_additional_works` (§1.4). `_warn_on_unexpected_baseline`
— только для договора.

### 2.10. `deviation_from_baseline_cost` — впервые в базе

Ключ фича 1 довела до JSON позиции; здесь он впервые записывается в
`position_items`. Принадлежит **позициям участников**: `_import_positions`
читает его `.get()` у любой позиции, где ключ есть, через `_money`. Postprocess
уже решил, где он есть: при валидной базе лота оставлен, при невалидной вычищен.
У `BaselineEstimateOwner` поле принудительно `NULL`, даже если странная
раскладка принесёт ключ.

`AGENTS.md` §4 «остаётся `NULL` (baseline в сметах нет)» ревизуется: у смет
договора — `NULL`; у offer-смет — из файла.

### 2.11. Удаление — команды, локи, файлы

Три команды по образцу `delete_contract` (`crud/contracts.py`): локи по единой
иерархии, отказ при активном job, **явное удаление `offers` там, где `RESTRICT`
от пакета не даст каскаду пройти**, каскад БД ниже, возврат `file_keys` на
удаление **после коммита** через `purge_files_best_effort` — ошибка одного файла
не мешает остальным и ответу.

**Иерархия локов одна для всех команд и для импорта: `tender → rounds по id →
package`.** Без неё импорт (`round FOR UPDATE`) и удаление участника
(`package → rounds`) брали бы одни строки в обратном порядке — готовый дедлок.
Upload и удаление раунда берут тендер `FOR KEY SHARE`: он не сериализует разные
раунды одного тендера между собой, но конфликтует с `FOR UPDATE` удаления
тендера и участника — тем же способом, каким сегодня `delete_contract`
сериализуется с загрузкой через FK. `FOR UPDATE` тендера, в свою очередь,
блокирует создание нового раунда и пакета через FK, и собранный список раундов
не устареет между чтением и удалением.

| Команда | Локи | Что уносит | Файлы |
|---|---|---|---|
| раунд | тендер `FOR KEY SHARE`, затем раунд `FOR UPDATE` | сметы раунда, все его jobs (каскад) | все ещё существующие `file_key` истории раунда |
| тендер | тендер `FOR UPDATE`, затем все его раунды по `id` | **сначала явно `DELETE offers` тендера**, затем тендер — каскад уносит раунды, пакеты, сметы, jobs | все ещё существующие `file_key` всех раундов |
| участник | тендер `FOR UPDATE`, затем все раунды по `id`, затем пакет `FOR UPDATE` | **сначала явно `DELETE offers` участника** (каскад уносит их сметы), затем `DELETE offer_package` | **не трогает** — jobs, XLSX, `parsed_data` сохраняются |

Явный `DELETE offers` — следствие `RESTRICT` в §2.1, а не оговорка: при
удалении пакета `RESTRICT` иначе откажет, а при удалении тендера порядок двух
каскадов от одного родителя PostgreSQL не гарантирует — ветка `packages` может
встретить ещё не удалённые `offers`. Обе команды проверяются на **полностью
заполненной решётке со сметами** (§6).

Локи раундов у тендера и участника обязательны: job ссылается на `round_id`, и
один лок строки тендера не мешает новому upload обогнать проверку активных jobs.

**Удаление участника — честное имя:** «удалить участника и его
материализованные предложения; исходные файлы и результаты разбора
сохраняются». После него прежний round-job перестаёт быть текущим (§2.12).

**Протокол подтверждения с версией состава.** Повторный счёт под локами
защищает от параллельного удаления, но не от того, что пользователь подтверждает
другое состояние, чем видел: между preview на 2 сметы и `confirm` завершился
импорт, стало 6 — и все 6 ушли. `confirm=true` несло два факта разом. Носитель
различия — token в данных:

```
DELETE /tenders/{id}/participants/{pid}
  → 409 code=confirmation_required
    {rounds_count, estimates_count, positions_count, overrides_count, confirmation_token}
DELETE /tenders/{id}/participants/{pid}?confirmation_token=…
  → локи → пересчёт token → совпал → 204
                          → не совпал → новый 409 с обновлённым preview и token, ничего не удалено
```

Token — хеш от отсортированных `offer_id`, `estimate_id`, числа позиций и
overrides. Одних счётчиков мало: состав меняется при тех же количествах.
`409 code=active_import` — **другой** код, чтобы UI ждал, а не предлагал
подтвердить.

### 2.12. Текущий job раунда и идемпотентность

Правила §5 повторной загрузки переносятся на раунд с одним владельцем вместо
пары. Но «текущая смета пары» у раунда — набор, и после удаления участника
набор неполон. Job раунда **текущий**, если:

```
status = done
И число текущих смет раунда с import_job_id = job.id == job.estimates_created
И других текущих смет у раунда нет
```

Идемпотентный `200` на повторный SHA — только для текущего job. После удаления
участника тот же файл отвечает `409` и требует `replace`, восстанавливающего
набор. Contract-job пишет `estimates_created = 1`; старые jobs с `NULL` — по
прежнему правилу.

### 2.13. API

Роутер `routers/tenders.py`, CRUD `crud/tenders.py`, по образцу `contracts`.

```
GET    /tenders                            список: объект, предмет, номер, класс, раундов, участников
POST   /tenders                            object_id, title, tender_number, rate_class_id, notes    admin
GET    /tenders/{id}                       карточка — см. форму ниже
PATCH  /tenders/{id}                       title, notes (object_id и rate_class_id — снимок, нет)  admin
DELETE /tenders/{id}                       команда §2.11                                          admin

POST   /tenders/{id}/rounds                stage_no, label, held_on                               admin
PATCH  /tenders/{id}/rounds/{rid}          label, held_on                                         admin
DELETE /tenders/{id}/rounds/{rid}          команда §2.11                                          admin
POST   /tenders/{id}/rounds/{rid}/upload   файл, replace → 202 / 200 idempotent / 409 / 404      member; replace — admin
GET    /tenders/{id}/rounds/{rid}/import-jobs   история; каждый job несёт estimate_ids[]

DELETE /tenders/{id}/participants/{pid}    команда §2.11 с token                                  admin
```

Раунд всегда ищется **парой `(round_id, tender_id)`**; чужой тендер в URL — 404.

Форма карточки — три массива, решётка собирается из них:

```
rounds[]:        id, stage_no, label, held_on, latest_job, current_job_id,
                 baseline_estimate_id | null, baseline_total_including_vat | null
participants[]:  package_id, contractor_id, title, inn
cells[]:         round_id, package_id,
                 offer_id | null,        -- null: участник в этом раунде не участвовал
                 estimate_id | null,     -- offer есть, estimate null: предложение было, сметы сейчас нет
                 total_including_vat | null
```

`cells[]` — полный прямоугольник `participants × rounds`, и `offer_id` **nullable
намеренно**: участник, впервые появившийся во втором раунде, в первом `Offer` не
имеет. Три состояния ячейки различимы данными, а не выводятся клиентом.

Общий `GET /import-jobs/{id}` — дискриминированный ответ по `owner_type`:
договорной сохраняет `estimate_id`, раундовый несёт `estimate_ids[]`.

**«Итого с НДС» сметы** — новая `crud.estimate_total_including_vat`: число
**только если у каждого предложения сметы ровно одно конечное значение**
`total_cost_including_vat.total_cost_total` **и все значения равны**; пропуск или
`NaN/Infinity` у одного предложения — `NULL`, «единогласия остальных» нет.
Блок summary общий для листа и повторяется у предложений лотов, поэтому сумма
дала бы N-кратный итог на многолотовом файле. Подпись везде — **«Итого с НДС»**.

> **Граница, названная явно.** Паспорт считает валовое ИТОГО как **сумму** по
> предложениям всех лотов (`_file_total_including_vat`), и это записанное
> правило спеки паспорта §2.5, а не небрежность. На однолотовых сметах договора
> обе семантики дают одно число; на многолотовых — разное. Дизайн **не переводит**
> паспорт на единогласие: это ревизия чужой спеки, которая здесь не проводится.
> Расхождение записывается в `TECH_DEBT.md` (запись 19) с тем, что сделать.

Словарь `translating_integrity` пополняется именами новых FK и UNIQUE (рамка
§5.4) — иначе `RESTRICT` прилетит необработанным `IntegrityError`.

**`delete_contractor` получает третьего потребителя.** Сегодня он считает
`contracts` и `proposals` и затем делает прямой `db.delete` без
`translating_integrity` (`references.py:485`). Новый FK
`offer_packages.contractor_id RESTRICT` ломает его на подрядчике, который
остался участником тендера, но уже не имеет материализованных предложений
(после §2.11) — сырой `IntegrityError`. Правка: считать `offer_packages` рядом с
двумя другими и отказывать доменным `409` с числом тендеров; тест — подрядчик,
участвующий **только** в тендере. Это касание `references.py` вне контура,
вызванное самим контуром.

**Права.** Чтение и upload — `member` и `admin`; создание/правка/удаление
тендера и раунда, удаление участника, `replace` — только `admin`. Автосоздание
`Contractor` при upload — расширение права `member`, §3.

### 2.14. Экран

Пункт меню **«Тендеры»**, маршруты `/tenders`, `/tenders/:tenderId`. Только
shadcn/ui, по образцу `ContractsPage` / `ContractCardPage`.

**Список** — объект, предмет торга, номер, класс, раундов, участников; создание
— диалог с полями `POST`.

**Карточка** — шапка с реквизитами; **решётка «участники × раунды»**: строки —
участники, колонки — раунды, ячейка — одно из трёх состояний §2.13 с «Итого с
НДС» при наличии. Это единственная новая форма представления; она отвечает на
§2.6 рамки — «две проекции одной решётки».

**Выбранный раунд — `?round=<id>`**, по умолчанию последний по `stage_no`; иначе
не определено, какой раунд обслуживает панель после обновления страницы.

**Панель раунда:** загрузка, статус job с поллингом, warnings, и **baseline в
трёх состояниях** — по источнику факта, а не по одному булеву:

| Факт | Подпись |
|---|---|
| текущий `done`-job, baseline-смета есть | «Расчётная стоимость загружена», «Итого с НДС: …» |
| текущий `done`-job, baseline нет | «Расчётная стоимость в файле не заполнена» |
| текущего job нет, смет нет | «Файл раунда не загружен» |
| текущего job нет, сметы остались | «Состав раунда изменён после импорта — требуется полная замена» |

До первой загрузки экран не вправе утверждать, что база пуста: файла он ещё не
видел. Это то же правило §11 «пустое поле — отсутствие факта».

Кнопки удаления раунда и участника — с подтверждением, показывающим, что уйдёт;
у участника — протокол token §2.11, `active_import` показывается ожиданием.
Кнопки `admin`-действий у `member` скрыты.

**`EstimateUploadPanel` не обобщается union-пропом**: он жёстко содержит
`amendment_no`, загрузку карточки договора и счёт теряемых решений. Общие части —
dropzone, polling, counters, warnings — выделяются в компонент; поверх — две
оболочки, договорная и раундовая (с `replace` уровня раунда).

Сравнение участников между собой **не входит** (рамка §5.5); ячейка показывает
факт и итог, смету не открывает — это фича 3.

## 3. Отвергнутые альтернативы

**Одна смета раунда с N предложениями внутри лота.** Снять `uq_proposals_lot_id`,
положить все блоки в один `Estimate` — ближе к JSON парсера. Отвергнуто:
ломает инвариант §4 «одно предложение на лот», на котором стоят
`_replace_existing`, паспорт, матрица, сравнение; будущий `awarded_offer_id`
указывал бы в середину сметы, и «две независимые сметы» рамки §3.2 перестали бы
быть структурной правдой.

**Отдельный конвейер `round_import.py`.** Отвергнуто рамкой §3.3 и замером
§2.1: формат КП = формат сметы ГП, дублировать нечего; «дублирование сегодня —
расхождение завтра».

**Каскад `offers.package_id → offer_packages ON DELETE CASCADE`.** Отвергнуто:
делает потерю всей истории участника доступной из любого места, где кто-то
удалит строку (§2.1).

**`confirm=true` без версии состава.** Отвергнуто: подтверждение другого
состояния, чем видел пользователь (§2.11).

**Пятая таблица под полный JSON.** Отвергнуто: две колонки на `import_jobs`
несут тот же факт без новой сущности (§2.3).

**«Всегда можно разобрать XLSX заново».** Отвергнуто: доказательством
эквивалентности старому разбору это не является (§2.3).

**Отказ при неизвестном ИНН до ручного заведения участника.** Отвергнуто
пользователем: файл раунда — сам источник состава участников; загрузка раунда
на четыре участника стоила бы четырёх карточек руками до первого файла.

**Частичное участие (разные наборы ИНН по лотам) как предупреждение.**
Отвергнуто: бизнес-правило не принято, а молчаливый импорт дал бы участников с
разным составом смет (§2.7).

**Обобщить `EstimateUploadPanel` одним union-пропом.** Отвергнуто: компонент
несёт договорную логику, общие части выделяются отдельно (§2.14).

## 5. Definition of Done

1. Сводная таблица раунда импортируется одним job в N offer-смет и опциональную
   baseline-смету **атомарно**: падение на любом участнике откатывает всё.
2. `import_jobs.parsed_data` + `parser_version` хранят точный `ParseResult`
   каждого разбора, у обоих владельцев, независимо от исхода импорта;
   `estimate_raw_data` — проекция сметы; докстроки и §4 ревизованы.
3. Замена раунда — целиком, до цикла, под `FOR UPDATE` раунда; `replace=false`
   при существующих сметах — отказ; `Offer` при замене не удаляется.
4. Текущий job — `done` и равенство наборов через `estimates_created`;
   идемпотентный `200` только у текущего; после удаления участника тот же SHA →
   `409`.
5. ИНН каноничен на уровне данных (`CHECK`), одна `canonicalize_inn()` в create,
   update, поиске, импорте и сверке шапки; миграция данных отказывает при
   схлопывании.
6. Составные FK с `NOT NULL` защищают единство тендера; каждый `CHECK` и
   частичный индекс доказан пробоем.
7. Baseline — по лотам, без контура допработ; `deviation_from_baseline_cost`
   заполнен у offer-позиций при валидной базе лота, `NULL` при пустой и всегда
   `NULL` у baseline.
8. Удаление участника не трогает jobs, XLSX и `parsed_data`; протокол token:
   устаревший token → обновлённый preview, ничего не удалено.
9. Удаление раунда и тендера чистят все файлы истории после коммита; отказ
   одного файла не мешает остальным и `204`.
10. Единая иерархия локов `tender → rounds → package` у импорта и всех трёх
    удалений; гонки upload ↔ delete для тендера, раунда, участника и удаление
    участника ↔ создание раунда — **двухсессионные тесты с реальным
    опережением**, не готовым active-job; дедлок между импортом и удалением
    участника недостижим, доказано прогоном.
11. Экран `/tenders`: список, карточка с решёткой в трёх состояниях ячейки,
    панель раунда с четырьмя состояниями baseline, `?round=`.
12. Права по матрице §2.13; §3 `AGENTS.md` ревизован.
13. **Договорной импорт**: внешнее и доменное поведение не изменилось —
    `test_estimate_import.py`, `test_import_pipeline.py`,
    `test_import_fixture_e2e.py` зелёные без правок утверждений,
    `positions_total` тот же; **новыми** утверждениями — contract-job пишет
    `parsed_data`, `parser_version`, `estimates_created = 1`.
14. `estimate_total_including_vat` — единогласие; паспорт не тронут; запись 19 в
    `TECH_DEBT.md`.
15. `AGENTS.md` §3, §4, §5, §7, §8 ревизованы одним коммитом со ссылкой на спеку.
16. `just ci` зелёный; реальная сводная таблица (класс 3 фичи 1) загружена на
    стенд: 4 участника, baseline «в файле не заполнена»; снимки экрана в обеих
    темах для **каждого** состояния взаимодействия — пустой раунд, идущий
    импорт, ошибка, replace-confirmation, preview удаления участника, «состав
    изменён после импорта».

## 6. Доказательства

**Схема** (`test_schema_constraints.py` + `test_tenders_schema.py`): каждый
`CHECK` и частичный индекс — `INSERT` с ожиданием `IntegrityError`, ровно одно
нарушенное ограничение на вход: три владельца сметы и два у job; `amendment_no`
вне договора; `is_baseline` ↔ `contractor_id`; **`offers(round_id = NULL)` —
прямой пробой `MATCH SIMPLE`**; скрещивание раундов двух тендеров; лок активного
round-job и его освобождение по terminal-статусу; `parsed_data` ↔
`parser_version`; `estimates_created > 0`; канон ИНН. Parity 0015 ↔ `models.py`.
Миграция данных: два подрядчика с одним каноном → отказ с обоими `id`.
`downgrade` — отказ по каждому из трёх счётчиков отдельно.

**Импорт** (`test_round_import.py`, синтетические листы `sheet_builders`,
живой кластер):

- 2 участника + валидная baseline → 3 сметы, 3 проекции `raw_data`, один
  `parsed_data`, `estimates_created = 3`;
- 2 участника без baseline → 2 сметы, warning «не заполнена»;
- baseline валидна в одном лоте из двух → baseline-смета из одного лота, warning
  называет второй;
- **атомарность**: инъекция отказа на втором участнике → первого нет; job
  `error`, но `parsed_data` и `parser_version` записаны;

  карточка не изменилась, warning; ИНН с разделителями → тот же подрядчик;

  отказ; пустой ИНН → отказ;

**Договорной импорт: внешнее и доменное поведение не изменилось, три поля
job — новые.** Существующие `test_estimate_import.py`, `test_import_pipeline.py`,
`test_import_fixture_e2e.py` зелёные **без правок утверждений**; отдельными
новыми утверждениями: contract-job пишет `parsed_data`, `parser_version`,
`estimates_created = 1`.

**Startup-recovery раундового лока** — обязательный сценарий: round-job в
`pending`/`parsing` → `recover_interrupted_jobs` → `error` → повторная загрузка
того же `round_id` **разрешена**. Новый частичный индекс — вторая точка, где
неполное обобщение даёт вечный `409`, а §5 называет recovery условием запуска.

**API** (`test_tenders_api.py`): 404 на чужой тендер в URL раунда; идемпотентный
`200` только у текущего `done`-job; после удаления участника тот же SHA → `409`;
протокол token — preview, совпадение → `204`, устаревший → новый preview и
ничего не удалено; `active_import` — свой код; матрица прав — каждая запретная
пара роль × действие; `cells[]` — прямоугольник, тест с участником, появившимся
**только во втором раунде** (прямоугольный корпус дефект не ловит).

**Гонки** (двухсессионные, по образцу `test_category_override_concurrency.py`):
upload обгоняет удаление раунда / тендера / участника — вторая сессия стартует
между проверкой и удалением; защита доказывается **снятием лока раундов** у
тендера и участника — без него тест обязан покраснеть. Плюс два сценария
иерархии §2.11: **удаление участника против конкурентного создания раунда** —
`FOR UPDATE` тендера обязан задержать вставку раунда до конца удаления; и
**импорт против удаления участника одновременно** — обе сессии доходят до конца
без дедлока, потому что берут `tender → rounds → package` в одном порядке;
снятие лока тендера у удаления участника обязано воспроизвести гонку.

**Удаления на полной решётке** (§2.11): тендер с двумя раундами, двумя
участниками и сметами в каждой ячейке плюс baseline — удаление участника уносит
его два `offers` и две сметы, пакет удалён, чужие сметы и все jobs целы;
удаление тендера с тем же составом проходит до конца — без явного
`DELETE offers` `RESTRICT` от пакета обязан его остановить, и это проверяется
снятием явного шага.

**`delete_contractor`**: подрядчик, участвующий только в тендере (пакет есть,
материализованных предложений нет) → доменный `409` с числом тендеров, не
`IntegrityError`.

`NaN` у одного — четыре теста, все кроме первого → `NULL`.
