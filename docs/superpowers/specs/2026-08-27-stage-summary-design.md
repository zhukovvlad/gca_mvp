## 1. Что показали код и стенд

### 1.1. Величина статьи уже посчитана — `v_category_totals`

VIEW (миграция 0012) группирует `position_items` по `(estimate_id, proposal_id,
vat_rate_base, work_category_id, source)` и отдаёт `amount` без `NaN`/`±Infinity`,
`row_count`, `rows_with_amount`, `rows_not_finite`. Статья строки берётся из
строки-раздела (`pi.chapter_item_id → ch.work_category_id`), а ручной разнос
**материализован на самих строках-разделах** (`services/category_override.py`).
Собственный запрос «по последней встреченной статье СМР» разошёлся бы с паспортом
на одной и той же смете — поэтому источник ровно один, и складывать
`total_cost_total` самостоятельно нельзя.

Дополнительные работы приходят второй ветвью того же VIEW (`source =
'additional_works'`). **Они входят в свод**: он отвечает «сколько стоит предмет
торга», а допработы — его часть. Признак источника не теряется — он нужен фиче 4.

### 1.2. Дерево статей и подписи разноса строит паспорт

`services/category_rollup.build_tree(CategoryRef[], direct)` сворачивает
подстатьи в статьи по `parent_id` и упорядочивает по `WorkCategory.sort_order`;
корни присутствуют всегда, узел глубже — только при `rows > 0`. Свод зовёт
`build_tree`, второй свёртки не заводит. Ручные решения сметы с подробностями
(раздел, автор, заметка, суммы поддерева) отдаёт
`crud/project_passport._manual_assignments` — это источник **паспорта**, он
тянет `_section_metrics` и делает несколько запросов на смету. Своду нужны только
признак и дата: он читает `count` и `max(assigned_at)` из
`estimate_category_overrides` **одним пакетным агрегатом по списку смет трассы**
(§2.10, §2.12) — иначе число запросов росло бы с числом колонок.

### 1.3. Ставка и итог сметы — правилом единогласия

`crud/estimate_totals.estimate_total_including_vat` — «Итого с НДС» сметы,
`None` при разногласии предложений или неконечном значении. Эффективная база
НДС — `COALESCE(estimates.vat_rate_base_override, proposals.vat_rate)`, она уже
стоит колонкой `vat_rate_base` в `v_category_totals`; при разногласии между
предложениями одной сметы правило то же, что у `_fold_cell`
(`crud/analytics.py`): единой ставки нет → `unknown_vat_base`.

### 1.4. Стенд подтверждает контракт на данных

## 2. Решение

### 2.1. Вход — выбор предложений на решётке

Свод — не пункт меню и не вкладка: он строится по **выбору**, а выбор делается
на решётке «участники × раунды» карточки тендера (`OfferGrid`), тем же правилом,
что у сравнения договоров (`AGENTS.md` §7 п.7: вход только выбором, пункта в меню
нет).

- Ячейка со сметой (`offer_id` и `estimate_id` не пусты) становится
  **плиткой-переключателем**: shadcn `Toggle` с `aria-pressed`, сумма внутри, у
  выбранной — акцентная рамка и иконка `Check` (lucide) в правом верхнем углу.
  Ячейки «—» и «нет сметы» плиток не получают — сводить нечего.
- **Нажатие на имя участника выбирает все его сметы разом**; отдельные этапы
  затем снимаются нажатием на плитку. Отдельного чекбокса у участника нет.
- **Один участник на трассу — состоянием, не сюрпризом:** пока выбрана хотя бы
  одна плитка участника, плитки других строк недоступны с подсказкой «Свод
  строится по одному участнику»; сняты все — доступны снова. Одна смета на раунд
  получается сама: у участника в раунде одна ячейка.
- Над решёткой — счётчик «выбрано N смет · {участник}» и кнопка «Свод по этапам
  (N)», **активная от двух смет**: вопрос поверхности — изменение, ему нужны две
  точки. При одной — подсказка «выберите хотя бы два этапа».
- Заголовки колонок решётки выравниваются под плитки (вправо). Больше на
  карточке не меняется ничего.

Выбор на карточке — локальное состояние; перезагрузка карточки его сбрасывает.
Сохранённых трасс нет (§3).

### 2.2. Маршрут

`/tenders/:tenderId/summary?offers=27&offers=29&offers=38` — идентификаторы
предложений, повторяющимся параметром. Порядок в URL не важен: колонки сортирует
сервер по `stage_no`. **Выбор живёт только в URL страницы свода** — ссылка
воспроизводима. Открыли без `offers` или с непроходящим набором — пустое
состояние с причиной отказа (§2.4) и ссылкой на решётку, не пятисотка.

Хлебные крошки: Тендеры → {номер тендера} → Свод по этапам. Заголовок «Свод по
этапам · {участник}», подзаголовок — предмет торга, объект и «этапов в своде N из
M загруженных у участника» с перечислением исключённых — список этапов участника
отдаёт сервер (`participant.stages[]`, §2.16), клиент ничего не вычисляет.

### 2.3. Эндпоинт и проверка выбора

`GET /api/v1/tenders/{tender_id}/stage-summary?offers=…` в `routers/tenders.py`;
чтение, права — как у карточки тендера. Расчёт — новый модуль
`crud/stage_summary.py`: чистые функции над уже прочитанными данными плюс тонкий
слой запросов.

Отказы — каждый со своим кодом в `detail`, не пятисотка:

| Условие | Ответ |
|---|---|
| тендер не существует | 404 `tender_not_found` |
| предложение не принадлежит тендеру либо не существует | 404 `offer_not_found` |
| выбрано меньше двух | 422 `too_few_offers` |
| два предложения одного раунда | 422 `one_offer_per_round` |
| предложения разных участников | 422 `single_participant` |
| у предложения нет сметы (состояние «нет сметы» после замены раунда) | 422 `offer_has_no_estimate` |

**Задел смешанных трасс:** контракт запроса — список `offer_id`, и единственное,
что снимется для трасс из разных участников, — проверка `single_participant`.
Семантика подписей (§2.5, §2.6) написана про путь одного подрядчика и для
смешанных трасс потребует своей редакции; это отдельная фича, здесь только не
закрывается дверь.

### 2.4. Величина ячейки

```
сумма статьи в колонке = Σ amount из v_category_totals
                         по (estimate_id колонки, статья и её подстатьи),
                         обе ветви source ('positions' + 'additional_works')
```

Ячейка несёт отдельно `additional_works_amount` — минимум, которого требует
сохранение признака источника (§1.1). Свёртка подстатей в статью — `build_tree`
(§1.2). Ячейка несёт `rows: {row_count, rows_with_amount, rows_not_finite}` —
суммы по ветвям и поддереву; при `rows_with_amount < row_count` сумма **неполна**,
и поверхность обязана это показать: иначе частичный итог читается как полный.
Подпись — «учтено X из N строк», отдельно «неконечных значений: k», если
`rows_not_finite > 0`. Слово «без цены» не годится: строка без числа и строка с
`NaN` — разные факты, и VIEW их различает.

### 2.5. Четыре состояния ячейки

| Состояние | Условие | Показывается |
|---|---|---|
| `amount` | сумма ≠ 0 | число |
| `removed` | сумма = 0 **и** хотя бы в одной предыдущей *выбранной* колонке была ≠ 0 | пилюля «снято» |
| `not_evaluated` | сумма = 0 **и** ни в одной предыдущей выбранной не была ≠ 0 | пилюля «не оценивалась» |
| `absent` | статьи нет в смете ни одной строкой | прочерк |

`rows` (§2.4) — ортогональная характеристика поверх любого состояния, не пятое
состояние. `appeared` и прочие — виды изменения (§2.6), не состояния.

**`removed` считается по пройденному пути, а не по предыдущему шагу:** признак
«по предыдущему шагу» помечал бы вторую подряд нулевую колонку как «не
оценивалась» — утверждал бы, что статью не оценивали никогда, хотя цена у неё
была. **`absent` не равно `not_evaluated`**: первое — статьи нет в файле, второе
— есть, но не оценена; смешивать нельзя по тому же правилу, каким `AGENTS.md` §4
разводит `no_standard` и `unknown_vat_base`. **Ноль никогда не даёт «−100 %»**
(рамка §2.3: обнуление — снятие работы, а не уступка в цене).

Состояние не зависит от ставки НДС: «ноль / не ноль / нет строки» читается по
валовой сумме и при `unknown_vat_base` вычисляется как обычно; недоступна только
показанная сумма (§2.8).

### 2.6. Путь и изменения

**Путь = выбранные колонки.** «Предыдущая колонка» — предыдущая *выбранная* по
`stage_no`; `removed` — «в одной из предыдущих *выбранных* была ≠ 0». Пропуск
номера раунда законен (раунд могли отменить), исключение раунда выбором — тоже.

Цена решения названа и принята: исключив раунд, где статья единственный раз имела
цену, дальше читатель увидит «не оценивалась», а не «снято». Принято потому, что
поверхность обязана воспроизводиться из своего URL, а не из скрытого знания о
невыбранных раундах; подзаголовок «этапов в своде N из M» предупреждает.
Альтернатива — считать историю по всем M раундам участника, показывая N —
отвергнута (§3).

**Матрица переходов — по состояниям**, не по «пусто/есть»: `absent`,
`not_evaluated` и `removed` — разные факты.

| Начало → конец | `change.kind` | Показывается |
|---|---|---|
| `amount → amount`, база > 0 | `percent` | процент со знаком |
| `amount → amount`, база < 0 | `abs_only` | абсолютная дельта, без процента |
| `amount → removed` | `removed` | «снято» — в колонке «Торг»; в ячейке этапа не печатается, см. правило о повторе ниже |
| `amount → absent` | `disappeared` | «нет в файле» — исчезновение строки из файла **не доказывает** снятия |
| `not_evaluated → amount`, `absent → amount` | `appeared` | «появилась» |
| `removed → amount` | `reappeared` | «вернулась» |
| `removed → removed` | `none` | прочерк: состояние ячейки уже говорит «снято», повторного «снято» в изменении нет |
| любой переход между `not_evaluated`, `absent`, `removed` без суммы | `none` | прочерк — **отдельная числовая дельта не заявляется**; изменение факта (`absent → not_evaluated`, `removed → absent`) видно по состояниям самих ячеек |
| любой переход, где на конце недоступна сумма (§2.8) | `none` + `reason` | прочерк с причиной |

`change.kind ∈ {percent, abs_only, appeared, reappeared, removed, disappeared,
none}`; у `none` — `reason`, когда расчёт недоступен.

**«Прочерк» в колонке «Показывается» — это «числовой дельты не заявляется», а
не обязательно литерал «—» на экране** (уточнение 28.08.2026, редакционное:
правило не меняется, называется точнее). Где именно рисуется литерал, решает
макет гейта 1, на который §2.14 ссылается как на источник вида: в ЯЧЕЙКЕ ТАБЛИЦЫ
при `kind = 'none'` под состоянием не рисуется ничего — состояние («снято», «не
оценивалась», плоский прочерк `absent`) уже стоит строкой выше и второй прочерк
под ним был бы повтором; в KPI «Последний к первому» и под столбиком трассы
литерал «—» рисуется, потому что там никакого состояния рядом НЕТ и пустой слот
читается как «значение почему-то не показали». По тому же доводу литерал стоит и
в колонке «Торг» (макет, статьи «15» и «99»): состояния рядом с ней нет тоже. Уточнение заведено потому, что
буквальное чтение слова «прочерк» разошлось и с макетом, и с реализацией, а
разойтись они не имеют права молча.

**Значок изменения не повторяет СЛОВО, которое уже сказало состояние ячейки**
(28.08.2026, по просмотру на стенде: пользователь нашёл двойную пилюлю). Виды с
пилюлей (`appeared`, `reappeared`, `removed`, `disappeared`) печатаются под
состоянием как обычно — кроме случая, когда подпись вида совпадает с подписью
состояния слово в слово. Сегодня такой случай ровно один: `state = 'removed'`
вместе с `kind = 'removed'` — оба пишутся «снято», и ячейка показывала это
дважды, тогда как макет рисует одну пилюлю тоном состояния. Для `removed` это
не исключение, а ПРАВИЛО: сервер возвращает `kind = 'removed'` единственной
веткой `amount → removed`, поэтому он влечёт `state = 'removed'` всегда, и в
ячейке статьи такой значок не печатается никогда — видимым вид остаётся в
колонке «Торг». Тон у него там тревожный, как у одноимённого состояния и как на
макете (`pill warn` в обеих колонках); остальные структурные виды — нейтральные. Факты за двумя
пилюлями РАЗНЫЕ (состояние: «цены нет сейчас, а была раньше»; вид: «сняли именно
на этом шаге»), но читателю они предъявлены одним и тем же словом, и второе
вхождение не сообщает ничего. Правило проверяется по самим словарям подписей, а
не списком пар: переименование подписи не имеет права ни завести новый молчаливый
дубль, ни погасить нужный значок (тест на единственность совпадения —
`StageSummaryTable.test.tsx`).

**База процента:** `(конец / начало − 1) × 100` только при `начало > 0`. Нулевая
база уходит в `appeared`/`none`, отрицательная — в `abs_only`: отрицательная
статья возможна (`position_items.total_cost_total` без `CHECK` на знак, миграция
0010; статья с исправляющей строкой), а при отрицательной базе знак процента
инвертирует смысл — тот же довод, каким [дельта-модель допсоглашений](../../proposals/2026-08-18-amendments-delta-model.md)
§2 лишает корзину ДС медианы. **Деление при базе ≤ 0 не вызывается по
построению**; `DivisionByZero` здесь — дефект расчёта, который обязан упасть
тестом (§6), а не превратиться в HTTP-отказ.

**Направление** — строка `direction ∈ {up, down, flat}`, считается по величинам,
не по знаку множителя; равенство — третье состояние, не «рост» (`AGENTS.md` §11).
Рост и снижение подписываются знаком и цветом, но **не называются хорошим или
плохим**: снижение из-за уступки и снижение из-за снятой работы по одному числу
не различить.

### 2.7. Правые колонки

- **«Торг: первый → последний»** — изменение между первой и последней выбранной
  колонкой по матрице §2.6.
- **«Вклад в итог»** — абсолютная разница концов пути. `contribution.value =
  null` с `reason = absent_endpoint`, если на любом конце `absent`: `absent` не
  равен нулю, число здесь было бы выдумкой; структурная подпись
  (`disappeared`/`appeared`) при этом остаётся. То же с `reason =
  unknown_vat_base` при недоступной сумме на конце.
- **«После торга»** (последний раунд → смета договора) — **не в этой фиче**:
  `contracts.awarded_offer_id` не существует (§4). Складывать «Торг» и «После
  торга» в одно число нельзя и тогда, когда колонка появится: два разных
  вопроса.

### 2.8. Оси измерения

**Налоговый состав.** Ось выбирается по множеству *известных* ставок среди
выбранных колонок; колонка с неизвестной базой (`vat_state =
'unknown_vat_base'` — база ни заявлена, ни назначена, либо разногласие
предложений внутри сметы) в это множество не входит. Три случая, и они записаны
одинаково здесь и в `AGENTS.md` §10:

| Известных ставок среди выбранных | Известные колонки | Колонки `unknown_vat_base` |
|---|---|---|
| одна | **валовые**, как в файлах (`display.tax_basis = 'gross'`) | суммы недоступны |
| несколько | **нетто** целиком (`display.tax_basis = 'net'`) | суммы недоступны |
| ни одной | сопоставимых итогов нет: таблица показывает состояния ячеек без сумм, `track.available = false` | суммы недоступны |

- **Одна ставка** — единый множитель сокращается в проценте и одинаково
  масштабирует «Вклад», поэтому таблица сходится тождественно (на стенде — 16 из
  16).
- **Несколько ставок** — валовой оси показа больше нет: 100 с НДС 20 % и 100 без
  НДС — разные деньги. Известные колонки приводятся к нетто (`gross_to_net` по
  эффективной базе каждой), подпись оси называет причину и перечисляет ставки по
  этапам, на колонке смены ставки — отметка. Дельты и проценты считаются по
  нетто и от смены ставки не зависят.
- **Тендер начинается в одной ставке и кончается в другой — нормальный ход дела**
  (решение пользователя 25.08.2026, подтверждено 27.08). Запрещать нельзя,
  отказывать в дельтах — тоже.
- **`unknown_vat_base`** — суммы недоступны **на любой оси**: под подписью «с НДС
  20 %» валовая величина неизвестного состава была бы ложью, а на нетто-ось
  валовая сумма не попадает никогда. У каждой ячейки такой колонки
  `amount_unavailable_reason = 'unknown_vat_base'`, показанная сумма `null`,
  состояние ячейки сохранено (§2.5); дельты к ней и от неё — `none` с причиной;
  в трассе — штрихованный слот без высоты и числа с подписью причины (§2.11).
  Ось остальных колонок она не меняет.

Правило не новое — `_fold_cell` уже гасит эффективную ставку при разногласии
(«единой ставки показа нет вовсе»). Режимов показа, как чипы на `/compare`, не
заводится: поверхность одного участника (§3).

**Ценовой уровень.** Поверхность объявляет: **номинальные цены, без приведения к
ценовому уровню месяца.** `AGENTS.md` §10 (v6.10) требует объявления от
сравнительных поверхностей, а торг растягивается на месяцы. Приведение в фичу не
входит.

Обе подписи стоят на самой поверхности, под шапкой; тултип подпись не заменяет.

### 2.9. «Нераспределённое» и сходимость

**Строка «Нераспределённое» обязательна**, даже пустая: в измеренных образцах
покрытие статьями 100 %, на стенде — нет (§1.4), и это свойство файла, а не
формата. Строка закреплена внизу вне сортировки. **Её дельта не читается как
уступка**: рост может означать и новые разделы без статьи, и незаконченный
разнос — «Торг» у неё «без %» с подсказкой, тем же доводом, каким спека
сравнения §2.1.4 лишает её медианы.

**Сходимость проверяется, а не предполагается.** У каждой колонки
`convergence: {categories_sum, file_total, converged, delta, reason}` — три
состояния:

| `converged` | Показывается |
|---|---|
| `true` | «сходится» |
| `false` | «не сходится: Δ …» — дефект данных или разноса, показывается, не гасится |
| `null` | «сверка невозможна: причина» — `file_total` пуст (итог файла не единогласен, `estimate_total_including_vat` вернул `None`) |

**Сходимость — диагностика исходного файла и от ставки НДС не зависит.** Она
всегда считается в **исходных валовых величинах**: сумма статей первого уровня
плюс «Нераспределённое» по `v_category_totals` против «Итого с НДС» файла — на
любой оси показа, в том числе у колонки `unknown_vat_base` (её валовые величины
известны, неизвестен только состав). Единственная причина `converged = null` —
недоступный или неединогласный файловый итог. На нетто-поверхности подпись
называет, что Δ сходимости измерена в исходных деньгах файла, а не в показанных.

**Источник итога колонки — решение, а не следствие:** `columns[].total`, трасса
и `kpi.first_to_last` берутся из **суммы дерева статей плюс «Нераспределённое»**
на оси показа, а не из файлового итога. Тогда трасса раскладывается вкладом
строк тождественно даже при расхождении с файлом; файловый итог остаётся
диагностикой в `convergence.file_total`, и расхождение между ними видно как
`converged = false`, а не спрятано в разнице двух чисел на одном экране.

### 2.10. Ручной разнос

Разнос работает на сметах предложений без правки кода: маршрут
`/api/v1/estimates/{estimate_id}/category-overrides/{position_item_id}` привязан
к смете, не к договору. **Право `member` на разнос распространяется на сметы
предложений** — записано здесь явно, а не выведено из того, что код не запрещает.

Отсюда обязанность поверхности: у каждой колонки `manual_overrides: {count,
last_at}` — признак и дата последнего разноса, под шапкой колонки («разнос: 3
решения · 26.08.2026» / «без ручного разноса»). Разнос делается человеком между
просмотрами, и без этой подписи две выгрузки одной трассы разошлись бы без единой
новой загрузки файла. Источник — пакетный агрегат `count` / `max(assigned_at)` по
`estimate_category_overrides` для всех смет трассы одним запросом (§1.2);
подробности решений остаются у `_manual_assignments` паспорта.

### 2.11. KPI и трасса — считает сервер

`kpi`: `stages_selected` / `stages_loaded` (M — раунды участника со сметой),
`last_stage_positions` (позиции последней выбранной колонки, `is_chapter =
false`), `categories_with_amount` (корни с ненулевой суммой любого знака),
`categories_total` (число корней классификатора — клиент ничего не зашивает),
`first_to_last` (изменение итога по матрице §2.6). Последняя колонка —
максимальный выбранный `stage_no`.

`track: {available, reason}` — доступность столбиковой трассы: `false` при
неположительном сопоставимом итоге либо когда сопоставимых положительных итогов
нет вовсе. Высоту столбика тоже считает сервер: у каждой колонки
`bar_height_pct` — доля от максимального сопоставимого итога, 0–100, `null` у
колонки без сопоставимой суммы; клиент Decimal-строки не сравнивает и не делит.
`unknown_vat_base` доступность трассы **не выключает** — это недоступность
отдельной колонки (§2.8).

### 2.12. Арифметика и представление

- `Decimal` на сервере, `float` нигде. Деление — под `_DIV_CONTEXT`
  (`crud/comparison.py`), недостижимость нуля в делителе — §2.6.
- Агрегаты не округляются. Квантование — на выходе: деньги `quantize_money`,
  проценты — 0,1 п.п. **Слой представления чисел — сервер**: у клиента нет
  `Decimal`, а вторая копия правил разошлась бы с первой (тот же довод, каким
  §10 требует серверного приведения к инфляции). В JSON деньги — строки.
- Запросов к БД — постоянное число независимо от числа колонок: по одному на
  список смет для `v_category_totals`, итогов, ручных решений, позиций. N+1
  `get_tender_card` (`TECH_DEBT.md` запись 21) сюда не переносится.

### 2.13. Порядок строк

По **`sort_order` классификатора**, внутри каждого уровня отдельно: корни между
собой, дети — внутри своей статьи. Вклад в итог на порядок НЕ влияет — ни как
первичный ключ, ни как вторичный, — и строка с пустым вкладом стоит там же, где
стояла бы с числовым: на своём месте в классификаторе. «Нераспределённое» и
«Итого» закреплены внизу. Переключателя сортировки нет.

**Ревизия 28.08.2026 по просмотру на стенде, решение пользователя.** Прежняя
редакция сортировала по убыванию модуля «Вклада в итог», вторично по
`sort_order`, а строки с пустым вкладом ставила после числовых — осознанное
отклонение от макета 25.08 с обоснованием «поверхность отвечает, на чём
сложилось изменение, и первой должна стоять статья, давшая больше всего».
Отклонение не подтвердилось при первом же чтении готовой поверхности: на стенде
16 корней из 21 имеют числовой вклад, и порядок по вкладу перемешивает
классификатор целиком — читатель, который ищет знакомую статью, не находит её
там, где привык, а таблица сводом по классификатору и является. Вопрос «на чём
сложилось изменение» отвечает КОЛОНКА «Вклад в итог», которая никуда не делась:
она называет величину каждой статьи явным числом, и сортировать ради него всю
таблицу не нужно. Реализация прежнее правило исполняла верно — это смена
решения, а не исправление дефекта.

### 2.16. Форма ответа API

Один контракт, собранный из решений §2.3–§2.13. Деньги и проценты — строки,
уже квантованные (§2.12); `null` везде означает «величины нет» и несёт причину
рядом, а не «ноль». Имена полей — обязательство для плана.

```
GET /api/v1/tenders/{tender_id}/stage-summary?offers=27&offers=29&offers=38

200 →
tender:       { id, tender_number, title, object_title }
participant:  { package_id, contractor_id, title, inn,
                rounds_with_estimate: M,             -- раунды участника со сметой
                stages: [ { stage_no, label, offer_id, selected: bool } ] }
                                                     -- ВСЕ раунды участника со сметой по stage_no;
                                                     -- исключённые из свода = selected: false
columns[]:    { kind: 'round',                       -- задел: 'contract' за разделителем
                offer_id, estimate_id, round_id, stage_no, label, held_on,
                vat_rate_base: "20" | null,          -- эффективная база; null ⇔ vat_state = 'unknown_vat_base'
                vat_state: 'known' | 'unknown_vat_base',
                total: string | null,                -- итог на оси показа; null при unknown_vat_base
                total_change: Change,                -- к предыдущей выбранной колонке
                bar_height_pct: string | null,       -- 0–100, null без сопоставимого итога
                manual_overrides: { count, last_at: iso | null },
                convergence: { categories_sum: string,          -- ВСЕГДА в исходных валовых деньгах файла (§2.9)
                               file_total: string | null,
                               converged: bool | null, delta: string | null,
                               reason: 'file_total_unavailable' | null } }
rows[]:       Row                                    -- корни, порядок §2.13
unallocated:  Row                                    -- флаг is_unallocated = true, bargain без процента
total:        { cells: TotalCell[] }                 -- итог колонки = Σ корней + unallocated на оси показа (§2.9); = columns[].total
display:      { tax_basis: 'gross' | 'net' | 'none',
                reason: 'single_rate' | 'mixed_rates' | 'no_known_rates',
                rates_by_column: string[] | null,    -- при 'mixed_rates'
                price_level: 'nominal' }

                categories_with_amount: K, categories_total: L, first_to_last: Change }
track:        { available: bool, reason: 'non_positive_total' | 'no_comparable_totals' | null }

Row  = { work_category_id, code, title, is_unallocated: bool,
         cells: Cell[],                               -- выровнены по columns[]
         bargain: Change,                             -- первая → последняя выбранная
         contribution: { value: string | null, direction: 'up'|'down'|'flat'|null,
                         reason: 'absent_endpoint' | 'unknown_vat_base' | null },
                                                      -- у unallocated value ЧИСЛО: запрет касается только процента в bargain
         children: Row[] }                            -- по правилу видимости §2.14
TotalCell = { amount: string | null,                  -- на оси показа; null ⇔ amount_unavailable_reason ≠ null
              amount_unavailable_reason: 'unknown_vat_base' | null,
              rows: { row_count, rows_with_amount, rows_not_finite },   -- Σ по корням и unallocated этой колонки
              change: Change }                        -- к предыдущей выбранной; у первой kind = 'none', reason = 'first_column'
Cell = { state: 'amount' | 'removed' | 'not_evaluated' | 'absent',
         amount: string | null,                       -- на оси показа

         rows: { row_count, rows_with_amount, rows_not_finite },
```

Инварианты, которые план обязан закрепить тестами:

- (инварианты ниже про `Cell` — ячейки СТАТЕЙ; у `TotalCell` состояния нет вовсе)
- `cell.state = 'absent'` ⇔ `rows.row_count = 0`; `state = 'amount'` ⇔ сумма по
  валовым величинам ≠ 0 — состояние **не зависит** от `amount_unavailable_reason`.
- `amount = null` ⇔ (`state ∈ {absent, removed, not_evaluated}` **или**
  `amount_unavailable_reason ≠ null`).
- `additional_works_amount` **независим от состояния ячейки**: ветви могут
  взаимно погашаться (итог статьи 0 при ненулевых допработах), и сумма допработ
  сохраняется как есть. `null` ⇔ (ветви `additional_works` у статьи в этой смете
  нет **или** `amount_unavailable_reason ≠ null`).
- `change.kind = 'percent'` ⇒ `value ≠ null`, `direction ≠ null`; `kind = 'none'`
  ⇒ `value = null`, `direction = null`, `reason ≠ null`.
- `contribution.value = null` ⇔ `reason ≠ null`; у `unallocated` `value` — число
  (при известных концах), `bargain.kind = 'none'` с `reason = 'unallocated'`.
- **У итоговой строки НЕТ состояния, и это структурно, а не по соглашению.**
  `TotalCell` не несёт поля `state`: итог — АГРЕГАТ, а не статья, и состояния
  «снято» / «не оценивалась» / «нет в файле» к нему неприменимы по смыслу —
  сумма нулей равна нулю, а не «неизвестна». Поэтому при известной оси
  `total.cells[].amount` — ВСЕГДА число, включая `"0.00"` и пустую смету, а
  `null` возможен единственно при `unknown_vat_base`. Изменение итога считается
  ЧИСЛЕННО, а не по матрице состояний: положительная база — `percent`, база
  ≤ 0 — `abs_only`, недоступный конец — `none` с причиной. Неположительный итог
  по-прежнему выключает трассу (`track.reason = 'non_positive_total'`).
  Ревизия 28.08.2026 по внешнему ревью PR #34: прежняя редакция типизировала
  итог как `Cell`, и на нулевом итоге с живыми строками он публиковал состояние
  «снято» вместе с суммой `"0.00"` — нарушение сразу двух инвариантов ниже,
  причём строка статьи в том же ответе честно отдавала пустую сумму. Правка
  структурная: у типа, к которому состояния неприменимы, их не должно быть.
- `columns[i].total = total.cells[i].amount = Σ rows[].cells[i].amount +
  unallocated.cells[i].amount` на оси показа (§2.9); `convergence.categories_sum`
  — та же сумма в исходных валовых деньгах; `converged = true` ⇒
  `categories_sum = file_total`; `converged = null` ⇔ `file_total = null` ⇔
  `reason = 'file_total_unavailable'`.
- `display.tax_basis = 'none'` ⇔ `track.available = false` с
  `reason = 'no_comparable_totals'` ⇔ у всех колонок `vat_state = 'unknown_vat_base'`.
- `bar_height_pct ≠ null` ⇔ колонка имеет сопоставимый положительный `total` и
  `track.available = true`; максимум среди ненулевых — ровно сто. Записан он как
  `"100.0"`: проценты квантуются до 0,1 п.п. ОБЩИМ правилом §2.12, и делать
  ради одного поля исключение дороже, чем записать литерал точно (редакционная
  правка 28.08.2026 по внешнему ревью PR #34).
- Длина `cells` у каждой строки, у `unallocated` и у `total` равна длине `columns`.
- `participant.stages` отсортирован по `stage_no`; число элементов с `selected = true`
  равно длине `columns`, а их `offer_id` — ровно `columns[].offer_id`;
  `len(stages) = rounds_with_estimate = kpi.stages_loaded`.

## 3. Отвергнутые альтернативы

**Свод тендера целиком** (все участники в одной таблице). Ячейка контракта —
сумма статьи в смете *одного* предложения; суммы разных подрядчиков в одну
колонку не складываются. Это была бы неспроектированная поверхность сравнения
участников (рамка §5.5) — новый гейт 1, не эта фича.

**Смешанные трассы в этой фиче** (разные участники в разных колонках). Подписи
«снято», «уступка», «торг» верны только внутри одного подрядчика; для смешанных
нужны два режима подписей и состояний. Отложено заделом (§2.3).

**Путь по всем раундам участника при показе выбранных.** Ячейка утверждала бы
факт о колонке, которой на экране нет; ссылка перестала бы воспроизводить
показанное. Отвергнуто в пользу «путь = выбранные» с предупреждением в шапке.

**Расчёт на клиенте из per-estimate ответов паспорта.** Нет `Decimal`, вторая
копия правил состояний, негде единообразно проверить сходимость и ось НДС —
противоречит `AGENTS.md` §10.

**Сохраняемая сущность «трасса».** Таблица, миграция, CRUD и права ради того, что
URL даёт бесплатно. Ляжет поверх при необходимости без переделки эндпоинта.

**Колонка `awarded_offer_id` внутри фичи 3 без команды «создать договор из
раунда».** Мёртвая колонка в схеме: заполнять нечем. Тонкая фича provenance идёт
отдельно, её очередь — за пользователем (рамка §4).

**Режимы показа НДС** (своя ставка / единая / нетто, как на `/compare`).
Поверхность одного участника; при одной ставке валовая ось однозначна, при
разных — единственная честная ось нетто. YAGNI.

**Трасса на recharts.** Осей и наведения нет; библиотека принесла бы только свои
грабли.

**Сортировка по сумме первого этапа** (макет 25.08). Первой стояла бы самая
дорогая статья, а не давшая больше всего изменения — не тот вопрос.

## 5. Definition of Done

1. `just ci` зелёный; интеграция против `gca_test` — один прогон за раз.
2. Соответствие «требование спеки → тест» — списком в devlog; требование без
   теста либо получает тест, либо объявлено границей.
3. **Стенд `gca_dev`**, участник с четырьмя раундами: у каждой колонки
   `converged = true` (16 из 16 смет сходятся до копейки); `additional_works_amount`
   ненулевой хотя бы у одной статьи (на стенде — у всех смет); у участника с
   непустым «Нераспределённым» строка непуста; исключение среднего раунда меняет
   проценты соседей и подпись «N из M».
   **Пункт про подписи разноса снят решением пользователя 28.08.2026** и заменён
   долгом: разнос статей привязан к смете и маршрут принимает смету предложения,
   но поверхности, с которой человек дошёл бы до неё, в продукте нет — панель
   разноса живёт только в паспорте договора. Требование невыполнимо не потому,
   что реализация неполна, а потому, что совершать разнос негде; оно вернётся
   в DoD той фичи, которая заведёт поверхность (`docs/TECH_DEBT.md` запись 22).
   Серверная часть при этом проверена: интеграционный тест гоняет штатный
   `set_override` на смете предложения и убеждается, что подпись появляется у
   своей колонки и не появляется у соседних.
4. **Замер раскладки в браузере** при 8 и 10 колонках со всеми раскрытыми
   статьями, 1280 и 1100 px, обе темы: `scrollWidth > clientWidth` у
   контейнера, страница не едет, первая колонка на месте (`AGENTS.md` §11:
   jsdom раскладку не считает). **Контейнер здесь — тот, что рендерит примитив
   `Table`** (`div[data-slot="table-container"]`), а не `Surface` вокруг него:
   кандидатов с `overflow-x-auto` два, прокручивается всегда внутренний, и
   проверка, поставленная на внешний, дала бы зелень ни о чём. В замере он
   находится поиском ПЕРВОГО прокручиваемого предка таблицы, а не по классу.
   **Дополнено 28.08.2026: этих трёх проверок НЕДОСТАТОЧНО, и это доказано.**
   Все три были зелёными на поверхности, где раскрытие статьи выталкивало
   «Торг» и «Вклад в итог» за край: «прокрутка живёт внутри контейнера» — не
   критерий читаемости. Мерить надо ещё ПЯТЬ величин, каждую числом:
   1. долю ширины, которую занимает колонка подписи (у зажатой она не растёт
      при раскрытии статей);
   2. достижимость правой колонки без прокрутки на штатной ширине окна;
   3. переполнение ячеек первой колонки по ширине (`scrollWidth > clientWidth`)
      — ловит зажим без переноса;
   4. совпадение верхних строк ВСЕХ числовых ячеек каждой строки (ловит и
      разное выравнивание, и разные отступы у ячеек одной строки);
   5. центр односложного нечислового содержимого против центра строки.
   Последние две мерить ТЕКСТОВЫМИ прямоугольниками (`Range`), а не рамками
   элементов: у inline-`span` и block-`div` рамки считаются по-разному, и замер
   по элементам даёт ложные расхождения (замерено — 9 px из ниоткуда).
5. **Снимки всего экрана в обеих темах**: решётка с выбором и недоступными
   строками; свод; свод с раскрытой статьёй; наведение на значок неполноты;
   пустое состояние отказа. Расхождение с макетом — либо правка, либо запись в
   долг с причиной (`AGENTS.md` §11).
6. Карточка тендера без выбора сохраняет прежние факты и суммы (состав решётки,
   три состояния ячейки, «Итого с НДС»); её DOM и тесты меняются из-за
   плиток-переключателей — сохраняются утверждения о фактах, не о разметке.
7. Смешанный случай ставок и `unknown_vat_base` — фикстурами (§1.4); границей в
   devlog записывается, что живых данных под них нет.

## 6. Доказательства

### 6.1. Бэкенд, юнит — чистые функции без БД

Таблично: четыре состояния, включая `removed` по выбранному пути и различие
`absent`/`not_evaluated`; полная матрица §2.6, отдельно — `amount → absent` даёт
`disappeared`, а не `removed`, и `removed → removed` даёт `none`; база процента
трёх знаков (`> 0`, `= 0`, `< 0`) — у величины, чей знак участвует в решении,
тест покрывает оба знака (`AGENTS.md` §11); **деление не вызывается при базе ≤
0** — шпион на делении, утверждение о потоке данных
(`docs/insights/data-flow-assertions-for-order.md`); `direction` трёх состояний,
`flat` при равенстве; «Торг» и «Вклад» при исключённой средней колонке — между
крайними выбранными; `contribution.value = null` при `absent` на конце;
сортировка внутри уровня и закрепление служебных строк; квантование только на
выходе.

### 6.2. Бэкенд, интеграция

Фикстура: тендер, участник с четырьмя раундами, второй участник, смета с
допработами, статья с ручным разносом, второй лот с другим итогом.

- пять отказов §2.3 — каждый своим кодом, каждый **проверен снятием защиты**
  (`docs/insights/verifying-guards.md`), вход нарушает ровно одно ограничение;
- сумма статьи складывает обе ветви VIEW и видит материализованный разнос:
  перенос раздела штатным маршрутом сдвигает свод, `manual_overrides` заполнены;
- три состояния сходимости, включая `null` при неединогласном итоге;
- ось НДС — три случая §2.8: одна ставка → валовые; расхождение → нетто с
  `reason` и перечислением ставок; **«20 % + неизвестная»** → известные
  колонки остаются валовыми, у ячеек неизвестной `amount_unavailable_reason`,
  `change.kind = none` с причиной, состояние ячейки сохранено,
  `track.available` не выключен, слот колонки без `bar_height_pct`; то же с
  неизвестной на нетто-оси; все выбранные неизвестны → `track.available =
  false`, состояния ячеек на месте;
- KPI: последняя колонка — максимальный выбранный `stage_no`; позиции без
  разделов; `categories_with_amount` считает оба знака; `categories_total` — по
  корням; `track.available = false` при неположительном итоге;
- порядок колонок по `stage_no` независимо от порядка в запросе;
- `rows_not_finite` доезжает до ячейки при `NaN` в позиции;
- число SQL-запросов не растёт с числом колонок (образец —
  `test_query_count_does_not_grow_with_selection`).

### 6.3. Фронтенд, vitest

Решётка: плитка только у ячеек со сметой; имя участника выбирает все его этапы;
чужие строки недоступны с подсказкой; кнопка от двух; `aria-pressed` отражает
выбор. Свод: ячейки рендерят состояние **по данным** — `state`, `change.kind`,
`direction`, `amount_unavailable_reason` прибиваются к каждому значению и
проверяются в обе стороны; подпись оси для `gross` и `net` с причиной; три
состояния сходимости; слот `unknown_vat_base`; трасса скрыта при
`track.available = false` с текстом `reason`; пустые состояния по каждому коду
отказа; тест токенов по образцу `src/pages/compare/chartTokens.test.ts` — каждое
имя CSS-переменной компонентов свода существует в `index.css`.

### 6.4. Границы наблюдаемости

Называются в докстроках тестов вместе с напарником на стенде
(`docs/insights/unobservable-in-the-runner.md`): jsdom не считает раскладку —
прокрутка, закреплённая колонка и ширина проверяются только замером (DoD 4);
каскад и тёмная тема — только снимками через `getComputedStyle` (DoD 5);
наведение и раскрытие — снимком **после** взаимодействия (DoD 5); смешанные
ставки и `unknown_vat_base` — только фикстурами (DoD 7).
