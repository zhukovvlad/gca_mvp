# Правка имени поставщика в форме СФ — каноническое переименование с каскадом

**Дата:** 2026-06-15
**Статус:** дизайн утверждён, готов к плану

## Проблема

При редактировании СФ (`PUT /api/invoices/{id}`) правка имени поставщика молча
откатывается, если ИНН совпадает с уже существующим поставщиком. Запрос
возвращает `200`, `commit` проходит — но в БД ложится старое каноническое имя,
а не введённое пользователем.

### Первопричина

В [`update_invoice`](../../../backend/routers/invoices.py) (строки 270–274):

```python
if _name:
    supplier = get_or_create_supplier(db, name=_name, inn=_inn)
    invoice.supplier_id = supplier.id
    invoice.supplier_name = supplier.name   # ← имя НАЙДЕННОГО поставщика, не _name
    invoice.supplier_inn = supplier.inn
```

`get_or_create_supplier` при заданном ИНН ищет **только по ИНН** и для
существующей записи игнорирует аргумент `name` — возвращает поставщика со старым
именем. Хендлер записывает это старое имя обратно в счёт.

Откат срабатывает **только** когда ИНН совпадает с существующим поставщиком.
Без ИНН или с новым ИНН создаётся новая запись и имя сохраняется (этот путь
покрыт `test_update_invoice_links_supplier`).

Текущее поведение задокументировано как намеренное в
[`docs/agent/suppliers.md`](../../agent/suppliers.md) (строка 18): инвариант
«витрина `invoice.supplier_name` = каноническое `Supplier.name`».

## Целевой сценарий

Менеджер правит написание организационно-правовой формы того же контрагента
(«общество с ограниченной ответственностью …» → «ООО …») при неизменном ИНН.
Имя — это ярлык для ИНН; исправление должно закрепиться за поставщиком и
подтянуться во все его счета.

## Решение (вариант A: авто-переименование с каскадом + уведомление)

Когда `get_or_create_supplier` вернул существующего поставщика (ИНН совпал),
но введённое `_name` отличается от `supplier.name` — трактуем это как
исправление канонического имени: обновляем `Supplier.name` и каскадим новое имя
во все счета этого поставщика (та же семантика, что у существующего
`update_supplier`), затем кладём warning в ответ.

### Изменения в коде

Файл: `backend/routers/invoices.py`, функция `update_invoice`.

1. Поднять объявление `warnings: list[dict] = []` **выше** блока поставщика
   (сейчас оно на строке 289, ниже).
2. Заменить блок поставщика:

```python
if _name:
    supplier = get_or_create_supplier(db, name=_name, inn=_inn)
    if _name != supplier.name:
        # ИНН совпал, имя изменилось → каноническое переименование.
        # Каскадим в денормализованную витрину всех счетов поставщика.
        supplier.name = _name
        affected = db.query(Invoice).filter(Invoice.supplier_id == supplier.id).update(
            {Invoice.supplier_name: _name}, synchronize_session=False
        )
        warnings.append({
            "field": "supplier_name",
            "code": "supplier_renamed",
            "message": f"Имя поставщика обновлено во всех счетах ({affected})",
        })
    invoice.supplier_id = supplier.id
    invoice.supplier_name = supplier.name   # теперь == _name
    invoice.supplier_inn = supplier.inn
else:
    invoice.supplier_id = None
    invoice.supplier_name = None
    invoice.supplier_inn = None
```

Без отдельного `commit` внутри блока — используем единый `db.commit()` в конце
хендлера. Поэтому логика `update_supplier` инлайнится, а не вызывается напрямую
(`update_supplier` коммитит сам и преждевременно зафиксировал бы частичные
правки счёта).

### Новые счета (путь парсинга) — изменений не требуется

[`create_invoice`](../../../backend/crud/documents.py) (строки 63–67) уже пишет
в `supplier_name` каноническое `supplier.name` (а не сырой текст из накладной).
Поэтому после переименования любой новый счёт с тем же ИНН автоматически получит
исправленное имя — переименование «закрепляется вперёд». Это свойство усиливает
вариант A и не требует правок.

## Намеренные решения и границы

- **Каскад затрагивает и подтверждённые счета** поставщика — согласуется с
  существующим `update_supplier` (имя — денормализованный ярлык, не финансовые
  данные; нормализация ОПФ не отменяет проверку). Гард `verified` (строка 260)
  по-прежнему защищает редактирование *текущего* счёта.
- **Конфликта уникальности нет**: `uq_suppliers_name_no_inn` — частичный индекс
  только для `inn IS NULL`; у поставщика с ИНН уникальность имени не проверяется,
  переименование в любое значение безопасно.
- **Путь без ИНН вне scope**: ввод нового имени без ИНН по-прежнему
  создаёт/линкует нового поставщика по ветке `inn IS NULL, name == ...`. Это
  существующее ограничение MVP.
- **Фронт без изменений**: канал `warnings` уже отображается тостом в
  [`Review.tsx`](../../../frontend/src/pages/Review.tsx) (строки 273–279).

## Проверка (TDD)

Новый интеграционный тест в `backend/tests/integration/test_invoices.py`:

- Дано: поставщик с ИНН `X` и именем «общество с ограниченной ответственностью Ромашка»,
  два счёта, привязанных к нему.
- Действие: `PUT /api/invoices/{id}` с тем же ИНН `X` и именем «ООО Ромашка».
- Ожидается:
  - `200`;
  - `Supplier.name` == «ООО Ромашка»;
  - `supplier_name` обновлён в **обоих** счетах (каскад);
  - в ответе присутствует warning с `code == "supplier_renamed"`.

Существующие тесты (`test_update_invoice_links_supplier`,
`test_update_invoice_clears_supplier_when_name_empty`,
`test_update_invoice_inn_without_name_returns_422`) должны продолжать проходить.

## Документация

Обновить [`docs/agent/suppliers.md`](../../agent/suppliers.md) (строка 18): при

каскадится во все его счета (warning `supplier_renamed` в ответе), вместо отката
к старому значению.
