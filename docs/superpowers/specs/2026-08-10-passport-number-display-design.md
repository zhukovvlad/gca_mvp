# Ф6a: показ вычисленных чисел в паспорте проекта — дизайн

**Ветка:** `fix/passport-number-display`.
**Фаза:** 7, [рамка](../../phase7-frame.md) — правка по следам Ф6, как Ф4a была
правкой по следам Ф4.
**Источник дизайна:** макет, утверждённый на гейте 1 Ф6 —
[2026-08-09-project-passport-mockup.html](2026-08-09-project-passport-mockup.html),
и спека Ф6 [2026-08-10-project-passport-design.md](2026-08-10-project-passport-design.md)
§2.6, §2.9. Новых доменных решений здесь нет — спека **тонкая** (§9.1 `AGENTS.md`):
источник плюс дельта.

Ф6 довела до экрана числа, которые считает сервер. Два из них доезжают до
пользователя в виде, которого не предполагали ни макет, ни спека, и оба нашлись
на живом стенде, а не тестами. Это дефект показа: сами величины верны, врёт их
изображение.

---

## 1. Замеры

Все три замера сняты со стенда `gca_dev` (парсер 3.1.0, три исходные сметы),
чтением, без изменения данных. Числа ниже — форма, а не суммы: реальные величины
в документы не переносятся (DoD фазы, политика `samples/`).

### 1.1. `per_sqm` приезжает с 22 знаками после запятой

`_per_sqm` делит `Decimal` на `Decimal`, и контекст Python даёт 28 значащих
цифр. Замер частного на реальной паре «сумма ÷ площадь»: **22 знака после
запятой**. `MoneyCell` в паспорте вызван **без** `maxFractionDigits`, а
`formatDecimalMoney` без него значащие цифры не округляет намеренно
(докстрока: «показать 1 075,35 вместо утверждённой ставки 1 075,35475 значило бы
соврать о цифре, по которой идёт торг»). Прогон настоящих функций показа на
снятых со стенда значениях:

```
per_sqm  <22 знака>  ->  [<целая часть>,<22 знака> ₽]
```

Правило для этого случая **уже существует и записано** — в докстроке самого
[`MoneyCell`](../../../frontend/src/components/ui-domain/MoneyCell.tsx):
округление обязательно «только для вычисленных величин», где лишние знаки —
артефакт деления. Матрица его соблюдает (`maxFractionDigits={2}`), паспорт —
четыре новые точки вызова — нет. То есть это не новое правило, а старое,
не прогнанное по новым входам ([replaying-new-rules](../../insights/replaying-new-rules.md),
слой 2).

**Охват.** Видно на одном договоре из трёх — на том единственном, у чьего объекта
заведены ТЭП; у двух других `per_sqm` пуст, и дефект **латентен**: заполнение
площадей (ровно то, ради чего сделана Ф5) немедленно проявит его и там. 13 из 21
корневой строки таблицы, плюс показатель «Стоимость за м²» в шапке, плюс строка
«Итого по договору».

### 1.2. Ноль от деления приезжает в экспоненциальной записи

Замер:

```
Decimal('0') / Decimal('50000.00')         ->  Decimal('0E+2')
str(...)                                   ->  '0E+2'
format(..., 'f')                           ->  '0'
format(Decimal('10.00'), 'f')              ->  '10.00'   (не меняется)
```

Python сохраняет «идеальную экспоненту» частного, `_decimal_encoder`
([responses.py](../../../backend/responses.py)) отдаёт `str(obj)`, и в JSON
уезжает `"0E+2"`. Фронтовая `DECIMAL_RE` объявлена как `-?цифры[.цифры]`,
E-нотацию не разбирает и по своему сознательному правилу «неожиданный формат
отдаём как есть, чтобы не спрятать пришедшее с сервера» печатает вход дословно:

```
per_sqm  0E+2  ->  [0E+2 ₽]
share    0E+2  ->  [0E+2 %]
```

**Охват — все три договора**, счётом значений в ответе: 31 + 31, 6, 21. На
договоре с ТЭП видно **сразу**, без единого действия: корневые строки таблицы
переключатель «показывать нулевые подстатьи» не фильтрует (фильтр стоит только на
детях), и три корневые статьи с нулевой суммой печатают `0E+2` в обеих колонках.
На двух других — при раскрытии узла или включённом переключателе.

Источник — только вычисления Python. `numeric` из PostgreSQL в E-нотации не
приходит, поэтому хранимые деньги (`total`, `own`, `amount`) этим не задеты; задеты
ровно два вычисляемых поля, `share_pct` и `per_sqm`, и только когда числитель —
точный ноль.

### 1.3. Доля не добивается до двух знаков, и форматтеров доли ДВА

`roundDecimal(value, 2)` **возвращает вход без изменений**, когда знаков и так не
больше двух (`if (fraction.length <= digits) return value`). Макет, утверждённый
на гейте 1, форматирует долю через `nf2 = { minimumFractionDigits: 2,
maximumFractionDigits: 2 }`, то есть обещает ровно два знака всегда.

Форматтеров доли в паспорте **два, независимых и с одинаковым телом**:
`formatSharePct` в [`CategoryTable`](../../../frontend/src/pages/passport/CategoryTable.tsx)
(таблица) и `formatShareText` в [`StructureRing`](../../../frontend/src/pages/passport/StructureRing.tsx)
(легенда кольца). Первая редакция этой спеки чинила только табличный — пробел
найден внешним ревью на гейте 2 и подтверждён по коду. Показательно, что пробел
**создан самой дубликацией**: два экземпляра одного правила расходятся ровно
тогда, когда правят один.

Замер настоящих функций (`roundDecimal`, `addDecimalStrings`) на долях, снятых со
стенда, даёт **три независимых пути** к дефекту в легенде:

```
zero share TODAY      -> 0E+2 %          (путь §1.2)
zero share AFTER FIX  -> 0 %             (нужно 0,00 %)
trailing-zero sum     -> 1,1 %           (нужно 1,10 %)
```

Третий путь — самостоятельный и достижим **уже сегодня, без нулевых статей и без
всяких правок**: долю «Остальных статей» кольцо считает суммой через
`addDecimalStrings`, а тот срезает хвостовые нули
([decimal.ts](../../../frontend/src/lib/decimal.ts), `fraction.replace(/0+$/, "")`).
Сумма долей, оканчивающаяся нулём во втором знаке, печатается одним знаком —
«1,1 %» в легенде рядом с «12,72 %».

То есть добивание до двух знаков — не косметика на будущее: один путь живой
сейчас, второй открывается правкой §2.1.

### 1.4. Живой дефект: процент «Остальных статей» гаснет целиком

`addDecimalStrings` на входе `"0E+2"` не разбирает строку и возвращает `null`, а
свёртка в `buildSlices` по первому же `null` гасит **всю** сумму, и легенда
опускает процент. Замер на реальном составе «Остальных» одного из договоров
стенда (восемь статей, три из них с нулевой суммой):

```
rest TODAY     -> sum=null  text=null     (процента в легенде НЕТ вовсе)
rest AFTER FIX -> sum=5.05…  text=5,05 %
```

Это не гипотеза и не следствие будущей правки: **на стенде процент у «Остальных
статей» не показан прямо сейчас**, и причина — тот же `0E+2`. Правка §2.1 его
чинит; спека фиксирует это как наблюдаемое следствие, которое обязано быть
закреплено тестом, а не как приятную неожиданность.

Замерять это пришлось дважды: первый пробник печатал успокаивающий `0` вместо
числа нулевых долей, потому что искал признак в словаре, а не в значении поля
([false-test-premises](../../insights/false-test-premises.md) — предпосылка
пробника оказалась ложной, и видно это было только по выводу самих данных).

## 2. Решение

Три правки. Гейт 1 пройден в диалоге; выбор слоя для §2.1 и точности для §2.2 —
решения пользователя, зафиксированные здесь.

### 2.1. Нормализация приходит в энкодер, на бэкенд

`_decimal_encoder` отдаёт `format(obj, 'f')` вместо `str(obj)`.

Выбран **бэкенд**, а не разбор E-нотации на фронте: контракт «деньги — строки
вида `-?цифры[.цифры]`» обещает бэкенд, он же его и нарушает, а чинить на фронте
значило бы лечить следствие — следующий потребитель (Excel-выгрузка, новый экран)
наступил бы снова. Правка одна и общая для всех эндпоинтов.

Отвергнуто: **оба слоя** (defense in depth) — после правки энкодера случай на
фронте не воспроизводится ничем, и вторая защита была бы непроверяемой снятием.

Граница правки, названная явно: `format(x, 'f')` меняет изображение **только**
значений в экспоненциальной записи; замер §1.2 показывает, что обычные суммы со
шкалой (`10.00`) не меняются. Проверяется прогоном всего backend-набора, а не
рассуждением: энкодер общий, через него идёт каждый ответ с деньгами.

### 2.2. `per_sqm` округляется на слое показа, до двух знаков

`maxFractionDigits={2}` на четырёх точках вызова `MoneyCell`: строка статьи,
строка «Нераспределённое», строка «Итого по договору», показатель «Стоимость за
м²» в шапке. Точное значение остаётся доступным — `MoneyCell` кладёт его в `title`
сам, и только когда округление действительно что-то изменило.

Округление стоит **на слое показа, а не в CRUD**: то же правило, что §4
`AGENTS.md` держит для `deviation_pct` («точный Decimal, округление только на слое
представления»). Сервер продолжает отдавать точную величину.

Отвергнуто: **целые рубли, как в макете** (`nf0`). Макет действительно задаёт для
₽/м² ноль знаков, но `formatDecimalMoney` печатает копейки всегда — сознательное
правило («Копейки показываем всегда»), — поэтому `maxFractionDigits={0}` дал бы не
«N ₽», а «N,00 ₽» (проверено разбором кода: при `digits = 0` дробная часть пуста и
тут же добивается до `«00»`), и ради вида макета пришлось бы править общую
функцию, которой пользуются матрица, договоры и нормативы. Решение пользователя —
два знака и общий форматтер не трогать; отступление от макета осознанное и
названо здесь.

### 2.3. Доля добивается до ровно двух знаков — в ОБОИХ форматтерах

Доля печатается ровно двумя знаками после запятой (`minimumFractionDigits: 2`
макета) **и в таблице, и в легенде кольца**. Оба места — §1.3.

`roundDecimal` остаётся как есть: его контракт («не больше `digits` знаков»)
верен, добивание до ровно двух — забота вызывающего, у которого колонка.

**Общий помощник, а не две правки по месту.** В проекте есть сознательное правило
держать трёхстрочные копии по месту использования (`isZeroDecimal` живёт тремя
экземплярами с объясняющим комментарием), и первая редакция спеки собиралась ему
следовать. Здесь оно отменяется — не вкусом, а замером §1.3: пробел найден
ревью **именно потому**, что копий две и правка одной их разводит. Заводится один
`formatSharePercent(value: string): string` в `lib/format.ts` — «decimal-строка →
`«N,NN %»`»; обработка `null` остаётся на месте вызова, потому что она у двух
экранов **разная и должна такой остаться**: таблице нужен прочерк в колонке,
легенде — опустить процент вовсе (правило 5 §2.10 спеки Ф6). Общим становится
ровно то, что у них общее.

**Наблюдаемое следствие §2.1, закрепляемое здесь:** после нормализации процент у
«Остальных статей» в легенде **появляется там, где сегодня его нет** (§1.4). Это
часть DoD и требует своего теста; молча «само починилось» — недопустимая форма
для правки, которая меняет то, что видит пользователь.

## 3. Что сознательно НЕ делается

1. **`_share_pct` и `_per_sqm` не квантуются на сервере.** Округление — слой
   показа (§2.2); сервер отдаёт точное, потребитель решает, сколько показать.
2. **`formatDecimalMoney` и `roundDecimal` не трогаются вовсе** — решение
   пользователя (§2.2). Их поведение «копейки всегда» и «вход короче `digits`
   возвращается как есть» остаётся контрактом. В `lib/format.ts` только
   **добавляется** `formatSharePercent` (§2.3); существующие функции и их тесты
   остаются как есть, и это проверяется тем, что ни один их тест не меняется.
3. **Прочие потребители энкодера не пересматриваются.** Правка §2.1 их чинит
   заодно там, где было что чинить, но охота за другими местами показа вне скоупа.
4. **Дефект `_money` с `NaN`/`Infinity`** — хвост Ф4, в силе, этой фичей не
   закрывается.

## 4. DoD фичи

- ₽/м² в паспорте показан двумя знаками во всех четырёх местах; точное значение
  доступно в `title`.
- **Ни одно `Decimal`-поле ответа не уезжает в экспоненциальной записи** —
  проверено **сплошным прогоном по всем трём договорам стенда**, а не по одному.

  Формулировка «нет строки с `E`» отвергнута как негодная (находка ревью на гейте
  2): латинская `E` законна в тексте, и наименования статей и смет её несут —
  проверка красила бы честные данные. Признак берётся **по типу, а не по тексту**:
  обход словаря, который вернул `get_project_passport`, отбирает значения
  `isinstance(value, Decimal)`. Тип не подделывается наименованием, и перечень
  полей от этого не устаревает при добавлении нового.

  **Утверждение делается о результате настоящего `_decimal_encoder(value)`, а не
  о самом `Decimal`** (вторая находка ревью на гейте 2). Причина в том, что
  правка §2.1 меняет только сериализацию: в словаре CRUD значение остаётся
  `Decimal('0E+2')` и после неё. Замер по 407 `Decimal`-листьям одного паспорта
  показывает, что выбор признака решает, живая проверка или мёртвая:

  | Критерий | Нарушений сейчас | После правки §2.1 |
  |---|---|---|
  | `str(value)` | 62 | **62** — словарь не меняется, критерий красен навсегда |
  | `format(value, 'f')` | 0 | 0 — **зелен и при снятой защите**, то есть ничего не стережёт |
  | `_decimal_encoder(value)` | 62 | **0** — переключается ровно правкой |

  Годен только третий: он и краснеет при возврате `str(obj)`, и зеленеет от самой
  правки. Это тот же слой 7 [verifying-guards](../../insights/verifying-guards.md)
  («не валит ничего → защиты нет»), пойманный до написания теста, а не снятием
  после.

  **Парный критерий на уровне API:** те же пути в **отрендеренном**
  `DecimalJSONResponse` эндпоинта. Проверка через `_decimal_encoder` доказывает,
  что энкодер верен, но не то, что эндпоинт им пользуется; парная — что ответ
  доезжает до клиента нормализованным. Обе нужны, и ни одна не заменяет другую.
- Доля печатается ровно двумя знаками, включая ноль, **и в таблице, и в легенде
  кольца**.
- Процент «Остальных статей» в легенде показан там, где сегодня гаснет (§1.4), —
  отдельным тестом.
- Каждая правка закреплена тестом, и **каждый тест проверен снятием защиты**
  ([verifying-guards](../../insights/verifying-guards.md)) — с контрольным
  прогоном до снятия и восстановлением из побайтовой копии.
- `just ci` зелёный целиком; backend-набор прогнан **весь** — энкодер общий.
- Замер в браузере на живом стенде: колонки ₽/м² и «Доля» на договоре с ТЭП,
  **легенда кольца — включая строку «Остальные статьи (N)» и её процент**, плюс
  раскрытое дерево на договоре без ТЭП (там живут нулевые доли). Легенда в этот
  список добавлена ревью гейта 2: замер Ф6 её проценты не смотрел, и живой дефект
  §1.4 поэтому доехал до стенда.
