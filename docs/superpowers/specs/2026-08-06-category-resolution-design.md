документов. Границы зоны позиций брались **продакшен-хелперами** парсера

(§4.1), а не на файле.

### 1.2. Уточнение факта брифа: «4.3 Металлоконструкции» — не пробел

Бриф §2 называет раздел `4.3` в 159-ТУ «настоящим пробелом», который «остаётся
без привязки», и его DoD §8 требует тест «пробел `4.3` → нераспределённое».
**Замер это опровергает.** У `4.3` действительно нет своей статьи, но её имеет
родитель `4`, поэтому `4.3` наследует «4», и её позиции (через `4.3.1`, четыре
позиции) ложатся в статью «4». Тест из брифа утверждал бы неправду.

Настоящие пробелы в 159-ТУ — строка лота, `10` и `10.4`, и **у всех трёх ноль
прямых позиций**, поэтому по деньгам «Нераспределённое» в 159-ТУ и 42-ТУ пусто.
Настоящий пробел с деньгами есть в 449-ТУ и в fixture: верхний раздел
`14 SHELL & CORE` со всем поддеревом и `15 Рабочая документация` идут без статьи
вовсе — 39 разделов, 38 позиций. Тест «Нераспределённое» строится на нём.

Побочное следствие решения §2.6: в 159-ТУ «Нераспределённое» будет содержать
ровно одну строку — агрегатную строку допработ.

### 1.3. Замеры по коду (а не по файлам)

1. **`is_chapter` не является независимым признаком:** он равен
   `bool(raw chapter_number)`
   ([postprocess.py:267](../../../backend/parser/postprocess.py#L267)). На
   измеренных строковых цифровых номерах это совпадает с наличием номера;
   расхождения на `0` и на пробельной строке закрывает §2.3. То есть развилка
   «`is_chapter` или наличие № раздела» ставилась не там, где дырка: выбирать
   между двумя именами одного предиката незачем, а согласованность имён надо
   проверять.
2. **`bool()` парсера и нормализованный предикат расходятся на двух входах:**
   `bool(0)` ложно, а `norm(0)` = `"0"` непусто; `bool(" ")` истинно, а `norm(" ")`
   пусто. Отсюда проверка согласованности §2.3.
3. **Позиции вставляются одним `add_all` + одним `flush`**
   ([estimate_import.py:734](../../../backend/services/estimate_import.py#L734)):
   id известны только после flush, поэтому «вставка по ходу прохода» означала бы
   flush на каждую из 2576 строк.
4. **`updated_at` — серверный `onupdate=now()`**
   ([models.py:37](../../../backend/models.py#L37)), а `now()` в PostgreSQL — время
   **начала транзакции**. Второй проход внутри той же транзакции не оставляет
   наблюдаемого следа: после commit `updated_at` равен `created_at`. Тот же факт
   лежит в основе разбора вакуозного `test_update_moves_updated_at`
   ([false-test-premises.md](../../insights/false-test-premises.md)).
5. **Порядок `position_items.id` контрактом не является**: ни один
   продакшен-запрос не сортирует по нему (сортировки по `id` есть только в двух
   тестах матчинга). Решение §2.8 его тем не менее не портит, но опираться на него
   в аналитике нельзя — Ф6 сортирует по явному порядку строки.
6. **Частичные индексы в этом проекте декларативны.**
   [phase2-schema.md §2](../../phase2-schema.md) прямо говорит, что
   `Index(..., postgresql_where=...)` Alembic выражает декларативно, такие индексы
   остаются в `Base.metadata`, и raw SQL здесь **был бы шагом назад — индекс выпал
   бы из детектора дрейфа**. В 0002 четыре частичных индекса сделаны через
   `postgresql_where=sa.text(...)`; `op.execute` оставлен COALESCE-уникальным,
   partial UNIQUE, EXCLUDE, хэш-выражению и VIEW.
7. **Место создания резолвера** — [import_pipeline.py:243](../../../backend/services/import_pipeline.py#L243),
   внутри транзакции сессии B, рядом с `UnitResolver(db)`.
8. **Составной self-FK ведёт себя как одноколоночный — замерено отдельно, на PG
   16.14.** Эксперимент брифа §3 проверял **одноколоночный** self-FK, а
   `(proposal_id, chapter_item_id) → (proposal_id, id)` — другой объект, поэтому
   все четыре факта сняты заново на scratch-таблицах: (а) каскад от `proposals`
   сносит все строки предложения, `RESTRICT` ему не мешает — то есть replace-флоу
   работает; (б) поперечная ссылка на строку **чужого** proposal отвергается
   `ForeignKeyViolation`; (в) точечное удаление строки-раздела, на которую
   ссылаются, упирается в `RESTRICT`; (г) одиночный `DELETE`, сносящий раздел
   **вместе** с его позициями, проходит. Партия детей в пробнике — 12 строк, то
   есть через порог `prepare_threshold`
   ([batch-larger-than-five.md](../../insights/batch-larger-than-five.md)).
   Побочно подтверждено: `chapter_item_id IS NULL` ограничение не нарушает —
   у FK по умолчанию `MATCH SIMPLE`, и NULL в любой из колонок пропускает проверку
   (`proposal_id` — `NOT NULL`, так что NULL бывает только у второй).
9. **Левый префикс работает: `UNIQUE (proposal_id, id)` обслуживает поиск по
   `proposal_id`.** Замерено на таблице в 60 000 строк: `WHERE proposal_id = …`
   идёт `Bitmap Index Scan` по составному уникальному индексу **при включённом**
   `enable_seqscan`, то же для `count(*)`. На пробнике в 15 строк планировщик
   выбирал `Seq Scan` — то есть маленькая таблица этот факт не показывает вовсе, и
   первый замер был непригоден.

## 2. Решения

### 2.1. Миграция 0006 — четыре колонки и три инварианта

Стиль 0001–0004: CHECK на всё непредставимое, литералы строками (миграция
неизменна во времени — константы из кода не импортируются, капкан `UNITS_SEED`
в 0001), явный `downgrade`, круговой рейс `downgrade base → upgrade head`
прогоняется, а не объявляется.

```
position_items +=
  smr_article_raw   Text        NULL   -- «Статья СМР» как в файле, только на разделах
  work_category_id  BigInteger  NULL   -- FK work_categories(id) ON DELETE RESTRICT
  category_source   Text        NULL
  chapter_item_id   BigInteger  NULL   -- цель задаёт СОСТАВНОЙ self-FK ниже

uq_position_items_proposal_id_id
  UNIQUE (proposal_id, id)            -- ЗАМЕНЯЕТ idx_position_items_proposal_id
fk_position_items_chapter
  FOREIGN KEY (proposal_id, chapter_item_id)
    REFERENCES position_items (proposal_id, id) ON DELETE RESTRICT

ck_position_items_article_only_on_chapters
  is_chapter OR (smr_article_raw IS NULL AND work_category_id IS NULL
                 AND category_source IS NULL)
ck_position_items_category_source_pairs
  (work_category_id IS NULL) = (category_source IS NULL)
ck_position_items_category_source
  category_source IS NULL OR category_source = 'file'

idx_position_items_work_category_id  WHERE work_category_id IS NOT NULL
idx_position_items_chapter_item_id   WHERE chapter_item_id  IS NOT NULL
```

Имена по соглашению проекта: `ck_<таблица>_<что>`, `idx_<таблица>_<колонки>`,
`uq_<таблица>_<колонки>`. FK в `ALTER TABLE` именуются **явно** —
`fk_position_items_work_category_id` и `fk_position_items_chapter`: иначе
`alembic check` и `downgrade` опирались бы на автогенерируемые имена.
**Одиночный FK `chapter_item_id → position_items.id` не создаётся** — составной
проверяет и существование цели, и совпадение proposal; второй FK по тем же
колонкам был бы дублирующей проверкой.

Оба индекса — **декларативные**: `op.create_index(..., postgresql_where=sa.text(...))`
в миграции и зеркальный `Index(..., postgresql_where=...)` в `__table_args__`
модели (§1.3 факт 6). `op.execute` в 0006 не нужен вовсе.

**Почему `work_category_id` — `ON DELETE RESTRICT` явно.** Бриф этого не
оговаривал. Без `SET NULL` удаление и так не обнулило бы ссылку молча, поэтому
ценность явного `RESTRICT` — в запрете и документировании: удалить статью, на
которую ссылаются деньги, нельзя, и это видно в схеме. Согласуется с
`work_categories.parent_id` из Ф1.

**Почему `chapter_item_id` — `ON DELETE RESTRICT`.** Проверено экспериментом на
PG 16.14 (бриф §3): каскад `proposals → position_items` сносит все строки одним
оператором, self-FK-проверка выполняется по его завершении и replace-флоу не
мешает; а точечное удаление строки-раздела, на которую ссылаются, даёт громкую
ошибку FK вместо тихого каскадного уноса позиций и подразделов.

**Инвариант `chapter_item_id`: половины неравноценны, и защищаются по-разному.**

- **«Тот же proposal» — держит схема.** Составной FK `(proposal_id,
  chapter_item_id) → (proposal_id, id)` делает межсметную привязку
  **непредставимой**, а не «обычно не возникающей». Это тот же довод, которым Ф1
  сделала `is_bucket` generated-колонкой: ложь должна быть невозможна, а не
  отвергаема ревью. Гарантия построением (карта `key → PositionItem` живёт один
  вызов на один proposal, §2.8) остаётся, но перестаёт быть единственной.
- **«Цель — строка-раздел» декларативно не выражается вовсе:** подзапросы в CHECK
  запрещены, остался бы триггер. Триггер ради этого не вводится — половина держится
  резолвером и тестом (§4.2).

**Цена составного FK — ширина индекса, а не лишний индекс.** `UNIQUE (proposal_id,
id)` **заменяет** существующий `idx_position_items_proposal_id`: `proposal_id` —
его левый префикс, и это замерено, а не выведено из общего правила (§1.3 факт 9).
То есть в 0006 один индекс уходит, один приходит, и поиск по `proposal_id`
продолжает идти индексом.

ORM зеркалит `UniqueConstraint` и `ForeignKeyConstraint` с теми же именами.

Поведение составного FK под `RESTRICT` замерено отдельно от одноколоночного
эксперимента брифа (§1.3 факт 8): каскаду replace-флоу не мешает, поперечную ссылку
отвергает, точечное удаление ссылаемого раздела запрещает, NULL-родителя пропускает.

`downgrade` снимает добавленные индексы, констрейнты и колонки и
**восстанавливает** `idx_position_items_proposal_id` — иначе откат оставил бы
таблицу без индекса по `proposal_id`. Защитного отказа, как в 0003, не требуется:
данные новых колонок производные. Но обещать «всегда восстановимо
перезагрузкой файла» нельзя — сохранённый XLSX может уже уйти по ретенции (§8
AGENTS.md). Точная формулировка: значения выводятся из неизменяемого
`estimate_raw_data.raw_data`, который содержит `article_smr` по каждой строке,
поэтому их можно пересчитать повторным импортом при наличии файла либо отдельным
перерасчётом из raw JSON (в Ф3 такой перерасчёт не делается).

ORM `PositionItem` зеркалит **всё**: четыре колонки с их nullable-семантикой, три
CHECK, оба явно именованных FK и оба частичных индекса с теми же именами и
`postgresql_where`. Иначе `just db-test-check` (`alembic check`) покажет дрейф — а
у Ф3, в отличие от Ф2, миграция есть, и дрейф реален.

### 2.2. Модуль и интерфейс

Новый `backend/services/category_resolution.py` по образцу
[unit_resolution.py](../../../backend/services/unit_resolution.py): справочник
читается один раз, разрешение идёт в памяти, резолвер передаётся в
`import_estimate` параметром.

```python
CategoryRef        = (id, title)          # title — каноническое название справочника
RowResolution      = (position_key, kind, parent_position_key,
                      smr_article_raw, work_category_id, category_source)
                     # kind ∈ {chapter, position, outside_structure} (§2.3)
ProposalResolution = (rows: dict[str, RowResolution], warnings: list[str],
                      structure_disabled: bool, counters: ResolutionCounters)
                     # counters: chapters_own, chapters_inherited, chapters_unassigned,
                     #           positions_unassigned, rows_outside_structure

class CategoryResolver:
    def __init__(self, by_code: Mapping[str, CategoryRef]) -> None: ...
    @classmethod
    def from_db(cls, db: Session) -> "CategoryResolver": ...   # один SELECT, 362 строки
    def resolve_proposal(self, positions: Mapping[str, Mapping[str, Any]]) -> ProposalResolution: ...
```

**Осознанное отступление от прецедента:** у `UnitResolver` конструктор берёт
`Session`, из-за чего его тесты обязаны быть интеграционными. Здесь конструктор
берёт готовую карту, а `from_db` — фабрика. Тогда алгоритм стека, единственная
по-настоящему нетривиальная часть Ф3, проверяется юнит-тестами на входах из
нескольких строк, без БД и без xlsx.

`resolve_proposal` не принимает ORM-объекты, не знает `Session` и в БД не пишет.
**Warnings и счётчики возвращаются результатом, а не копятся в состоянии
объекта** — поэтому один экземпляр безопасно обслуживает все proposal сметы.

**Порядок обхода.** Ключи `positions` — контракт парсера «1..N»
(`get_lot_positions` нумерует подряд). Резолвер **валидирует каноническую
непрерывную последовательность**: множество ключей равно `{"1", …, "N"}`.
Проверки «приводится к `int`» недостаточно — `"1"` и `"01"` дают одно число.
Нарушение — явная ошибка контракта парсера, а не тихий фолбэк на порядок
словаря: фолбэк дал бы правдоподобную, но чужую структуру. Порядок ключей во
входном `Mapping` произволен (в `raw_data`, который JSONB, он не сохраняется);
обход — численный по ключу, как в `postprocess.annotate`.

### 2.3. Классификация строки и проверка согласованности

Парсер вычисляет `is_chapter` через `bool()` сырого значения ячейки, а пустоту A и
B определяет своим предикатом `cell_text_is_blank`. Нормализованный предикат
расходится с `bool()` на двух входах (§1.3 факт 2). Расхождение не косметическое:
если резолвер сочтёт разделом строку, у которой в БД окажется `is_chapter = false`,
запись полей статьи **уронит весь импорт** о
`ck_position_items_article_only_on_chapters`.

Поэтому расхождение трактуется как **конфликт структуры и включает деградацию D**
(§2.4). Конфликт — любое из трёх:

1. A и B пусты, но `is_chapter = true`;
2. нормализованный B непуст, но `is_chapter = false` (случай числового `0`);
3. `is_chapter = true`, но нормализованный B пуст.

Порядок условий ничего не перекрывает молча: сначала проверка согласованности по
всему proposal, и только на согласованном входе — классификация:

1. **A и B пусты** (предикат парсера) → **строка вне структуры** (§2.6);
2. **`is_chapter = true`** → **строка-раздел**;
3. иначе → **строка-позиция**.

Настоящая агрегатная строка допработ согласована (A и B пусты,
`chapter_number = None` → `is_chapter = false`) и идёт ветвью 1. Класс «вне
структуры» гарантирован сверху: парсер такую строку либо признал агрегатной
«Дополнительные работы», либо уже отказал (`EstimateParseError`, спека Ф2 §2.2).

В корпусе конфликтов нет (B во всех четырёх файлах — всегда `str`), то есть
проверка защитная; но её поведение задано спекой, а не оставлено реализации.

### 2.4. Две фазы: валидация, затем стек

**Фаза 1 — валидация всего proposal.** Проверяются: согласованность (§2.3) и
формат номера каждой строки-раздела — нормализованный `chapter_number` против
`^\d+(\.\d+)*\.?$`. Хотя бы одно нарушение → `structure_disabled = True`:

- строки сметы сохраняются полностью, ни одна не теряется;
- `smr_article_raw` у разделов сохраняется как аудит;
- `chapter_item_id`, `work_category_id`, `category_source` остаются NULL **по
  всему proposal**;
- импорт завершается **успешно**, с предупреждением.

Частичной структуры не бывает: половина сметы с привязкой и половина без дала бы
паспорт, правдоподобный ровно настолько, насколько неверный.

**Почему не «вложить в текущую вершину» (глубина = глубина вершины + 1).**
Физический порядок строк сообщает только, что строка встретилась после текущего
раздела. Он не сообщает ни её глубину, ни момент окончания её области действия.
Догадка о глубине — это догадка не об одной строке, а обо **всей области**: она
молча меняет привязку всех последующих строк, а не только своей. Warning этого не
лечит. И «§5 требует не падать» на этот случай не распространяется: там
деградация описана для неизвестного кода статьи и отсутствующего предка, но не
для неразбираемой структуры.

**Фаза 2 — стек (только при успехе фазы 1).**

Глубина строки-раздела = число сегментов её номера после срезания завершающей
точки. Раздел глубины N **вытесняет из стека всё с глубиной ≥ N**. Родитель =
вершина стека **после** вытеснения.

Родителя, таким образом, определяют **совместно** физический порядок и глубина:
глубина управляет вытеснением, родителем становится оставшаяся вершина. Без
корректной глубины область действия раздела неизвестна — это и есть причина D.
Скачок глубины (ребёнок глубже родителя больше чем на 1; в корпусе — ноль
случаев) особой обработки не требует: он влияет на то, сколько будет вытеснено, а
не порождает выдуманного родителя.

Статья раздела вычисляется **в момент помещения в стек** и хранится в записи
стека как «эффективная» — тогда наследование стоит O(1) и не требует проходов
вверх:

- `article_smr` пуст → эффективная = эффективная вершины стека (наследование),
  либо NULL при пустом стеке;
- `article_smr` непуст, код разобран и найден в `work_categories` → эффективная =
  он; название сверяется (§2.5), расхождение — warning, не блок;
- `article_smr` непуст, но код **неизвестен** либо префикс **не разбирается в
  код** → эффективная = NULL + warning (§2.5).

Строка-позиция: родитель = вершина стека (либо NULL), поля статьи не заполняются.
Строка вне структуры: родитель = NULL, в стек не помещается и из него ничего не
вытесняет.

Строка самого лота — раздел глубины 1 без статьи; её вытесняет первый настоящий
раздел «1», после чего стек пуст и у этого раздела `chapter_item_id = NULL`
(§1.1).

### 2.5. Код, название и правило «утверждение файла сильнее наследования»

**Что кладётся в `smr_article_raw`:** значение ячейки C, обрезанное по краям, пустое
→ NULL (то же преобразование `_text`, которым импорт кладёт остальные текстовые
поля). Полная сырая форма, включая внутренние переносы, всё равно остаётся в
неизменяемом `raw_data`.

**Код статьи:** префикс до первого пробела нормализованного значения, формат
`^\d+(\.\d+)*\.?$`, завершающая точка срезается. Покрывает оба формата оферты —
`14.99. Прочее (MR Base)` и код без завершающей точки. Дефект формата шаблона
(`(6.6 .)`, пробел внутри кода) к Ф3 не относится: он погашен Ф1 при построении
карты, и резолвер получает канонический `6.6`.

**Название:** остаток значения после первого пробела; сравнивается с каноническим
названием из справочника в нормализованной форме — схлопнутые пробелы и
`casefold`. Расхождение → warning с **обоими** текстами. Значение из одного кода
без названия сверять не с чем — предупреждения нет. Расхождения ожидаемы: бриф §2
насчитал 10 уникальных кодов с опечатками на трёх файлах.

**Правило: утверждение файла сильнее наследования.** Если `article_smr` непуст, но
код неизвестен или префикс не разбирается, эффективная статья = NULL, а **не**
статья предка. Файл говорит «здесь статья X»; если X прочитать нельзя, подставить
статью предка значило бы отнести деньги к статье, которую файл для этой строки не
называл. Следствие честное и громкое: такой раздел и всё его поддерево без своих
кодов уходят в «Нераспределённое» с предупреждением. Инвариант суммы при этом
держится — деньги не теряются, они видимы. Наследование срабатывает **только**
когда файл про статью молчит.

Автосоздание статей запрещено (бриф §2): неизвестный код лечится справочником или
файлом, а не выдумыванием строки классификатора.

### 2.6. Агрегатная строка допработ: `chapter_item_id = NULL`

Строка «Дополнительные работы» имеет пустые A и B, поэтому `is_chapter = false` и
для импорта она обычная позиция — то есть по умолчанию получила бы
`chapter_item_id` последнего раздела стека («Рабочая документация» в 159-ТУ), и её
деньги легли бы в чужую статью.

**Решение: строка вне структуры не привязывается — `chapter_item_id = NULL` плюс
агрегированный warning.** Формулировка структурная и не упоминает названия:
привязка требует, чтобы строка стояла в структуре файла; строка без номера
позиции и без номера раздела в структуре не стоит. `chapter_item_id` означает
фактическую структурную принадлежность, а у такой строки её нет — присвоить
последний раздел значило бы материализовать заведомо ложный факт.

Множество, которое это правило начинает судить, замерено заранее (инсайт
[replaying-new-rules.md](../../insights/replaying-new-rules.md), слой 2): строк с
пустыми A и B — `0 / 1 / 0 / 0` по fixture и трём офертам, и единственная — ровно
агрегатная (замер Ф2, подтверждён здесь заново, §1.1).

Чего решение **не** делает:

- **не устраняет двойной счёт.** Строка остаётся `position_item` со своими
  деньгами, а `raw_data.additional_works` содержит их копию — `raw_data`
  неизменяем. Обязательство Ф4 (рамка фазы; спека Ф2 §7) в силе целиком: доменная
  запись по `additional_works` создаётся только с атомарным удалением этой
  позиции, сверка — с независимым ИТОГО файла, потому что инвариант «паспорт =
  позиции + допработы» двойного счёта не поймает (обе стороны вырастут одинаково);
- **не меняет допуск строки к каталожному матчингу.** Сегодня она в каскад
  попадает и получает каталожную строку `TO_REVIEW`. Это существующее поведение,
  Ф3 его не касается — объявлено границей (§5).

Выгода в том, что при любом сдвиге порядка последующих фич такая сумма попадёт в
«Нераспределённое», а не в правдоподобную чужую статью (о видимости — §7: до Ф6
потребителя привязки нет вовсе).

### 2.7. «Статья СМР» на строке-НЕразделе

Замер: ноль случаев во всех четырёх файлах. Решение защитное: значение **не
материализуется** (`smr_article_raw` живёт только при `is_chapter = true`), в
резолве не участвует, и выдаётся агрегированный warning с количеством и
ограниченным списком примеров.

**Аудит от этого не страдает** — ключевой довод: `estimate_raw_data.raw_data`
неизменяем и содержит `article_smr` по **каждой** строке файла, включая ту, чьё
значение мы не сохранили. Концы находятся, вторая колонка не нужна.

Деградация здесь локальная, а не D, и это различие содержательное: лишняя ячейка C
на позиции не меняет ни глубину, ни стек, ни принадлежность соседних строк — под
сомнением только эта одна строка. Неразбираемый номер раздела, наоборот, портит
привязку всех последующих строк неизвестным образом. Гасить паспорт всей сметы
из-за одной ячейки — цена без выгоды.

### 2.8. Порядок материализации

В `_import_positions`, по одному proposal:

1. `resolution = category_resolver.resolve_proposal(positions)` — полный план до
   единой записи в БД (это же обеспечивает атомарность решения D);
2. строки создаются **сразу** с заполненными `smr_article_raw`,
   `work_category_id`, `category_source`;
3. один `add_all` + `flush` — появляются `id`;
4. `parent_position_key` переводится в `id` по карте `key → PositionItem`,
   построенной **в этом же вызове**;
5. проставляются только ненулевые `chapter_item_id`;
6. один явный второй `flush`.

Второй проход не переписывает поля статьи — они уже на месте с шага 2. SQL UPDATE
затрагивает две колонки, `chapter_item_id` и `updated_at` (из-за
`onupdate=now()`), но значение `updated_at` остаётся временем начала транзакции,
поэтому после commit наблюдаемого временного следа нет (§1.3 факт 4). Обещание
формулируется как «один дополнительный flush с пакетными однотипными UPDATE» —
конкретное batching-поведение остаётся деталью SQLAlchemy и драйвера.

Карта `key → item` строится на **один** proposal, поэтому «ссылка не уходит в
чужой proposal» держится по построению: чужого ключа в карте просто нет. С 0006 за
то же самое независимо отвечает схема — составной FK (§2.1). Две защиты здесь не
дублирование, а разные слои: построение объясняет, почему дефекта нет, схема делает
его непредставимым.

Порядок `id` **не объявляется контрактом**: решение его сегодня сохраняет, что
удобно для отладки, но drill-down Ф6 обязан сортировать по явному порядку строки
(численное значение `position_key_in_proposal` либо отдельный ordinal, если он
понадобится).

`CategoryResolver.from_db(db)` создаётся в
[import_pipeline.py:243](../../../backend/services/import_pipeline.py#L243) рядом с
`UnitResolver(db)`, внутри транзакции сессии B, и передаётся в `import_estimate`
параметром — как `unit_resolver`.

### 2.9. Предупреждения

Все — из **сессии B**: они описывают сохранённое доменное состояние, поэтому не
должны существовать, если домен откатился (AGENTS.md §5). Все агрегированные, с
ограниченным числом примеров (образец — `_long_title_warning`), и все **с
сырьём**, чтобы концы находились без захода в БД:

| Предупреждение | Содержит |
|---|---|
| неизвестный код статьи | код, номер раздела, `position_key`, название; агрегируется по уникальному коду |
| префикс «Статьи СМР» не разбирается в код | сырое значение, номер раздела, `position_key` |
| название статьи расходится со справочником | код и **оба** текста; агрегируется по коду |
| разделов без статьи: N, позиций под ними: M | счётчики и примеры |
| строка вне структуры не привязана (§2.6) | количество, `position_key`, название |
| «Статья СМР» на строке-НЕразделе (§2.7) | количество, примеры; сказано, что значение не сохранено |
| структура отключена (D, §2.4) | **обе причины по отдельности**: количество неразбираемых номеров и количество структурных конфликтов §2.3, для конфликтов — какое именно из трёх расхождений сработало; примеры по каждой причине: `position_key`, значения A и B, `is_chapter`, название |

**Что подавляется при D и что нет.** Подавляются только предупреждения
неисполненного категорийного резолва: неизвестный код, **нечитаемый префикс
«Статьи СМР»**, расхождение названия, счётчики нераспределённых — они описывали бы
резолв, которого не было.
**Сохраняются** независимые: причина D, строка вне структуры, «Статья СМР» на
не-разделе. Иначе D молча отменил бы предупреждение, принятое решением §2.6.

Номер строки листа XLSX в предупреждениях **не приводится**: у обычного раздела
импорт его не получает — парсер отдаёт `source_row` только для агрегатной строки,
и без изменения его контракта гарантировать номер строки нельзя. Вместо него —
`position_key_in_proposal`, сырой номер раздела и название; этого достаточно,
чтобы найти строку в файле поиском.

Предупреждение «разделов без статьи» на 449-ТУ и на fixture срабатывает штатно
(39 и 38) — это не сигнал дефекта, а честное «Нераспределённое». Записано, чтобы
никто не «починил» его подгонкой ожидания.

### 2.10. `category_source`: только `'file'`

В v1 единственное ненулевое значение — `'file'`, включая унаследованные статьи:
наследование выведено из данных файла, а не из чужого решения.

```sql
CHECK (category_source IS NULL OR category_source = 'file')
```

Явная форма с `IS NULL` — для читаемости; PostgreSQL пропустил бы NULL и при
`category_source = 'file'`.

**Зарезервированные `'llm'` и `'manual'` в CHECK не вносятся**, хотя бриф §3 их
называл. Довод — тот же, которым Ф1 отвергла хранимый `is_bucket` и колонку
`level`: БД не должна разрешать состояние, которое ни одна строка кода не может
произвести. `'manual'` появилось бы только руками в psql, и с этого момента
паспорт рассказывал бы про воркфлоу, которого нет — ни очереди подтверждения, ни
автора решения, ни времени. Когда появится manual/LLM-контур, его миграция
расширит CHECK **одновременно** с добавлением нужного аудита и поведения; на
`position_items` это дешёвая операция (PG16: `ADD CONSTRAINT … NOT VALID` +
`VALIDATE`).

**Значения `'inherited'` не нужно:** различие «своя статья / унаследована» уже
выводится из данных — `smr_article_raw IS NULL AND work_category_id IS NOT NULL`
и есть «унаследована». Хранить его отдельно значило бы завести вторую правду об
одном факте.

## 3. Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| Агрегатной строке — `chapter_item_id` последнего раздела, дефект просто описать | Записывает в БД заведомо ложный факт. У неверной привязки нет ни одного признака неверности, у NULL он есть по определению (§2.6). |
| Ей же — последний раздел плюс warning | Та же ложь, плюс шум: предупреждение читается как «мы знаем, и всё в порядке». |
| Неразбираемый номер раздела → «вложить в текущую вершину» + warning | Догадка не о строке, а обо всей её области действия: молча меняет привязку всех последующих строк (§2.4). |
| Неразбираемый номер → отказ импорта | Роняет смету на 2,5 тыс. строк из-за одной ячейки при верной шапке и верных деньгах. Guard раскладки Ф2 файл уже пропустил. |
| Неразбираемый номер → раздел не участвует в стеке | Его позиции физически стоят под ним, а получили бы статью соседа сверху — молча и неверно. |
| Расхождение `is_chapter` с нормализованным номером — разрешать порядком условий | Порядок молча перекрыл бы противоречие: в БД осталась бы строка-раздел, которую резолвер счёл внешней. Конфликт → D (§2.3). |
| «Статья СМР» на не-разделе → D по всему proposal | Непропорционально: не меняет ни глубину, ни стек, ни соседей — под сомнением одна строка (§2.7). |
| Хранить `smr_article_raw` на всех строках | Разрешает двум слоям доменной таблицы выражать статью, тогда как денежная привязка задумана исключительно через раздел; а факт и так лежит в неизменяемом `raw_data`. |
| Резолв внутри `estimate_import.py` | Алгоритм достижим только через БД: каждый из шести дублей и случай D требовали бы xlsx или полного JSON-payload'а. Файл уже 802 строки. |
| Пополам: стек в модуле, справочник и warnings в импорте | Решение «наследовать или нет» зависит от того, нашёлся ли код, а знание об этом жило бы в другом файле; D (валидатор до материализации) оказался бы разорван. |
| Вставка по строке с `flush` на каждую | Заменяет один `executemany` на 2576 отдельных INSERT — платит на каждой смете за случай, которого можно избежать одним UPDATE-проходом. |
| Две волны без UPDATE: разделы по уровням, затем позиции | Больше flush'ей и сложнее, а выгоды нет; `id` перестают идти в порядке файла без причины. |
| `CHECK (category_source IN ('file','llm','manual'))` (буква брифа) | Разрешает состояния, которые код произвести не может (§2.10). |
| Значение `'inherited'` | Вторая правда о факте, который выводится из `smr_article_raw IS NULL` (§2.10). |
| Частичные индексы raw SQL | Индекс выпал бы из `Base.metadata` и из детектора дрейфа — шаг назад против [phase2-schema.md §2](../../phase2-schema.md). |
| Одиночный FK `chapter_item_id → id`, а «тот же proposal» — только построением и тестом | Оставляло бы межсметную привязку **представимой**: любой будущий путь записи (backfill, ручной override, миграция) мог бы её создать, и заметило бы это только ревью. Составной FK делает её невозможной, а платой оказалась ширина индекса, не лишний индекс (§2.1, §1.3 факт 9). |
| Триггер ради «цель — строка-раздел» | Единственный способ выразить эту половину декларативно, но триггер в проекте не применяется ни разу, и его цена (скрытая логика в БД, отдельный путь отката) выше, чем регрессионный тест на инвариант, который создаёт ровно один потребитель — резолвер. |
| Тихий фолбэк на порядок словаря при неканоничных ключах | Даёт правдоподобную, но чужую структуру — тот же класс ошибки, что «вложить в текущую вершину». |
| Join позиций к разделам по номеру раздела | Запрещено брифом §2 и подтверждено замером: дубли дают fan-out, деньги считаются дважды и ложатся в обе статьи (§1.1). |
| Читать `chapter_ref_in_proposal` парсера как родителя | Это «родитель по номеру», строковая арифметика ([postprocess.py:273](../../../backend/parser/postprocess.py#L273)), ровно тот способ, который на дублях врёт. Остаётся legacy-подсказкой и в новой денежной логике не читается. |

## 4. Тесты

### 4.1. Юнит, без БД и без xlsx (алгоритм)

Входы — синтетические словари позиций из нескольких строк; каждый вход назван и
пройден руками до утверждения (инсайт
[replaying-new-rules.md](../../insights/replaying-new-rules.md), слой 1).

- наследование по стеку: раздел без своего кода получает статью предка, позиции
  получают статью своего раздела;
- вытеснение: раздел глубины N вытесняет всё с глубиной ≥ N;
- **три реальных дубля 159-ТУ**: `4.1.2.2` → 4.1.2 и 4.1.3; `5.1.2` → 5.1 и 5.2;
  `7.3` → 7.2 и 7.3 вместе с `7.3.1`–`7.3.3`, которые без своих кодов стоят под
  разными родителями и получают 7.2 и 7.3;
- **дубль `1` от строки лота**: лот без статьи вытесняется первым настоящим «1»,
  у того `chapter_item_id = NULL`, позиции под ним получают статью «1»;
- строка вне структуры: родитель NULL, полей статьи нет, warning есть (§2.6);
- **утверждение файла сильнее наследования**: неизвестный код и нечитаемый
  префикс дают NULL **и детям тоже**, а не статью предка (§2.5);
- код с завершающей точкой и без неё; значение из одного кода без названия не
  даёт warning о расхождении;
- расхождение названия: привязка есть, warning есть, в тексте оба варианта;
- **D по неразбираемому номеру**: все три поля NULL по всему proposal,
  `smr_article_raw` разделов сохранён, ровно один D-warning, предупреждения
  категорийного резолва подавлены, а независимые (вне структуры, статья на
  не-разделе) — нет (§2.9);
- **D по конфликту классификации**: A и B пусты при `is_chapter = true` → D, а не
  распознавание внешней строки; числовой `0` в B при `is_chapter = false` → D;
  `is_chapter = true` при пустом нормализованном B → D (§2.3);
- перемешанный порядок ключей во входном `Mapping` даёт тот же результат;
  неканоничный набор ключей (`"01"`, пропуск номера, начало не с «1») — явная
  ошибка.

### 4.2. Интеграционные

На закоммиченном fixture (`pytestmark = pytest.mark.integration`, инсайт
[silent-test-runs.md](../../insights/silent-test-runs.md)):

- замеренные числа **из БД**: 222 раздела со своей статьёй, 485 унаследованных,
  39 без статьи, 38 позиций без статьи;
- `chapter_item_id` ведёт только на строки с `is_chapter = true`;
- **независимая проверка вложенности**: раздел, на который ссылается позиция,
  стоит в файле **выше** неё — по численному `position_key_in_proposal`, а не «как
  посчитал резолвер» (инсайт [verifying-guards.md](../../insights/verifying-guards.md),
  слой 5: эталон не должен ехать вместе с проверяемым);
- три CHECK'а отвергают запись: статья на не-разделе; `work_category_id` без
  `category_source`; `category_source = 'manual'`;
- `replace=true` над сметой с заполненными `chapter_item_id` проходит — составной
  self-FK с `RESTRICT` каскадному удалению всего proposal не мешает (§1.3 факт 8
  замерил это на scratch-таблицах, тест закрепляет на настоящей схеме);
- точечное удаление строки-раздела, на которую ссылаются, упирается в RESTRICT;
- **прямая попытка записать поперечную ссылку** — `UPDATE` строки одного proposal
  на `chapter_item_id` строки другого — даёт нарушение FK. Это отдельный тест, а не
  следствие импорта двух proposal: импорт такую ссылку не построит и при снятом
  констрейнте, поэтому результат импорта половину инварианта не стережёт;
- `DELETE` статьи `work_categories`, на которую ссылается позиция, упирается в
  RESTRICT;
- fixture на 2576 строк — проверка масштаба: пакетная материализация и
  обслуживание индексов на реальном объёме (**без** ссылки на
  `prepare_threshold`: порог >5 был существен для повторяемого параметризованного
  `ON CONFLICT`, обязанного совпасть с raw-SQL expression index, а такого запроса
  в Ф3 нет);
- **изоляция proposal — на синтетическом payload'е с двумя лотами** по одному
  предложению: ни одной поперечной ссылки `chapter_item_id`. На fixture этот тест
  был бы вакуозен — там один proposal;
- круговой рейс `alembic downgrade base && upgrade head`;
- `alembic check` без дрейфа (`just db-test-check`, входит в `just ci`).

### 4.3. Негативная проверка снятием защиты

По протоколу [verifying-guards.md](../../insights/verifying-guards.md) полностью, с
контрольным прогоном до снятия и доказательством, что патч применился.
**Делает оркестратор лично, не исполнитель.** Минимальный набор: валидатор D
(неразбираемый номер и конфликт классификации — это разные пути, и снятие
доказывает только исполняемый, слой 6 инсайта), правило
«утверждение файла сильнее наследования», правило вытеснения по глубине, привязка
строки вне структуры к NULL.

### 4.4. Соответствие «требование → тест»

На финале фичи, до PR, строится явное соответствие «поведенческое требование этой
спеки → тест, который его исполняет», требование за требованием по тексту спеки
(инсайт [replaying-new-rules.md](../../insights/replaying-new-rules.md), слой 3).
Требование без исполнителя либо получает тест, либо объявляется границей в devlog;
молчаливого третьего варианта нет.

## 7. Следствия за пределами Ф3

- **Обязательство Ф4 не ослаблено и не изменено.** Ф3 материализует привязку и
  потому обязана сказать вслух, что деньги агрегатной строки остаются в
  `position_items` и продублированы в `raw_data.additional_works`. Ф4 не создаёт
  доменную запись по `additional_works` без атомарного удаления соответствующего
  `position_item`; сверка — с независимым ИТОГО файла (рамка фазы, спека Ф2 §7).
  Решение §2.6 двойного счёта не устраняет и **видимой** эту сумму до Ф4 не
  делает — потребитель привязки появляется только в Ф6. Точная формулировка:
  структурно она остаётся нераспределённой и попала бы в строку
  «Нераспределённое», если бы аналитический потребитель появился раньше Ф4.
- **Бриф §2 требует правки факта** (§1.2): «4.3 Металлоконструкции» — не пробел, и
  тест «пробел `4.3` → нераспределённое» из DoD брифа §8 надо заменить настоящим
  пробелом `14 SHELL & CORE` / `15 Рабочая документация`. Правка вносится в
  реализации Ф3, а не «планируется».
- **Ф6 не имеет права сортировать по `position_items.id`.** Решение §2.8 порядок
  сохраняет, но контрактом он не объявлен; drill-down сортирует по численному
  `position_key_in_proposal` либо по отдельному ordinal.
- **Перерасчёт из `raw_data` возможен, но не реализован.** `raw_data` неизменяем и
  содержит `article_smr` по каждой строке, поэтому будущая фича может пересчитать
  привязку без исходного XLSX. Обещать «восстановимо перезагрузкой файла» нельзя:
  файл может уйти по ретенции (AGENTS.md §8).
- **Расширение `category_source`** делает та фича, которая вводит новый источник,
  вместе с аудитом и поведением (§2.10).
