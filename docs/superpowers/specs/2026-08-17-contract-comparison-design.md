# Сравнение договоров — дизайн

**Ветка:** `feat/contract-compare-scaffold`.
**Статус:** все решения гейта 2 приняты (последнее — скелет строк, §2.1.1,
2026-08-17).
**Инварианты:** [`AGENTS.md`](../../../AGENTS.md) §3, §6, §7.4, §7.6, §8, **§10**
(налоговый состав денег живёт именно в §10 «Definition of Done», не в §3).
Спека аргументирует от них; при противоречии побеждает `AGENTS.md`.

## 1. Задача

Аналитик сравнивает объекты между собой: из чего складывается стоимость каждого
и чем они отличаются. Сегодня такой поверхности нет — есть паспорт **одного**
договора (§7.4) и сквозная матрица **работ** (§6). Сравнение объектов делается
вне системы, в Excel: образец лежит в `samples/Пример сравнения.xlsx`.

**Что в образце.** Шапка объекта (год подписания, класс здания, генподрядчик,
площади подземная/надземная/общая/полезная), суммы ДГП и ДС, коммерческие
условия (аванс, банковская гарантия, гарантийное удержание) и главная таблица:
иерархические статьи работ (1, 2, 3, 3.1, … 5.3.2) с объёмом, ставкой, итогом и
стоимостью на 1 м². Блок колонок повторяется — рядом стоят около пяти объектов.

Это, по существу, **паспорт проекта, развёрнутый на N договоров с общей осью
строк**. Отсюда и требование пакетной выборки: паспорт сегодня отдаётся по
одному договору за запрос (`/analytics/project-passport/{contract_id}`).

### 1.1. Чем отличается от сквозной матрицы

Различие несущее, и его нельзя размывать: две поверхности отвечают на разные
вопросы, и обе нужны.

| | Матрица (§6) | Сравнение (эта фича) |
|---|---|---|
| Вопрос | сколько стоит **эта работа** у разных подрядчиков | сколько стоит **этот объект** по разделам |
| Строки | каталожные `POSITION` | статьи классификатора (дерево) |
| Ячейка | средневзвешенная ставка **за единицу** | сумма и ₽/м² |
| Ось денег | только нетто | три режима (§2.3) |

## 2. Решение

### 2.1. Состав экрана

Строки — дерево статей классификатора (`work_categories`, `parent_id`), по
умолчанию видны корни; ветка раскрывается шевроном. Тот же способ чтения, что у
паспорта (§7.4): полный плоский список — сто с лишним строк на широкой таблице,
и скролл в обе стороны сразу.

**Замер дерева (2026-08-17):** три уровня — 21 корень, 127 узлов второго уровня,
214 третьего, всего 362. С данными на стенде: 9 / 72 / 117, то есть **198
непустых узлов**. Раскрывается всё дерево целиком, а не один уровень.

**Свёртка переиспользуется, а не пишется заново.** `services/category_rollup`
уже решает эту задачу для паспорта: `build_tree(categories, direct)` — чистая
функция без `Session`, ORM и SQL, на входе плоский справочник и прямые суммы из
`v_category_totals`, на выходе дерево `CategoryNode`. Узел несёт **обе**
величины: `total` (итог поддерева) и `own` (собственные деньги узла).

Вторая величина не декоративная. **Замер: 36 нелистовых узлов несут данные
напрямую** — позиции привязаны не только к листьям. Без неё раскрытая ветка не
сходилась бы с родителем, и это читалось бы как дефект счёта. Модуль намеренно
не выводит собственную величину вычитанием «родитель минус дети»: это выдавало
бы за факт результат вычитания (докстрока модуля).

**Внимание: `own` — НЕ все собственные деньги узла.** Прежняя редакция этой
спеки утверждала обратное, и это было неверно (найдено внешним ревью, проверено
по коду). `category_rollup._build_node` кладёт в `own` только ветку
`SOURCE_POSITIONS`; прямые допработы (`SOURCE_ADDITIONAL_WORKS`) входят в
`total`, но в `own` не входят. Значит собственные деньги узла — это
`own + прямые допработы`, и сводить родителя с детьми по одному `own` нельзя.

**Замер: допработы существуют** — 4 группы на стенде (статьи 3.2 на 12,7 млн ₽ и
12.99 на 0, у договоров 1 и 4), все на листьях. Сегодня родитель с детьми не
расходится, но механизм расхождения живой.

**Синтетическая строка.** Паспорт при раскрытии рисует отдельную строку «Без
подстатьи» (`CategoryTable.tsx`). Сравнение делает то же самое **одним числом** —
`own + прямые допработы`, — и выравнивает эти строки по тому же союзу выборки:
строка «Без подстатьи» у статьи присутствует, если непуста хотя бы у одного
сравниваемого договора. Двумя отдельными строками не разводим: на широкой
таблице это удвоило бы число строк ради различия, которого читатель сравнения не
делает.

### 2.1.1. Что сравнение обязано добавить сверх паспорта

`build_tree` включает узел глубже первого уровня, только если **у этого
договора** в его поддереве есть строки (корни присутствуют всегда — общий
скелет). Для паспорта одного договора это верно; для сравнения — недостаточно:
статья, которая есть у одного договора выборки и отсутствует у другого, обязана
быть строкой у **обоих**, иначе колонки разъедутся.

**Это не крайний случай, а основной — замерено (2026-08-17):**

| Договор | Узлов в дереве паспорта |
|---|---|
| 12-СИТ-МР | 180 |
| ДГП-42-TU | 117 |
| ДГП-159-TU | 103 |
| СДП-1-МР | 103 |
| ТЕСТ | 75 |

Объединение по выборке — **215** узлов, общих у всех пяти — **66**. То есть 149
узлов из 215 есть у одних договоров и отсутствуют у других. Классификатор —
общий шаблон, и одинаковость строк верна для **корней** (их всегда 21, это и
есть общий скелет), но не глубже: ниже корня паспорт обрезает пустые ветки
намеренно, иначе нёс бы все 362 строки справочника.

Отсюда размер таблицы: полностью раскрытое сравнение этих пяти — **215 строк**,
ровно объединение непустых узлов. **Корень, пустой у всей выборки, тоже
удаляется** — `build_tree` возвращает все 21 корень безусловно (общий скелет
паспорта), но союз выборки затем отбрасывает те, что пусты у всех сравниваемых.
Прежняя редакция говорила здесь «219 строк = 215 плюс четыре пустых корня», и это
противоречило собственному решению абзацем ниже; исправлено по ревью плана.

**РЕШЕНО: скелет — союз узлов ВЫБОРКИ.** Строка присутствует, если статья
непуста хотя бы у одного сравниваемого договора; у остальных в этой строке
прочерк (§2.1.2). Строка, пустая у всех сравниваемых, не показывается: она не
несёт ничего — ни числа, ни факта отсутствия, потому что отсутствие у всех и
есть отсутствие вопроса.

Замер, показывающий, что правило действительно сжимает таблицу:

| Выборка | Строк |
|---|---|
| Все пять | 215 |
| ТЕСТ + 12-СИТ-МР | 184 |
| ТЕСТ + ДГП-159-TU | 109 |
| ДГП-159-TU + СДП-1-МР | 103 |
| ТЕСТ один | 75 |

Отвергнутые варианты и причина:

| Вариант | Строк | Почему нет |
|---|---|---|
| Весь классификатор | 362 | 147 строк не задействованы ни одной сметой — мёртвый груз в каждой раскрытой ветке |
| Задействованные хоть где-то в базе | 215 | не отвечает на вопрос «нужна ли строка ЭТОМУ сравнению»; тащит статьи, которых нет ни у одного из сравниваемых |
| Общие у всех договоров выборки | 66 | теряется всё, что есть не у всех, — 149 узлов из 215 |
| «Как в паспорте», по каждому договору | 75 … 180 | **ломает выравнивание**: у договоров разные наборы строк |

**Цена принятого решения, названная вслух:** форма таблицы зависит от выборки,
поэтому два сравнения с разными выборками не совпадают построчно. Это осознанно:
сравнение читается как самостоятельный документ, а не подкладывается под другое
сравнение. Практика в `samples/Пример сравнения.xlsx` устроена иначе —
фиксированный шаблон из 96 статей, пустых ячеек нет ни одной, у четвёртого
проекта 80 строк из 96 нули, и он всё равно остаётся в скелете, — но тот шаблон
и не наш классификатор (у них РД первая статья, у нас шестнадцатая), а
воспроизводить в интерфейсе строки, пустые у всех сравниваемых, значит
переносить ограничение бумаги туда, где его нет.

### 2.1.2. Состояние ячейки: прочерк и ноль — разные вещи

**Решено:** статья, которой нет в смете договора, показывается **прочерком**;
ноль ставится только там, где статья в смете есть и расценена в ноль.

Замер по сетке 5 договоров × 215 узлов (1075 ячеек): **497** — статьи нет,
**89** — есть и расценена в ноль, **489** — есть значение. Третьего состояния
(«есть, но не расценена») в данных нет: `rows_with_amount = 0` не встретилось ни
разу.

В Excel-образце оба первых случая пишутся нулём — у ячейки просто нет третьего
знака. У нас данные их различают, и написать ноль во всех 586 значило бы
утверждать, что работы предусмотрены и стоят ноль там, где их в смете нет.

На медиану выбор не влияет: из неё исключаются оба состояния (§2.5, правила 3
и 4). Влияет только на честность прочтения.

### 2.1.3. Неполнота ячейки: одно правило, четыре причины

**Правило.** Ячейка пуста **целиком** и несёт **список причин**
(`incomplete_reasons`), если выполнено хотя бы одно:

1. `unpriced_rows` — `rows_priced < rows`, часть позиций без цены;
2. `not_finite_rows` — `rows_not_finite > 0`, есть `NaN`/`±Infinity`;
3. `vat_base_unknown` — неизвестна `vat_rate_base` хотя бы у одной вошедшей
   группы;
4. `display_rate_undefined` — только в режиме «своя ставка»: у сметы нет
   определённой ставки показа (§2.3.2).

**Список, а не один код с приоритетом** (уточнено по второму кругу внешнего
ревью): причины совмещаются, и прятать одну за другой значит терять факт.
Прецедент существующий, а не изобретённый: паспортный `incompletenessCaption`
уже перечисляет причины через запятую («без цены: 3, с ошибкой: 1»), а не выбирает
старшую. Первые три причины не зависят от режима показа, четвёртая — зависит, и
это единственная причина с таким свойством.

Третья причина была в спеке с самого начала (наследство §6), первые две добавлены
по внешнему ревью. Основание одно и то же и уже записано в §6: **единица
неполноты — ячейка**, и «показать сумму по известным строкам, замолчав про
неизвестные, значило бы выдать неполное значение за полное». Для сравнения это
опаснее, чем для паспорта: частичная сумма попадает в медиану и портит её
молча.

**Расхождение с паспортом осознанное.** Паспорт в этом случае показывает число и
подпись под строкой — «без цены: N, с ошибкой: M» (`incompletenessCaption`).
Сравнению так нельзя: при пяти колонках места для подписи под каждой ячейкой нет,
а число участвует в расчёте медианы. Поэтому здесь — пустая ячейка с кодом
причины, а не число с оговоркой.

**Замер: на стенде ни одного случая** — 474 группы, частично расценённых 0,
нефинитных 0. Правило вводится как инвариант, а не по наблюдению, и проверяется
искусственными фикстурами.

### 2.1.4. «Нераспределённое»

`build_tree` намеренно не пускает `direct[None]` в дерево — это не категория;
паспорт показывает остаток отдельной строкой. Сравнение делает так же:
**синтетическая строка «Нераспределённое»** по тем же правилам союза (есть, если
непуста хотя бы у одного сравниваемого договора).

- **входит** в «Итого по договору» — иначе итог оказался бы больше суммы видимых
  строк, и деньги исчезли бы из таблицы молча;
- **не входит** в медиану и не получает подсветки. Это не статья, а остаток
  разноса: сравнивать остатки между договорами значит сравнивать качество
  разноса, а не цены. (Внешнее ревью предлагало включать при вычислимом ₽/м²;
  отвергнуто по этой причине.)

**Замер: на стенде остаток пуст у всех** (ни одной группы с
`work_category_id IS NULL`). Но `AGENTS.md` §10 прямо говорит, что глобальный
ноль не гарантирован, поэтому правило нужно до того, как появится первый
непустой остаток.

Колонки — договоры выборки, **все**, с горизонтальной прокруткой и закреплённой
первой колонкой. В этом решение то же, что у матрицы (§6.4), — но **только в
этом**.

**Пагинации строк у сравнения НЕТ.** Агрегат возвращает полное дерево союза
выборки; раскрытие и свёртка — клиентские. Прежняя редакция ссылалась на §6.4
целиком, вместе со словами «серверная пагинация по строкам», и этим требовала
пагинации иерархии, которой не проектировала: планировщик либо изобретал бы
разрез страницы с родителями и детьми, либо формально нарушал спеку. Уточнено по
второму кругу внешнего ревью.

Основание для отказа от пагинации — размер: справочник статей ограничен
**362 узлами** (замер §6), союз выборки на стенде даёт 215, а сравнение читается
свёрнутым до корней. Резать нечего.

**Граница, за которой решение придётся пересмотреть:** объём ответа растёт
линейно по числу колонок (узлы × договоры × три корзины). На пяти договорах это
порядок единиц тысяч ячеек; на пятидесяти — десятков тысяч. Числа замерены не
были: выборок такого размера в системе пока нет. Если появятся — это отдельное
решение, а не молчаливое ухудшение.

Порядок колонок — `signed_date DESC`, при равных датах `id DESC`: от новых к
старым.

Шапка колонки несёт то же, что шапка образца: номер договора, объект, класс,
общая площадь, коммерческие условия. Отсутствующие данные называются словами
(«ТЭП не заведены», «условия не заведены»), а не прочерком в пустоте.

### 2.2. Три корзины: ДГП, ДС, Итого

Ячейка несёт три суммы: базовый договор (`amendment_no IS NULL`), допсоглашения
(сумма всех `amendment_no > 0`) и итог. Так устроен образец, и так решено
пользователем на гейте 1.

**Третья корзина образца — «ДС на рассмотрении» — не делается.** У `estimates`
нет признака подписанности: есть только `amendment_no`. Ввести его — значит
завести статус сметы, правила его смены, место в интерфейсе и ответ на вопрос,
что этот статус означает для паспорта, матрицы и отчётов, которые тоже читают
сметы. Это отдельная фича, а не деталь этой.

**Замер (2026-08-17, стенд `gca_dev`):** допсоглашений в системе **ноль**, все
пять смет базовые. Корзина «ДС» будет пуста до первого ДС, и это ожидаемое
состояние, а не дефект. Реализация обязана быть проверена на искусственных
фикстурах с `amendment_no > 0` — на живых данных путь не исполняется.

Экран не показывает три денежные колонки на договор: при пяти договорах их
пятнадцать. Показатель выбирается переключателем «Итого / ДГП / ДС» на всю
таблицу.

**Прочерк и ноль различаются по корзинам** (уточнено по внешнему ревью):

- статьи нет **ни в одной смете** договора → прочерк во **всех** корзинах;
- статья в договоре есть, но в **выбранной** корзине её нет → **ноль**.

То есть у договора без допсоглашений корзина «ДС» даёт нули там, где статья есть,
и прочерки там, где статьи нет вовсе. Макет показывает нули везде именно потому,
что ДС в системе нет ни одного, а не потому, что правило такое.

**Медиана пересчитывается для выбранной корзины**, а не берётся от «Итого»:
отклонения в режиме «ДС» — это отклонения сумм ДС, иначе подсветка отвечала бы на
другой вопрос, чем показанные числа.

### 2.3. НДС: три режима показа

Пользователь читает договоры в той ставке, в которой они существуют, — поэтому
нетто как единственная ось (как в §6) не годится.

| Режим | Как считается | Зачем |
|---|---|---|
| **Своя ставка** (по умолчанию) | `effective_display_rate(vat_rate_target, vat_rate_base_override, declared)` на договор, затем `restate_gross` из базовой ставки в неё | Договор виден таким, каким существует. Та же ставка, что показывает паспорт |
| Единая ставка | `restate_gross` из базовой в одну ставку, выбранную на странице | Сопоставление: умножение всей таблицы на один множитель |
| Нетто | `gross_to_net` по базовой ставке | Общий язык с матрицей (§6) и отчётом «для банка» (§7.6) |

Приоритет ставки показа — существующий (`money/vat.py:126`): цель → перекрытая
база → единогласная заявленная ставка предложений; разногласие или неизвестность
дают `None`.

**Замер:** ставки показа на стенде — 16, 20, 20, 22, 22; `None` нет ни одного.
То есть режим «своя ставка» даёт по странице разброс в шесть процентных пунктов
чистого налога.

### 2.3.1. Это ревизия инварианта, и она названа

`AGENTS.md` **§10** («Деньги показываются в объявленном налоговом составе» — пункт DoD
проекта, а не §3, где только правило `Decimal`) требует:
«много-договорные РАСЧЁТНЫЕ поверхности (сквозная матрица §7.5, отчёт „для
банка“ §7.6) — в нетто». Сравнение — такая поверхность, а показывает по умолчанию
каждую колонку в её ставке. Это **осознанная ревизия, а не исключение**, и без
неё спека противоречила бы инварианту (найдено внешним ревью).

Ревизия до **v6.8**, три утверждения:

1. у много-договорных **сравнительных** поверхностей ось сравнения — всегда
   нетто (в действующей редакции эта строка уже есть);
2. **показ** может иметь объявленные режимы, и состав объявляется на самой
   поверхности;
3. в режиме «своя ставка» итог по договору вправе складывать суммы разного
   состава при обязательной подписи — тем же основанием, каким это уже
   разрешено обзорной главной.

Каркас для этого в инварианте уже готов: он запрещает не сложение разных
составов, а **молчаливое** сложение, и главная (`/`) уже складывает валовые
суммы разных ставок с обязательной подписью.

### 2.3.2. Договор, у которого ДГП и ДС в разных ставках

Случай штатный, а не аномальный: ставка меняется законодательно, и договор
2025 года с допсоглашением 2026-го — норма. На стенде разброс ставок показа
16 / 20 / 22 уже есть.

**Правило.** `effective_display_rate` определён на **смету**, не на договор,
поэтому:

- **пересчитывается каждая СМЕТА, а не корзина** — в свою ставку показа; затем
  суммы смет складываются в корзину. У корзины ДС может быть несколько смет с
  разными ставками (ДС №1 в 20 %, ДС №2 в 22 %), и «ставки корзины» не
  существует — это уточнение внесено по второму кругу внешнего ревью, прежняя
  формулировка «корзина в ставке своей сметы» была неопределённой;
- «Итого» складывает корзины и несёт **подпись состава в шапке колонки**,
  перечисляющую все вошедшие сметы: «ДГП 20 % · ДС №1 20 %, №2 22 %».
  Совпадающие ставки сворачиваются: «ДГП 20 % · ДС 20 %», а при полном
  совпадении — «20 %»;
- ось сравнения остаётся нетто, поэтому смешанный состав не портит ни медиану,
  ни отклонения.

**Смета без определённой ставки показа.** `effective_display_rate` возвращает
`None`, когда цель и перекрытая база не заданы, а заявленные ставки предложений
расходятся. Базы при этом известны по группам, то есть нетто вычисляется, а
единой валовой ставки у сметы нет.

**Правило гасит ЯЧЕЙКУ, а не договор** (уточнено по третьему кругу внешнего
ревью; прежняя формулировка «ячейки такого договора пусты» допускала чтение
«одна проблемная смета гасит весь столбец», и это было бы неверно):

> В режиме «своя ставка» причина `display_rate_undefined` добавляется ячейке
> **выбранной корзины**, если в эту ячейку входит хотя бы одна смета без
> определённой ставки показа, **непустая по этой статье**. Смета из другой
> корзины ячейку не гасит; смета без строк по этой статье — тоже не гасит. Для
> строки «Итого по договору» правило применяется по всем вошедшим в неё деньгам.

**Пример, на котором правило проверяется** (прежняя редакция приводила здесь
пример, противоречивший самому правилу, — исправлено по четвёртому кругу ревью):
статья присутствует **и в ДГП** (ставка определена), **и в ДС** (ставка не
определена). Тогда в режиме «ДГП» ячейка — число, в режимах «ДС» и «Итого» — пуста
с причиной.

**Контрольный случай, который причины НЕ вызывает:** статья есть только в ДГП. По
ДС она пуста, значит проблемная смета в ячейку не входит, и правило не
срабатывает: «ДГП» — число, «ДС» — **ноль** (§2.2), «Итого» — число ДГП. Прежний
пример утверждал здесь причину, и это была прямая ошибка.

В режимах «нетто» и «единая ставка» причина `display_rate_undefined` не возникает
вовсе: там ставка задана извне, а нетто вычислимо по базам групп. Основание общее
с остальными причинами неполноты: неизвестное не подменяется догадкой.

Отвергнуто: «разногласие ставок → режим недоступен» (отключало бы режим по
умолчанию для самого типичного многолетнего договора), «всё в ставке последней
сметы» и «всё в ставке базовой» (обе показывают одну из корзин суммой, которой
нет ни в одном документе).

**Цена, названная вслух:** в режиме «своя ставка» число «Итого» нельзя сравнивать
между колонками глазами — составы разные. Законный канал сравнения — подсветка
отклонений, и она считается по нетто именно поэтому.

**Какая ставка предлагается в режиме «единая».** Список — объединение двух
множеств:

1. определённые ставки показа смет выборки (`effective_display_rate`);
2. **известные базовые ставки групп** (`vat_rate_base`) — включая группы тех смет,
   у которых ставка показа не определена.

**Предвыбор:** частота считается **только по определённым ставкам показа**;
известные базовые ставки идут в список как резерв и в подсчёте частоты не
участвуют. Самая частая, при равенстве частот — бо́льшая. Без записанного правила
«единая ставка» открывалась бы с произвольным значением, и два человека увидели бы
разные числа по одной ссылке.

**Если определённых ставок показа нет вовсе, предвыбор считается по известным
базовым ставкам групп: самая частая, при равенстве — бо́льшая.** Без этой строки
правило оставляло предвыбор неопределённым ровно в том краю, ради которого резерв
и заводился, — а DoD 8ж требует, чтобы режим «единая» сразу показывал числа
(найдено пятым кругом внешнего ревью).

**Замер на стенде: ставки показа дают ничью** — 22 у двух договоров, 20 у двух,
16 у одного. По правилу «при равенстве — бо́льшая» предвыбор равен **22**.
Прежняя редакция спеки называла здесь 20; это была ошибка, и четвёртый круг ревью
её повторил, не пересчитав. Число получено запросом, а не рассуждением.

**Второе множество — не избыточность, а гарантия непустоты списка** (найдено
третьим кругом внешнего ревью). Если бы список строился только из ставок показа,
выборка, где у всех смет `effective_display_rate = None`, дала бы режим «единая»
вычислимым, но без единого варианта на выбор — тупик. Базовые же ставки известны
всегда, когда ячейка вообще считается: неизвестная `vat_rate_base` сама гасит
ячейку причиной `vat_base_unknown` (§2.1.3). Отсюда инвариант: **если в таблице
есть хоть одно показываемое число, в списке есть хоть одна ставка.** Ввод ставки
числом поэтому не нужен.

Режим и выбранная ставка живут **в URL**: ссылка обязана воспроизводить то, что
человек видел. Excel-лист забирает тот же режим и печатает его подписью.

**Неполнота базы НДС.** Правило §6 переносится дословно: ячейка, где хотя бы у
одной вошедшей группы неизвестна `vat_rate_base`, пуста **целиком**, а не
частично. Единица неполноты — ячейка. Замер: на стенде неизвестных баз нет ни
одной (0 из 474 групп), поэтому правило работает страховкой корректности, а не
повседневным поведением.

### 2.4. Удельная стоимость

₽/м² считается по **общей** площади объекта (`objects.area_total_sp`).

**Замер:** `area_total_sp` заполнена у 4 объектов из 6, `area_useful_sp` — **ни
у одного**. Поэтому строка образца «Стоимость за м² полезной площади» в этой
фиче не строится: показывать нечего, а колонка сплошных прочерков хуже её
отсутствия.

У объекта без ТЭП ячейка ₽/м² — прочерк, не ноль: ноль читался бы как
«бесплатно» (то же решение, что в паспорте).

### 2.5. Отклонение от медианы

Пять колонок больших чисел не отвечают на вопрос «где дорого»: разницу читатель
считает в уме. Строка получает медиану и отклонения от неё.

Правила:

1. **Считается по ₽/м², не по рублям.** Абсолютные суммы между объектами разного
   размера несравнимы: `TOP TOWER` — 166 757 м², `Объект 159-TU` — 75 741 м², и
   по рублям большой объект «дорогой» всегда.
2. **Всегда по нетто, в любом режиме показа.** Медиана — утверждение о цене, а
   не о налоге. В режимах «нетто» и «единая ставка» это совпадает с видимой осью
   с точностью до множителя, поэтому расхождения не видно; в режиме «своя
   ставка» подпись прямо говорит «отклонения посчитаны без НДС». Иначе подсветка
   мерила бы разницу 16 % и 22 % и выдавала налог за дороговизну.
3. **Пустые ячейки не входят** ни в медиану, ни в подсветку.
4. **Нулевые ячейки не входят.** Ноль в этой таблице означает «работы в договор
   не входят либо учтены в другой статье», а не «дёшево». Пример со стенда,
   «Благоустройство, дороги», ₽/м²: 0 · — · 0 · 2 981 · 4 076. С нулями медиана
   равна 1 490, и появляются «+173 %» и «−100 %» там, где сравнивать нечего.
5. **Минимум три сопоставимых значения.** При двух медиана — середина отрезка, и
   отклонения выходят симметричными ±одно число: видимость анализа без анализа.
   Меньше трёх — подсветки в строке нет вовсе.
6. **Полоса ±10 % нейтральна**, дальше две ступени интенсивности.
7. **Цвет означает «выше/ниже медианы», а не «плохо/хорошо».** Дешевле может
   быть недобором объёма.

Медиана чётного числа значений — среднее двух средних, в `Decimal`.

### 2.6. Выборка

Два входа, одна страница, оба выражаются в URL:

- `?ids=1,2,4` — явный выбор галочками в списке договоров;
- `?...&all=1` — «сравнить всё по текущему фильтру»; выборка пересчитывается на
  сервере, и новый подходящий договор попадёт в неё сам.

**Перечень фильтров перечислен полностью, а не «те же, что у списка»** (уточнено
по внешнему ревью — прежняя редакция называла два из четырёх):
`q`, `object_id`, `contractor_id`, `rate_class_id` — ровно контракт
`routers.contracts.list_contracts`. `page` и `page_size` не переносятся:
сравнение берёт всю выборку, а не страницу списка.

Второй режим — причина, по которой список id в URL не может быть единственной
формой: пользователь хочет сравнивать все договоры, а перечисление id
устаревает в момент заведения следующего.

### 2.7. Один агрегат — два представления

Экран и Excel-лист считаются **одним** серверным агрегатом. Разные пути расчёта
для экрана и файла разошлись бы в числах; этот класс дефектов в проекте уже
ловили (§11).

Выравнивание строк — серверная забота: объединение непустых статей по всей
выборке считается один раз, поэтому колонки сходятся по построению. Клиент,
сшивающий N паспортов, выравнивал бы их сам и по-своему.

### 2.8. Excel

Один лист: шапка с составом выборки, режимом НДС и датой; таблица «статьи ×
договоры» с ₽/м² и отклонениями. Разрез — статьи, в отличие от отчёта «для
банка» (класс → работа).

**Три корзины на листе печатаются все три колонками** (ДГП, ДС, Итого), в
отличие от экрана с переключателем: у листа нет ограничения ширины экрана, а
переключателя на бумаге не бывает. Это осознанное расхождение представлений при
одном агрегате, а не рассинхрон.

**У каждой корзины на листе своя сумма, свой ₽/м² и своё отклонение от медианы**
(уточнено по внешнему ревью): медиана считается по корзине (§2.2), поэтому одно
отклонение на три колонки было бы отклонением неизвестно чего. Строка
«Нераспределённое» и строки «Без подстатьи» на лист попадают по тем же правилам,
что на экран.

**Ревизия §7.6:** «два отчёта — два файла» становится тремя. Не противоречие, а
расширение: у выгрузки сравнения своя выборка и свой разрез.

### 2.9. Права и вход

Читают `admin` и `member` — это чтение, как паспорт (§3).

Вход — из списка договоров: колонка галочек, кнопки «Сравнить выбранные (N)» и
«Сравнить всё по фильтру». **Пункта в главном меню нет**: сравнение без выборки
бессмысленно, а пункт меню обещал бы страницу, которую не с чем открыть.

## 2.10. Ревизия `AGENTS.md` → v6.8

Фича трогает инварианты в трёх местах, и все три обязаны быть названы врезкой,
а не внесены молча.

**Это ОБЯЗАТЕЛЬНАЯ задача плана, а не примечание.** На момент написания спеки
`AGENTS.md` остаётся v6.7 и несёт прежний инвариант; пока правка не внесена,
реализация формально противоречит документу. Задача не последняя в плане и не
«если останется время».

1. **§10, налоговый состав денег** (пункт DoD проекта, не §3 — ссылка
   исправлена по третьему кругу ревью). Много-договорные сравнительные поверхности:
   ось сравнения всегда нетто; **показ** может иметь объявленные режимы; в
   режиме «своя ставка» итог по договору вправе складывать суммы разного состава
   при обязательной подписи — тем же основанием, каким это разрешено обзорной
   главной. Обоснование — §2.3.1, §2.3.2.
2. **§7, состав экранов.** Добавляется страница сравнения договоров: маршрут
   `/compare`, вход из списка, пункта меню нет.
3. **§7.6, отчёты.** «Два отчёта — два файла» становится тремя: у выгрузки
   сравнения своя выборка и свой разрез (статьи × договоры против «класс →
   работа»).

## 3. Отвергнутые альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Строки — каталожные работы, как в матрице | Это и была бы матрица со скоупом выборки, а не новая поверхность. Вопрос «из чего складывается стоимость объекта» остался бы без ответа |
| Только верхнеуровневые показатели (сумма, ₽/м², класс) | Разбивка по статьям — то, ради чего аналитик и открывает сравнение |
| N запросов к `/analytics/project-passport/{id}`, сшивка на клиенте | N-кратная агрегация и выравнивание строк на клиенте: у каждого паспорта свой набор непустых статей |
| «Длинная» форма ответа, дерево собирает клиент | Логика сортировки и вложенности уехала бы на фронт и продублировала паспортную |
| Жёсткий предел 5–6 колонок, как в образце | Противоречит задаче «сравнивать все договоры между собой» |
| Каждая колонка в своей ставке **и** отклонения по ней же | Отклонения мерили бы разницу ставок (16 % против 22 %), а не цен |
| Нули как значения в медиане | Медиана съезжает туда, где работ нет; см. §2.5 пример |
| Поправка на инфляцию в этой фиче | См. §4.1 |

## 4. Границы

Названы вслух, чтобы не выглядеть недосмотром.

### 4.1. Рубли разных лет складываются без поправки

Договоры стенда подписаны с 20.02.2025 по 06.07.2026 — 17 месяцев разброса.
₽/м² 2025 года и 2026-го — разные рубли, и страница сравнивает их напрямую.

Источника индекса в системе нет: `inflation_index` существует только как колонка
`rate_standards` (коэффициент разового переутверждения норматива), ряда «период
→ индекс» нет, в `app_settings` лежит один `passport_top_n`. Поправка требует
миграции, решения о дате приведения (подписания? сметы? `data_prepared_on_date`
у смет ГП всегда пуст — фаза 3), базового периода и правила для договоров вне
ряда. И затрагивает не только эту страницу: паспорт, матрица и отчёт «для банка»
тоже складывают разные годы.

Решение гейта 1: **отдельной фичей после этой.** Тогда на странице появится
четвёртый переключатель «в ценах такого-то года».

У нормативов инфляция уже учтена — они переутверждаются по периодам (§7.3);
дыра именно в сравнении договора с договором.

### 4.2. Прочие границы

- **Миграций нет.** Схема не меняется.
- **«ДС на рассмотрении» не делается** (§2.2).
- **₽/м² полезной площади не делается** (§2.4).
- **Печати нет.** Паспорт печатается (§7.4), сравнение — нет: широкая таблица на
  бумагу не ложится, а решать это надо отдельно.
- **Drill-down из статьи в позиции нет.** У матрицы он есть (§6), здесь — нет;
  вход в детали остаётся через паспорт договора.
- **Маршрут `/matrix` без ссылки в интерфейсе не чинится.** Обнаружено при
  разведке: попасть на матрицу можно только вводом адреса. Чужой долг, не эта
  фича.

## 5. Definition of Done

Каждый пункт — исполняемый тест, кроме отдельно оговорённых.

**Агрегат и API**

1. Выборка по `ids` и выборка по фильтру с `all=1` дают одинаковый ответ на
   одинаковом множестве договоров.
2. Строки выровнены: статья, непустая хотя бы у одного договора выборки, есть у
   всех колонок (со значением либо с прочерком).
3. Порядок колонок — `signed_date DESC`, затем `id DESC`.
4. Дерево: у корня сумма равна сумме поддерева.
5. Три корзины: на фикстуре с `amendment_no > 0` ДГП + ДС = Итого; на базовой
   смете ДС равен нулю.
5а. Статьи нет ни в одной смете договора → прочерк во всех трёх корзинах;
   статья есть, но не в выбранной корзине → ноль (§2.2).
5б. Синтетическая строка «Без подстатьи» равна `own` + прямые допработы, а не
   одному `own`; на фикстуре с допработой на РОДИТЕЛЬСКОЙ статье раскрытая
   ветка сходится с родителем (§2.1.1).
5в. Строка «Нераспределённое» есть при непустом остатке хотя бы у одного
   договора, входит в «Итого по договору» и НЕ входит в медиану (§2.1.4).

**НДС**

6. Режим «своя ставка»: колонка со ставкой 16 % и колонка со ставкой 22 %
   показывают суммы, пересчитанные каждая в свою (`restate_gross`).
7. Режим «единая ставка»: все колонки пересчитаны в выбранную; отношение к
   режиму «нетто» — один и тот же множитель для всех ячеек.
8. Неизвестная `vat_rate_base` хотя бы у одной группы → ячейка пуста целиком.
8а. `rows_priced < rows` → ячейка пуста целиком с кодом причины «без цены»;
   `rows_not_finite > 0` → пуста с кодом «с ошибкой» (§2.1.3). Обе проверяются
   искусственными фикстурами: на стенде таких данных нет.
8б. Договор с разными ставками ДГП и ДС: каждая **смета** пересчитана в свою
   ставку, «Итого» складывает их, шапка колонки несёт подпись состава (§2.3.2).
8в. Корзина ДС из **двух** смет с разными ставками (например 20 % и 22 %): сумма
   корзины равна сумме смет, каждая в своей ставке; подпись перечисляет обе.
   Совпадающие ставки в подписи свёрнуты (§2.3.2).
8г. Смета без определённой ставки показа (заявленные ставки предложений
   расходятся, цель и перекрытая база не заданы): в режиме «своя ставка» ячейки
   пусты с причиной `display_rate_undefined`; в режимах «нетто» и «единая» тот же
   договор считается нормально (§2.3.2).
8д. Ячейка, у которой совпали две причины неполноты, несёт **обе** в
   `incomplete_reasons`, а не старшую (§2.1.3).
8е. Причина гасит **ячейку, а не столбец**. Фикстура: статья присутствует и в
   ДГП (ставка определена), и в ДС (ставка НЕ определена). Тогда в режиме «ДГП»
   ячейка — число, в режимах «ДС» и «Итого» — пуста с причиной
   `display_rate_undefined` (§2.3.2). Контрольный случай той же фикстуры: статья,
   которая есть только в ДГП, в режиме «ДС» даёт **ноль**, а не причину, и «Итого»
   равен числу ДГП — проблемная смета по этой статье пуста и ячейку не гасит
   (§2.2, правило прочерка и нуля).
8ж. Выборка, где ставка показа не определена **ни у одной** сметы: режим «единая»
   открывается, список ставок непуст (берётся из известных `vat_rate_base`), числа
   показываются (§2.3).

**Отклонения**

9. Медиана считается по ₽/м², исключая пустые и нулевые ячейки, **и отдельно для
   каждой корзины** (§2.2).
10. Отклонения одинаковы во всех трёх режимах показа (проверка правила «всегда
    по нетто»).
11. Меньше трёх сопоставимых значений → подсветки в строке нет.
12. **Искусственная фикстура**, а не строка стенда: строка с двумя положительными
    ячейками, двумя нулевыми и одной отсутствующей медианы НЕ получает — после
    исключения нулей и пустой остаётся два значения (правила 3–5). Исторический
    пример, из которого правило и выросло: «Благоустройство, дороги» на
    пятидоговорном стенде давала 0 · — · 0 · 2 981 · 4 076. Привязывать
    исполняемый DoD к данным стенда нельзя: два договора из этой пятёрки удалены
    2026-08-17, и та же строка утверждает теперь другое свойство.

**₽/м²**

13. Объект без `area_total_sp` → ₽/м² прочерк, и он не входит в медиану.

**Экран**

14. `member` видит страницу; галочки и кнопки видны обеим ролям.
15. Переключатель «Итого / ДГП / ДС» меняет показатель во всех ячейках.
16. Раскрытие ветки показывает второй уровень; по умолчанию видны только корни.
17. Первая колонка остаётся видимой при горизонтальной прокрутке.
18. Режим НДС и выбранная ставка восстанавливаются из URL.

**Excel**

19. Числа листа совпадают с числами экрана при том же режиме (один агрегат).
20. Лист называет режим НДС подписью, а в режиме «своя ставка» — состав по
    договору («ДГП 20 % · ДС 22 %»).
21. На листе у каждой из трёх корзин своя сумма, свой ₽/м² и своё отклонение
    (§2.8).
22. Выборка по фильтру принимает все четыре параметра списка — `q`, `object_id`,
    `contractor_id`, `rate_class_id` (§2.6).

**Не тест, проверяется прогоном на стенде:** читаемость таблицы при пяти
колонках и раскрытой ветке; поведение горизонтальной прокрутки.
