**Источник — дизайн**
[`2026-11-18-our-price-slow-queries.md`](../design/2026-11-18-our-price-slow-queries.md)
(гейт 1 одобрен 18.11.2026 после второго круга Codex на `c078c8a`). Спека тонкая

## 1. Что есть (разведка кода 18.11.2026)

**`crud/our_price_load.py::_conflicted_parameters(db, context_ids)`** — главные
параметры контекстов со значением `path_conflict`: `context_id → schema_id →
frozenset(parameter_id)`. Пустой вход — `{}` без обращения к БД. Один запрос
SQLAlchemy Core: `context_parameter_values` JOIN `family_parameters` с условиями
`context_id IN (…)`, `source = 'path_conflict'`, `role = 'main'`,
`archived_at IS NULL`. Вызывающие — два, оба в том же модуле:
`load_work_history` (строки истории) и `load_kp_lines` (строки КП); результат
каждый раскладывает через `_conflicts_of` по схеме своего варианта.

**`services/context_routing.py::_chapter_chain_rows(db, chapter_item_ids)`** —
строки рекурсивного запроса пути разделов: `start_id, current_id, depth, title,
number, is_cycle`, по возрастанию `depth` внутри каждого `start_id`; найденный
цикл (`CYCLE current_id SET is_cycle USING visited_path`) — `RoutingError`.
Пустой вход — `[]` без обращения к БД. Текстовый SQL, `ids` — массивом
(`= ANY(:ids)`). Им пользуются две открытые функции:

- `chapter_paths` (пути названиями сверху вниз) — `crud/section_chains.py`,
  `crud/semantic.py`, `services/auto_split.py`,
  `services/semantic_request.py` (в том числе по одному разделу в цикле);
- `chapter_steps` (шаги: ключ, название, номер) — `crud/our_price.py` (строки
  разбора, панель, аналоги), `crud/reference_search.py`.

Тесты сегодня (дизайн, «Проверка»): `test_semantic_api.py::TestChapterPaths`
и `test_analog_scene.py::test_path_conflict_of_the_main_parameter_is_not_a_match`.
`TestChapterPaths::test_repeated_calls_beyond_prepare_threshold` находит
подготовленный запрос по тексту `WITH RECURSIVE chain` в
`pg_prepared_statements`.

## 2. Решение

### 2.1. Что сдаёт фича

Оба запроса переписаны так, что их план не зависит от того, что планировщик
ошибается: первый — в оценке фильтра `family_parameters`, второй — в оценке
размера рекурсии. Подписи, возвращаемые значения, порядок строк и отказы обеих
функций не меняются; вызывающие не трогаются. Миграций, новых индексов, правок
фронта и API нет.

### 2.2. Параметры с `path_conflict`

Сначала отбираются строки `context_parameter_values` по `context_id` из входа и
`source = 'path_conflict'` — в материализованном CTE (`MATERIALIZED`: без него
PostgreSQL вправе встроить подзапрос обратно в соединение и вернуть прежний
план). Затем — соединение с `family_parameters` по `parameter_id` с условиями
`role = 'main'` и `archived_at IS NULL`. Форма — SQLAlchemy Core, как сейчас:
CTE через `.cte(…)` с префиксом `MATERIALIZED`; значения условий — из тех же
перечислений (`ValueSource`, `ParameterRole`), что сегодня.

Остаются прежними: тип результата, группировка по `context_id` и `schema_id`,
пустой вход без запроса, игнорирование контекстов без конфликтов (их нет в
результате, а не `{}` в значении).

### 2.3. Цепочка разделов

Рекурсивный шаг берёт следующий раздел `LATERAL`-подзапросом к
`position_items` по первичному ключу (`q.id = chain.next_id`) с барьером
`OFFSET 0` — без барьера планировщик разворачивает подзапрос в соединение и
возвращает хэш по всей таблице (дизайн, «Подходы»). Стартовая часть, колонки,
`CYCLE`-разметка, `ORDER BY start_id, depth`, проверка `is_cycle` с
`RoutingError` и пустой вход — без изменений. Текст запроса по-прежнему
начинается с `WITH RECURSIVE chain` (на нём держится проверка подготовленного
плана в `TestChapterPaths`). Правка внутри `_chapter_chain_rows` — одна на всех
вызывающих `chapter_paths` и `chapter_steps`.

Рядом с запросом — комментарий, почему барьер нужен: иначе следующий читатель
уберёт «лишний» `OFFSET 0`.

### 2.4. Замер на коде приложения

`measure.py` из папки дизайна сегодня умеет только «до» (функции приложения) и
«после» (прототипы) — после реализации его режим «после» продолжил бы мерить
прототипы, а не код (неблокирующее замечание Codex на гейте 1). Скрипт
получает три варианта:

- `old` — прежний текст обоих запросов, подставленный вместо функций
  приложения (переносится в скрипт дословно из `main`);
- `prototype` — нынешние прототипы;
- `app` — функции приложения без подмен.

Варианты выбираются аргументом (`--variants old,app` и т. п.), каждый вызов
снимается всеми выбранными вариантами попеременно в каждом круге, как сейчас;
равенство ответов сверяется между всеми выбранными вариантами. Итоговый замер
— `--variants old,app` на коде ветки: «до» и «после» в одном процессе и одном
прогоне, без сравнения с цифрами другого дня. `results.json` дизайна остаётся
как есть — это замер прототипа; итоговый пишется рядом отдельным файлом.

### 2.5. Грабли

В `docs/pitfalls/db.md` — два пункта:

- маленькая справочная таблица после заливки дампа остаётся без статистики:
  порог автоанализа (50 изменений + 10 %) не достигается, оценка фильтра падает
  до 1 строки, и запрос получает вложенный цикл с полным просмотром соседней
  таблицы на каждую строку; лечится формой запроса (сначала отбирать редкое),
  а не надеждой на `ANALYZE`;
- рекурсивный CTE: рабочая таблица оценивается в разы больше стартового
  набора, и шаг рекурсии получает хэш по всей таблице; `LATERAL` без барьера
  планировщик разворачивает обратно, барьер — `OFFSET 0`.

## 3. Проверки

Уровень — где живёт дефект: фильтры и форма результата — прямые
интеграционные тесты двух функций на тестовой базе; скорость — замер на
`gca_dev` (на маленькой базе планы другие, тестом скорость не проверить).
Новые тесты пишутся ДО правки запросов и обязаны быть зелёными и на старом
запросе, и на новом: они фиксируют поведение, а не форму.

1. **Фильтры `_conflicted_parameters`.** В одном вызове контексты, каждый из
   которых проверяет одно условие:
   - главный параметр с `path_conflict` — в результате;
   - второстепенный параметр с `path_conflict` — нет;
   - главный параметр в архиве с `path_conflict` — нет;
   - главный параметр с источником не `path_conflict` (значение из
     наименования) — нет;
   - контекст с `path_conflict`, не переданный во входе, — нет;
   - контекст с двумя главными параметрами в конфликте — один ключ схемы с
     обоими параметрами.

   Пустой вход — `{}` без запроса (счётчик запросов сеанса).
2. **Шаги `chapter_steps`.** Цепочка из трёх уровней и две строки на разных
   ветках под общим корнем: у каждой строки шаги сверху вниз, корень первым,
   сам раздел последним; у каждого шага — его ключ, название и номер в файле
   (`item_number_in_proposal`, в том числе пустой). Раздел без родителя — один
   шаг.
3. **Порядок, циклы, подготовленный план цепочки** — существующие
   `TestChapterPaths`, без правок, зелёные на новом запросе.
4. **Конфликт в сцене аналогов** — существующий
   `test_path_conflict_of_the_main_parameter_is_not_a_match`, без правок.
5. **Стенд, замер.** `measure.py --variants old,app --rounds 3` на `gca_dev` на
   коде ветки: ответы `old` и `app` совпадают во всех трёх вызовах; в каждом
   вызове медиана `app` по каждому из двух запросов — не больше 0,3 с на ответ
   (в замере прототипа: 0,04–0,17 с), а медиана всего ответа `app` — не больше
   половины `old`. Цифры и планы `app` — в devlog.

Снятия — по правилу проверок по риску (только критические свойства): фильтр
конфликтов решает, какая строка истории годится в аналоги, то есть какая цена
окажется «нашей». Поэтому проверка 1 предъявляется снятием каждого из трёх
условий (`role`, `archived_at`, `source`) и условия на вход в новом запросе —
тест обязан покраснеть. У цепочки разделов денежного свойства нет; её держат
существующие тесты 3 и новый 2 без снятий.

## 4. Отвергнутые альтернативы

Сверх дизайна («Подходы»):

- **Текстовый SQL для запроса конфликтов.** Сегодня он на Core со ссылками на
  колонки моделей; переход на текст потерял бы эти ссылки ради одного
  `MATERIALIZED`, который Core выражает префиксом CTE.
- **Подзапрос `IN (SELECT …)` вместо CTE.** Планировщик вправе развернуть его в
  соединение с той же ошибочной оценкой — защиты от плана он не даёт.
- **Тест на форму плана (`EXPLAIN` в тесте).** На маленькой тестовой базе
  планировщик выбирает другие планы и при старом запросе; тест проверял бы
  настройки планировщика, а не код.

## 5. Границы

- Не делается: кэш этапа, объединение двойных вызовов, `ANALYZE` и индексы
  (дизайн, «Не цели»).
- Не меняются: вызывающие обеих функций, фронт, API, справочник
  (`docs/reference/`), `AGENTS.md`.
- Карта (`docs/product-roadmap.md`, пункт 3): после фичи — запись о сделанной
  первой части со ссылкой на devlog и остатком (кэш — по замеру).

## 6. Definition of Done

- Проверки 1–2 — новые тесты, зелёные на старом и новом запросе; проверка 1
  предъявлена снятием каждого из четырёх условий.
- Проверки 3–4 и затронутые наборы (`test_semantic_api.py`,
  `test_analog_scene.py`, `test_variant_params_load.py`,
  `test_our_price_offer_api.py`, `test_ref_analogs_panel.py`) зелёные без
  правок; полный прогон — GitHub Actions.
- Проверка 5 — на стенде, цифры и планы в devlog.
- `docs/pitfalls/db.md` — два пункта §2.5.
- `docs/devlog/2026-11-18-our-price-slow-queries.md`: что сделано, замер,
  тронутые области и прочитанные файлы граблей (`db.md`, `runs.md`) —
  AGENTS §10; запись в карте.
