# Async Processing — Ступень 1: асинхронный контракт (202 + polling + dedup)

**Статус:** дизайн одобрен (2026-07-19, два раунда правок: [1] терминальный переход, sweep+pending, rollback в dedup-гонке, замена тостов; [2] Codex-ревью — no-overlap deployment, алгоритм QueryCache-детектора, ветка `winner is None` в dedup-гонке, guard на `pending`, тип `UploadResponse`, AC-S1-2 → смоук).
**Базовая спека:** `docs/superpowers/specs/2026-07-16-async-processing-design.md` §4 (S1-1…S1-7, AC-S1-1…6) и §7 Q6. Этот документ уточняет её решениями уровня реализации; при расхождении текстов побеждает этот документ.
**Предусловие:** Ступень 0 в main (PR #36, merge `21c8854`): фазы A/B, `process_document` c DI-фабрикой сессий, guard `try_acquire_processing`, условная error-запись, FOR UPDATE-защита мутаций, `last_error` в API/UI.

## Цель

Убрать висящий 3-минутный запрос: эндпоинты обработки отвечают немедленно (`202` + документ в `processing`), результат доезжает через polling. Обрыв клиента больше не влияет на обработку. Плюс идемпотентный upload по `file_hash` (Q6).

**Поставка:** один комбинированный PR (бэкенд + фронт) — по частям бессмысленны, main не бывает в сломанном состоянии.

---

## 1. Бэкенд: 202-контракт эндпоинтов (S1-1, S1-2)

Все три эндпоинта (`upload`, `reparse`, `deskew-reparse`) выполняют быструю синхронную часть и ставят `process_document` в `BackgroundTasks`:

- Синхронно (до 202): валидация; для upload — S3-запись; существующие проверки 404/400/verified-409; guard `try_acquire_processing` → 409.
- `background_tasks.add_task(process_document, doc_id, mode=..., pdf_bytes=... (только upload), session_factory=session_factory)` — фабрика из существующей DI `get_processing_session_factory` (S1-3 закрыт архитектурой S0; request-scoped `db` в таску не передаётся).
- Ответ: **`202 Accepted` + сериализованный документ со `status="processing"`**. Единый контракт формы для upload (оба кода): поле `invoices` ПРИСУТСТВУЕТ всегда — для свежего 202-документа это `[]` (СФ ещё нет), для дубликата — реальный набор победителя; поле `duplicate` присутствует всегда (`false` на 202, `true` на 200-дубликате) — один shape, не два неявно разных. Frontend-тип:

  ```ts
  type UploadResponse = DocumentDetail & { duplicate: boolean };
  ```

  (`frontend/src/services/api/upload.ts` — сейчас `Promise<DocumentDetail>`, поля `duplicate` нет — тип меняется вместе с контрактом.) Breaking change тела, не статус-кода — axios принимает любой 2xx, MSW-хэндлеры статус не проверяют.
- `rotations_applied` удаляется из ответа deskew (S1-2): фронт не читает, логирования в pdf_orientation достаточно.
- **deskew теряет синхронный маппинг 413/502** (следствие §2.2: фоновой таске отвечать некому, `reraise=False`). Ошибки ориентации доезжают как `status="error"` + человекочитаемый `last_error` через polling. HTTP-тесты на 413/502 deskew заменяются тестами на терминальный `error` + текст `last_error`.

## 2. Бэкенд: дедуп upload по file_hash (Q6)

Колонка `documents.file_hash` (String(64), index) и констрейнт `uq_documents_project_file_hash` уже существуют (миграция d1e2f3a4b5c6); сегодня хеш при загрузке не вычисляется. Новая миграция не нужна.

Алгоритм upload (полная последовательность — перечисление и есть код):

1. Валидация `.pdf` → чтение байтов → `file_hash = sha256(исходных байтов)`. Хеш **оригинала**; после deskew НЕ пересчитывается (инвариант Q6: пересчёт молча ломает дедуп).
2. **Fast-path:** SELECT документа по `(project_id, file_hash)`. Найден → ответ `200 {"duplicate": true, ...сериализованный существующий документ}`; S3 не пишем, новый документ не создаём.
3. Не найден → S3-запись → `create_document(..., file_hash=file_hash)` + commit. **`create_document` (crud/documents.py:32) расширяется параметром `file_hash`** — в текущей сигнатуре его нет.
4. **Гонка** (две параллельные загрузки одного файла): commit падает `IntegrityError` → **`db.rollback()`** (обязателен: сессия в failed state, без него чтение победителя упадёт `PendingRollbackError`) → прочитать победивший документ по `(project_id, file_hash)`:
   - **победитель найден** → best-effort удалить СВОЙ S3-объект через `delete_file_async` (эндпоинт async — синхронный `delete_file` заблокировал бы loop; ошибка удаления — warning-лог, не 5xx) → ответ `200 duplicate:true` с документом-победителем;
   - **`winner is None`** → `IntegrityError` был НЕ про `uq_documents_project_file_hash` (например, FK проекта) — blanket-обработка запрещена: удалить свой S3-объект (`delete_file_async`, best-effort) и **перевыбросить исходную ошибку** (обычный 5xx/422-путь).
5. Не дубликат → guard → add_task → `202` (см. §1).

Дубль, пока оригинал ещё обрабатывается: fast-path вернёт `200 duplicate:true` с документом в `processing` — строка Upload покажет «Файл уже был загружен» и статус «обрабатывается» через подписку. Это ожидаемое поведение, не совпадение.

Дубль при существующем документе в `error` — тоже ожидаемое поведение: повторная загрузка того же файла после неудачи вернёт «Файл уже был загружен» со ссылкой на error-документ; **путь ретрая — кнопка reparse** на нём (байты в S3 есть), а не повторный upload. Пользователь, «перезагружающий» файл как способ ретрая, упирается в понятный UI со ссылкой — осознанный размен, не баг.

Бэкфилл хешей старых документов не делается — дедуп работает для новых загрузок.

## 3. Бэкенд: startup-sweep (S1-4)

В `lifespan` (main.py), до `yield`, одним UPDATE:

```sql
UPDATE documents SET status='error', last_error='Обработка прервана перезапуском сервера'
WHERE status IN ('pending', 'processing')
```

- **`pending` включён обязательно**: crash в окне между commit `create_document` (pending) и guard-commit (processing) оставил бы зомби-pending навсегда, а `pending` нетерминален для polling — один такой документ заставил бы список поллиться вечно. На старте процесса легитимных `pending`/`processing` не существует (однопроцессная модель).
- Залогировать количество переведённых строк.
- **Deployment-инвариант: `workers=1, replicas=1` И no-overlap deployment** — sweep корректен только когда новый процесс стартует ПОСЛЕ полной остановки старого (stop-then-start / recreate, НЕ rolling): при overlap новый процесс пометил бы живые таски старого как `error`. Комментарий в justfile инвариант не обеспечивает — он его документирует; обеспечение — выбор стратегии деплоя (зафиксировать в деплой-конфиге/доке при развёртывании прод; прод пока не развёрнут). Проверка входит в AC (AC-S1-3b). Advisory-lock-вариант (process-wide PostgreSQL advisory lock на старте) отложен: реальная защита от overlap понадобится вместе с `workers>1` — это триггер и повестка Ступени 2. Uvicorn `--reload` в dev перезапускает воркер stop-then-start — инвариант соблюдён.
- Dev `--reload`: sweep срабатывает на каждую правку кода — желаемое поведение.
- Таймаут-детектор по `processing_started_at` НЕ делается (Q5, отложен до S2).

## 4. Фронт: polling (S1-5)

`services/queries.ts`, react-query **v5** (`^5.100.9`):

- Хелпер `processingRefetchInterval` — колбэк для `refetchInterval: (query) => ...`: в данных есть документ с нетерминальным статусом (`pending` | `processing`) → `2500`, иначе `false`.
- Вешается на **оба** хука: `useDocuments` (список: поллим, пока есть хоть один нетерминальный док) и `useDocument` (карточка: Review-страница иначе не увидит завершения reparse).

## 5. Фронт: терминальный переход (S1-7)

**Механизм — один глобальный слушатель QueryCache** (в App.tsx, рядом с созданием `QueryClient`):

```typescript
queryClient.getQueryCache().subscribe(event => ...)
```

Алгоритм детектора (фиксируется, т.к. один документ живёт одновременно в list- И detail-квери — снапшот «на квери» дал бы по инвалидации от каждой):

1. Состояние — **общая `Map<documentId, status>`** на весь детектор (НЕ снапшот на query): обе квери пишут в одну карту, второй репорт того же перехода видит уже обновлённый статус и не срабатывает.
2. Фильтрация событий: только `type === "updated"` квери с ключами documents **list/detail** (по префиксу queryKey); прочие квери игнорируются.
3. `event.query.state.data` имеет ДВЕ формы: массив (list-квери) и одиночный объект (detail-квери) — **нормализовать к массиву** (одиночный док → `[док]`) перед итерацией. Для каждого документа: прочитать прежний статус из Map, **обновить Map ДО вызова `invalidateQueries`** (иначе инвалидация, синхронно передёрнув кэш, может репортнуть тот же переход повторно).
4. Переход = `prev ∈ {pending, processing}` И `next ∈ {parsed, error}`. **Первое наблюдение документа** (в Map нет записи) переходом НЕ считается — иначе первая загрузка списка с терминальными документами дала бы шквал ложных инвалидаций.
5. На переходе: инвалидировать documents list/detail + dashboard-квери проекта (ровно один раз на документ при упорядоченных ответах — гарантируется пунктами 1 и 3). **Семантика — at-least-once**: запоздалый out-of-order ответ (in-flight detail-запрос, стартовавший до перехода и донёсший старый `processing` после него) откатит Map и следующий свежий ответ даст повторную инвалидацию — это допустимо (инвалидация идемпотентна, цена — лишний refetch в редкой гонке). Отличить такой откат от ЛЕГИТИМНОГО даунгрейда (новый reparse: parsed → processing) на уровне детектора невозможно без ordering-метаданных, а легитимный даунгрейд обязан записываться — иначе следующий терминальный переход не сработает.
6. Подписка создаётся один раз рядом с `QueryClient`; **обязательный unsubscribe / защита от повторной подписки при HMR** (module-scope флаг или cleanup — иначе dev-режим накапливает слушателей и инвалидации множатся).

- **Почему не `onSuccess` на квери:** в react-query v5 `onSuccess`/`onSettled` из `useQuery` удалены (существующие onSuccess в queries.ts легальны — они на мутациях). **Почему не `useEffect` в хуках:** переход детектился бы каждым подписчиком (список + карточка + N строк Upload) — инвалидации задвоились бы (идемпотентно, но шумно). Один детектор на приложение — центральная оркестрация.
- Инвалидация dashboard — **на терминальном переходе**, не при постановке (на 202 новых СФ ещё нет).
- **Терминальный переход операционного тоста НЕ даёт** (детектор не знает, какая операция шла — reparse/deskew/upload) — только инвалидация. Осознанный размен: обратная связь о завершении — смена статуса/бейджа в UI.

## 6. Фронт: тосты и UI-состояния (S1-6, S1-7)

- Тосты мутаций reparse/deskew: «Документ переразобран» (queries.ts:190) и «Документ выпрямлен и переразобран» (queries.ts:~203) **ЗАМЕНЯЮТСЯ** на «Обработка запущена» — success мутации теперь означает «поставлено в очередь», старые тексты лгут. Не добавить рядом, а заменить.
- Upload-страница: `j.result.invoices` (Upload.tsx:170) уходит. Каждая строка job'а после 202 — компонент **`<UploadJobRow>`** с `useDocument(result?.id, { enabled: !!result?.id })` внутри (хук не дёргается до 202). Per-row компонент инкапсулирует оба этапа жизненного цикла строки — локальный (uploading/ошибка загрузки, машина `pending|uploading|ready|error`) и серверный (processing → parsed/error из query-кэша). Альтернатива `useQueries` на уровне страницы отвергнута: размазала бы этапы между страницей и строкой + глобальный ререндер на каждый tick. Hook в `jobs.map` — нарушение Rules of Hooks, поэтому именно компонент.
- Терминальное состояние строки job'а — из статуса документа; список СФ с confidence-бейджами и кнопка «Проверить» — из документа в query-кэше (не из снапшота ответа).
- UX дубликата: нейтральный бейдж **«Файл уже был загружен»** (формулировка Q6 базовой спеки; не error-стиль) + ссылка на существующий документ. Если документ-дубликат в `processing` — строка дополнительно показывает «обрабатывается».
- Бейдж «Обрабатывается» в списках документов (ProjectPage; ErrorDocsTab не трогаем — он фильтрует терминальный `error`).
- Дизейбл для документов в `pending|processing`: кнопки reparse/deskew, verify/редактирование/удаление СФ, удаление документа.
- **Серверная часть обязана совпасть с UI:** текущий `_reject_if_processing` (routers/invoices.py:40) проверяет ТОЛЬКО `status == "processing"` — `pending`-документ в окне между commit `create_document` и guard-commit можно удалить, оставив S3-сироту. Хелпер расширяется до `status in ("pending", "processing")` (и переименовывается сообразно, например `_reject_if_busy`); 409-тесты S0-8 дополняются параметром `pending`. Легитимных мутаций pending-документа не существует (у него нет СФ и он не показан пользователю как готовый).

## 7. Тестирование (AC-S1-1…6)

Backend:
- AC-S1-1: 202, `status="processing"`, `invoices: []`, `duplicate: false` (единый shape §1); enqueue проверяется **структурно** (спай/мок `BackgroundTasks.add_task` подтверждает постановку) — wall-clock непроверяем (Starlette TestClient выполняет background tasks до возврата ответа). Тайминг — ручной смоук через реальный uvicorn; фиксируется в тест-плане, не в CI.
- AC-S1-2: обрыв клиента после 202 не влияет на результат. **В CI непроверяем**: TestClient выполняет background tasks ДО возврата ответа — «закрыть response и проверить БД» дал бы ложноположительный тест (таска уже завершилась к моменту получения ответа). Гарантия структурная (Starlette выполняет BackgroundTasks после отправки ответа независимо от состояния соединения); проверка — **ручной смоук через реальный uvicorn** (upload → убить клиента → дождаться `parsed` в БД), фиксируется в тест-плане рядом со смоуком тайминга. Если в ходе реализации появится дешёвый ASGI-harness с разрывом соединения после 202 — тест добавляется, но AC им не обусловлен.
- AC-S1-3: sweep — документы в `pending` И `processing` + перезапуск lifespan → оба в `error` с внятным `last_error`.
- AC-S1-3b: no-overlap deployment зафиксирован — комментарий-инвариант в justfile (`dev-backend`) + раздел в `docs/agent/pdf-parsing.md` («новый процесс — только после полной остановки старого; rolling запрещён до S2»); проверка — ревью текста, не автотест.
- Q6: повторный upload того же файла → `200 duplicate:true`, S3 не растёт, новый документ не создан; дубль во время обработки оригинала → `200 duplicate:true` со статусом `processing`. Гонка — ДВА теста: (а) юнит с мок-сессией на последовательность `IntegrityError → rollback → победитель → delete_file_async → 200` и на ветку `winner is None → re-raise`; (б) **конкурентный integration-тест с двумя реальными DB-сессиями** (паттерн из test_conditional_error_write_concurrency): две параллельные вставки одного `(project_id, file_hash)` → в итоге ровно один документ, ровно один enqueue, ровно один живой S3-объект.
- deskew: прежние HTTP-тесты 413/502 заменяются на «терминальный error + last_error» (см. §1).

Frontend:
- AC-S1-4: юнит на `processingRefetchInterval` (нетерминальный → 2500, терминальный → false).
- AC-S1-5: компонентный тест Upload с MSW — после 202 строка «обрабатывается», после завершения polling'а — СФ из данных query; тест дубликата («Файл уже был загружен»).
- Тест дизейбла кнопок для processing-документа; тест замены тостов («Обработка запущена»).
- Тест детектора терминального перехода — три случая: (а) переход в одной квери → инвалидация ровно один раз; (б) тот же документ репортится list- И detail-кверями → всё равно ровно один раз (общая Map, п.1/3 алгоритма §5); (в) первое наблюдение терминального документа (свежая Map) → ноль инвалидаций.
- AC-S1-6 (E2E Playwright: upload → бейдж → СФ) — сценарий зафиксирован, реализация в E2E-эпике, вне S1.
