# План фичи — из утверждений, а не из кода

**Гейт 1 пройден 03.09.2026** в диалоге. Источник — предложение
`docs/proposals/2026-09-02-plans-as-assertions.md`, которое этой спекой
заменяется и удаляется (`docs/proposals/README.md`: двух правд об одном решении
быть не должно).

**DoD фичи.** `AGENTS.md` §9.1 запрещает плану нести тела тестов и тела
реализации; §9.2 описывает состав задачи плана в новой редакции; существует
`docs/superpowers/plans/TEMPLATE.md`. Правка только документации, поэтому по
§9.1 — без плана.

## 1. Проблема с замерами

За девять смерженных фич (PR #25–#36) добавлено 87 350 строк:

| Слой | Строк | Доля |
|---|---|---|
| Документы (`docs/` + `AGENTS.md`) | 38 254 | 44 % |
| Тесты | 24 618 | 28 % |
| Код фронта | 13 335 | 15 % |
| Код бэка | 10 658 | 12 % |

Внутри документов (7 фич): **планы 16 959 строк**, спеки 12 649, devlog 5 261,
инсайты 598, `TECH_DEBT.md` 419, `AGENTS.md` 468. Планы — крупнейший класс
документов проекта.

Объём плана сопоставим с объёмом кода, который по нему пишется:

| Фича | План, строк | Код фичи (бэк + фронт), строк |
|---|---|---|
| `tenders-contour` | 6 010 | 3 750 |
| `round-unallocated` (#37) | 3 242 | 2 362 |
| `position-drilldown` | 2 821 | 3 405 |
| `stage-summary` | 2 448 | 2 382 |
| `passport-volumes` | 2 300 | 1 070 |
| `parser-columns-by-header` | 2 193 | — |

**Решающий замер — не объём, а состав.** В плане `round-unallocated` (3 242
строки) **2 200 строк лежат внутри блоков `` ``` ``, то есть 68 %**. Это 53
блока кода. Task 1 несёт 165 строк тел тестов («Step 1: написать падающие
тесты») и следом 162 строки тела реализации («Step 3: Реализация») — то есть
план содержит и тесты, и реализацию целиком. План перестал быть планом и стал
первым черновиком кода.

Круги ревью гейта 3, которые этим оплачены: в `main` семь коммитов правок плана
по кругам, из них четыре на одной фиче — `438786b` («четыре P1 и два P2»),
`d01bbe5`, `ba9780d`, `572572f` («компонентный тест пилюли и **три пересказа
контракта**»). Отдельно от них 21 коммит «круг ревью» уже по реализации.

**Контрпример, который надо знать:** у #37 кругов ревью плана **ноль** при
плане на 3 242 строки. Значит объём плана и круги ревью — две разные цены.
Фича бьёт по первой наверняка, по второй — вероятно.

## 2. Что уже сказано в §9.1 и почему этого мало

Действующая редакция требует на гейте 3 пройти `grep`-ом по каждому имени,
которое план упоминает, и пометить несуществующие. Правило верное, но оно не
убирает **возможность** нарушения: план вправе содержать законченный код, а
корректность держится на том, что ревьюер проверит каждое имя. Семь кругов —
цена этой конструкции: ошибка обнаруживается проверкой, а не отсутствует по
построению.

Там же зафиксирован вывод, который эта фича доводит до конца: «утверждения с
числами в планах не подводили ни разу: ломается обвязка, а не смысл»
(`docs/insights/replaying-new-rules.md`, слой 1).

## 3. Решение

### 3.1. Граница: плану разрешены подписи и типы, запрещены тела

**Разрешено:** датаклассы, константы, `TypedDict`/интерфейсы, сигнатуры функций
и методов, форма ответа API, имена маршрутов. Это интерфейс, и именно о нём
гейт 3 договаривается.

**Запрещено:** тела тестов (`def test_…` с `assert`, `describe`/`it`),
тела реализации, готовые фикстуры, рукописные JSON-ответы целиком.

Замер на Task 1 плана #37: 327 строк кода (165 тестов + 162 реализации)
сокращаются примерно до 40 — остаются датаклассы `Vector`, `Classification`,
`ChapterNode`, константы состояний и подпись `classify`.

### 3.2. Состав задачи плана

1. **Files** — что создаётся, что правится, где тест.
2. **Interfaces** — что задача потребляет из проекта и что производит
   (подписи и типы по §3.1).
3. **Утверждения** — списком, о поведении. Каждое проверяемо и не содержит
   имён, кроме введённых самой задачей.
4. **Имена**: заводимые этой задачей — помечены; существующие, на которые
   задача опирается, — перечислены.

### 3.3. Числа: остаются те, что утверждают

Уточнение к формулировке предложения «числа остаются». Правило точнее:
**остаются числа, которые что-то утверждают; уходят произвольные литералы
фикстур.**

- `category=11`, `T1 = dt.datetime(2026, 8, 29, …)`, `note="раз"` — обвязка,
  уходят; вместо них утверждение «различие в статье порознь даёт `conflict`».
- «объём раздела 159 342 против 39 836 на одном файле», «медиана считается по
  нетто», «`(matched_cache + matched_exact) / positions_total ≥ 90 %`» —
  утверждения, остаются.

Признак: если число можно заменить любым другим той же природы, не поменяв
смысла утверждения, — это обвязка.

### 3.4. Как выглядит утверждение

Task 1 плана #37 в новой редакции — вместо 165 строк тел тестов:

> **`classify(vectors)`**
> - пустой радиус — ошибка контракта (`ValueError`), а не состояние;
> - ни одного решения → `unassigned`; часть → `partial`; все и одинаковые →
>   `resolved`; все и различающиеся → `conflict`;
> - `assigned` — смет с решением, `total` — offer-смет в радиусе;
> - конфликт определяется **покомпонентно**: различие в статье, заметке, авторе
>   или времени порознь даёт `conflict`. Четыре негативных случая, каждый
>   нарушает ровно одну компоненту;
> - `categories` и `notes` — различные значения в порядке первого появления;
>   `None` в заметке — значение, а не пропуск;
> - `audit_differs` истинно тогда и только тогда, когда различаются
>   `assigned_by` или `assigned_at`;
> - у раунда из одной сметы состояний ровно два;
> - **свойство разбиения**: на всех кортежах длины 1–3 из домена {нет решения,
>   базовый вектор, иной по каждой из четырёх компонент} кортеж попадает ровно
>   в одно состояние — исчерпывающе и без пересечений.

Ни один факт исходных 165 строк не потерян: покомпонентные негативные случаи,
`None` как значение, порядок первого появления, свойство разбиения — всё
названо. Утрачены только литералы.

## 4. Отвергнутые альтернативы

1. **Оставить как есть, ужесточив гейт 3.** Испробовано и записано в §9.1:
   шесть кругов на пересчёте НДС, четыре на `position-drilldown`.
2. **Запретить в плане любой код, включая подписи.** Отвергнуто на гейте 1:
   форму ответа API словами описывать мучительно, а интерфейс — это то, о чём
   гейт 3 и договаривается.
3. **Разрешить тела тестов «там, где словами неясно».** Отвергнуто на гейте 1:
   «неясно» — резиновый критерий, через две фичи план вернётся к 2 000 строк.
4. **Генерировать тесты из плана.** Превращает план в исходник: он получает
   собственную корректность и расходится с кодом так же, как расходятся два
   описания одного контракта.
5. **Отказаться от плана вовсе.** Гейт 3 нужен для согласования состава задач и
   границ фичи; без плана исчезает единственное место, где виден скоуп до
   начала работы.
6. **Лимит на строки плана (например, 500).** Не отличает утверждение от
   эскиза: 500 строк эскизного кода дадут те же круги, только реже.

## 6. Чем проверяется, что сработало

Два счётчика на следующих трёх фичах:

- **доля строк внутри блоков `` ``` `` в плане** — ожидание ниже 25 % против
  нынешних 68 %. Это прямой признак запрета, а не следствие;
- строк плана на фичу — ожидание ниже 800 против 2 200–6 000;
- коммитов «круг ревью плана» на фичу — ожидание 0–1 против до четырёх.

**Исход, при котором надо откатываться:** строки плана упали, а круги ревью
РЕАЛИЗАЦИИ выросли. Это означало бы, что план нёс не только обвязку и часть его
содержания была нужна. Различимо по тем же счётчикам, поэтому проверка стоит
одного `git log`.
