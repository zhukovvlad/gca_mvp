# Параметры варианта с названиями — спека (гейт 2)

**Редакция 1, 17.11.2026.** Ветка `feat/variant-params`, черновой PR #89.
Вход — [дизайн, редакция 2](../design/2026-11-17-variant-params.md) (гейт 1:
два круга Codex, второй без блокирующих замечаний, 17.11.2026) и
[макет](../design/2026-11-17-variant-params/mockup.html). Спека уточняет
дизайн и при расхождении побеждает (`AGENTS.md` §9.2); расхождения собраны в
§2.11. Замечание P3 второго круга Codex (перечень «как учитывается» против
«можно не учитывать» строки без ступени) решено признаком основания у строки
(§2.3).

Сокращения: **строка КП** — позиция сметы КП участника; **строка каталога** —
контекст (`catalog_contexts`), которому принадлежит строка КП; **запись
значения** — строка `context_parameter_values` строки каталога; **схема
варианта** — версия схемы параметров, на которой стоит вариант строки
каталога; **действующая схема** — `frozen` версия семьи.

## 1. Что есть (разведка кода и стенда 17.11.2026)

### 1.1. Код

- **Подпись варианта** — `crud/our_price_load._variant_infos`: семья, затем
  тексты значений активных главных параметров **схемы варианта** по `ordinal`,
  пустое — «не уточнено», через « · ». Четыре запроса на любое число
  вариантов. `main_values` и `forms` (id составного либо `"simple"`) — только у
  варианта на действующей схеме. Отдаётся строкой `variant_label`
  (`crud/our_price._line_view`).
- **Второстепенные** — `_secondary_values`: записи значений строки каталога с
  ролью `secondary`, текст уже собран сервером («не уточнено», «не из списка:
  «…»»). Параметр **без записи** в список не попадает вовсе. Отдаются
  `secondary: [{name, value}]`.
- **Запись значения** хранит `source` (`name`, `path`, `manual`,
  `path_conflict`, `none`, `off_list`), `off_list_text` и
  `refresh_requested_at` (миграция 0022). Записи лежат по действующей схеме;
  идентификаторы параметров у каждой версии свои (`family_parameters.id` —
  первичный ключ версии).
- **Лестница работ** — `services/analog_ladder.ladder_for`: ступени 1/3 — тот
  же вариант; 2/4 — ключ `_values_key`: значения неотпускаемых главных
  (`_required_ids`) и **формы** отпускаемых (`_releasable_ids`, `_form`;
  конфликт читается как простое). Ступени 2/4 есть, только если схема строки —
  действующая и у семьи есть отпускаемый параметр (`releasable IS TRUE`;
  `NULL` — не отпускается). `WorkLadder.released` — имена всех отпускаемых
  параметров семьи на ступенях 2/4.
- **Лестница систем** — `services/our_price.LineKey.at`: `v` — вариант
  целиком, `p` — `(семья, первый главный)` без сравнения остальных и их форм,
  `f` — семья. Первый главный есть только у варианта на действующей схеме с
  двумя и более главными.
- **Ответ панели** (`build_line_view`): аналоги ступени — `_analogs_view` (без
  значений параметров); у кандидатов лестницы `WorkHistoryLine.main_values`,
  `forms`, `conflicted` уже есть.
- **Фронт.** `OfferLinesTable` — ячейка «Работа»: `variantCaption` (подпись
  либо семья) и ⓘ со второстепенными в `title`; клик по строке таблицы
  открывает панель (`onClick` строки). `LineSheet` — подзаголовок
  `variantCaption`, строка «Второстепенные» в «Ценах»; `workRungLabel` —
  «тот же вариант» / «без {имена}» в таблице, панели и `ReferenceBlocks`.
  `refReleased` («отпущен: …») нигде не вызывается.

## 2. Решение

### 2.1. Что сдаёт фича

1. Поле `params` строки КП и признак `params_basis` в ответах разбора
   участника и панели (§2.2–§2.4).
2. Колонки значений отпущенных параметров у аналогов панели (§2.5).
3. Подпись ступени без номера и слова «отпущен» (§2.6).
4. Таблица «Против нашей цены»: семья и параметры столбиком, первые три,
   «подробнее / свернуть» (§2.7).
5. Панель: подзаголовок — семья; раздел «Работа» (§2.8).

Цифры, состояния строк, вилки, цели, плитки, итоги, файл подрядчику и
комментарий **не меняются ни в одном сценарии**. `variant_label` и `family`
остаются в ответе.

### 2.2. Параметры строки

**Состав и порядок.** Только у строки с вариантом; без варианта `params = []`.
Сначала активные главные параметры **схемы варианта** по `ordinal` (те же, что
в `variant_label`), затем активные второстепенные **действующей схемы** семьи
по `ordinal`.

**Значение** (`value`: текст или `null`):

- главный — текст значения **варианта** (по нему шёл подбор); составное —
  его текст («трансферные конструкции + балки + капители»);
- второстепенный — текст значения записи.

**Откуда** (`source`) — закрытое множество из девяти:

| `source` | Когда | Показ «откуда» |
|---|---|---|
| `name` | запись, `source = name` | из наименования |
| `path` | запись, `source = path` | из разделов смет |
| `manual` | запись, `source = manual` | задано вручную |
| `path_conflict` | запись, `source = path_conflict` | разделы расходятся |
| `none` | запись, `source = none` | нет ни в наименовании, ни в разделах |
| `off_list` | запись, `source = off_list` | не из списка |
| `refreshing` | у записи `refresh_requested_at` | уточняется: прежнее значение |
| `missing` | записи нет | ещё не разобрано |
| `old_schema` | главный параметр варианта не на действующей схеме | по прежней версии схемы |

Порядок проверки: `old_schema` (только главные) → `missing` → `refreshing` →
источник записи. Запись главного ищется по `parameter_id` — у варианта на
действующей схеме идентификаторы совпадают; у варианта на прежней схеме
записи не сопоставляются, и все его главные — `old_schema`.

**Показ значения** (одна функция фронта для таблицы и панели):

| Условие | Текст |
|---|---|
| `source = missing` | ещё не разобрано |
| `source = path_conflict` | расходится по разделам |
| `source = off_list` | не из списка: «`off_list`» |
| `value = null` | не уточнено |
| иначе | `value`; при `refreshing` — приписка «— уточняется» |

Поля параметра: `name`, `role` (`main` / `secondary`), `value`, `off_list`
(текст записи или `null`), `composite` (главное значение составное — только у
варианта на действующей схеме, где известны формы), `source`, `match` (§2.3).

### 2.3. Как учитывается при подборе

Признак строки `params_basis`:

- `rung` — у работы есть ступень лестницы (`work_rung ≠ null`) или у системы
  ступень семьи (`rung ≠ null`): правила описывают **фактический** подбор
  показанных аналогов;
- `catalog` — работа с вариантом без ступени: правила описывают, что сделала
  бы лестница по настройке каталога (дизайн §6 п. 1);
- `null` — система без ступени или строка без варианта: `match` у всех
  параметров `null`.

`match` параметра — `required` / `ignored` / `same_set` / `null`. Правило —
одна функция в `services/analog_ladder.py` рядом с `_values_key`, на тех же
`_required_ids`, `_releasable_ids`, `_form`:

| Строка | Главный параметр | `match` |
|---|---|---|
| работа, ступень 1 или 3 | любой | `required` |
| работа, ступень 2 или 4 | неотпускаемый | `required` |
| работа, ступень 2 или 4 | отпускаемый, форма составная | `same_set` |
| работа, ступень 2 или 4 | отпускаемый, форма простая (в т. ч. конфликт) | `ignored` |
| работа без ступени, ступени 2/4 доступны | как ступень 2 | — |
| работа без ступени, ступени 2/4 недоступны (прежняя схема, нет отпускаемых) | любой | `required` |
| система, уровень `v` | любой | `required` |
| система, уровень `p` | первый главный | `required` |
| система, уровень `p` | остальные | `ignored` |
| система, уровень `f` | любой | `ignored` |
| любая с `params_basis = null` | любой | `null` |

Второстепенный параметр — всегда `ignored` (при `params_basis ≠ null`).

**Подписи** (фронт):

| `match` | `rung` | `catalog` |
|---|---|---|
| `required` | должен совпасть | должен совпасть |
| `ignored` | не учитывается | можно не учитывать |
| `same_set` | нужен такой же набор | нужен такой же набор |
| `null` | — | — |

У работы заголовок колонки «При подборе» несёт подсказку: «Не учитывается —
значение не сравнивается; сборные строки договоров при этом не берутся.
Нужен такой же набор — строка договора должна быть сборной из тех же частей».
У системы подсказки нет (уровень `p` форм не сравнивает).

### 2.4. API

Ответ разбора участника (строки статей) и панели (`line`, `group_lines`)
получают у каждой строки:

```ts
params_basis: "rung" | "catalog" | null;
params: Array<{
  name: string;
  role: "main" | "secondary";
  value: string | null;
  off_list: string | null;
  composite: boolean;
  source: "name" | "path" | "manual" | "path_conflict" | "none" | "off_list"
        | "refreshing" | "missing" | "old_schema";
  match: "required" | "ignored" | "same_set" | null;
}>;
```

Поле `secondary` **удаляется** (его содержимое — второстепенные в `params`);
`variant_label` остаётся. Сервер собирает состав, значения и источники в
`load_kp_lines` (в `KpLineRow` — параметры без `match`), `match` и
`params_basis` — в `_line_view`, где уже есть результат строки и сведения
семей.

### 2.5. Аналоги: значения отпущенных параметров

Ответ панели получает `analog_columns: Array<{ name: string }>` — отпускаемые
параметры семьи по `ordinal`, только когда ступень работы 2 или 4 (те же, что
`work_rung.released`); иначе `[]`. Каждый аналог — `released_values: Array<{
value: string | null; conflict: boolean; differs: boolean }>` в порядке
`analog_columns`:

- `value` — текст значения строки договора (составное — его текст);
- `conflict` — у строки договора по этому параметру `path_conflict`;
- `differs` — `value_id` строки договора ≠ `value_id` строки КП, либо конфликт
  у любой из двух.

Аналоги ступеней 2/4 все на действующей схеме (`by_values`), поэтому значения
сопоставимы по идентификатору. Тексты — один запрос на ответ по множеству
`value_id`. Блоки «та же работа в другой зоне» и «семья по связи» колонок не
получают (дизайн §5).

### 2.6. Подпись ступени

`workRungLabel`: ступень 1/3 — «тот же вариант» (как сейчас); 2/4 — «без
учёта: {имена через запятую}», у каждого имени первая буква строчная, если
вторая буква не заглавная («Марка по водонепроницаемости» → «марка по
водонепроницаемости», «МАФ» остаётся). Таблица, бейдж панели и
`ReferenceBlocks` меняются вместе — у них одна функция. `refReleased` удаляется
(мёртвый код).

### 2.7. Таблица «Против нашей цены»

Ячейка «Работа»: наименование, путь (если показан), **семья** отдельной
строкой (`family`), под ней параметры столбиком «название: значение», каждый
своей строкой, в порядке `params`.

- Видны первые три. Больше трёх — кнопка «подробнее · ещё N», по ней строка
  таблицы раздвигается и показывает все, кнопка становится «свернуть».
  Состояние — у строки, в памяти компонента, не запоминается; общего
  переключателя нет.
- Нажатие «подробнее» / «свернуть» **не открывает панель** (клик по строке
  таблицы открывает её сегодня).
- Значение — по §2.2; «не уточнено», «ещё не разобрано» и «расходится по
  разделам» — предупреждающим цветом.
- Приписки: «— не учитывается при подборе» у `match = ignored` и «— при
  подборе нужен такой же набор» у `same_set` — **только при `params_basis =
  rung`** и только у главных (второстепенные не учитываются всегда, приписка
  им не нужна); «(из разделов)» у `source = path`.
- Значок ⓘ и подсказка со второстепенными уходят.

### 2.8. Панель строки

- Подзаголовок — семья (`family`), без склейки значений; без семьи — как
  сейчас.
- Строка «Второстепенные» в «Ценах» уходит.
- Новый раздел **«Работа»** сразу после «Цен», если `params` не пуст:
  таблица «Параметр | В строке КП | Откуда | При подборе»; у второстепенного
  под названием — «второстепенный»; «Откуда» — по §2.2; «При подборе» — по
  §2.3, у `catalog` в заголовке колонки — «(аналогов нет — настройка
  каталога)».
- Если хотя бы у одного параметра `source = path` — под таблицей строка:
  «Значение «из разделов смет» общее для строк каталога с этим наименованием;
  они бывают из разных разделов и смет, какой раздел дал значение — не
  хранится».
- Таблица аналогов — колонка на каждый элемент `analog_columns` (заголовок —
  имя), ячейка — значение по §2.2-показу («не уточнено» / «расходится по
  разделам»); `differs` — подсветка.

Компоненты — shadcn/ui, уже стоящие в проекте (таблица, кнопка-ссылка,
подсказка). Макет гейта 1 — образец вида; после каждой фронтовой задачи —
снимок стенда рядом с макетом.

### 2.9. `AGENTS.md`, справочник

- `AGENTS.md` не меняется: инвариантов фича не заводит, наружу ничего не
  уходит.
- `docs/reference/screens.md` — ячейка «Работа» таблицы разбора, раздел
  «Работа» панели, колонки аналогов, подпись «без учёта: …»; места с ⓘ,
  «Второстепенные», «без …» и «отпущен» перечислит план по `grep`.

### 2.10. Скорость и размер ответа

Долг скорости 4а фича не чинит и не усугубляет:

- **Запросы.** `load_kp_lines` — плюс один на ответ: `_secondary_values`
  заменяется чтением записей значений всех параметров строк каталога и
  списка второстепенных действующих схем (два запроса вместо одного); имена
  главных берутся тем же запросом `_variant_infos`, что и идентификаторы.
  Панель — плюс один запрос (тексты значений аналогов). Число запросов не
  зависит от числа строк.
- **Размер.** Разбор оффера 76: не больше +10 % к 6 049 094 байт (≈ 3 300
  параметров по ~110 байт ≈ +6 %, `secondary` уходит).
- **Время.** Разбор оффера 76: медиана трёх прогонов не больше +5 % к медиане
  трёх прогонов на `main` в том же сеансе стенда.

### 2.11. Расхождения с дизайном

1. **«без учёта: марка по водонепроницаемости»** вместо «без учёта марки по
   водонепроницаемости»: родительный падеж имени параметра автоматически не
   построить (имена бывают с прилагательным впереди, «Поверхностная
   плотность»), двоеточие держит именительный.
2. **Справочные блоки** уже подписаны общей `workRungLabel` («без …»), а не
   «отпущен: …» — `refReleased` мёртвый; дизайн §3.2 про «отпущен» в блоках
   выполняется удалением.
3. **Признак основания** `params_basis` вместо четвёртого значения `match`
   (P3 Codex): «можно не учитывать» — та же `ignored` при основании
   `catalog`, один признак на строку.
4. **Приписки в таблице — только при фактической ступени**; у строки без
   аналогов «не учитывается при подборе» в таблице было бы неправдой, её
   правило — в панели.
5. **Строка без варианта** параметров не показывает, в том числе
   второстепенных (сегодня их тоже не видно: ⓘ стоит внутри подписи варианта).
6. **`secondary` удаляется** из ответа, а не дублируется в `params`.

## 3. Отвергнутые альтернативы

- **Четвёртое значение `match = releasable`** — правило и его основание в
  одном поле; таблица §2.3 удвоилась бы, а подпись всё равно зависит от
  основания.
- **Правило «при подборе» на фронте** по `work_rung.released` и `rung.level` —
  фронту не видны формы и отпускаемость; правило жило бы в двух местах.
- **Словарь имён параметров на ответ** вместо имени в каждом параметре —
  экономия ~100 КБ из 6 МБ ценой второго уровня ссылок в контракте.
- **Родительный падеж** через морфологию — см. §2.11 п. 1.

## 4. Границы

Не в этой фиче (дизайн §5): переключатель правила в панели (А12); разбивка
плитки «Не с чем сравнить» (А13); скорость панели и разбора; значения
параметров у справочных аналогов; файл подрядчику; название конкретного
раздела в «откуда».

## 5. Definition of Done

| Свойство | Риск | Снятие |
