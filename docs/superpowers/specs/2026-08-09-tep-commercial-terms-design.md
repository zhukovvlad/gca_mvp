# Дизайн Ф5: ТЭП и коммерческие условия

**Ветка:** `feat/tep-commercial-terms`. **Рамка фазы:**
[phase7-frame.md](../../phase7-frame.md), строка Ф5. **Гейт 1 закрыт** в диалоге
2026-08-09.

Ф5 заводит два блока данных, которые вводятся **руками** и которых в системе нет
вовсе: технико-экономические показатели объекта (площади) и коммерческие условия
договора (аванс, банковская гарантия, удержание). Первый нужен Ф6 как знаменатель
руб/м², второй — как шапка паспорта. Ни один из них не приходит из XLSX и не
может прийти: `AGENTS.md` §3 — реквизиты договора не апсертятся из файла, а
площади живут в смежном портале, к которому доступа по API нет.

Черновик-предшественник — [phase7-brief.md](../../phase7-brief.md) §3, блок «ТЭП и
коммерческие условия». Он **перекрыт этой спекой целиком**: номер миграции там
устарел (0008 занят Ф4б, авторитетна рамка — **0009**), состав площадей не
подтвердился замером, а `CHECK` на площади в нём неверен (§3 п. 2 ниже).

### 1.2. Где живут ТЭП: замер отношения объектов и договоров

Схема допускает `N` договоров на объект: `contracts.object_id` — обычный FK без
`UNIQUE`, и уникальным его сделать нельзя (смена подрядчика с перезаключением
договора законна). На стенде `gca_dev` — 3 объекта и 3 договора, связь `1:1`.

Решение домена, полученное от пользователя на гейте 1: **объект = область охвата
одного ГП; разные очереди заводятся отдельными объектами.** Именно это
соглашение, а не схема, делает площадь объекта верным знаменателем для денег его
сметы. Соглашение держится людьми — см. границу §5 п. 3.

### 1.3. Источник ТЭП: смежный портал, ввод руками

Площади ведутся во внутреннем портале компании и переносятся в GCA **руками**:
доступа по API к порталу нет. Из структуры его экрана следуют три факта, каждый
из которых влияет на схему.

1. **«Общая площадь» там не одна.** Рядом стоят два блока с разными
   определениями и разными значениями: «Общая площадь СП» (СП = **стандарты
   проектирования**, корпоративное определение) и «Общая площадь по правилам MR
   Групп». Колонка с именем `area_total` была бы неоднозначна по построению:
   заводящий выбирал бы, какую из двух вписать, и его выбор нигде бы не
   сохранялся. Отсюда суффикс `_sp` в §2.2 — он **обязателен**, а не украшение.
2. **ТЭП версионированы по стадиям проектирования** (в шапке портала — этап, дата
   техсовета, дата заключения экспертизы и список версий с автором). То есть
   площадь не константа объекта, а значение на стадию. Ф5 стадию **не хранит** по
   решению пользователя — см. границу §5 п. 2.
3. **Не все ТЭП скаляры.** Высота зданий и этажность надземной части записаны
   перечнями по корпусам через дефис; количества помещений — парами «м²/шт» в
   одной ячейке. Ни одно поле этажности или количества не могло бы быть числом, и
   ни одно из них Ф6 не потребляет. В v1 не берём.

Реальные значения площадей и наименования проектов **в репозиторий не попадают**
ни в каком виде (политика `samples/`, рамка фазы). Здесь зафиксирована структура
и словарь — как коды классификатора в Ф1.

### 1.4. Состояние фронтенда: экрана объекта нет

Замерено по коду. Формулировка «CRUD объектов есть с фазы 5» верна на уровне API
и **неверна на уровне интерфейса**:

| Слой | Объекты |
|---|---|
| API | `GET /v1/objects`, **`GET /v1/objects/{object_id}`** ([references.py:171](../../../backend/routers/references.py#L171)), `POST`, `PATCH`, `DELETE` — всё есть |
| Клиент | `listObjects`, `createObject`, `updateObject` ([domain.ts:54-61](../../../frontend/src/services/api/domain.ts#L54-L61)); **`getObject` отсутствует** |
| Хуки | `useObjects`, `useCreateObject`, `useUpdateObject` ([queries.ts:170-201](../../../frontend/src/services/queries.ts#L170-L201)) |
| Экран | **нет вовсе**: ни списка, ни карточки, ни формы правки |

`useUpdateObject` определён и **не вызывается ниоткуда** — ноль мест
использования во всём `frontend/src`. Единственный путь создания объекта в
интерфейсе — быстрое создание по названию внутри формы договора
([ContractFormDialog.tsx:195](../../../frontend/src/components/contracts/ContractFormDialog.tsx#L195)),
и оно отправляет только `title`.

Следствие: площади сегодня вводить **некуда**, и поверхность для ввода Ф5 обязана
построить сама.

### 1.5. Замеры по коду, определяющие решения

1. **`decimal_json` обязателен для любого ответа с `Decimal`.** Замер фазы 5,
   зафиксирован в [responses.py:1-30](../../../backend/responses.py#L1-L30):
   когда хендлер возвращает `dict`, FastAPI прогоняет его через
   `jsonable_encoder` **до** рендера, и `ENCODERS_BY_TYPE[Decimal]` превращает
   значение во `float`. Объектные эндпоинты сегодня `decimal_json` не
   используют — им нечего было отдавать.
2. **`POST /v1/objects` сегодня отвечает `201`**
   ([references.py:179](../../../backend/routers/references.py#L179)) и
   возвращает обычный `dict`. Как только он станет возвращать `decimal_json(...)`,
   экземпляр `Response` принесёт **свой** статус, и эндпоинт молча начнёт
   отвечать `200`. Это регресс существующего поведения, а не недоделка нового
   кода. Правильная форма рядом:
   `return decimal_json(body_out, status.HTTP_201_CREATED)`
   ([contracts.py:159](../../../backend/routers/contracts.py#L159)).
3. **`translating_integrity` всегда отвечает `409`**
   ([common.py:99-120](../../../backend/crud/common.py#L99-L120)) — она написана
   под нарушение уникальности. Для нарушения `CHECK` этот код неверен: это не
   конфликт, а невалидный ввод.
4. **`alembic check` расхождение `Computed`- и `CHECK`-выражений не ловит.**
   Замер Ф1, [test_schema_constraints.py:754-775](../../../backend/tests/integration/test_schema_constraints.py#L754-L775):
   autogenerate их не сравнивает, на `Computed` выдаёт лишь `UserWarning`
   «cannot be modified», а предупреждение прогон не роняет.
5. **`sa.Computed(..., persisted=True)` — идиома репозитория,** два прецедента:
   FTS-колонка в миграции 0002 и `work_categories.is_bucket` в 0005.
6. **В `decimal.ts` есть только `multiplyDecimalStrings`**
   ([decimal.ts:44](../../../frontend/src/lib/decimal.ts#L44)); сложения
   десятичных строк нет. Там же замерено, что промах `Number` **выборочный**:
   `1000.10 × 1.07` даёт `1070.1070000000002`, а `1000.33 × 1.075` совпадает
   точно.
7. **Карточка договора полей объекта не несёт.** `_contract_row_dict`
   ([contracts.py:57-81](../../../backend/crud/contracts.py#L57-L81)) отдаёт
   `object_id` и `object_title`; `rate_class_id` в ней — **снимок договора**, а
   не текущий класс объекта ([models.py:302-304](../../../backend/models.py#L302-L304)).
8. **Ключи кэша централизованы** в
   [queryKeys.ts](../../../frontend/src/services/queryKeys.ts): у каждой сущности
   есть корень `*.all`, и `qk.contracts.all`, `qk.objects.all`,
   `qk.passport.all` существуют.
9. **`_MoneyMixin._reject_float`**
   ([contracts.py:38-47](../../../backend/routers/contracts.py#L38-L47)) отвергает
   только `float`; `str` и точные целые проходят.

## 2. Решения

### 2.1. ТЭП живут на `objects`

Площадь — свойство здания, а не договора. Довод, который решил развилку: правка
площади почти всегда есть **исправление ошибки** (опечатка при переносе,
уточнённая проектная документация), и тогда распространение исправления на уже
напечатанные паспорта — желаемое поведение, а не дефект. Снимок на договоре
заморозил бы неверное число.

Это отличает ТЭП от `rate_class_id`, который на договоре именно снимок:
переклассификация объекта — новое решение, а не исправление, и прошлое ею
двигать нельзя.

### 2.2. Состав ТЭП: две вводимые площади, третья вычисляемая

Берутся три строки блока «Общая площадь СП» портала и только они. Полезная
площадь, площадь ГНС, пространственные параметры и «другие объекты» — вне v1:
Ф6 их не потребляет, а два из них не скаляры (§1.3 п. 3).

| Колонка | Тип | Роль |
|---|---|---|
| `area_aboveground_sp` | `Numeric NULL` | вводится руками |
| `area_underground_sp` | `Numeric NULL` | вводится руками |
| `area_total_sp` | `Numeric`, `Computed("area_aboveground_sp + area_underground_sp", persisted=True)` | знаменатель руб/м² |

Общая площадь **вычисляется, а не хранится** — решение пользователя: «ввести два
числа и на выходе получить третье». Тождество становится непредставимым, а не
проверяемым. Цена решения названа границей §5 п. 1.

`Numeric` без точности — стиль миграций 0001–0008.

### 2.3. Ограничения площадей

```
ck_objects_area_aboveground_sp_non_negative
    area_aboveground_sp IS NULL OR area_aboveground_sp >= 0
ck_objects_area_underground_sp_non_negative
    area_underground_sp IS NULL OR area_underground_sp >= 0
ck_objects_area_total_sp_positive
    area_total_sp IS NULL OR area_total_sp > 0
ck_objects_areas_both_or_neither
    (area_aboveground_sp IS NULL) = (area_underground_sp IS NULL)
```

Три решения, каждое с причиной:

1. **Части `>= 0`, а не `> 0`.** Объект без подземной части законен, и его
   подземная площадь равна **нулю**, а не «неизвестна». Заявленный ноль обязан
   быть отличим от отсутствия — то же различение, за которое Ф4б заплатила
   четырьмя снятиями защиты (её devlog §4a п. 1). Черновик брифа предписывал всем
   площадям `> 0`; это его дефект, и он здесь снимается.
2. **Целое `> 0`.** `area_total_sp` — знаменатель, и ноль в нём даёт деление на
   ноль в Ф6. `CHECK` делает это состояние непредставимым **в схеме**, а не
   отлавливаемым в коде Ф6. Вместе с армом п. 1 это означает «хотя бы одна часть
   положительна».
3. **Обе или ни одной.** Записано как `(A IS NULL) = (B IS NULL)`, а не через
   `num_nonnulls(...) IN (0, 2)`: для пары это тождественно, но не зависит от
   системной функции и повторяет идиому, уже стоящую в 0006
   (`(work_category_id IS NULL) = (category_source IS NULL)`). Выражение никогда
   не даёт `NULL`, поэтому вакуозно не проходит.

Смысл п. 3 — сделать «ТЭП не заведены» **одним** состоянием, а не спектром
частичных заполнений: иначе Ф6 пришлось бы определять, что считать заполненным,
чтобы показать бейдж.

**Ни одно из этих ограничений не проверяется только схемой** — у каждого есть
парная проверка прикладного слоя, см. §2.4.

### 2.4. Двойная валидация: прикладной слой даёт `422`, схема — последний рубеж

**Правило целиком:** ни одно ограничение §2.3 и §2.5 не доходит до `CHECK`
штатным путём. Каждое проверяется **прикладным (доменным) слоем** и отвергается
`422` с человекочитаемым текстом; `CHECK` остаётся последним рубежом — на гонку,
на прямой SQL и на забытую ветку кода.

Причина не стилистическая. `translating_integrity` (§1.5 п. 3) переводит только
известные ей имена и только в `409`; нарушение `CHECK`, до неё дошедшее, уходит
наружу `IntegrityError` и превращается в **`500`**. То есть без проверки
прикладного слоя отрицательная площадь или `101` процента — это не «строгая
схема», а серверная ошибка на синтаксически верном запросе.

**Где какая проверка живёт.** Та, которой хватает самого запроса, — Pydantic, по
образцу `_MoneyMixin`
([contracts.py:34-55](../../../backend/routers/contracts.py#L34-L55)). Та,
которой нужна запись из БД, — CRUD, после `db.get`.

| Проверка | Слой | Почему там |
|---|---|---|
| `float` на входе | Pydantic | это форма значения, БД не нужна |
| площадь `>= 0` | Pydantic | значение самодостаточно |
| процент в `[0, 100]` | Pydantic | то же |
| пара «обе или ни одной» | CRUD | нужно итоговое состояние после слияния |
| общая `> 0` (пара `0/0`) | CRUD | то же: в PATCH слагаемое приходит одно |

**Пару и общую судит одна функция, вызываемая обоими путями.** `create_object` и
`update_object` зовут её одинаково — у создания «итоговое состояние» есть просто
вход. Иначе правило жило бы в двух местах и разъехалось бы при первой правке.

**Входы, которые обязаны получить `422`, а не `500`:**

| Эндпоинт | Вход |
|---|---|
| `POST /v1/objects` | одна площадь без второй; отрицательная площадь; пара `0/0` |
| `PATCH /v1/objects` | отрицательная площадь; итоговая пара `0/0`; итоговая пара «одно `NULL`, другое число» |
| `POST /v1/contracts` | процент вне `[0, 100]` — каждое из трёх условий, обе границы |
| `PATCH /v1/contracts` | то же |

Пара `0/0` отвергается **не** из-за арифметики, а потому что даёт `area_total_sp`
равной нулю, то есть знаменатель, которым нельзя делить (§2.3 п. 2). Текст отказа
говорит именно это, а не «площадь должна быть больше нуля» — части-то нулю равны
законно.

**Инвариант PATCH площадей:** валидируется состояние пары **после слияния PATCH с
записью из БД**, а не переданная дельта. Условие итогового состояния — то же, что
в `ck_objects_areas_both_or_neither`.

Из одного инварианта следует всё поведение:

| Вход | Исход |
|---|---|
| обе площади уже заполнены, передана одна | принимается — отдельное исправление **уже заполненной** (`NOT NULL`) площади разрешено |
| в БД `NULL`/`NULL`, передана одна | `422` |
| передан `null` для обеих | принимается — сброс |
| передан `null` для одной при заполненной другой | `422` |
| любая итоговая пара «одно `NULL`, другое число» | `422` |

«Уже заполненная» — значит `NOT NULL`, **не** «не равная нулю»: ноль здесь
законное значение, и правка подземной площади с `0` на число в одиночку
разрешена.

Дополнительного запроса это не требует: `update_object`
([references.py:241-259](../../../backend/crud/references.py#L241-L259)) уже
начинается с `db.get(ObjectModel, object_id)`.

Существующая семантика `UNSET` («непереданное поле не меняется») сохраняется без
изменений; новый инвариант судит только результат слияния.

**У каждого ограничения защит две**, и по слою 8
[verifying-guards](../../insights/verifying-guards.md) это меняет протокол
проверки: снятие одной дефект не воспроизводит — соседняя маскирует. Снимать надо
по отдельности **и парой**, потому что исходов три и ни один не выводится из двух
других:

| Что снято | Наблюдаемый исход |
|---|---|
| проверка прикладного слоя | ответ деградирует с `422` до `500`; значение в БД по-прежнему не попадает |
| `CHECK` | ответ прежний, `422`; защиты в схеме больше нет, и это видно только прямым SQL |
| обе | значение **ложится в таблицу** |

Отсюда состав §4.4.

### 2.5. Коммерческие условия: три пары «процент + комментарий»

На `contracts`:

```
advance_pct          Numeric NULL   CHECK (IS NULL OR (>= 0 AND <= 100))
advance_note         Text    NULL
bank_guarantee_pct   Numeric NULL   CHECK (IS NULL OR (>= 0 AND <= 100))
bank_guarantee_note  Text    NULL
retention_pct        Numeric NULL   CHECK (IS NULL OR (>= 0 AND <= 100))
retention_note       Text    NULL
```

Комментарий заведён потому, что в договорах рядом с процентом регулярно стоят
сопроводительные оговорки (замер — ответ пользователя на гейте 1). Общий
`contracts.notes` для них не годится: оговорка относится к **конкретному**
условию, и из общего поля её не вернуть — паспорт напечатал бы «Аванс: 30%», то
есть выдал бы условное число за безусловное.

Три решения:

1. **Парного `CHECK` между процентом и комментарием нет.** Комментарий без
   процента законен и означает «условие есть, но одним процентом не
   выражается» (аванс траншами, гарантия с потолком в деньгах). Требование
   процента запретило бы честное описание в пользу пустоты.
2. **Ноль в проценте законен** и отличим от `NULL`: «аванса не предусмотрено»
   против «не заполнено». Та же причина, что в §2.3 п. 1.
3. **База процента — сумма договора**, по соглашению; иная база пишется в
   комментарий этого условия. Машинно база нигде не выражена — граница §5 п. 4.

**Диапазон `[0, 100]` проверяется прикладным слоем и `CHECK`-ом**, как и всё
остальное (§2.4). Обе границы, у каждого из трёх условий.

**Контракт API.** Шесть полей добавляются в `ContractCreate`, `ContractUpdate`,
`crud.contracts.create_contract` / `update_contract` и клиентские типы
(`ContractInput`, карточка договора).

**Возвращаются в карточке договора и в ответах create/update — но не в списке.**
Достигается тем, что поля добавляются в `get_contract_dict`, а **не** в
`_contract_row_dict`: ровно туда, где сейчас добавляется `notes`
([contracts.py:201](../../../backend/crud/contracts.py#L201)), и по той же
причине — список договоров это выбор, а не карточка. Отдельного решения для
ответов create/update не требуется: обе функции уже возвращают
`get_contract_dict` ([contracts.py:316](../../../backend/crud/contracts.py#L316)).

**PATCH:** семантика `UNSET` без изменений — непереданное поле не меняется,
`null` **очищает** это условие. Парности между процентом и комментарием нет
(п. 1), поэтому каждое из шести полей правится независимо; правила «итогового
состояния», как у площадей, здесь нет и быть не должно.

**Пустой комментарий — это `NULL`, а не пустая строка:**
`(value or "").strip() or None` — тот же приём, которым уже приводятся `title`,
`signer` и `notes` ([contracts.py:299-303](../../../backend/crud/contracts.py#L299-L303)).
Пустая строка означала бы «условие заведено, комментария нет», хотя заведено
ничего не было, и паспорт напечатал бы пустую оговорку как факт.

**Ставка НДС сюда не переезжает никогда.** У неё другой источник: она приходит из
шапки ценового блока XLSX и живёт в `proposals.vat_rate` (Ф4б §2.1), тогда как
коммерческие условия — реквизиты договора, вводимые руками (`AGENTS.md` §3).

### 2.6. Decimal-дисциплина: вход, выход, `float`

**В ответах — всегда строки. На входе — строка или точное целое; `float`
отвергается** явным валидатором с понятным сообщением, по образцу
`_MoneyMixin._reject_float`.

Площади и проценты — не деньги, и `AGENTS.md` §3 буквально их не покрывает.
Причина распространить дисциплину на них другая и более узкая: `area_total_sp`
есть **делитель денег**. `Decimal / float` в Python падает, а `float`,
приведённый Pydantic к `Decimal`, приносит двоичный хвост прямо в знаменатель
руб/м². Проценты идут туда же ради единообразия правила — иначе на ревью
неизбежен вопрос «почему у этого поля иначе», а ответа по существу нет.

### 2.7. `decimal_json` на объектных эндпоинтах и явный `201`

Все эндпоинты `objects`, возвращающие площади (`GET` списка, `GET` одного,
`POST`, `PATCH`), оборачиваются в `decimal_json` — иначе `float` (§1.5 п. 1).

**`POST /v1/objects` передаёт статус явно:**
`decimal_json(body, status.HTTP_201_CREATED)`. Без этого эндпоинт молча
деградирует с `201` на `200` (§1.5 п. 2). Тест утверждает именно `201`.

### 2.8. Миграция `0009`

Номер выведен рамкой фазы однозначно: `head` = `0008` (Ф4б). Файл —
`2026_08_09_0009-tep_commercial_terms.py`.

Содержание: три колонки на `objects` (§2.2) с четырьмя `CHECK` (§2.3), шесть
колонок на `contracts` (§2.5) с тремя `CHECK`. Модели SQLAlchemy объявляют те же
выражения.

**Обратимость.** Миграция — чистое добавление колонок: ни переноса данных, ни
backfill, ни правки существующих строк. `downgrade` снимает те же колонки.
Ожидание, что вычисляемую колонку придётся снимать **раньше** её слагаемых
(иначе PostgreSQL откажет по зависимости), — именно ожидание: оно
**проверяется круговым рейсом, а не объявляется**
([replaying-new-rules](../../insights/replaying-new-rules.md), слой 1). Рейс
`alembic downgrade base && upgrade head` гоняется **на тестовой базе**; на стенде
он запрещён (`AGENTS.md` §11 — откат ниже 0003 упрётся в
`ProgramLimitExceeded`).

### 2.9. Фронтенд: диалог правки объекта с карточки договора

Отдельного раздела «Объекты» Ф5 не строит (критерий пользователя — скорость).
Поверхность ввода — **диалог правки объекта, открываемый с карточки договора**:
название, адрес, класс, наземная и подземная площади.

Объект берётся **отдельным запросом** `GET /v1/objects/{object_id}` (эндпоинт
существует, §1.4; в клиенте появляется обёртка `getObject` и хук), а не полями,
подмешанными в ответ карточки договора. Причина: в карточке уже есть
`rate_class_id` — **снимок договора**, и класс объекта рядом с ним дал бы два
поля с одним именем и разным смыслом (§1.5 п. 7).

Форма коммерческих условий — **секция в существующем `ContractFormDialog`,
свёрнутая по умолчанию**. Отдельный диалог означал бы новый компонент со своим
набором тестов, а свёрнутая секция не утяжеляет создание договора (условия на
момент заведения карточки обычно ещё неизвестны).

**Карточка договора показывает оба блока на чтение**, включая пустое состояние
«ТЭП не заведены». Без этого Ф5 давала бы формы для данных, которых до Ф6 нигде
не видно, и принять фичу целиком (`AGENTS.md` §9.1) было бы нечем.

Компоненты — только shadcn/ui. Права — `require_admin`, как у существующих правок
объектов и договоров; нового решения по правам фича не принимает.

### 2.10. Живая общая площадь считается точно, а не через `Number`

Под полями площадей форма показывает **вычисленную общую** — это единственная
доступная сверка с порталом: заводящий видит третье число и сличает его с тем,
что перед ним на экране СУИП. Схемы это не касается, хранить нечего.

Сумма считается новой `addDecimalStrings` в
[decimal.ts](../../../frontend/src/lib/decimal.ts) — по образцу
`multiplyDecimalStrings`: разбор регуляркой, выравнивание масштабов, сложение в
`BigInt`, сборка строки. `Number` запрещён: он внёс бы двоичный хвост в величину,
которая на бумаге станет знаменателем руб/м².

**Предпосылка «наши слагаемые в `Number` промахиваются» не утверждается**:
промах float выборочный (§1.5 п. 6). Тест замеряет её **внутри себя**
([false-test-premises](../../insights/false-test-premises.md), п. 3) и падает,
если перестанет быть верной.

### 2.11. Инвалидация кэша после правки объекта

`useUpdateObject` сегодня инвалидирует только `qk.objects.all` и
`qk.rateClasses.all` ([queries.ts:190-201](../../../frontend/src/services/queries.ts#L190-L201)).
Добавляются **`qk.contracts.all`**, **`qk.passport.all`** и **`qk.matrix.all`** —
корни, а не точечные ключи.

Причина одна и общая: **название объекта денормализовано в три семейства
ответов**, и все три кэшируются. Замерено:

| Кэш | Где денормализовано |
|---|---|
| список и карточка договоров | `object_title` в `_contract_row_dict` ([contracts.py:70](../../../backend/crud/contracts.py#L70)) |
| паспорт фазы 6 | `object_title` в ответе ([analytics.py:148](../../../backend/crud/analytics.py#L148)) и на экране ([PassportPage.tsx:156](../../../frontend/src/pages/passport/PassportPage.tsx#L156)) |
| колонки матрицы | `object_title` ([analytics.py:494](../../../backend/crud/analytics.py#L494)) |

Корень, а не карточка текущего договора: у объекта может быть несколько
договоров, и `object_title` лежит в каждом. Сам объектный запрос обновляется
через `qk.objects.all`.

**Дыра существует сегодня и не проявлялась только потому, что
`useUpdateObject` не вызывается ниоткуда** (§1.4): переименовать объект в
интерфейсе невозможно, поэтому устареть кэшу не от чего. Ф5 делает правку объекта
достижимой впервые — и тем самым делает дыру наблюдаемой. Это не расширение
скоупа, а часть цены за первую поверхность правки объекта: фича, включающая
мутацию, отвечает за её инвалидацию целиком.

Первая редакция этой спеки откладывала `qk.passport.all` до Ф6 на том основании,
что паспорта «ещё нет». Основание неверно: паспорт фазы 6 существует и
`object_title` показывает. Замер исправил вывод.

## 4. Тесты

Списки ниже — требования к покрытию; точные имена и разбивка по задачам — в плане.

### 4.1. Схема (integration, `test_schema_constraints.py`)

- Каждый из четырёх `CHECK` на `objects` отвергает своё: отрицательная наземная;
  отрицательная подземная; **ноль в частях, дающий ноль в общей** (арм `> 0`);
  одна заполненная при второй `NULL` — с обеих сторон пары.
- **Ноль в части — представимое состояние**: пара `(число, 0)` вставляется и
  читается как `Decimal("0")`, не как `NULL`.
- Пара `NULL`/`NULL` — представимое состояние («ТЭП не заведены»).
- `area_total_sp` действительно вычисляется: вставка двух частей даёт сумму;
  **попытка записать в неё напрямую отвергается** PostgreSQL.
- Каждый арм диапазона процентов **по отдельности**: `-1` и `101` для всех трёх
  условий. Нижнюю границу забывают — это находка финального ревью Ф4б.
- Комментарий без процента вставляется (отсутствие парного `CHECK`).
- **Парность выражений**: один тест сверяет выражения `Computed` и `CHECK` в
  **БД**, другой — в **модели**. `alembic check` здесь не защита (§1.5 п. 4).

### 4.2. Домен и API

- Таблица исходов PATCH из §2.4 целиком, случай за случаем, включая отдельное
  исправление уже заполненной площади и правку части, равной нулю.
- **Таблица «входы, обязанные получить `422`» из §2.4 целиком** — по строке на
  вход: `POST /objects` с одной площадью, с отрицательной, с парой `0/0`;
  `PATCH /objects` с отрицательной и с итоговой парой `0/0`; `POST` и `PATCH`
  договора с процентом ниже нуля и выше ста, для каждого из трёх условий.
  Утверждается именно **`422`**, а не «не 2xx»: `500` мимо такого утверждения
  прошёл бы.
- Текст отказа на паре `0/0` говорит про общую площадь, а не про части: части
  нулю равны законно (§2.4).
- `float` на входе отвергается для каждой площади и каждого процента; строка и
  точное целое принимаются.
- **Коммерческие условия, round-trip:** `POST` с шестью полями → карточка
  возвращает их же; `PATCH` правит **одно** поле, не трогая остальные пять;
  `null` очищает отдельное условие; процент есть, комментарий пуст — и наоборот.
- **Пустая строка в комментарии становится `NULL`**, а не сохраняется как `""`.
- **Шести полей нет в ответе списка договоров** и есть в карточке — иначе
  решение §2.5 держалось бы только на том, в какую функцию их случайно дописали.
- Проценты приходят в **сыром теле** ответа строками, как и площади.
- **`Decimal` доезжает до JSON строкой** во всех четырёх объектных эндпоинтах.
  Тест смотрит на **сырое тело ответа**, а не на разобранный JSON: `float` и
  строка после разбора могут выглядеть одинаково.
- **`POST /v1/objects` отвечает `201`**, а не `200`.
- Права: `member` получает `403` на правку площадей и условий.

### 4.3. Фронтенд (vitest)

- `addDecimalStrings`: разные масштабы, целые, ноль, невалидный вход → `null`.
  Предпосылка о промахе `Number` замеряется **внутри теста** (§2.10).
- Живая общая обновляется при вводе и **совпадает со строкой**, а не с числом.
- Диалог объекта: отдельная правка одной площади, сброс обеих, отказ сервера
  показывается человеку.
- Секция условий свёрнута по умолчанию и не блокирует создание договора.
- Карточка договора показывает оба блока и пустое состояние «ТЭП не заведены».
- `useUpdateObject` инвалидирует пять корней: `qk.objects.all`,
  `qk.rateClasses.all`, **`qk.contracts.all`**, **`qk.passport.all`**,
  **`qk.matrix.all`**. Проверяется каждый по отдельности — иначе тест,
  утверждающий «вызвано пять раз», прошёл бы и при пяти одинаковых ключах.

### 4.4. Негативные проверки снятием защиты

Протокол [verifying-guards.md](../../insights/verifying-guards.md) целиком:
контрольный прогон **до** снятия; `assert old in text` с проверкой
единственности вхождения; sha256 до и после; число упавших по каждому снятию;
восстановление **из побайтовой копии**, не через `git checkout --`. Шаблоны
патчей приводить к фактическому разделителю строк файла — CRLF против LF уже один
раз не дал патчу примениться (devlog Ф4б §3.0). **Делает оркестратор лично.**

Список синхронизирован с фактическим составом защит после §2.4: **19 одиночных
снятий и 4 комбинированных, всего 23.** Каждая строка — одна независимая мутация;
там, где защит на ограничении две, одиночное снятие доказывает только свою
(таблица трёх исходов в §2.4).

**Схема — 7:**

1. арм `>= 0` у наземной; 2. арм `>= 0` у подземной; 3. арм `> 0` у общей;
4. `(A IS NULL) = (B IS NULL)`; 5. выражение `Computed` (подмена слагаемого);
6. нижний арм диапазона процента; 7. верхний арм диапазона процента.

**Прикладной слой — 5:**

8. Pydantic: площадь `>= 0`; 9. Pydantic: процент в `[0, 100]`; 10. Pydantic:
отказ от `float`; 11. CRUD: пара «обе или ни одной» по итоговому состоянию;
12. CRUD: общая `> 0` (пара `0/0`).

**Прочее — 7:**

13. `decimal_json` на объектном эндпоинте; 14. явный `201` в `POST /objects`;
15. `addDecimalStrings` → `Number`; 16. инвалидация `qk.contracts.all`;
17. инвалидация `qk.passport.all`; 18. инвалидация `qk.matrix.all`;
19. приведение пустого комментария к `NULL`.

Пункты 16–18 снимаются **по отдельности**: снятие одного корня не должно
маскироваться двумя остальными, а тест «вызвано пять раз» прошёл бы и при пяти
одинаковых ключах.

**Комбинированные снятия (слой 8) — 4:** `4 + 11` (парность), `3 + 12` (общая
больше нуля), `1 + 8` (неотрицательность площади), `6 + 9` (нижняя граница
процента). Каждое доказывает третий исход — **значение ложится в таблицу**, —
который из одиночных снятий не выводится. Для армов, у которых комбинированное
снятие не делается (2, 7), одиночные покрывают обе стороны диапазона.

Если по ходу реализации число защит изменится, список пересобирается: расхождение
между «19 + 4» и фактом — сигнал, что защита появилась или исчезла незамеченной.

Снятие, не уронившее ничего, — не «тест плох», а вопрос, существует ли защита
(слой 7). Такой результат разбирается, а не замалчивается: в Ф4б одна из проб
дала ноль красных, и правильным ответом оказалось «модель дефекта неверна», а не
«защиты нет».

### 4.5. Соответствие «требование → тест»

На финале фичи, до PR, строится явное соответствие **по тексту §2, требование за
требованием** ([replaying-new-rules](../../insights/replaying-new-rules.md), слой
3). Не «покрыто ли», а «каким именно тестом и упадёт ли он, если требование
нарушить». Требование без исполнителя **объявляется границей в devlog** —
молчаливого третьего варианта нет.

### 4.6. Прогон нового правила по уже существующим входам

До написания кода (слой 2 того же инсайта) прогоняются:

- **тесты и фикстуры, создающие объекты**, — новые `CHECK` начнут судить их;
  `ObjectFactory` ([factories.py:89](../../../backend/tests/factories.py#L89))
  площадей не задаёт, то есть должен попадать в законное `NULL`/`NULL`;
- **существующие вызовы `createObject`** во фронтенд-тестах — форма получает
  новые поля;
- **три объекта стенда** — у всех площади `NULL`, `CHECK` их не трогает.

Признак, по которому этот прогон обязателен: у добавляемых полей есть
**вычисление** (`Computed`) и **проверки**, а у проверок — входы, которые они
вправе отвергнуть (уточнение к слою 2, оплаченное Ф4б).

## 5. Границы Ф5

Требование без исполнителя объявляется границей, а не замалчивается.

1. **Опечатка в наземной или подземной площади ничем не ловится.** Общая
   вычисляется, сверять её не с чем; неверный знаменатель доедет до руб/м² в
   паспорте без единого признака ошибки. Живая общая в форме (§2.10) делает
   сверку с порталом **возможной**, но она остаётся ручной и тестом не
   стережётся. Это прямая цена решения пользователя «два числа на входе, третье
   на выходе».
2. **Стадия и дата ТЭП не хранятся.** Площади в портале версионируются по
   стадиям проектирования (§1.3 п. 2), и паспорт напечатает руб/м², не сообщив,
   по какой версии ТЭП он посчитан. Решение пользователя.
3. **Объект может иметь несколько договоров, и Ф5 этому не мешает.**
   `contracts.object_id` не уникален и уникальным быть не может. Тогда два
   паспорта делят **разные** деньги на **одну** площадь. Соглашение «объект =
   охват одного ГП» держится людьми, а не схемой. Ф5 не чинит — нечем; см. §7.
4. **База процента машинно не выражена.** «От суммы договора» держится подписью
   поля и комментарием условия; поля «база» нет, и проверить её нечем.
5. **Отсутствие backfill тестом не стережётся** — отсутствие кода тестом не
   проверяется. Та же граница, что у Ф4a §5.6 и Ф4б §6 п. 2. Существующие
   объекты остаются с `NULL`/`NULL`, то есть «ТЭП не заведены», пока их не
   заведут руками.
6. **`alembic check` в этой фиче ничего не доказывает** для `Computed` и `CHECK`
   (§1.5 п. 4). Зелёный `alembic check` — не признак согласованности модели и
   миграции; согласованность держат два теста §4.1.
7. **Правило «партия больше пяти» не применяется.**
   [batch-larger-than-five](../../insights/batch-larger-than-five.md) про
   `ON CONFLICT` по COALESCE-уникальным и частичным индексам, где меняется план
   подготовленного запроса; в 0009 таких объектов нет — только `CHECK` и
   `Computed`. Названо, чтобы отсутствие проверки было решением, а не пропуском.
8. **Объект без договоров недостижим для правки:** единственный вход в диалог
   объекта — карточка договора (§2.9). Возникнуть такой объект может, только если
   его создали в форме договора и форму бросили.
9. **Печатная раскладка паспорта в Ф5 не проверяется** — печатать пока нечего.
   Обязательство переходит в Ф6, см. §7.

## 6. DoD фичи

- `just ci` целиком, **шагами и в форме CI**, — `EXIT=0`: `uv lock --check`,
  ruff, `db-test-check` с `alembic check`, backend pytest, eslint,
  `tsc -b --noEmit`, vitest. Вердикт читается по **напечатанным числам**, а не по
  коду возврата ([silent-test-runs](../../insights/silent-test-runs.md)).
- Число собранных тестов замерено **после каждой задачи** и пофайлово; отправная
  точка — 1276 / 1270 passed / 6 skipped, vitest 175 (§1.1). Расхождение
  разбирается как дефект.
- Круговой рейс `alembic downgrade base && upgrade head` пройден **на тестовой
  базе**; порядок снятия колонок при живой вычисляемой — **замерен**, а не
  предположен (§2.8).
- Негативные проверки §4.4 выполнены оркестратором лично, с числом упавших по
  каждому снятию; снятие, не уронившее ничего, разобрано.
- Соответствие «требование → тест» построено списком (§4.5); требования без
  исполнителя перечислены в devlog как границы.
- Прогон по существующим входам (§4.6) сделан **до** написания кода.
- Стенд `gca_dev`: на одном договоре площади и коммерческие условия заведены
  **через интерфейс**, прочитаны из БД, счётчики объектов, договоров, смет и
  каталога до и после совпали. Стенд не чистится и не пересоздаётся; круговой
  рейс на нём запрещён.
- Существующие тесты не ослаблены; правки в `docs/` от `just ci` освобождены
  (`AGENTS.md` §9.3).

## 7. Следствия за пределами Ф5

- **Ф6 получает `area_total_sp` и `NULL` как честное «ТЭП не заведены»** — бейдж,
  а не скрытая колонка и не ноль. Деление на ноль невозможно по схеме (§2.3
  п. 2), поэтому отдельной защиты в коде паспорта не требуется.
- **Новый паспорт Ф6 должен либо переиспользовать корень `qk.passport.all`, либо
  расширить инвалидацию `useUpdateObject` своим ключом.** Ф5 закрывает три
  существующих корня (§2.11); корень, заведённый Ф6, автоматически туда не
  попадёт, и стало бы это видно только на живом экране.
- **Ф6 обязана зажимать комментарии коммерческих условий по высоте** и проверять
  печатную раскладку **замером в браузере**. `AGENTS.md` §11 несёт два
  оплаченных замера: экранные KPI-карточки давали 284 мм при доступных 277, а
  класс `block` рядом с `line-clamp` отменяет зажим вовсе. Свободный текст в
  шапке А4 сломает лист так же, и ни один jsdom-тест этого не увидит.
- **Ф6 решает, показывать ли признак «у объекта больше одного договора»** —
  вход, на котором руб/м² молча делит разные деньги на одну площадь (§5 п. 3).
- **Будущему парсеру договоров ничего не закладывается** (рамка фазы, «вне
  скоупа v1» п. 6, `AGENTS.md` §1). Когда он появится, ему понадобится признак
  происхождения значения (`'manual'` против `'llm'`); добавление такого признака
  **аддитивно** и смысла колонок Ф5 не меняет — тот же довод, которым Ф4б §7
  отложила `vat_rate_override`.
- **Полная карточка объекта остаётся не построенной.** Когда она понадобится,
  диалог §2.9 переиспользуется, а граница §5 п. 8 закроется сама.
