# Этапный разнос «Нераспределённого» в тендерном контуре — дизайн

**Фаза: ни к одной.** Фича закрывает запись №22 техдолга («У ручного разноса
статей нет поверхности для смет предложений») — прецедент оформления тот же,
что у [спеки разноса](2026-08-11-unallocated-category-override-design.md):
номера `ФN` нет, фаза не расширяется задним числом.

В комментариях кода эта спека называется **«спека этапного разноса»** — «спека
разноса» уже занята договорной фичей 2026-08-11, и безымянная ссылка рядом с ней
была бы неразличима.

Опирается на: [спеку разноса](2026-08-11-unallocated-category-override-design.md)
(механизм override, границы §5.5), [спеку контура](2026-08-26-tenders-contour-design.md)
(решётка, загрузка по раундам), [спеку свода](2026-08-27-stage-summary-design.md)
(§2.10 — подпись `manual_overrides`), [спеку раскрытия](2026-08-30-position-drilldown-design.md)
(групповые ключи). Макет гейта 1: [2026-09-01-offer-unallocated-mockup.html](2026-09-01-offer-unallocated-mockup.html)
— утверждён 01.09.2026 после четырёх кругов внешнего ревью (этапная модель,
полный вектор решения, входное множество агрегатора, три кода диагностики).

Правило, которое фича обязана сохранить: **сумма дерева статей плюс
«Нераспределённое» равна итогу сметы** — для каждой сметы раунда в отдельности.

## 1. Замеры и факты, на которых стоит дизайн

### 1.1. Все сметы раунда — проекции одного файла

Загрузка тендерного контура идёт по раунду, одним файлом «Сводная таблица
предложений» (`POST /tenders/{tender_id}/rounds/{round_id}/upload`).
`split_round_payload` ([round_import.py](../../../backend/services/round_import.py))
режет разобранный JSON на проекции: для каждого участника — `copy.deepcopy(data)`
с подменой только блока предложения (`_lot_shell`), и baseline тем же способом.

Следствие, на котором стоит вся фича: **ведомость работ, строки-разделы и клетки
«Статья СМР» у всех смет раунда одинаковы по построению** — различаются
подрядные значения (цены, предлагаемые количества, отклонения); структурные
поля и логические ключи общие. «Нераспределённое» из позиций — одни и те же разделы у всех.
Разнос, привязанный к отдельной смете, заставил бы повторять одно решение N раз
и позволил бы разнести один раздел этапа в разные статьи у разных участников.

### 1.2. Замер стенда: два слоя нераспределённого

Тендер 449-ТУ, `gca_dev` (замер 01.09.2026, `v_category_totals` с
`work_category_id IS NULL`):

- **Этапы 3–4, слой позиций:** у всех участников этапа ровно **38 одинаковых
  позиций** под разделами `14.*` и `15` (source=`positions`), все расценены,
  деньги свои у каждого: 480,3 млн (ГЭС) / 495,5 млн (АНТТЕК) / 613,4 млн
  (ЕНИГЮН) / 535,2 млн (ЭРБЕК) — порядка 3 % от итогов 15–18 млрд. Это предмет
  этапного разноса.
- **Этапы 1–2, слой допработ:** нераспределённое есть только у двух участников
  и различается — АНТТЕК «c +6,650м до +16,500м» на 316,1 млн / 4,4 млн,
  ЕНИГЮН «Дополнительные работы» на 0 ₽ (source=`additional_works`,
  `chapter_ref_raw IS NULL`). Эти строки по-участниковые и разносом разделов
  не закрываются — граница §5.5 спеки разноса.
- **Baseline-смет на стенде нет вовсе** — «Расчётная стоимость» в файлах пуста.

Тендер 159-ТУ: слой позиций пуст, у двух участников по одной допработе с нулём.

Гипотеза «нераспределённое — виды работ без денег» замером **опровергнута**:
38 строк расценены у всех, суммы до 0,6 млрд на участника.

### 1.3. Существующий механизм по-сметный, и его no-op не выравнивает аудит

`set_override`/`clear_override` ([category_override.py](../../../backend/services/category_override.py))
принимают смету и раздел; повторный вызов с теми же `(work_category_id, note)` —
no-op с сохранением прежних `assigned_by`/`assigned_at` («в паспорте для банка
автор решения и есть содержательная часть»). Следствие: **наивный фан-аут
`set_override` по сметам раунда не годится** — там, где старое решение совпало
с новым, останутся старые автор и дата, и аудит раунда будет разнородным.

### 1.4. `unallocated.extras` шире границы

`_extras_by_category` кладёт в нераспределённое ведро **все** допработы с
`work_category_id IS NULL` — включая те, чья ссылка на раздел разрешима и
которые разнос раздела закроет пересчётом (`resolve_ref`, спека разноса §1.4).
Для блока диагностики «не закрывается разносом» нужен свой селектор: только
строки за границами §5.5.

### 1.5. `current_round_job` — не признак доступности смет

`current_round_job` требует полного набора смет job; после удаления участника
набор неполон, job перестаёт быть текущим — а оставшиеся offer-сметы существуют
и участвуют в своде. Доступность разноса привязывается к **наличию offer-смет
раунда**, не к job. Замена файла раунда атомарна и сохраняет `round_id` —
поэтому 404 формулируется «Раунд или его сметы больше недоступны», а не «файл
был заменён»: тот же URL после замены показывает новый набор.

### 1.6. Логический ключ раздела раунда

Внутри одной сметы раздел адресуется `position_item_id`; между сметами раунда —
парой **`(lot_key, position_key_in_proposal)`**: ключ строки файла, одинаковый
во всех проекциях по построению (`uq_position_items_proposal_id_key` даёт
однозначность внутри предложения; лоты сопоставляются по `lots.lot_key`).
Это **точное соответствие, не эвристика** — запрет Ф3 на join по номеру раздела
в денежной логике не задевается: соединяются проекции одного файла, а не разные
файлы.

### 1.7. Свод уже готов читать результат

Колонки свода несут `round_id` и `estimate_id`; подпись `manual_overrides`
реализована и покрыта тестом `test_manual_override_marks_only_its_own_column`.
Пункт DoD свода о подписи разноса был снят 28.08 решением пользователя с
формулировкой «вернётся в DoD той фичи, которая заведёт поверхность» — это
та самая фича.

## 2. Решение

### 2.1. Носитель разноса — раунд; радиус — offer-сметы

Единица решения — **логический раздел раунда** `(lot_key,
position_key_in_proposal)`. Решение применяется ко **всем существующим
offer-сметам раунда**; baseline исключён **на уровне выборки смет**
(`Estimate.offer_id IS NOT NULL` через offers раунда), не фильтром в цикле —
решение пользователя 01.09.2026: baseline не участвует ни в своде, ни в
матрице, разносить её незачем.

По-сметные маршруты и панель паспорта не меняются ничем.

### 2.2. Входное множество агрегатора и четыре состояния

**Входное множество:** логические разделы раунда, у которых хотя бы в одной
offer-смете эффективная статья отсутствует **или** существует хотя бы один
override. Раздел, корректно классифицированный файлом и не тронутый рукой,
в ответ не попадает (иначе панель включила бы весь справочник ведомости).

**Вектор решения** раздела в одной смете: `(work_category_id, note,
assigned_by, assigned_at)` его override. Состояние логического раздела —
агрегат по всем offer-сметам раунда, разбиение исчерпывающее:

| Состояние | Определение | Где показывается |
|---|---|---|
| `unassigned` | override нет ни в одной смете | «Требуют решения» |
| `partial` | override есть не во всех сметах | «Требуют решения», пометка «разнесено не во всех сметах: k из n» |
| `conflict` | override есть во всех, но полные векторы различаются (статьи, заметки ИЛИ аудит) | «Требуют решения», пометка «решения в сметах различаются» с частным пояснением |
| `resolved` | один полный вектор во всех сметах | «Разнесено вручную» |

Конфликт определяется по **полному** вектору: без этого раздел с единой статьёй
и разошедшимся аудитом исчез бы из обоих блоков (находка ревью гейта 1).

Структура дерева (родители, глубина, номера, заголовки, счётчик позиций
поддерева) берётся из **представительной сметы** — первой по `estimate_id ASC`;
состояния агрегируются по всем. Расхождение структуры между сметами раунда
(логический ключ отсутствует хотя бы в одной offer-смете) — нарушение
целостности наших данных, класс `mapping_broken`: 500 с логом, не 409
(пользователю нечего повторять).

### 2.3. Чтение: `GET /api/v1/tenders/{tender_id}/rounds/{round_id}/unallocated`

Роутер — `routers/tenders.py`, контракт маршрутизатора тендерных GET:
ответ через `decimal_json`, `DomainError` → `raise_domain_error`. Права —
аутентификация, `member` вправе (решение пользователя 01.09.2026: та же роль,
что у разноса в паспорте, — рабочая операция аналитика).

```
{
  round:        { id, stage_no, label, held_on },
  offers_count: int,                      -- offer-смет в радиусе (для шапки Sheet)
  sections: [ {                           -- входное множество §2.2, кроме resolved;
                                          -- файловый порядок ведомости (порядок
                                          -- представительной сметы)
    lot_key, position_key_in_proposal,    -- логический ключ (и ключ мутаций §2.4)
    parent_key: [lot_key, position_key] | null,   -- вершина нераспределённой части
    depth, number, title, smr_article_raw,
    rows: int,                            -- ПОЛНЫЙ размер файлового поддерева
                                          -- (подпись «N позиций»): стабилен и не
                                          -- зависит от вложенных решений; «позиции
                                          -- в Нераспределённом» не годится —
                                          -- конфликт возможен при нуле таких строк
                                          -- (rows_priced НЕ отдаётся: расценённость
                                          -- по-участниковая, а панель без денег)
    state: 'unassigned' | 'partial' | 'conflict',
    partial:  { assigned: int, total: int,                 -- только у partial
                notes: [string | null] },                  -- различные заметки
                                                           -- назначенной части
    conflict: { categories: [{id, code, title}],           -- только у conflict
                notes: [string | null],                    -- различные заметки
                audit_differs: bool }
                                          -- notes нужны клиенту, чтобы показать и
                                          -- предзаполнить заметку при выравнивании
                                          -- (§2.4, §2.7) — по одному notes_differ
                                          -- осознанный выбор был бы невозможен
  } ],
  manual: [ {                             -- состояние resolved
    lot_key, position_key_in_proposal, number, title, rows,
    work_category_id, category_code, category_title,
    assigned_by_email, assigned_at, note
  } ],
  diagnostics: [ {                        -- границы §5.5, не действия; см. §2.5
    code: 'outside_structure' | 'structure_disabled' | 'unresolved_chapter_ref',
    contractor_title,                     -- чья смета несёт строку
    title,                                -- наименование строки/предложения
    rows: int                             -- строк за этой границей у этого участника
  } ],
  category_options: [ {id, code, title, is_bucket} ]   -- справочник целиком,
                                          -- той же функцией, что у паспорта
                                          -- (разносить можно и в статьи,
                                          -- которых в смете ещё нет)
}
```

Денег в ответе нет — решение пользователя 01.09.2026: разнос — настройка
классификации ведомости, масштаб в деньгах виден в строке «Нераспределённое»
свода, откуда сюда и приходят.

404 (`code`): `tender_not_found`, `round_not_found` (раунд не в этом тендере —
поиск парой, как `get_round`), `round_has_no_offer_estimates` («Раунд или его
сметы больше недоступны»).

### 2.4. Запись: раундовые PUT и DELETE

```
PUT    /api/v1/tenders/{tender_id}/rounds/{round_id}/category-overrides
       { lot_key, position_key_in_proposal, work_category_id, note }
DELETE /api/v1/tenders/{tender_id}/rounds/{round_id}/category-overrides
       { lot_key, position_key_in_proposal }
```

`note` — **обязательное nullable-поле**, семантики «omitted» нет: тело всегда
объявляет заметку целиком, явный `null` — явная очистка. Перезапись §2.4 п. 4
всегда полная по вектору, и никакая существующая заметка не затирается молчком:
предзаполнение существующей заметкой и показ различающихся — обязанность
экрана (§2.7), для этого GET и отдаёт `notes` (§2.3). Затирание возможно
только действием человека, очистившего предзаполненное поле.

Логический ключ — в теле, не в пути: `position_key_in_proposal` — строка из
файла, её место в URL потребовало бы экранирования без выгоды. Права — как у
GET. Транзакцию ведёт роутер.

**HTTP-контракт раундовых маршрутов** (свой, а не наследованный от по-сметного
роутера — тот живёт на `CategoryOverrideError` и своей карте, раундовые
маршруты живут по конвенции тендерного контура): пользовательские исходы
сервис поднимает как `DomainError` с кодом и статусом, роутер переводит их
`raise_domain_error`; `mapping_broken` — НЕ `DomainError`, а собственное
исключение целостности, которое роутер обязан залогировать
(`log.error(..., exc_info=True)`) и пробросить в 500 — пользователю повторять
нечего, чинить нам (тот же принцип, что у `mapping_broken` по-сметного
роутера):

| Код | Статус | Кто и когда |
|---|---|---|
| `tender_not_found`, `round_not_found` | 404 | раунд ищется парой (tender_id, round_id) |
| `round_has_no_offer_estimates` | 404 | «Раунд или его сметы больше недоступны» |
| `section_not_found` | 404 | логический ключ отсутствует во ВСЕХ offer-сметах (§2.4 п. 2) |
| `category_not_found` | 404 | `work_category_id` тела PUT нет в классификаторе |
| `not_a_chapter` | 422 | ключ есть во всех сметах, строки — не разделы |
| `structure_disabled` | 409 | привязка по структуре погашена — как у по-сметного маршрута |
| `mapping_broken` | 500 + лог | ключ в части смет, либо `is_chapter` различается |

По-сметный `not_found` объединяет «нет раздела» и «нет статьи» в одном коде;
раундовые маршруты эти смыслы **разводят** (`section_not_found` /
`category_not_found`) — по-сметный контракт при этом не меняется.

**Порядок проверок одинаков у PUT и DELETE:** блокировки → разрешение
логического ключа по таблице §2.4 п. 2 (все исходы выше) → и только затем
предикат no-op. Ключ, отсутствующий во всех сметах, — это `section_not_found`
404, а не «override нет ни в одной → no-op»: no-op определён только для
успешно разрешённого раздела.

Семантика PUT (сервис `services/round_category_override.py`):

1. **Блокировки в объявленном порядке: tender → round → offer-сметы по
   `estimate_id ASC`** — тот же тотальный порядок у всех писателей раунда,
   иначе взаимоблокировка с параллельным PUT соседнего раздела.
2. Разрешить логический ключ в **каждой** offer-смете раунда — проверки одной
   представительной сметы недостаточно, разбиение исходов полное:

   | Исход разрешения | Классификация |
   |---|---|
   | ключ отсутствует во всех сметах | `section_not_found` → 404: обычный неверный вход клиента, не поломка |
   | ключ есть лишь в части смет | `mapping_broken` → 500 с логом: проекции разошлись |
   | ключ есть во всех, все строки не разделы | `not_a_chapter` → 422 |
   | `is_chapter` различается между сметами | `mapping_broken` → 500 с логом |
3. **Предикат no-op:** все текущие векторы одинаковы между собой **и** их
   `(work_category_id, note)` совпадают с телом PUT. Без второго условия выбор
   новой статьи при согласованном старом решении ошибочно сошёл бы за no-op
   (находка ревью гейта 1). No-op не трогает ни решения, ни аудит.
4. Иначе — **атомарная перезапись всех смет**: единое решение И единый аудит
   (`assigned_by` = автор запроса, `assigned_at` = now()) в каждой offer-смете.
   `set_override` для этого не переиспользуется (его no-op сохранил бы старых
   авторов там, где содержимое совпало, — §1.3); сервис пишет
   `EstimateCategoryOverride` сам, а **пересчёт материализации и допработ**
   вызывает тем же кодом, что по-сметный сервис (общая apply-часть выносится
   из `category_override.py`, поведение по-сметного маршрута не меняется —
   проверяется его же тестами).
5. Либо разнесено во всех сметах, либо ни в одной — одна транзакция.

DELETE симметричен и проходит шаги 1–2 дословно (блокировки, затем разрешение
ключа по таблице — ключ, отсутствующий во всех сметах, это `section_not_found`
404, до предиката no-op дело не доходит); no-op DELETE — когда у успешно
разрешённого раздела override нет ни в одной смете; иначе снять во всех и
пересчитать. Частичное и конфликтное состояния DELETE тоже приводит к «без
решения» — это и есть «повторное решение выравнивает этап».

### 2.5. Диагностика: три кода, свой селектор

Блок «Не закрывается разносом» перечисляет строки за границами §5.5 спеки
разноса — по всем offer-сметам раунда, с участником:

| Код | Селектор |
|---|---|
| `outside_structure` | позиции вне структуры файла (не-раздел без `chapter_item_id`) |
| `structure_disabled` | предложения с погашенной привязкой по структуре — одной строкой на предложение |
| `unresolved_chapter_ref` | допработы без статьи, чья ссылка не разрешается планом резолва (включая `chapter_ref_raw IS NULL`) |

`unallocated.extras` паспорта не переиспользуется — он шире границы (§1.4).
Селектор `unresolved_chapter_ref` обязан исполнять тот же план резолва, что
пересчёт (`categories_by_chapter_number`/`resolve_ref`), а не приближение:
допработа, которую разнос закроет, в диагностику попасть не должна.

Диагностика — не действие: кнопок нет, строки не участвуют в состояниях §2.2.

### 2.6. Карточка тендера: счётчик раунда

`get_tender_card` дополняет каждый элемент `rounds[]` полем:

```
unallocated_pending_sections: int | null
```

`null` — у раунда нет offer-смет (триггер не рисуется); иначе число логических
разделов в состояниях `unassigned + partial + conflict` — **тем же этапным
агрегатором, что GET §2.3** (общая функция, не вторая формула), по уникальным
`(lot_key, position_key_in_proposal)`. Частичный override возможен и у раздела
со статьёй из файла, поэтому «нераспределённые плюс конфликтные» было бы
неполно (находка ревью гейта 1).

Существующие поля ответа карточки остаются посимвольно теми же.

### 2.7. Экран: триггер, Sheet, URL

**Триггер** — в заголовке этапа решётки, отдельным элементом (ячейки-`Toggle`
не трогаются): при `unallocated_pending_sections > 0` — тёплый бейдж
«⚠ N разделов требуют решения — разнести», при `0` — тихое «разнести» (снять
ошибочное решение можно и при нуле), при `null` — ничего.

**Sheet** (shadcn `Sheet`, справа) — этапный верстак:

- шапка: «Разнос статей — Этап N», подзаголовок «Ведомость одна на этап:
  решение по разделу применяется ко всем сметам раунда (K участников)»;
- «Требуют решения — N»: дерево в файловом порядке, счётчик «N позиций» —
  полный размер файлового поддерева (§2.3), пометки `partial`/`conflict` из
  §2.2, `Command`-выбор статьи по `category_options` (компонент выбора — тот
  же, что в паспорте) **плюс необязательное поле «Заметка»** в том же
  Popover: предзаполняется единой существующей заметкой; при различающихся
  (`notes` из §2.3) — показывает их и требует явного выбора; в PUT уходит
  содержимое поля, пустое — как `null` (§2.4);
- «Разнесено вручную»: только `resolved`, с «снять»;
- «Не закрывается разносом»: диагностика §2.5, поимённо;
- свои loading / error / 404-состояния; ленивый GET — только при первом
  открытии; наименования разделов зажаты `line-clamp` (ядро паспорта уже
  зажимает — свойство сохраняется при выделении ядра).

**Ядро**: из `UnallocatedPanel` выделяется презентационный `UnallocatedWorkbench`
с настраиваемой правой колонкой и сортировкой (паспорт: две суммы, сортировка по
убыванию свёртки; тендер: счётчик позиций, файловый порядок) и настраиваемыми
блоками. Паспортная обёртка сохраняет имя, пропсы и поведение — тесты паспорта
остаются зелёными без ослабления.

**Контракт URL:** открытие пишет `?unallocated=<round_id>` (прочие параметры
сохраняются), закрытие удаляет только `unallocated`. Параметр принимается,
лишь когда раунд принадлежит текущей карточке и несёт offer-сметы; чужой или
устаревший id не запускает запрос вовсе.

**Хуки:** раундовые мутации — свои `useSetRoundCategoryOverride` /
`useClearRoundCategoryOverride` (ревизия решения гейта 1 о дискриминированном
union: у тендера теперь собственные раундовые маршруты, смешивать нечего;
по-сметные хуки паспорта не меняются). Успешная мутация инвалидирует:
`qk.tenders.card(tenderId)`, `qk.tenders.stageSummaryForTender(tenderId)`,
`qk.tenders.stagePositionsForTender(tenderId)`, ключ GET §2.3. Перекрёстных
инвалидаций договорного контура нет — проверяется тестом.

### 2.8. Свод: переход к разносу

Ячейка строки «Нераспределённое» с ненулевым числом нераспределённых строк
(`unallocated.cells[i].rows.row_count > 0` — счётчики, не деньги: у колонки с
неизвестной базой НДС суммы скрыты, а строки разносимы) получает действие
«разнести →» — ссылку на `/tenders/{tenderId}?unallocated=<columns[i].round_id>`.
По `round_id`, не по `offer_id`/`estimate_id` — носитель разноса этап (§2.1).

## 3. Что сознательно НЕ делается

1. **Межэтапное распространение решений.** Файлы разных раундов — разные файлы;
   соответствие разделов между ними — эвристика, которую Ф3 не зря запретила в
   денежной логике. Повторить разнос по этапам (их единицы) дешевле, чем строить
   и охранять сопоставление. Кандидат в отдельную фичу, если стенд покажет боль.
2. **Baseline вне радиуса** (§2.1) — и вне входного множества GET.
3. **Деньги в верстаке** (§2.3) — включая `rows_priced`.
4. **Разнос допработ за границей** — граница §5.5 сохраняется, диагностика
   называет её поимённо.
5. **По-сметные маршруты, сервис, панель и хуки паспорта** — без изменений;
   выделение общей apply-части и ядра панели обязано сохранить их поведение
   и тесты дословно.
6. **Инвариант AGENTS.md** «Ручной разнос статей не обещает нуля глобально» —
   не пересматривается: границы §5.5 остаются границами и в тендере.

## 4. Тесты

### 4.1. Агрегатор состояний (юнит + интеграция)

- Входное множество: раздел со статьёй из файла и без override не попадает;
  с частичным override — попадает; пустая ведомость → пустой ответ.
- Разбиение исчерпывающее и непересекающееся: каждый раздел входного множества
  ровно в одном из четырёх состояний (свойство на сгенерированных векторах —
  урок «сходимость не доказывает разбиения»: состав проверяется отдельно).
- Конфликт по каждой компоненте вектора отдельно: статьи / заметки / только
  аудит (негативный к «конфликт = разные статьи»).
- Структура из представительной сметы; ключ представительной сметы отсутствует
  в другой → `mapping_broken`.
- `rows` — полный размер файлового поддерева: конфликт при нуле нераспределённых
  строк несёт ненулевой `rows` (негативный к прежнему смыслу «строки в
  Нераспределённом»).

### 4.2. Раундовая запись (интеграция)

- PUT ставит единое решение и единый аудит во все offer-сметы; baseline той же
  выборкой не тронут (фикстура с baseline обязательна).
- No-op: оба условия предиката, негативные к каждому — (а) векторы одинаковы,
  но статья в теле новая → перезапись; (б) векторы различаются только аудитом,
  тело совпадает со статьёй → перезапись с выравниванием аудита.
- Заметки: тело с `note: null` очищает заметки во всех сметах (явная очистка);
  тело с новой заметкой ставит её во всех; `note` в теле обязательное —
  запрос без поля отвергается валидацией (негативный: omitted ≠ null).
- Разбиение исходов разрешения ключа §2.4 п. 2 — тест на каждый из четырёх:
  404 при отсутствии во всех, 500 при частичном присутствии, 422 при
  не-разделах во всех, 500 при различающемся `is_chapter`.
- Атомарность: искусственный отказ на последней смете → ни одна не изменена.
- Пересчёт: деньги переезжают между статьями свода у ВСЕХ колонок этапа;
  допработы с разрешимой ссылкой переезжают следом (связка, не предикат —
  урок «проверять на уровне, где живёт дефект»).
- Порядок блокировок: параллельные PUT двух разделов одного раунда не
  взаимоблокируются (проверка снятием защиты — тест обязан краснеть при
  нарушении порядка, урок «тесты на гонки»).
- DELETE: выравнивает частичное и конфликтное в «без решения»; no-op при
  пустом векторе у разрешённого раздела; ключ, отсутствующий во всех сметах,
  → `section_not_found` 404, а НЕ no-op (коллизия, найденная ревью гейта 2).
- По-сметный маршрут после выделения apply-части отвечает как прежде — его
  существующие тесты без правок.

### 4.3. GET и карточка

- Все три 404-кода; `member` допущен.
- Диагностика: по фикстуре на каждый из трёх кодов; допработа с разрешимой
  ссылкой в диагностику НЕ попадает (негативный, §2.5).
- Счётчик карточки равен агрегатору GET на одних данных (общая функция,
  тест — что второй формулы нет: подмена агрегатора меняет оба ответа).
- Прежние поля ответа карточки — посимвольно как до фичи.

### 4.4. Экран (vitest, msw)

- Триггер: три состояния (бейдж / тихое / отсутствует).
- Sheet: ленивый GET (не уходит до открытия), loading/error/404, пометки
  partial/conflict, «снять» у resolved, диагностика без кнопок.
- Заметка в пикере: предзаполнение единой существующей; показ различающихся
  при конфликте; пустое поле уходит в PUT как `null`.
- URL: открытие/закрытие, сохранение прочих параметров, отказ по чужому и
  устаревшему `round_id` (запрос не уходит — проверка на уровне запроса).
- Инвалидации тендерной ветки и отсутствие перекрёстных к договорной.
- Свод: «разнести →» по `columns[i].round_id`; условие видимости по
  `rows.row_count`, включая колонку с неизвестной базой НДС.
- Паспорт: тесты `UnallocatedPanel`/`CategoryTable` зелёные без правок.

### 4.5. Стенд (ручная приёмка)

На 449-ТУ: разнос этапа 3 вершинами `14`/`15` → счётчик заголовка этапа
обнуляется, строка «Нераспределённое» свода по колонке этапа 3 становится
`0,00`, у колонки появляется подпись `manual_overrides`. На этапах 1–2
диагностика называет допработы АНТТЕК/ЕНИГЮН поимённо, и остаток строки свода
совпадает с их вкладом.
