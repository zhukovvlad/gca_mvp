## 2. Решение

### 2.1. Что сдаёт фича

1. До 10 параметров на семью в ручной правке; модель строит схему как раньше
   — до трёх параметров (§2.8).
2. Роль параметра «главный / второстепенный»; вариант — только из активных
   главных (§2.3).
3. Ручная правка меняет действующую версию **на месте**, новая версия
   рождается только пересборкой моделью (§2.5).
4. Частичный запрос значений: модель отвечает только на нужные параметры
   контекста; известные значения остаются (§2.4).
5. Вид значений «точные / диапазоны», диапазоны — границами и шагом, два
   крайних всегда; перестройка значений заполненного параметра (§2.6).
6. «Только из списка» и значения не из списка (§2.7).
7. Пересборка схемы переносит параметры человека (§2.8); слияние семей
   предупреждает о параметрах, которые пропадут (§2.9).
8. Окно «Править схему» — раскладка «Список и редактор» с предпросмотром
   правки (§2.10, §2.11).

### 2.2. Схема: миграция `0022`

**`family_parameters`** — новые колонки:

- `role text NOT NULL DEFAULT 'main'`, CHECK `role IN ('main', 'secondary')`;
- `value_kind text NOT NULL DEFAULT 'exact'`, CHECK `IN ('exact', 'range')`;
- `closed boolean NOT NULL DEFAULT false` — «только из списка»;
- `range_from numeric`, `range_to numeric`, `range_step numeric` — NULL;
- `origin text NOT NULL DEFAULT 'model'`, CHECK `IN ('model', 'human')` —
  чей параметр для пересборки (§2.8);
- `archived_at timestamptz` — NULL; убранный параметр архивируется, не
  удаляется.

CHECK `ck_family_parameters_range_shape`: либо `value_kind = 'exact'` и все
три границы `NULL`; либо `value_kind = 'range'`, все три `NOT NULL`,
`range_step > 0`, `range_from < range_to`, `mod(range_to - range_from,
range_step) = 0`, `(range_to - range_from) / range_step <= 28` и `closed`.
Двадцать восемь внутренних плюс два крайних — тридцать, предел значений
параметра.

CHECK ordinal — `BETWEEN 1 AND 100`; `UNIQUE (schema_id, ordinal)` остаётся
и покрывает архивные параметры: **номер внутри версии не используется
повторно** — новый параметр получает `max(ordinal) + 1` по всем параметрам
версии, архивным тоже. Повторное использование сводило бы ключи: «не
уточнено» в ключе — `N=?` без идентификатора значения, и у архивного и
нового параметра с номером `N` ключ совпал бы, а `_resolve_variant` вернул бы
вариант со строками архивного параметра (ревью Codex гейта 2, проверено
`values_key_of` базового коммита). Номера уплотняются только новой версией
пересборки (§2.8); исчерпание ста номеров в одной версии — отказ
`schema_ordinals_exhausted` с подсказкой пересобрать схему.

**Предел «не больше 10 активных параметров»** держит сервис: каждый
писатель схемы берёт семью `FOR UPDATE` первой
(`_lock_family_for_schema_life`), проверка числа активных идёт под этим
замком; тест — 11-й параметр отказ, 10-й проходит, две параллельные правки
по 6 новых параметров — одна отказ.

**`family_parameter_schemas`** — `revision integer NOT NULL DEFAULT 0`:
счётчик изменений действующей версии на месте; растёт на единицу при каждой
записи в версию — правка (§2.5), слияние значений, «не из списка» (§2.7),
расширение списка моделью (`_extend_with_value`), косметика. Входит в
`preview_hash` (§2.5).

**`family_parameter_values`** — новые колонки:

- `range_lo numeric`, `range_hi numeric` — NULL; у значения
  параметра-диапазона: `range_lo` NULL у «до …», `range_hi` NULL у «… и
  более»; CHECK `range_lo < range_hi`, когда оба заданы;
- `retired_at timestamptz` — NULL; значение, ушедшее из списка без слияния
  (§2.6). CHECK: `retired_at` и `merged_into_id` не заданы одновременно.

`UNIQUE (parameter_id, value_norm)` остаётся: значение с нормой выведенного
возвращается из истории (`retired_at := NULL`), а не заводится заново.
Перестройка значений (§2.6) **не пишет `merged_into_id`** — только перенос и
вывод, — поэтому каждое значение, которое она убрала из списка, выведено и
возвращаемо; слитыми остаются только синонимы, слитые человеком.

**Инвариант строк:** строка контекста, ссылающаяся на выведенное значение,
всегда несёт `refresh_requested_at` (вывод ставит отметку той же
транзакцией, ответ модели заменяет строку). CHECK-ом межтабличное условие не
выразить — держит сервис, тест проверяет после каждой операции §2.6.

**`context_parameter_values`** — новые колонки:

- `off_list_text text` — NULL; текст значения не из списка (§2.7);
- `refresh_requested_at timestamptz` — NULL; «уточняется»: значение у
  контекста ждёт перезапроса этого параметра (§2.6).

`ValueSource` получает `off_list`: CHECK перечисления источников
`ck_context_parameter_values_source` получает `'off_list'`, CHECK
`ck_context_parameter_values_source_value_pair` переписывается: `(value_id
IS NULL) = (source IN ('path_conflict', 'none', 'off_list'))`; новый CHECK
`ck_context_parameter_values_off_list_text`: `(source = 'off_list') =
(off_list_text IS NOT NULL)`.

**`semantic_jobs`** — `requested_ordinals smallint[]` NULL: номера
параметров частичного запроса значений (§2.4); CHECK — непусто только у
`kind = 'context_values'`. В уникальный индекс заданий колонка не входит:
подмножество входит в тело и потому в `request_hash`.

**`semantic_events`** — новый тип `family_schema_edited` (субъект — семья);
CHECK-и `ck_semantic_events_event_type` и `ck_semantic_events_subject_by_type`
переписываются по образцу `0021` (:63-71), обязательные ключи — в
`services/semantic_events.py` `EVENT_REQUIRED_KEYS`.

**Заполнение:** все существующие параметры — `main`, `exact`, `closed =
false`, `origin = 'model'`, без архива; значения и строки контекстов не
меняются. Ни один `request_hash` от миграции не меняется (§2.4, байтовая
идентичность).

**downgrade** отказывает `RuntimeError`, если есть хоть одна строка с
непустым носителем: параметр `secondary`, `range`, `closed`, `human`,
архивный или с ordinal > 3; версия с `revision > 0`; значение с границами или `retired_at`; строка
контекста `off_list` или с `refresh_requested_at`; задание с
`requested_ordinals`; событие нового типа. На пустых — возвращает прежние
CHECK-и и `UNIQUE (schema_id, ordinal)`.

### 2.3. Идентичность варианта

Вариант — семья + версия + значения **активных главных** параметров
(`role = 'main' AND archived_at IS NULL`). `values_key_of` и
`_resolve_variant` (`work_variants.py:134`, `:243`) получают на вход
множество активных главных номеров версии вместо всех параметров; формат
ключа (`ordinal=value_id|…`, `?` — «не уточнено») не меняется, поэтому у
существующих вариантов стенда (все параметры главные) ключи остаются
прежними. `work_variant_values` пишет строки только главных параметров.

**Пересчёт вариантов** — общая процедура правок, меняющих состав или
значения главных (смена роли, архивирование главного, слияние значений
главного, перенос значений диапазона §2.6): для каждого неархивного
контекста семьи, у которого вариант действующей версии и у **каждого**
активного главного есть строка значения без `refresh_requested_at`,
вычисляется ключ, вариант разрешается `_resolve_variant` (вставка или
поиск, цепочка `merged_into_id`, возврат архивного), контекст переводится,
опустевшие варианты архивируются (`archive_variant_if_empty`). Контекст без
полного набора остаётся в прежнем варианте до ответа модели (§2.4).

Возврат прежних вариантов при смене роли туда и обратно (дизайн §2.3)
следует из того же: версия не меняется, номера не используются повторно
(§2.2), ключи совпадают, `_resolve_variant` возвращает архивную запись.
Гарантия верна, пока между сменами роли значения параметра не сливались
человеком: ключ с идентификатором слитого значения уже не совпадёт.
Пересчёт архивирует опустевшие варианты без `merged_into_id`
(`archive_variant_if_empty`), поэтому цепочки слияния вариантов от него не
появляются и возврат не уводит в чужой вариант.

Слияние значений **второстепенного** параметра вариантов не касается:
`merge_parameter_values` (`work_variants.py:1629`) переписывает варианты
только для главного параметра, для второстепенного — только
`context_parameter_values` и `merged_into_id` (ревью Codex гейта 1, дизайн
§2.3).

### 2.4. Частичный запрос значений

**Что нужно контексту** — две величины вместо булевой `_values_needed`
(`semantic_reconcile.py:572`); применимость (`_values_applicable`) не
меняется:

- `needed_ordinals` — номера, о которых спросить модель:
  - у схемы есть параметры и `variant_paths_hash` не совпал с путями — **все
    активные** (изменился материал, известные значения перестают быть
    известными);
  - иначе — активные параметры, у которых **нет строки значения в
    действующей версии или строка помечена `refresh_requested_at`**; одно
    правило для всех случаев — после пересборки, при ждущей семье, без
    варианта, после правки;
- `variant_due` — контексту нужно назначение варианта: ждущая семья, нет
  варианта или вариант чужой версии.

План по паре:

| `needed_ordinals` | `variant_due` | План |
|---|---|---|
| непусто | любое | задание `context_values` с этим подмножеством |
| пусто | да | **завершение без модели** (ниже) |
| пусто | нет | ничего |

**Завершение без модели** — сегодняшний путь схем без параметров
(`plan.free`, стоимость 0, `complete_without_model`,
`semantic_worker.py:915-946`) расширяется на любой контекст, у которого все
строки действующей версии уже есть и не помечены: вариант разрешается по
сохранённым строкам активных главных (у схемы без параметров — ключ `""`,
как сегодня), применяется ждущая семья (`_switch_pending_family`),
выполняется промоушен `TO_REVIEW → POSITION`, пишется
`context_variant_assigned`. Это закрывает два входа, которые правило «пусто —
ничего» оставило бы без варианта: новая строка семьи без параметров и
контекст после пересборки, где модель не предложила параметров, а все
параметры человека перенесены со строками (ревью Codex гейта 2).

**Рендер подмножества.** `ValuesRequestMaterial` / `load_values_material`
несут номера запроса; `render_values_request` строит блок схемы и
перечисление номеров формата ответа (`values_response_format_for`) только из
них, в порядке номеров. `VALUES_PROMPT` не меняется: он просит объект на
каждый параметр **блока схемы**, а блок теперь перечисляет запрошенные.
**Когда подмножество совпадает со всеми активными параметрами и среди них
нет диапазонов, тело запроса совпадает с сегодняшним байт в байт** —
существующие задания, отпечатки и кэш префикса не сдвигаются от выката.
Параметр-диапазон добавляет в свой раздел блока схемы строку правила:
значения — диапазоны, найти число в наименовании или разделах и выбрать
диапазон, нижняя граница включается, верхняя нет, числа нет — `none`.
Роль параметра в запрос не попадает.

**Задание** хранит `requested_ordinals` (NULL — все активные на момент
рендера). `render_request_for` (`variant_request.py:461-487`) и
`render_job_request` (`semantic_worker.py:286-297`) воспроизводят рендер по
заданию; `_plan_context_values` / `_plan_applicable` считают «текущий ключ»
контекста по тому же подмножеству — иначе следующая сверка отменяла бы
частичное задание как `input_changed`. То же — в сопоставлении пачек
(`semantic_decisions.py:879-919`) и `without_discarded_values`
(`semantic_reconcile.py:889-910`).

**Разбор** (`parse_values_answer`): отвеченные номера равны **запрошенным**;
вызов в `_record_variant_result` передаёт запрошенные параметры, а не всю
схему.

**Запись** (`apply_values`):

- проверка номеров — по запрошенным;
- строки запрошенных параметров удаляются и вставляются заново (с них
  снимается `refresh_requested_at`); строки остальных параметров
  действующей версии остаются; строки параметров других версий (прежняя
  версия после пересборки, схема прежней семьи после смены семьи)
  удаляются, как сегодня удаляются все;
- ответ `new` у параметра с `closed = false` расширяет список, как сегодня;
  у `closed = true` — строка `source = 'off_list'`, `off_list_text` —
  прочитанный текст, список не меняется (§2.7);
- ответ `new` у параметра-диапазона, чей текст — одно число (запятая или
  точка, необязательное слово единицы), система относит к диапазону сама по
  границам (§2.6), источник — ответа модели; не число — `off_list`;
- вариант разрешается по полному набору активных главных из сохранённых и
  новых строк (§2.3); если главного всё ещё нет — вариант не меняется;
- `variant_split_hint` считается по строкам всех активных параметров, а не
  только отвеченных; `variant_paths_hash` — как сегодня;
- событие `context_variant_assigned` несёт отвеченные номера и номера
  сохранённых.

**Волна расширения** (`schedule_extension_wave`,
`semantic_reconcile.py:1695`) спрашивает только расширенный параметр, а не
всю схему (`force_needed` заменяется подмножеством).

**Стоимость** — `rebuild_preview` и `_estimate_totals` считают рендеры по
тем же подмножествам, что планировщик, иначе предпросмотр разошёлся бы с
очередью.

**Без модели** — путь «завершение без модели» выше; подмножество не бывает
пустым у поставленного задания.

### 2.5. Ручная правка на месте

**Правка не заводит версию**: все изменения §2.5–§2.7 пишутся в действующую
`frozen` версию; новая версия рождается только пересборкой (§2.8). Действующая
версия уже изменяема и сегодня — косметика, слияние и расширение моделью
пишут в неё на месте; фича добавляет к ним параметры. История правок —
события `family_schema_edited`.

**Тело правки** — полное желаемое состояние активных параметров:

- `ordinal` — номер существующего активного параметра или `null` для нового
  (номер выдаёт сервер: `max(ordinal) + 1` по всем параметрам версии, §2.2);
- `name`, `role`, `value_kind`, `closed`;
- `values` — список текстов для `exact`; `range` — `{start, stop, step}` для
  `range` (числа — строками, как деньги проекта; у `exact` диапазон в теле
  отбрасывается).

Существующий активный параметр, которого нет в теле, архивируется.

**Проверки** (отказ — §2.10): больше 10 активных; пустое имя или значение;
дубль имени по норме среди активных; смысловое переименование параметра;
исчезновение значения точного параметра без смены вида (слияние — отдельным
действием, как сегодня); неверный диапазон (`start >= stop`, `step <= 0`,
нецелое число шагов, больше 28 внутренних; граница или шаг не конечны, по
модулю не меньше 10⁹ или с более чем шестью знаками после запятой — дальше
используется каноническая запись числа без хвостовых нулей; подпись значения
диапазона совпадает по норме со значением, которое человек слил синонимом в
другое, — разслияние значения не разслило бы вариантов); правка при версии `building` или
без действующей версии; семья не активна. `closed` у диапазона сервер
ставит сам.

**Следствия** (уточняют таблицу дизайна §2.3):

| Правка | Варианты | Что спрашивается у модели |
|---|---|---|
| добавить параметр (любой роли) | второстепенный — не меняются; главный — каждый контекст остаётся в прежнем варианте до ответа | только новый параметр — у всех применимых контекстов семьи |
| убрать второстепенный | не меняются | ничего |
| убрать главный | пересчёт без него (§2.3) — варианты сливаются | ничего |
| сменить роль сохранённого параметра | пересчёт: делятся или сливаются | ничего; контексты без значения этого параметра — в прежнем варианте до ответа |
| добавить значение точного параметра | не меняются | только этот параметр — у контекстов, где он `none` или `off_list` (строка помечается «уточняется»); `off_list` с тем же текстом по норме получает значение сразу, без модели (§2.7) |
| слить значения | главный — как сегодня; второстепенный — не меняются (§2.3) | ничего |
| включить или снять «только из списка» | не меняются | ничего |
| поправить написание | как сегодня | как сегодня (отпечатки обновляются) |
| перевести в диапазоны, сменить границы или шаг, вернуть в точные | §2.6 | §2.6 |

Две строки уточняют дизайн. **«Убрать главный»** дизайн относил к «как
сегодня» (полный перезапрос); на месте это смена роли и архивирование —
известных значений хватает, и перезапрос был бы платой за ничто. **«Добавить
значение главного»** — тоже не полный перезапрос, а та же волна, что у
расширения моделью: спрашиваются контексты, где параметр не уточнён или не из
списка. Обе уточнения следуют принципу дизайна §2.3 «известные значения
заново не запрашиваются».

**Чей параметр.** Новый параметр — `origin = 'human'`. Параметр модели,
которого правка коснулась (имя, в том числе косметически, значения, роль,
«только из списка», вид или границы), становится `human` (дизайн §2.4);
так же — слияние значений параметра (в окне правки и в блоке схемы).
Архивирование происхождения не меняет.

**Предпросмотр и подтверждение.** Правка идёт двумя вызовами, как
пересборка: предпросмотр (§2.10) считает следствия по телу и возвращает
сводку и `preview_hash`; сохранение принимает тело и `preview_hash`,
пересчитывает предпросмотр под блокировкой семьи и при расхождении
отказывает `409 preview_changed`. Задания правки ставятся с `NO_CAP`:
стоимость человек видел. Сводка: варианты — было, станет сразу, «итог после
ответов» (есть ли контексты, ждущие ответа по главному); запросы — число
контекстов по параметрам и оценка резерва и ожидаемой цены (`_estimate`);
переносы значений и выведенные значения с числом контекстов (§2.6); число
контекстов «уточняется»; число ждущих запросов значений семьи, которые
правка пересчитает (ниже, «Охват правки»). `preview_hash` — от семьи,
действующей версии **и её `revision`** (§2.2), нормализованного тела, чисел
сводки, тарифов и `RESERVE_FORMULA_VERSION`. Версия меняется на месте и её
идентификатор постоянен, поэтому без `revision` параллельная правка, не
сдвигающая чисел сводки (косметическое переименование, слияние без
следствий), прошла бы незамеченной, и сохранение полного старого тела
затёрло бы её без `preview_changed` (ревью Codex гейта 2).

**Охват правки — одна семья, не единица.** Список семей в запросе
предложения семьи несёт номер, имя, единицу и определение семьи
(`semantic_request.py:188-197`), параметров в нём нет; поэтому правка схемы
не меняет ни одного тела предложения и не перезапрашивает единицу — в
отличие от правки имени или определения семьи (devlog 3б, «Сброшенный
перезапрос»: переименование одной семьи отменило 666 ждущих заданий
перезапроса «компл»). Правка трогает только запросы значений контекстов
своей семьи: новые — по таблице выше; **ждущие** (`pending`,
`privacy_hold`) — пересчитываются, если правка изменила их рендер
(значения, написание, вид параметра подмножества), как сегодня при
переименовании (`work_variants.py:1555-1558`); записанные ответы не
перезапрашиваются. Сводка называет число ждущих запросов значений семьи,
которые правка пересчитает, — чтобы правка не сбрасывала их молча.

**Блокировки.** Порядок модуля (`work_variants.py:5-8`): семья `FOR UPDATE`
(`_lock_family_for_schema_life`) → действующая версия `FOR UPDATE` →
параметры и значения по id → варианты по id → контексты по id → задания
последними. **Сериализует правку с записью ответа замок семьи**: запись
ответа берёт семью `FOR UPDATE` первой (`_acquire_domain_locks` →
`_lock_families(..., exclusive=True)`, `work_variants.py:712`), правка —
тоже (`:1287`); запись ждёт правку и после неё видит изменившийся рендер —
`stale_fingerprint`. `FOR UPDATE` версии в правке — второй рубеж против
второй правки, но не против записи ответа: без замка семьи правка держит
версию, запись — семью и ждёт версию, а вставка события правки проверяет
внешний ключ семьи (`FOR KEY SHARE`) — взаимоблокировка, запись
откатывается, потери записи нет (замер реализации). Сериализацию с записью
держит только замок семьи. Каждый писатель схемы на месте
(слияние значений, «не из списка», расширение моделью) берёт семью первой —
та же цепочка.

**Событие** `family_schema_edited`: автор, номер версии, список изменений по
параметрам (добавлен, архивирован, роль, вид и границы, «только из списка»,
значения добавлены, выведены, перенесены), варианты до и после, число
поставленных запросов. Отдельные `family_schema_value_added` для значений,
добавленных человеком, остаются (`origin = manual`).

### 2.6. Диапазоны и перестройка значений

**Значения диапазона** строит система по `{start, stop, step}`: «до `start`»,
внутренние «`a`–`b`» с шагом, «`stop` и более»; границы — `range_lo`,
`range_hi`; нижняя включается, верхняя нет; числа — без лишних нулей,
десятичный разделитель — запятая. Происхождение — `manual`. Значение с той
же нормой, выведенное раньше, возвращается из истории.

**Перестройка** — перевод точного параметра в диапазоны, смена границ или
шага, возврат в точные. Каждое прежнее активное значение (не слитое, не
выведенное) разрешается так:

- **точное число** (одно число, запятая или точка, необязательное слово
  единицы) — в единственный новый диапазон, содержащий его;
- **прежний диапазон** — в единственный новый, целиком содержащий его
  (бесконечные края учитываются);
- **иначе** (не число, прежний диапазон делится, возврат диапазонов в
  точные) — неразрешимо.

**Цель совпадает с источником** — прежний диапазон, чьи границы в новом
наборе те же (крайние «до 2» и «10 и более» при смене шага 2 → 1 с теми же
`from` и `to`), — **значение и его строки остаются без изменений**: ни
переноса, ни `retired_at`, ни отметки, ни запроса. Без этого случая правило
переноса вывело бы действующее значение, на которое строки продолжают
ссылаться без «уточняется», — нарушение инварианта §2.2 (ревью Codex гейта
2, круг 2).

Разрешённое значение **переносится**: строки контекстов переводятся на цель
с прежним источником, само значение **выводится** (`retired_at`), у главного
параметра — пересчёт вариантов (§2.3). Неразрешимое **выводится** тоже, но
строки контекстов сохраняют его и получают `refresh_requested_at` — контекст
остаётся в прежнем варианте, карточка показывает «уточняется», планировщик
спрашивает этот параметр (§2.4). Ответ модели заменяет строку, вариант
пересчитывается; выведенное значение остаётся в истории. Значения точного
списка при возврате в точные задаёт человек в том же теле.

**Почему перенос, а не слияние** (дизайн §2.3 называл его слиянием —
уточнение, ревью Codex гейта 2). Слияние писало бы `merged_into_id`, и
обратная перестройка не могла бы вернуть значение: «4», слитое в «4–6», при
возврате в точные снова задаётся как «4», но `UNIQUE (parameter_id,
value_norm)` не даёт новой записи, а существующая канонизируется
(`get_or_create_value`) обратно в «4–6». Вдобавок `merge_parameter_values`
архивирует варианты с `merged_into_id`, и возврат значения уводил бы
`_resolve_variant` по цепочке в вариант-цель. Выведенное же значение
возвращается из истории одной отметкой.

**Возврат из истории.** Любое значение, которое правка (§2.5) или
построение диапазона называет, ищется по норме среди значений параметра:
активное — берётся, **выведенное — возвращается** (`retired_at := NULL`),
слитое человеком синонимом — канонизируется, как сегодня. Возврат на строки
контекстов не переносится: строки, перенесённые с него раньше, теперь
указывают на значение, которое эта же перестройка выводит или делит, и
модель спросит их по общему правилу. Пример: шаг 2 → 4 переносит «4–6» в
«4–8»; шаг 4 → 2 возвращает «4–6» из истории, «4–8» делится — его строки
«уточняется» и спрашиваются; варианты с «4–6», архивированные пересчётом без
`merged_into_id`, возвращаются `_resolve_variant` с прежними
идентификаторами, когда ответы придут.

Пример стенда (дизайн, пункт приёмки 7): «Толщина, мм» → от 2 до 10 шаг 2 —
все 12 значений точные числа, запросов 0, варианты 18 → 17; затем шаг 1 —
«до 2» и «10 и более» остаются теми же значениями (6 контекстов, ничего не
меняется), «2–4», «4–6», «8–10» делятся — 30 контекстов «уточняется».

### 2.7. «Только из списка» и значения не из списка

`closed = true`: ответ `new` не расширяет список, а пишет `off_list` (§2.4).
По умолчанию у точных `false`, у диапазонов всегда `true` (CHECK §2.2).
Снятие «только из списка» строк `off_list` не трогает.

**Значения не из списка** схема отдаёт по параметру: нормализованный текст,
показываемый текст, число контекстов и строк (§2.10). Действия:

- **«Добавить в список»** — обычная правка, добавляющая значение (§2.5;
  выведенное с той же нормой возвращается из истории, §2.6): строки
  `off_list` с тем же текстом по норме получают значение сразу,
  `source = 'manual'` (решение человека), без модели;
- **«Слить с…»** — отдельный вызов: строки `off_list` с текстом по норме
  получают выбранное активное значение параметра, `source = 'manual'`,
  список не меняется; у главного параметра — пересчёт вариантов затронутых
  контекстов. Событие — `family_schema_edited` с изменением «текст не из
  списка отнесён» (вид изменения `off_list_resolved`).

Решение человека модель не затирает: «Слить с…» в своей транзакции закрывает
открытые (`pending`, `running`, `privacy_hold`) задания значений затронутых контекстов, которые
запрашивают этот параметр, как устаревшие (`cancelled / input_changed`, токен
снят). Выполняющееся задание теряет захват, и его ответ отбрасывается
(`lost_claim`); недостающее спрашивает новое задание сверки. Нужно это потому,
что решение не меняет тело запроса единственного параметра, и без закрытия
задание осталось бы действующим.

Уже дописанные моделью значения (`origin = extension`) окно помечает; их
слияние — существующее действие.

### 2.8. Пересборка схемы

`rebuild_schema` и `freeze_schema` (`work_variants.py:1353`, `:559`):

- **Материал** `load_schema_material` добавляет активные параметры человека
  действующей версии (имя, значения); `SCHEMA_PROMPT` получает блок «уже
  заданы человеком, не предлагай» **только когда такие параметры есть** —
  без них тело совпадает с сегодняшним байт в байт.
- **Предел ответа модели** — `N = min(3, 10 − H)`, `H` — число активных
  параметров человека; текст «от 0 до N» и перечисление номеров 1..N — по
  `N` (при `H = 0` — сегодняшние «от 0 до 3», «1, 2, 3»);
  `parse_schema_answer` проверяет `N` и непрерывность 1..N в ответе;
  параметр модели с именем (по норме) активного параметра человека —
  схемная ошибка ответа, задание идёт на повтор, версия не замораживается.
  При `N = 0` (`H = 10`) задание схемы модели не уходит — версия
  замораживается из параметров человека путём без модели, стоимость 0.
- **Запись версии** (`_write_frozen_schema`): номера новой версии
  уплотняются — параметры человека получают 1..H в порядке прежних номеров,
  параметры модели — H+1..H+N в порядке ответа (номера ответа модели 1..N
  сдвигаются на H). Параметры человека копируются с ролью, видом, границами,
  «только из списка», происхождением и активными значениями (слитые и
  выведенные не переносятся, как слитые сегодня). Параметры модели прежней
  версии не переносятся.
- **Строки контекстов** параметров человека копируются в новую версию с
  переводом идентификаторов параметров и значений по норме:
  - строка со значением без отметки — копируется;
  - строка «не уточнено», «разделы расходятся», `off_list` — копируется с
    источником и `off_list_text`;
  - **строка «уточняется» не копируется**: она ссылается на выведенное
    значение, которого в новой версии нет (инвариант §2.2), — параметр у
    контекста становится недостающим, и `needed_ordinals` спросит его
    вместе с параметрами модели (ревью Codex гейта 2).
- **Дальше** — общее правило §2.4: `needed_ordinals` — параметры без строк в
  новой версии (параметры модели и прерванные «уточняется»), значения
  параметров человека заново не запрашиваются; если таких параметров нет —
  `variant_due` ведёт к завершению без модели.
- **Предпросмотр пересборки** (`rebuild_preview`) оценивает запросы значений
  по нынешним параметрам модели как приближению (у новой схемы до ответа
  параметров нет) — отличие от сегодняшней оценки по всем параметрам
  называется в сводке (ключ ответа `values_approximate`); в `preview_hash`
  входит `revision` действующей версии — правка на месте меняет хэш
  пересборки.

`SCHEMA_PROMPT_VERSION` → 4 (шаблон изменился; тела при `H = 0` прежние).

### 2.14. Чем держится каждое правило

| Правило | Держит |
|---|---|
| не больше 10 активных | проверка под замком семьи (все писатели схемы берут его первым) + тест гонки |
| номер внутри версии не повторяется | `UNIQUE (schema_id, ordinal)` по всем параметрам, архивным тоже |
| параллельная правка не затирается | `revision` версии в `preview_hash` |
| каждое убранное перестройкой значение возвращаемо | перестройка не пишет `merged_into_id` |
| форма диапазона, «только из списка» у диапазона | `ck_family_parameters_range_shape` |
| `off_list` ⇔ текст, «не уточнено» ⇔ нет значения | CHECK-и `context_parameter_values` |
| вариант только из главных | `values_key_of` / `_resolve_variant` + тест |
| правка второстепенного не трогает вариантов | сервис правки и слияния + тест на идентификаторы вариантов |
| известные значения не перезапрашиваются | `needed_ordinals` + тест на тело задания |
| байтовая идентичность прежних тел | снимок хэша на фикстуре |
| стоимость правки подтверждена | `preview_hash` под блокировкой семьи |

## 3. Отвергнутые альтернативы

- **Правка новой версией с переносом вариантов между версиями по ключу** —
  варианты привязаны к версии `UNIQUE (schema_id, values_key)` и FK
  `work_variants → family_parameter_schemas`; перенос идентичности между
  версиями — переделка ключа и всех ссылок ради истории, которую события
  ведут и так.
- **Второстепенные параметры отдельной таблицей вне версии** — второй путь
  запроса, разбора, показа и пересборки для того, что отличается от главного
  одной ролью.
- **Новый вид задания для частичного запроса** — ревизия `AGENTS.md` §3 и
  ещё одна ветвь захвата, очередей и тарифов при том же теле запроса.
- **Тип «число» у параметра** — дизайн §3, вариант 3.
- **Удаление убранного параметра и выведенного значения** — противоречит
  «ничего не удаляется» спеки вариантов §2.4 и рвёт ссылки истории.
- **Сводка правки на клиенте** — клиент не знает строк контекстов и
  тарифов; две копии правил разошлись бы.
- **Маршрут предпросмотра слияния семей** — окну хватает схемы источника,
  которую уже отдаёт `GET /families/{id}/schema`.

## 4. Границы

- Модель не предлагает второстепенных параметров и диапазонов (дизайн §2.1,
  §2.5); кандидаты в диапазоны — идея на потом.
- Возврат прежних вариантов при смене роли — пока между сменами значения
  параметра не сливались и не переносились (§2.3).
- Предпросмотр пересборки оценивает запросы значений приближённо (§2.8).
- Устойчивость вариантов при правках главных — вопрос фичи 4: пересчёт
  переводит контексты в другие варианты, нормативов на них ещё нет.
- Ручная простановка значения отдельной строке — только через «не из
  списка» (§2.7); общего ручного назначения нет.
- Дубли семей стенда («Устройство жб конструкций», «Шпатлевание») —
  работа с каталогом.

1. Миграция `0022` заводит §2.2; паритет перечислений и CHECK-выражений с

   на нарушение: роль, вид вне перечня; диапазон с каждой недостающей

   два параметра версии с одним номером — отказ, в том числе когда один из
   них архивный;
   значение с `range_lo >= range_hi`; `retired_at` вместе с `merged_into_id`;
   `off_list` без текста, текст без `off_list`, `off_list` со значением;
   `requested_ordinals` у не-`context_values`; downgrade при каждом непустом
   носителе §2.2 — `RuntimeError` по входу, на пустых — проходит и
   возвращает прежние ограничения; upgrade на копии стенда не меняет ни
   одного `request_hash` и ни одного ключа варианта.
2. **Байтовая идентичность:** тела запроса значений полной схемы без
   диапазонов и тела запроса схемы без параметров человека совпадают с
   сегодняшними (снимок хэша на фикстуре до фичи).
3. `needed_ordinals` и `variant_due` — по входу на каждую ветвь §2.4
   (изменившиеся пути; недостающий параметр; «уточняется»; ждущая семья, нет
   варианта, чужая версия — со строками и без); таблица плана — по входу на
   строку; **завершение без модели** — новая строка семьи без параметров и
   контекст после пересборки, где модель не предложила параметров, а строки
   человека перенесены: вариант назначен, ждущая семья применена, промоушен
   выполнен, событие записано, задания `context_values` нет (снятие ветки
   «пусто и `variant_due`» — тест красный); рендер подмножества:
   блок и перечисление номеров только запрошенных; строка правила только у
   диапазона; задание с `requested_ordinals` воспроизводится при захвате и
   при записи (не `stale_fingerprint` без изменений; `stale_fingerprint` при
   правке параметра подмножества между захватом и записью); сверка не
   отменяет частичное задание как `input_changed`.
4. Запись частичного ответа: строки незапрошенных параметров не меняются (по
   идентификаторам и источникам); `new` у открытого — расширение, у
   закрытого — `off_list`; число у диапазона — значение диапазона, не число —
   `off_list`; вариант — по полному набору главных; главного нет — вариант
   прежний; `split_hint` по всем строкам; волна расширения спрашивает один
   параметр.
5. Правка — по входу на каждую строку таблицы §2.5: варианты (идентификаторы
   до и после) и поставленные задания (номера подмножества) совпадают с
   таблицей; добавление второстепенного в семью-фикстуру — ни один

   тронута; смена роли туда и обратно возвращает те же идентификаторы
   вариантов; слияние значений второстепенного не меняет вариантов (проверено
   снятием ветки «только главный» в слиянии — тест красный).
6. Проверки правки — по входу на каждый отказ §2.10; 11-й параметр — отказ, 10
   — проходит; две параллельные правки, вместе превышающие 10, — одна
   отказ; новый параметр после архивного получает `max + 1`, а не его

   `schema_ordinals_exhausted`; правка при `building` — `schema_building`.
7. Перестройка §2.6 — по входу: точные числа в диапазоны (все разрешены,
   запросов 0); вложенный диапазон; делящийся — «уточняется», вариант
   прежний, запрос одного параметра, после ответа — новый вариант; **цель
   совпадает с источником** — смена шага с теми же `from` и `to`: крайние
   диапазоны сохраняют идентификаторы, `retired_at` пуст, их строки без

   пересчёт; отказы `off_list_not_found`, `off_list_target_invalid`.
9. Охват: правка схемы не меняет ни одного `request_hash` заданий
   предложения семьи единицы и не ставит заданий контекстам других семей

   своей семьи, чей рендер правка изменила, пересчитан, а не изменённый —
   нет; сводка называет число пересчитанных.
9а. Предпросмотр: числа сводки совпадают с тем, что делает сохранение (одна
   фикстура, предпросмотр и итог); `preview_changed` при изменении
   действующей версии, строк контекстов затронутых параметров или тарифов
   между вызовами и — отдельным входом — при параллельной правке, не
   сдвигающей чисел сводки (косметическое переименование между
   предпросмотром и сохранением; снятие `revision` из хэша — тест красный);
   каждый писатель версии на месте увеличивает `revision` (вход на каждого:
   правка, слияние значений, «не из списка», расширение моделью,
   косметика); задания правки — `NO_CAP`.
10. Гонки: правка ↔ запись ответа значений — без deadlock, ответ после правки
