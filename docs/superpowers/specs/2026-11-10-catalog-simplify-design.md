## 2. Решение

### 2.1. Что сдаёт фича

1. Составное значение главного параметра: виды «вместе» и «или», части —
   простые значения того же параметра (§2.3).
2. Модель отвечает о сборной строке видом `several`; два фильтра перед
   записью нового значения (§2.4).
3. Автоделение контекстов «к делению» по разделам с правилами маршрутизации
   от имени системы (§2.5).
4. Пометки решения человека, которые останавливают автоматику (§2.6).
5. «Журнал ИИ»: таблица, API, вкладка (§2.7).
6. Лестница: форма значения на ступенях 2/4, блок «по частям», цель «с этим
   подрядчиком» (§2.8–§2.9).
7. Страница участника: дерево статей во всю глубину с разделами сметы, новая
   панель строки (§2.10–§2.11).
8. Первый прогон на накопленном (§2.12).

### 2.2. Термины

- **Простое значение** — строка `family_parameter_values` с `composite_kind
  IS NULL`.
- **Составное значение** — строка с `composite_kind ∈ {all, any}` и не менее
  чем двумя частями. `all` — «вместе», `any` — «или».
- **Часть** — простое действующее (`merged_into_id IS NULL AND retired_at IS
  NULL`) значение того же параметра.
- **Форма значения** у контекста: `composite:<value_id>` для составного,
  `simple` для простого, «не уточнено» и конфликта.
- **Автодействие** — запись журнала (§2.7): деление, новое значение,
  склейка → составное, приравнивание.
- **Решение человека** — пометка, которую ставит исправление из журнала и
  которую автоматика не снимает (§2.6).

### 2.3. Составное значение

**Хранение** (миграция `0025`, §2.13):

- `family_parameter_values.composite_kind text NULL` — `all | any`;
- `family_parameter_values.composite_key text NULL` — `<kind>:<id,id,…>`, id
  частей по возрастанию; `CHECK ((composite_kind IS NULL) = (composite_key IS
  NULL))`; частичный уникальный индекс `(parameter_id, composite_key) WHERE
  composite_key IS NOT NULL AND merged_into_id IS NULL AND retired_at IS
  NULL`;
- таблица `family_value_parts(value_id, part_value_id, parameter_id)`, PK
  `(value_id, part_value_id)`, составные FK `(value_id, parameter_id)` и
  `(part_value_id, parameter_id)` → `family_parameter_values(id,
  parameter_id)` — часть всегда того же параметра; `CHECK (value_id <>
  part_value_id)`.

**Инварианты** (проверяются в сервисе, тестами — каждый):

1. Части составного — простые и действующие; составное из составных не
   бывает.
2. Частей не меньше двух; одинаковых частей нет.
3. Текст составного собирается из частей: `all` — через « + », `any` —
   через « или », части в порядке id; `value_norm` — от этого текста.
4. Одно составное на `(параметр, вид, состав)`; «Knauf + Gyproc» и «Knauf или
   Gyproc» — разные значения.
5. У контекста по-прежнему одно значение на параметр; составное попадает в
   `context_parameter_values.value_id` и в ключ варианта как обычный
   `value_id`.

**Сервис** `services/composite_values.py` (новый):
`find_or_create_composite(db, *, parameter_id, kind, part_ids, journal) ->
int` — ищет по `composite_key`, иначе создаёт (`origin = 'extension'`),
пишет автодействие `composite` (§2.7); `composite_parts(db, value_ids) ->
dict[int, tuple[int, ...]]`; `rebuild_after_part_merge(db, *,
parameter_id, source_id, canonical_id)` (место 2 ниже).

**Четыре места из дизайна** (§3.3 дизайна) — каждое с проверкой снятием
защиты в плане:

1. **Список для модели.** Все три запроса §1.1 добавляют фильтр
   `composite_kind IS NULL`. Составное модель не видит никогда.
2. **Слияние части.** `merge_parameter_values` после переписывания значений
   вызывает `rebuild_after_part_merge`: в каждом составном, где была
   `source`, часть заменяется на `canonical`; если частей стало меньше двух
   (слили одну часть с другой) — составное **сливается** в оставшееся
   простое тем же `merge_parameter_values`; если новый `composite_key` уже
   занят другим составным — составное сливается в него. Слияние составного и
   простого значения напрямую (через API) — отказ
   `merge_values_composite_mismatch` (422); составное со составным разного
   вида — тот же отказ.
3. **Вывод части.** `schema_edit._write_rebuild` выводит значения
   перестраиваемого параметра; если среди них часть составного, выводится и
   составное (то же `retired_at`), контексты на нём — как у выведенного
   простого. Иных путей вывода нет (§1.1).
4. **Редактор схемы.** `GET …/schema` отдаёт у значения `composite: {kind,
   part_ids} | null`; `SchemaBlock`/`ValueChip` показывают пометку
   «составное» и части; `PATCH …/schema` с изменённым текстом составного —
   отказ `schema_composite_text` (422). Составное в редакторе не заводится —
   только системой (§2.4).
5. **Новая версия схемы** (пятое место; дизайн его не называл, ревью Codex
   гейта 2):
   - **перенос параметров человека** (`_carry_human_parameters`,
     `work_variants.py:815`) — в два прохода: сначала простые значения (как
     сейчас), затем составные — части через `value_map`, `composite_kind` и
     пересобранный `composite_key`, строки `family_value_parts`; составное,
     у которого после переноса меньше двух частей, не переносится, а его
     контексты получают `none`. Вето составов и пары «не дубль» не
     переносятся — они записаны текстом и разрешаются в новой версии сами
     (§2.6);
   - **заморозка схемы моделью** (`freeze_schema`, `work_variants.py:937`):
     значения ответа о схеме проходят фильтр 1 (§2.4) против остальных
     значений того же ответа — склейка, все части которой названы в этом же
     ответе, заводится составным, а не простым значением `origin = 'schema'`.

Показ текста (`our_price_load`, `review.py`) и всё, что сравнивает по
`value_id`, не меняется.

### 2.4. Ответ модели и два фильтра

**Формат ответа.** В `VALUES_RESPONSE_FORMAT` новый вид `several`:
`{ordinal, kind: "several", combine: "all"|"any", values: [str, …] (≥ 2),
source}`; каждый элемент — текст значения из списка или новый.
`VALUES_PROMPT_VERSION = 2`; в промпт — правило: «если в строке названо
несколько значений параметра одной работой — `several`/`all`; если одно из
нескольких на выбор — `several`/`any`; `conflict` — только когда разные
строки контекста дают разные значения». Разбор (`_parse_value_item`):
`several` требует `combine`, ≥ 2 непустых различных значений и `source`;
иначе `answer_schema_error`, как сейчас.

**Запись** (`apply_values`, шаг 2, `work_variants.py:1487`): для `several`
каждый элемент проходит путь `value`/`new` (с фильтрами ниже) и
канонизируется (`canonical_value_id`, сквозь слияния). Затем:

- элемент, разрешившийся в составное того же вида, раскрывается в его части;
  в составное другого вида — ответ по параметру пишется как `none` («не
  уточнено»), в лог — причина;
- повторы id убираются; **одна** различная часть — пишется как простое
  значение; **две и больше** — `find_or_create_composite`;
- у закрытого параметра, если хоть одна часть не в списке, — `off_list` с
  текстом, собранным из элементов, как сейчас для `new`.

**Порядок для `new`:** сначала точное совпадение `value_norm` с действующим
значением — оно и ставится, фильтры не применяются; затем фильтр 1, затем
фильтр 2.

**Вето состава** (§2.6) проверяет `find_or_create_composite` — единственная
точка, где появляется составное (ответ `several`, фильтр 1, заморозка схемы,
первый прогон): если вето разрешается в запрошенный состав (§2.6),
возвращается канонический V (простое), составное не создаётся.

**Фильтр 1 — склейка → составное** (для `new` открытого параметра, до
`get_or_create_value`): текст режется по `,`, `;`, « и », « или », `/`;
запятая и `/` между цифрами (`3,6 м`, `В12,5`, `1/2"`) разделителем не
считаются. Если частей ≥ 2 и **каждая**
совпадает с действующим простым значением параметра по `value_norm` или по
лемматизированной норме (фильтр 2) — части канонизируются и идут в
`find_or_create_composite` (`all`, а если разделитель «или» — `any`;
схлопнувшиеся части — по правилу `several` выше), автодействие `composite`.
Иначе текст идёт дальше целым: «ГО и ЧС» и «трубопровод с изоляцией и
арматурой» не режутся, потому что их частей в списке нет.

Так склейка с незнакомыми частями остаётся целой, а различает её модель
видом `several` (§2.15, п. 2).

**Фильтр 2 — дубль → существующее**: если точной `value_norm` нет, текст
сравнивается с действующими простыми значениями параметра по
**лемматизированной норме** (`normalize_job_title_with_lemmatization`,
`context_routing.py:166`); совпадение → ставится существующее значение,
автодействие `equated` с исходным текстом. Пара, помеченная «не дубль»
(§2.6), не приравнивается. Совпадений больше одного — фильтр не срабатывает,
значение заводится новым.

**Новое значение** после обоих фильтров — как сейчас (`origin =
'extension'`) плюс автодействие `value_added`.

Ничего нового наружу не уходит: модель получает те же наименования и списки
(`AGENTS.md` §3).

### 2.5. Автоделение

**Вход** — контекст с `variant_split_hint = 'path_conflict'`, не
архивированный, без пометки `auto_split_blocked` (§2.6).

**Шаги** (`services/auto_split.py`, новый; одна транзакция на контекст под
замком корзины, как `split_context`):

1. Цепочки разделов членов (`chapter_paths`), заголовки нормализованы
   `normalize_job_title_with_lemmatization` (регистр, пробелы, конечное
   двоеточие).
2. **Уровень расхождения** — первый индекс (от корня), на котором
   нормализованные заголовки членов различаются. Группы — по заголовку на
   этом уровне. Член, у которого цепочка короче уровня, — в группу
   «прочее»; если «прочее» — единственная группа кроме одной, деления нет.
3. **Значения групп.** Для каждой группы — запрос значений модели по путям
   только этой группы (тот же рендер, что для контекста, на подмножестве
   путей; `several` допустим). Ответы с одинаковыми значениями всех главных
   параметров сливают группы.
4. Осталась одна группа → деления нет: контексту ставятся её значения
   (`source = 'path'`), пометка «к делению» снимается, автодействия нет.
5. Групп ≥ 2 → первая (по наименьшему `position_item_id`) остаётся в
   исходном контексте, остальные — новые контексты через `split_context` с
   правилом (шаг 6); новые контексты получают семью исходного и значения
   своей группы (без повторного запроса), исходный — значения своей группы;
   пометка «к делению» снимается у всех. Автодействие `split` с группами,
   правилами и id контекстов.
6. **Правило группы.** Уровень шага 2 считается **от корня**, а
   `chapter_level_equals` в `evaluate_predicate` (`context_routing.py:416`)
   — **от ближайшего раздела** (`chain[0]` — ближайший); у цепочек разной
   глубины один уровень от корня — разные уровни от ближайшего. Поэтому
   `chapter_level_equals` автоделение не использует. Правило выбирается так:
   - заголовок группы — ближайший раздел у **каждого** её члена →
     `nearest_chapter_equals {value: заголовок}`;
   - иначе → `chapter_chain_contains {value: заголовок}`.

   Правило принимается, только если реальный `evaluate_predicate` (с учётом
   правил корзины с меньшим `ordinal`) **покрывает всех членов своей группы и
   не срабатывает ни на одном члене других групп** — иначе следующая
   перемаршрутизация (`_apply_routing` пересматривает всех не-ручных членов)
   перетащила бы чужие строки. Нет подходящего правила хоть у одной группы —
   контекст не делится, остаётся «к делению», в журнал — ничего, в лог —
   причина. Будущие строки идут по тем же правилам заголовка: строка нового
   КП с разделом «Колонны» попадёт в часть «Колонны».

**Система как исполнитель:** `split_context(…, actor_id: int | None)`;
`context_routing_rules.created_by` становится `NULL`-допустимым (`NULL` —
система); события — с `actor_id = NULL`.

**Ручное деление** на «Семьях» не меняется.

**Отмена** (`POST /semantic/journal/{id}/undo` для `split`):

- берёт **нынешних** членов всех частей, включая пришедших по правилам после
  деления, и сливает части в исходный контекст (`merge_contexts`);
- снимает только правила из записи;
- контексту — `variant_split_hint = 'path_conflict'`, значения главных
  параметров — `path_conflict`, вариант — по правилам вариантов для
  конфликта; пометка `auto_split_blocked`;
- **недоступна** (отказ `journal_undo_locked`, 409), если после записи у
  любой части есть событие с `actor_id IS NOT NULL` из `members_moved,
  context_split, context_merged, context_archived, context_variant_assigned,
  context_family_assigned` либо член с `routed_by = 'manual'`, либо часть
  архивирована; ответ `GET` журнала несёт `undo: {available, locked_by:
  {event_type, actor_email, at} | null}`;
- диалог показывает нынешние числа: `GET /semantic/journal/{id}` отдаёт
  `parts: [{context_id, title, members_now, members_after}]`.

**Поправить** — `POST /semantic/journal/{id}/resplit {level}`: отмена и
деление заново на заданном уровне (от корня, как в шаге 2) в одной
транзакции, правила — по шагу 6 (те же условия доступности). Перенос строк между частями — существующий `POST
/members/move` (после него отмена недоступна — это ручная правка).

### 2.6. Решения человека

Миграция `0025`:

- **вето состава** — «этот состав — это одно простое значение V, решение
  человека». Таблицы `composite_vetoes(id, family_id, parameter_name_norm,
  kind, value_norm, set_by, set_at)` и `composite_veto_parts(veto_id,
  part_norm)`, PK `(veto_id, part_norm)`;
- **«не дубль»** — «текст T не приравнивать к значению W». Таблица
  `value_not_duplicates(id, family_id, parameter_name_norm, text_norm,
  value_norm, set_by, set_at)`, уникальность `(family_id,
  parameter_name_norm, text_norm, value_norm)`;
- `catalog_contexts.auto_split_blocked_at timestamptz NULL`,
  `auto_split_blocked_by` FK users — автоделение не трогает.

**Решения человека записаны текстом, а не id** (ревью Codex гейта 2): семья,
нормализованное имя параметра (`name_norm`), `value_norm` частей и
значений. Id меняются при каждой новой версии схемы, нормы действующих
значений — нет: перенос параметров человека копирует действующие значения
с их нормами, параметр новой версии с тем же `name_norm` — тот же параметр.

**Гарантия:** решение действует, пока в действующей версии параметра есть
**действующие** значения с нормами решения. Слитые написания в новую версию
не переносятся (`_carry_human_parameters` берёт только `merged_into_id IS
NULL AND retired_at IS NULL`), поэтому решения **держат только нормы
действующих значений**, и это обеспечивается **в момент слияния**:

- `merge_parameter_values` (и каждое слияние, которое он делает
  каскадом, §2.3 место 2) в той же транзакции переписывает в решениях
  семьи с `parameter_name_norm` этого параметра норму источника на норму
  канонического значения: `composite_veto_parts.part_norm`,
  `composite_vetoes.value_norm`, `value_not_duplicates.value_norm`;
  совпавшие после переписи части одного вето схлопываются в одну строку
  (вето с одной частью — инертно, см. ниже), совпавшие пары «не дубль» —
  в одну;
- слияние семей (`work_families` merge) переносит решения семьи-источника
  на семью-цель (`family_id`);
- больше нигде нормы значений не меняются: текст значения не правится
  (редактор переименовывает только через слияние), вывод значения
  (`retired_at`) норму не меняет — вето молчит, пока значения нет.

Решения **разрешаются при каждой проверке** (страховка на случай, если
слитая строка ещё в текущей версии):

- *разрешение вето* для параметра P: вето той же семьи с `parameter_name_norm
  = P.name_norm` и тем же `kind`; каждая `part_norm` → строка значения P с
  этой `value_norm` (в том числе слитая) → `canonical_value_id`; `value_norm`
  вето → так же канонический id V. Вето **совпадает** с запросом, если
  множество канонических id его частей равно запрошенному;
- *разрешение «не дубль»*: `value_norm` → канонический id W в P; фильтр 2 не
  приравнивает T к W;
- часть или V не найдены в P (параметр перестроен, значения нет) — вето
  молчит, решение остаётся в таблице и оживёт, когда значение вернётся;
  если V не найдено, а части нашлись — V заводится простым значением с
  исходным текстом (`origin = 'manual'`) и ставится;
- части вето схлопнулись (две части слили в одну) — вето ни с чем не
  совпадает: составного из одной части не бывает, писать и так нечего;
- **коллизия** (два вето разрешились в один состав с разными V) —
  ставится V самого позднего вето (`set_at`, затем `id`); оба вето
  остаются, коллизия пишется в лог; решение человека не теряется молча —
  отменить новое вето можно из журнала («вернуть автоматику»), и тогда
  снова действует прежнее.

Вето проверяет `find_or_create_composite` (§2.4), то есть **все** пути
появления составного: ответ `several`, фильтр 1, заморозка схемы, первый
прогон. Пример: человек отменил разбор «A и B» (значение V); модель снова
ответила `several/all/[A, B]` — пишется V; пришёл `new` «B и A» — фильтр 1
даёт состав {A, B}, вето → V; пришёл `new` «A и B» — точное совпадение с V,
фильтры не применяются; A слили в A′, затем `several/[A′, B]` — вето
разрешается через слитую строку A → A′ и снова даёт V; новая версия схемы —
то же через `name_norm` параметра и нормы значений.
- `catalog_contexts.auto_split_blocked_at timestamptz NULL`,
  `auto_split_blocked_by` FK users — автоделение не трогает.

Пометку ставит только исправление из журнала (§2.7) и снимает только
«вернуть автоматику» (`POST /semantic/journal/{id}/restore-auto`); модель,
прогоны и команды её не снимают.

### 2.8. Лестница: форма значения и «по частям»

**Форма на ступенях 2/4.** `_values_key` (`analog_ladder.py:154`) дополняется
формой каждого отпускаемого главного параметра: ключ = (`value_id`
неотпускаемых …, форма отпускаемых …), форма — по §2.2. Следствия:
составное совпадает только с тем же составным; простое — с любым простым и
«не уточнено», как сейчас; конфликт по отпускаемому параметру — форма
`simple`, не мешает, как сейчас. Ступени 1/3 не меняются: составное — часть
варианта. Подпись ступени не меняется.

**Состояние строки.** Сборная строка (хоть одно составное главное значение)
без кандидатов на всех ступенях → `no_history_reason = "composite"` с
подписью «нет аналога: в строке несколько значений параметра «{имя}»». Порядок
причин: `no_family`, `path_conflict`, `composite`, `no_params`,
`no_zone_match`.

**«По частям»** (`parts_reference`, только в ответе панели строки, на итоги
и плитки не влияет): для каждого составного главного параметра строки и
каждой его части `p` — кандидаты той же семьи, версии схемы и зоны, у
которых **этот параметр равен `p` по `value_id`** — даже если параметр
отпускаемый (иначе форма `simple` дала бы плитам и балкам один и тот же
набор, ревью Codex гейта 2); остальные главные параметры — по правилам
ступени 2 (неотпускаемые — по `value_id`, отпускаемые — по форме). Сначала
класс тендера, если пусто — другой класс (`other_class: true`); выбросы —
как в лестнице, отдельно по каждой части. Ответ: `[{parameter_id, parameter_name, kind, parts:
[{value_id, value, analogs, contracts, min, max, lowest: {value,
analog_id, object_title, contract_number, period}, other_class}]}]`. Части
целью не становятся: `PUT …/target` с `analog_id` кандидата «по частям» —
отказ `analog_unavailable`, как сейчас для не-остатка.

### 2.10. Страница участника: дерево

**Ответ `build_offer_view`** дополняется:

- `categories: [{id, parent_id, code, title, sort_order}]` — все статьи

  страницы; база НДС неизвестна → `kp_total = null`, как у корня; нулевая
  сумма узла — `0`, не «нет». `no_price` — число строк в состоянии
  `no_price`. Корневые `articles` и `node_totals.categories` корня
  согласованы: тест сверяет сумму корня с `articles`.

`articles` (корни с ₽/м², вилкой, «статьёй целиком», `lines_totals`) не
меняются.

- уровни: корень (как сейчас, все колонки), промежуточные и конечные статьи,

  сметы и без заголовков, совпадающих (по нормализованной форме) с

  целиком» там нет. Раздел, скрытый как повтор названия статьи, своих итогов
  не показывает — его строки видны у родителя;

- сортировка по столбцу, если пользователь её выбрал, выпрямляет дерево в
  список с путём под названием строки.

### 2.15. Расхождения спеки с дизайном

1. **Виды цели.** Дизайн называл серверные виды `lowest | freshest | analog |
   agreed`; хранятся `freshest | analog`, `lowest` — умолчание. Новый
   хранимый вид — `contractor`.
2. **Как отличить склейку от цельного значения** (дизайн §7 оставил
   строителю): сборную строку называет модель видом `several`; фильтр 1
   режет текст сам только когда **все** части уже в списке. Склейка с
   незнакомыми частями, пришедшая как `new`, заводится целой.
3. **Фильтр дублей** (дизайн §7): лемматизированная норма, не эмбеддинги и
   не отдельный вопрос модели; синонимы шире леммы — правилом промпта
   «выбирай из списка». Пример дизайна «плиты покрытий» = «перекрытия»
   лемматизация **не** поймает — и не должна: это разные конструкции.
4. **Первый прогон для склеек** (дизайн §3.5 «части, которых нет, заводятся
   по отдельности»): без модели раскладываются только склейки со всеми
   известными частями; остальные — отчётом, без изменений.
5. **«Поправить» деление** — смена уровня через `resplit` и перенос строк
   существующим `members/move`; перенос делает отмену недоступной (это ручная
   правка, §2.5).
6. **«По частям»** определено поиском с параметром, равным части по
   `value_id`, и правилами ступени 2 для остальных параметров (§2.8); дизайн
   давал только смысл.
7. **Пятое место** — новая версия схемы (перенос параметров человека и
   заморозка схемы моделью, §2.3); дизайн называл четыре.
8. **Итоги нижних уровней** считает сервер по правилу сумм статей, фильтр
   «без цены» их не меняет (§2.10); дизайн говорил только «сумма КП».

### 2.16. Чем держится каждое правило

| Правило | Проверка (снятием защиты в плане) |
|---|---|
| Модель не видит составных (§2.3, место 1) | убрать фильтр `composite_kind IS NULL` в любом из трёх запросов → тест на рендер запроса падает |
| Слияние части пересобирает составные (место 2) | убрать вызов `rebuild_after_part_merge` → составное ссылается на слитую часть |
| Вывод части выводит составное (место 3) | убрать ветку → действующее составное с выведенной частью |
| Текст составного не правится (место 4) | убрать отказ `schema_composite_text` → PATCH проходит |
| «Вместе» ≠ «или» (§2.3, инв. 4) | убрать вид из `composite_key` → два вида сливаются в одно |
| Форма на ступенях 2/4 (§2.8) | убрать форму из ключа → «плиты» аналог «плиты + балки» |
| Фильтр 1 не режет «ГО и ЧС» (§2.4) | убрать условие «каждая часть в списке» → значение разрезано |
| Решение человека сильнее всех путей составного (§2.6) | убрать проверку вето в `find_or_create_composite` → ответ `several/[A, B]` после отмены снова создаёт составное; то же через фильтр 1 и первый прогон |
| «Не дубль» сильнее фильтра 2 (§2.6) | убрать проверку `value_not_duplicates` → отвязанный текст снова приравнен |
| Вето переживает слияние части (§2.6) | разрешать вето по id, а не по нормам через `canonical_value_id` → «отмена {A, B} → слить A в A′ → `several/[A′, B]`» снова создаёт составное |
| Вето переживает новую версию схемы (§2.6) | разрешать вето по `parameter_id`, а не по `name_norm` → «отмена → новая версия схемы → повторный `several`» снова создаёт составное |
| Вето переживает слияние **и затем** новую версию (§2.6) | убрать переписывание норм решений в `merge_parameter_values` → «отмена {A, B} → слить A в A′ → новая версия схемы → `several/[A′, B]`» снова создаёт составное (норма A в новой версии не находится); то же для «не дубль», чья цель слита перед новой версией |
| Коллизия вето (§2.6) | убрать порядок по `set_at` → результат зависит от порядка чтения; два прогона дают разные V |
| «Не дубль» переживает слияние и новую версию (§2.6) | разрешать пару по id → после слияния W или новой версии текст снова приравнен |
| Схлопнувшиеся части (§2.4) | убрать снятие повторов → составное из одной части (`several/[плита, плиты]`, части через слитое значение) |
| Перенос составных в новую версию (§2.3, место 5) | убрать второй проход → составное параметра человека стало простым текстом; заморозка без фильтра 1 → склейка ответа о схеме заведена простой |
| Правило деления покрывает свою группу и только её (§2.5, шаг 6) | заменить выбор правила на `chapter_level_equals` с уровнем от корня → правило не покрывает свои строки на цепочках разной глубины; убрать проверку чужих групп → перемаршрутизация уводит чужую строку |
| «По частям» — по `value_id` части (§2.8) | искать по ключу ступени 2 при отпускаемом параметре → у плит и балок одинаковые вилки (контрпример: отпускаемый «Тип конструкции», плиты дешевле балок) |
| Итоги уровней — по правилу сумм статей (§2.10) | суммировать по предикату цены → строки +100 и −20 дают уровню 100 при корне 80; сверка корня с `articles` |
| Отмена деления недоступна после ручной правки (§2.5) | убрать проверку событий → отмена стирает ручной перенос |
| Отмена берёт нынешних членов (§2.5) | брать членов из payload → строки, пришедшие после деления, остаются в части |
| Цель — стратегия, а не аналог (§2.9) | сохранять `analog` при нажатии карточки → новая свежая не подхватывается |
| «С этим подрядчиком» — только из остатка (§2.9) | искать по всем договорам → цель вне показанных аналогов |

## 3. Отвергнутые альтернативы

- **Несколько значений у контекста на параметр** — отвергнуто пользователем
  (дизайн §3.3): меняет ключ варианта, лестницу и экраны контекстов.
- **Очередь предложений вместо записи моделью** — отвергнуто пользователем.
- **Эмбеддинги для дублей** — порог без замера на парах значений, ложные
  слияния разных конструкций дороже пропуска дубля (§2.15, п. 3).
- **Отдельный вопрос модели «одно или несколько» на каждый `new`** — лишний
  платный вызов; модель и так видит строку и список (§2.15, п. 2).
- **Журнал поверх `semantic_events`** — у события один субъект и нет
  состояния отмены; деление затрагивает несколько контекстов.
