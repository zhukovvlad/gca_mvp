## 1. Проблема (code-grounded, сверено 2026-07-16, HEAD main)

Все три тяжёлые операции — upload, reparse, deskew-reparse — выполняются внутри HTTP request/response цикла и держат соединение до `httpx timeout=180` (pdf_parser.py:202). Подтверждённые дефекты:

**P1. Обрыв клиента = обрыв обработки в произвольной точке.**
Перезагрузка страницы → axios обрывает POST → uvicorn отменяет asyncio-таску хэндлера. Корутина умирает где угодно: после списания денег в OpenRouter, до финального `db.commit()`.

**P2. Потеря данных при обрыве reparse.**
`_reparse_from_s3` (routers/invoices.py:165) удаляет старые СФ и **коммитит удаление до парсинга** (routers/invoices.py:171). Обрыв между этим коммитом и финальным: старые СФ стёрты, новых нет. Данные потеряны молча. Относится и к deskew-пути (он завершается через ту же функцию).

**P3. Ложный статус по умолчанию.**
`Document.status = Column(String, default="parsed")` (models.py:259). Документ, чей парсинг оборвался или ещё не начался, выглядит в UI как успешно распарсенный с нулём СФ. Состояния «в обработке» не существует ни в модели, ни в UI.

**P4. Блокировка event loop синхронным кодом в async-хэндлерах.**
- boto3 `put_object`/`get_object` (s3.py) вызываются напрямую из `async def upload_pdf` / `deskew_reparse_document`;
- `deskew_pdf` (pdf_orientation.py:154) синхронно вызывает `render_pages_for_detect` и `apply_rotations` — CPU-bound pdfium-рендер внутри корутины;
- синхронные SQLAlchemy-коммиты внутри `async def`.

С одним uvicorn-воркером (justfile:27) любая из этих операций останавливает **весь** API для всех пользователей.

**P5 (новое в round 2, уточнено в 2.1). Частичная запись СФ существует уже сегодня.**
В пути парсинга коммитят ровно два места: `create_invoice` — `db.commit()` на каждую СФ (crud/documents.py:104) и `get_or_create_material_class` (crud/materials.py:53, вызывается из pdf_parser.py:301 и 314). `get_or_create_supplier` (crud/suppliers.py:76) — уже flush-only с защитой от гонки через `INSERT ... ON CONFLICT DO NOTHING`; коммит на suppliers.py:34 принадлежит `create_supplier` (ручной CRUD-путь, парсером не используется). Следствие: PDF с несколькими СФ, у которого первая СФ распарсилась (закоммичена), а вторая провалила reconcile (pdf_parser.py:363) → документ получает `status="error"`, но первая СФ остаётся в БД. Комбинация «error + живые СФ» — уже существующая реальность, а не гипотетическая.

**Что НЕ является проблемой (перепроверено round 2):**
- Инкремент `parse_cost_usd` атомарный на уровне SQL (routers/invoices.py:185-189) — переносится в новую архитектуру как есть, в том же финальном коммите.
- ~~«create_invoice использует flush, частичной записи нет»~~ — утверждение round 1 **опровергнуто**, см. P5.

## 2. Целевая модель (общий фундамент всех ступеней)

### 2.1 Статусная модель документа

```
pending → processing → parsed | error
```

- `pending` — документ создан, PDF в S3, обработка не началась. Новый default.
- `processing` — обработка идёт. Выставляется атомарно (см. S0-5).
- `parsed` / `error` — терминальные, семантика не меняется (тесты test_invoices.py и фронты ErrorDocsTab/InvoiceKpiBar продолжают работать без правок для терминальных статусов).

Дополнительные поля `Document`:
- `processing_started_at: DateTime | None` — для детекции зависших задач;
- `last_error: String | None` — человекочитаемая причина последней ошибки (сейчас живёт только в логах).

### 2.2 Единая точка входа обработки

Три эндпоинта сводятся к одной функции ядра (новый модуль `processing.py`):

```
process_document(doc_id, *, mode: Literal["parse", "deskew"], pdf_bytes: bytes | None = None)
```

- `upload` → сохранить в S3, создать doc(`pending`), запустить `process_document(mode="parse", pdf_bytes=...)`;
- `reparse` → запустить `process_document(mode="parse")` (bytes из S3);
- `deskew-reparse` → запустить `process_document(mode="deskew")`.

На ступени 0 `process_document` вызывается инлайн (await в хэндлере), на ступени 1 — через `BackgroundTasks`, на ступени 2 — как procrastinate-таска.

Контракт — три слоя (round 3):

- **`run_processing_attempt(...)`** — одна попытка: фазы A/B (§2.3). Доменные ошибки (§2.5) **выбрасывает**; ничего не знает о записи `status="error"` и ретраях. Это ядро, не меняющееся между ступенями.
- **Обёртка ступеней 0/1** (`process_document`): любая ошибка попытки → терминальный `status="error"` + `last_error`, исключение гасится (в фоне его некому ловить).
- **Обёртка ступени 2** (worker-таска): `TransientError` пробрасывается в procrastinate для retry; `PermanentError` → `error` сразу; после исчерпания попыток on-failure hook → `error`.

Инвариант миграции: между ступенями не меняется `run_processing_attempt`; обёртка завершения — своя на ступень. (Формулировка «тело process_document буквально неизменно» из round 1–2 снята: она несовместима с retry-моделью S2 — procrastinate ретраит только выброшенное исключение, а обёртка S0/S1 обязана исключения гасить.)

### 2.3 Две фазы внутри `process_document` (ядро round 2)

Сегодня `parse_invoice_pdf` смешивает LLM-вызов и запись в БД (создание СФ, поставщиков, классов материалов по ходу разбора ответа). Транзакционный инвариант при такой структуре недостижим: любой `commit` внутри `get_or_create_*`/`create_invoice` фиксирует всю сессию, включая удаление старых СФ.

Разрез:

**Фаза A — чистая (LLM, без БД).**
`parse_invoice_pdf(pdf_bytes) -> ParseOutcome`: HTTP-вызов OpenRouter, валидация JSON, расчёт confidence/completeness, reconcile итогов. Возвращает plain-структуры (список dict-ов СФ с позициями) + `cost` + классифицированную ошибку. Параметр `db: Session` из сигнатуры уходит. Внутренности промпта, reconcile, confidence — не меняются.

**Фаза B — транзакционная (БД, без LLM).**
`persist_parse_result(db, doc_id, outcome)`: в **одной транзакции** — удалить старые СФ, `get_or_create` поставщиков/классов (**flush, не commit**), вставить новые СФ, обновить `status`/`doc_type`/`parse_cost_usd`/`parse_count`, единственный `commit`.

Обработка ошибок и учёт стоимости (round 3):
- **ошибка фазы A** → БД-транзакция обработки ещё не начиналась, rollback не нужен; отдельная короткая транзакция: `status="error"` + `last_error` + инкремент стоимости (если вызов был платным);
- **error-запись — всегда условная, одним statement'ом** (round 3.2, единый код для обоих путей ниже):
  ```sql
  UPDATE documents
  SET status='error', last_error=:msg,
      parse_cost_usd = parse_cost_usd + :cost,
      parse_count = parse_count + :calls
  WHERE id=:id AND status='processing'
  ```
  Семантика READ COMMITTED работает на нас: наткнувшись на строку, заблокированную незавершённой транзакцией, UPDATE дожидается её исхода и **перепроверяет WHERE на новой версии строки** (EvalPlanQual). rowcount 0 → запись не выполнена и не нужна;
- **детерминированная ошибка фазы B** (упавший flush/insert, constraint — исключение ДО вызова `commit()`) → транзакция гарантированно не зафиксирована: обязательный `rollback()` всей фазы B (старые СФ невредимы — их удаление откатилось вместе со всем остальным), затем условная error-запись свежей сессией (здесь `processing` гарантирован, rowcount всегда 1);
- **ambiguous commit** (исключение ИЗ вызова `commit()` — например, потеря соединения во время COMMIT) → исход неизвестен: серверный бэкенд доводит начатый COMMIT до конца независимо от смерти клиента, поэтому swap мог зафиксироваться без подтверждения. `db.commit()` оборачивается отдельно; при исключении из него — та же условная error-запись свежей сессией. Коммит состоялся → предикат после ожидания блокировки ложен (`status='parsed'`), rowcount 0 — ни затирания, ни двойного учёта (залогировать ambiguous-исход); коммит не прошёл → rowcount 1, обычная error-запись. Неблокирующий re-read здесь запрещён (round 3.2): обычный SELECT читает последнюю закоммиченную версию и не видит дорабатывающий COMMIT — «прочитал processing → записал error» имело TOCTOU-щель;
- **инвариант стоимости**: платный вызов фазы A учитывается ровно один раз при любом исходе фазы B — success-путь кладёт инкремент в транзакцию swap, error-путь — в условную error-запись, и её предикат гарантирует, что выполняется ровно один из них;
- **ambiguous commit самой error-записи** (round 3.3): условная запись тоже коммитится, и её подтверждение тоже может потеряться. Хелпер идемпотентен по построению — предикат `status='processing'` делает повтор безопасным: первая запись закоммитилась → повтор даёт rowcount 0; не закоммитилась → повтор выполняет запись. Политика: при connection error из коммита error-записи — bounded retry (2–3 попытки с паузой) на свежем соединении. Исчерпание попыток (БД недоступна) → залогировать **critical** (алерт-уровень, не warning) и оставить документ в `processing` — он останется в этом статусе **до следующего рестарта** (startup-sweep S1-4) **или ручного восстановления**: восстановление БД само по себе документ не чинит, живой процесс к нему не вернётся. Честная оговорка: в этом вырожденном случае стоимость попытки не будет учтена — exactly-once для стоимости выполняется при доступной БД, при её полной недоступности деградирует до at-most-once (сознательный размен, сумма — доли цента).

На S2 та же форма условной записи обобщается ужесточением предиката: `WHERE status = 'processing' AND processing_run_id = :run_id` (см. S2-3) — один паттерн на обе ступени. Голый run_id-предикат без status-условия недостаточен: ambiguous-repair того же запуска совпал бы по run_id уже после успешного `parsed` (альтернатива — атомарная очистка `processing_run_id` в terminal-write; выбор — на дизайн-раунде S2).

Следствия:
- инвариант §2.4 достижим;
- P5 (частичная запись при multi-СФ reconcile-fail) чинится автоматически;
- фаза A тестируется без БД, фаза B — без моков httpx;
- вариант без коммита нужен только `get_or_create_material_class` (параметр или `_no_commit`-обёртка — решить на реализации, см. Q7); `get_or_create_supplier` уже flush-only и не меняется — crud/suppliers.py в S0-2 не участвует. Прочие вызывающие `get_or_create_material_class` (ручные CRUD-пути) продолжают пользоваться коммитящей версией.

Известные компромиссы (гонки между **параллельными документами** — guard S0-5 сериализует только один документ). Важный контекст: транзакция фазы B не «длинная», а «широкая» — LLM-вызов в фазе A, S3 — вне транзакции, внутри только БД-операции, длительность — миллисекунды:
- у `material_classes` нет unique constraint на `(material_type_id, name)` (models.py:215-229) — гонка двух параллельных парсов даёт **дубликат класса**, и она существует уже сегодня (SELECT-miss → INSERT у обоих). Перенос коммита в конец фазы B её не создаёт, лишь слегка расширяет окно. Правильное лечение — unique constraint + ON CONFLICT по образцу suppliers; отложенное улучшение, фиксируется в TECH_DEBT;
- для suppliers: строка, вставленная нашим `ON CONFLICT`, остаётся незакоммиченной до конца фазы B — параллельный парс другого документа с тем же ИНН подождёт на unique-индексе эти миллисекунды. Это весь эффект. При READ COMMITTED (isolation_level в database.py не задан → дефолт Postgres) ветка RuntimeError (suppliers.py:97-98) недостижима: конкурирующий `INSERT ... ON CONFLICT` ждёт исхода чужой транзакции, а повторный SELECT берёт свежий per-statement снапшот и видит закоммиченную строку. Ветку из кода не удалять — это страховка на случай смены уровня изоляции (при REPEATABLE READ повторный SELECT держит старый снапшот, и путь становится достижимым).

### 2.4 Транзакционный инвариант reparse

Удаление старых СФ и запись новых происходят **в одной транзакции**, коммит — только после успешного парсинга. При ошибке парсинга старые СФ сохраняются, документ получает `status="error"` + `last_error`, но данные не теряются. Комбинация «error + живые СФ» уже существует в системе (P5) — UI-обработка см. §7 Q1.

### 2.5 Классификация ошибок (перенесено из S2 в фундамент)

`process_document` в фоне не может бросать `HTTPException` — отвечать некому. Доменная иерархия вводится сразу:

- `TransientError` — S3 недоступен, `httpx.TimeoutException`, 5xx OpenRouter, обрыв detect-запроса deskew;
- `PermanentError` — невалидный JSON от модели, reconcile failed, `finish_reason=length`, doc_type=unknown, слишком много страниц для deskew (сегодня HTTP 413, pdf_orientation.py:118).

`pdf_orientation.py` перестаёт бросать `HTTPException` (413/502 на строках 118 и 138) и бросает доменные типы; маппинг на HTTP-статусы остаётся в эндпоинтах только для синхронной валидации (404/409 до постановки).

Учёт стоимости в исключениях (round 3.1): доменные ошибки несут накопленный учёт попытки — поля `cost_usd: Decimal` и `paid_calls: int` на базовом классе. Без этого контракт §2.2 («ядро выбрасывает, обёртка пишет error») теряет деньги на составных попытках: deskew-detect вернул HTTP 200 (потратил деньги) → основной parse упал transient'ом → наружу летит `TransientError`, и error-обёртка обязана иметь доступ к стоимости детекта, чтобы учесть её в error-транзакции. Фаза A аккумулирует учёт по ходу попытки и вкладывает его в любое выбрасываемое доменное исключение.

На ступенях 0–1 обе категории ведут к `status="error"` + `last_error` (различие только в тексте). На ступени 2 `TransientError` получает retry-политику — чистое добавление, без рефакторинга.

**S0-3. Выделение `process_document`.**
Общее тело upload/reparse/deskew выносится в `processing.py` с сигнатурой из §2.2, внутри — фазы A/B. Эндпоинты становятся тонкими: валидация → постановка. На этой ступени постановка = `await process_document(...)`. Ядро принимает `doc_id`, не ORM-объект (заготовка под собственную сессию в фоне, см. S1-3).

**S0-4. Доменные ошибки (§2.5).**
`TransientError`/`PermanentError` в `processing.py`; `pdf_orientation` переводится на них; `process_document` конвертирует их в `status="error"` + `last_error`. `asyncio.CancelledError` перехватывается: `status="error"`, `last_error="Обработка прервана"`, re-raise (детерминированный исход, без «либо pending»).

**S0-5. Guard от параллельной обработки одного документа.**
Атомарный переход `pending|parsed|error → processing`:
```sql
UPDATE documents SET status='processing', processing_started_at=now()
WHERE id=:id AND status != 'processing'
```
rowcount 0 → HTTP 409 «Документ уже обрабатывается». Выполняется в эндпоинте (синхронная часть), чтобы второй запрос получил 409 немедленно. Для upload — тот же переход сразу после `create_document` (единообразие всех трёх режимов).

Граница коммита (round 3): guard-переход **коммитится немедленно**, отдельной короткой транзакцией. Это нужно уже на S0: незакоммиченный UPDATE не виден другим сессиям — параллельный запрос не получит 409. На S1 добавляется вторая причина: фоновая таска открывает свою Session и либо не увидит `processing`, либо упрётся в блокировку строки незавершённой request-транзакцией. Enqueue-последовательность эндпоинта: создать/найти документ → условный UPDATE в `processing` + очистка `last_error` → **commit** → постановка (S0: await; S1: BackgroundTasks) → ответ.

**S0-6. Разблокировка event loop.**
- s3.py: обернуть вызовы boto3 в `anyio.to_thread.run_sync` (или предоставить async-обёртки `upload_file_async`/`download_file_async` — выбор за реализацией, но все вызовы из async-контекста должны уйти в поток);
- pdf_orientation.py: `render_pages_for_detect` и `apply_rotations` внутри `deskew_pdf` — через `anyio.to_thread.run_sync`;
- БД остаётся sync (миграция на async-SQLAlchemy — вне скопа, оверкилл для текущего масштаба); коммиты короткие, приемлемо.

**S0-7. `last_error` в API и сериализаторе.**
`_serialize_document` (routers/invoices.py:67) и `list_documents` отдают `last_error`; ErrorDocsTab показывает причину вместо голого «Ошибка парсинга» (тултип или подстрока).

**S0-8. Защита СФ на время обработки (round 3, атомарность — round 3.1).**
Parse-then-swap оставляет старые СФ живыми и доступными на время LLM-вызова (до 180с). Без защиты второй пользователь успевает отредактировать/подтвердить/удалить СФ — а фаза B затем снесёт их вместе с правками. Два уровня:
- мутирующие эндпоинты СФ и документа возвращают 409 при `Document.status == "processing"`: `update_invoice` (invoices.py:338), `verify`/`unverify` (439/452), `delete_invoice` (488), bulk-delete (469), `delete_document` (501). Дизейбл кнопок на фронте (S1-6) — UX-слой, не защита;
- фаза B **повторно проверяет** отсутствие verified-СФ внутри своей транзакции, непосредственно перед удалением старого набора. Появившаяся verified-СФ → `PermanentError` («документ содержит подтверждённые СФ»), старый набор не тронут.

Атомарность (round 3.1): повторный SELECT без блокировки не закрывает two-transaction race — verify мог загрузить документ и пройти status-check до guard-коммита, увидеть `verified=false` мог и phase B до коммита verify. Сериализация через блокировку строки документа: guard-переход (S0-5), фаза B (до проверки verified и до swap) и все мутирующие эндпоинты из списка выше берут `Document` через `SELECT ... FOR UPDATE`; проверки `status`/`verified` и сама мутация выполняются под блокировкой. Порядок событий тогда детерминирован: кто первым взял строку — тот и решает (verify успел → фаза B видит verified и абортится; фаза B успела → verify после разблокировки видит либо `processing` → 409, либо уже новый набор СФ → 404 по исчезнувшему invoice_id).

**S0-9. Учёт стоимости deskew-детекта (round 3).**
`detect_rotations` — отдельный платный вызов OpenRouter, но payload не содержит `usage: {include: true}` и cost не читается (pdf_orientation.py:123-127) — стоимость deskew-детекта теряется **уже сегодня**, вразрез с инвариантом спеки parse-cost-tracking («HTTP 200 → стоимость учтена»). Фикс: detect-вызов запрашивает usage и возвращает `(rotations, cost)`; outcome deskew-режима суммирует cost детекта и парсинга; `parse_count` инкрементируется на каждый платный вызов (детект — платный).

## 4. Ступень 1 — фоновая обработка + polling (BackgroundTasks)

Цель: убрать висящий запрос. Обрыв клиента больше не влияет на обработку.

`upload` / `reparse` / `deskew-reparse` выполняют быструю часть (валидация, S3-запись для upload, guard S0-5 → `processing`) и ставят `process_document` в `BackgroundTasks`. Ответ — немедленный, `202 Accepted` + сериализованный документ со `status="processing"`.

`process_document` в фоне не может использовать request-scoped `Depends(get_db)` — сессия закрывается с ответом. Таска открывает сессию сама (context manager, гарантированный close). Это причина, почему S0-3 выделяет ядро с `doc_id`, а не ORM-объектом.

**S1-4. Startup-sweep зависших задач.**
BackgroundTasks не переживает рестарт процесса: crash → документ навечно `processing`. В lifespan (main.py:27) на старте: все `processing` → `error`, `last_error="Обработка прервана перезапуском сервера"`. Однопроцессная модель делает это корректным: на старте процесса не может быть живых тасок. В dev с `--reload` sweep срабатывает при каждой правке кода — это желаемое поведение (подвисшие «processing» честно падают в error). Таймаут-детектор по `processing_started_at` на этой ступени НЕ делается (см. §7 Q5).
Deployment-инвариант (round 3.1): startup-sweep корректен **только** при `workers=1, replicas=1`. Старт второго API-процесса пометил бы живые таски первого как error. До ступени 2 многопроцессный запуск запрещён — инвариант фиксируется в justfile/деплой-конфиге комментарием и упоминается в S2-триггерах (§6): потребность в `workers>1` — ещё один триггер открытия S2.

**S1-5. Polling на фронте — список И карточка.**
`services/queries.ts`: условный `refetchInterval` — 2500 мс, пока статус нетерминальный, иначе `false` — получают **оба** запроса: список документов проекта (`useDocuments`) и detail-карточка (`useDocument`, queries.ts:174 — Review-страница иначе не увидит завершения reparse). React-query поддерживает нативно (`refetchInterval: (query) => ...`).

**S1-6. UI-состояния.**
- Upload.tsx: локальная машина job'а (`pending|uploading|ready|error`, Upload.tsx:24) — `ready` теперь означает «принято сервером». Строка job'а после 202 подписывается на данные polling'а по `result.id`: список СФ с confidence-бейджами и кнопка «Проверить» (Upload.tsx:168-188) сегодня рендерятся из снапшота `j.result.invoices`, которого при 202 не будет — их источником становится документ из query-кэша; терминальное состояние job'а привязывается к статусу документа.

- Кнопки reparse/deskew, а также verify/редактирование/удаление СФ и удаление документа задизейблены для документов в `pending|processing` (соответствует 409-контрактам S0-5 и S0-8).

**S1-7. Единый terminal-transition механизм (round 3).**
Polling из S1-5 — только транспорт; согласованность остальных данных требует явной обработки перехода `pending|processing → parsed|error`:
- тосты мутаций reparse/deskew при 202 говорят «Обработка запущена», не «Документ переразобран» (queries.ts:190, 203 — сегодняшние тексты в async-модели врут);

Реализация: колбэк `refetchInterval` (или эффект над данными query) сравнивает статусы и при появлении терминального инвалидирует documents list/detail + dashboard-квери проекта;

- AC-S1-3: Рестарт приложения при документе в `processing` → после старта статус `error` с внятным `last_error`.
- AC-S1-4: Frontend: при наличии `processing`-документа список опрашивается; после перехода в терминальный статус polling останавливается (unit-тест на функцию refetchInterval).
- AC-S1-5: Upload-страница: после 202 строка job'а показывает «обрабатывается», после завершения — СФ из данных polling'а (компонентный тест с MSW).
- AC-S1-6: E2E-заготовка (когда появится Playwright-инфраструктура): upload → ожидание бейджа → появление СФ. Спека фиксирует сценарий, реализация — в E2E-эпике.

## 5. Ступень 2 — персистентная очередь (procrastinate, Postgres)

Цель: ретраи, переживание рестартов, наблюдаемость задач. Достаётся, когда появляется второй тип фоновой работы или потребность в ретраях — не раньше (YAGNI-гейт, см. §6).

> **Round 3:** раздел описывает направление, не финальный дизайн — перед реализацией S2 нужен отдельный дизайн-раунд (retry/ownership-контракт ниже — первый проход).
> Обязательная повестка дизайн-раунда S2:
> - условность по `processing_run_id` должна покрывать **всю транзакцию фазы B**, не только финальный UPDATE документа — к моменту UPDATE delete старых СФ и insert новых уже выполнены в той же транзакции, и rowcount 0 обязан откатывать её целиком (либо run_id проверяется в начале фазы B под `SELECT ... FOR UPDATE` строки документа);
> - предикат terminal-write: `status='processing' AND processing_run_id=:run_id` (оба условия) vs атомарная очистка `run_id` при terminal-write — выбрать один механизм (§2.3, round 3.3);
> - стоимость каждой неудачной платной попытки фиксируется в БД **до** передачи `TransientError` в retry procrastinate — иначе учёт промежуточных попыток теряется (учёт в исключениях из §2.5 даёт данные, но запись между попытками — ответственность worker-обёртки);
> - пересмотр deployment-инварианта S1-4 (`workers=1, replicas=1`) — sweep заменяется на stalled-detection (S2-4), после чего ограничение снимается.

### Pre-item

**S2-0. Спайк: Neon + LISTEN/NOTIFY.**
Procrastinate-воркер держит долгоживущее соединение с LISTEN. Проверить на реальном Neon-инстансе: (а) не мешает ли scale-to-zero / что это стоит в compute-часах; (б) поведение при разрыве соединения Neon'ом (pool_recycle=300 в database.py:13 существует не просто так). Выход спайка: go/no-go + при no-go — решение (ARQ+Redis либо procrastinate в polling-режиме с интервалом). **Спайк обязателен до любого кода ступени 2.**

### Fix items

**S2-1. Procrastinate app + миграции.**
Схема procrastinate заводится через тот же Alembic-пайплайн (procrastinate умеет отдавать SQL для миграций). Отдельный `just worker` рецепт.

**S2-2. Worker-обёртка вокруг `run_processing_attempt` + retry-политика.**
Ядро попытки не меняется (§2.2); worker-обёртка — новая, третий слой контракта: `TransientError` **пробрасывается** в procrastinate (retry: 3 попытки, экспоненциальный backoff), `PermanentError` → `error` сразу, on-failure hook после исчерпания попыток → `error`. Документ остаётся в `processing` между попытками — guard S0-5 воркером не перепроверяется (постановка уже прошла его в эндпоинте). Классификация ошибок существует с S0-4 — здесь добавляется только политика. (Формулировка round 2 «ретрай проходит guard, т.к. error терминальный» снята — она смешивала retry procrastinate с ручным повторным reparse.)

**S2-3. Ownership-токен запуска (`processing_run_id`).**
Транзакционность фаз не делает задачу идемпотентной относительно **позднего ретрая устаревшего запуска**: задача зависла → sweep S2-4 перевёл документ в `error` → пользователь запустил новый reparse → старая задача ожила и дописала свой результат поверх нового. Защита: `processing_run_id` генерируется в enqueue-транзакции guard-перехода (S0-5) и передаётся в таску; финальные UPDATE фазы B и error-записи — условные (`WHERE status = 'processing' AND processing_run_id = :run_id` — оба условия, см. §2.3: голый run_id совпал бы у ambiguous-repair того же запуска после `parsed`); чужой run_id или терминальный статус → результат отбрасывается, таска завершается без записи. На S0/S1 токен не нужен: таски умирают вместе с процессом, позднего писателя не существует — но колонку можно завести заранее в миграции S0-1, чтобы не делать вторую.

**S2-4. Sweep ступени 1 адаптируется.**
Startup-sweep из S1-4 в многопроцессной модели (API + воркер) становится некорректным (API рестартует → таска в воркере жива). Заменяется на: procrastinate `stalled` detection + таймаут по `processing_started_at` (документ в processing дольше ~15 минут без живой таски → error; ориентир: 180с парсинг + 30с detect + ретраи + запас). Деталь реализации — на ревью раунда ступени 2.

**S2-5. Фронт не меняется.**
Контракт (202 + статусы + polling) идентичен ступени 1. Это acceptance-критерий, а не пожелание.

### Acceptance criteria (S2)

- AC-S2-1: `kill -9` воркера посреди парсинга → после рестарта воркера задача доезжает (ретрай) либо документ в `error` — но не вечный `processing`.
- AC-S2-2: Транзиентная ошибка LLM (мок 503) → ретрай → успех; ошибка контента → `error` без ретраев (по логам задач ровно 1 попытка).
- AC-S2-3: Диффа во frontend/src между ступенями 1 и 2 нет (кроме, возможно, версий типов).
- AC-S2-4: Спайк S2-0 закрыт документированным go/no-go до начала S2-1.
- AC-S2-5: Поздний ретрай устаревшего запуска (тест: две таски с разными `processing_run_id`, старая финиширует после новой) не перезаписывает результат актуального запуска.

Ступени 0 и 1 реализуются подряд: ступень 0 без 1 оставляет главный симптом (висящий запрос), ступень 1 без 0 строит фон на гнилом фундаменте статусов.

## 7. Решённые вопросы (по итогам раундов ревью)

**Q1. Семантика «error + живые старые СФ» — подтверждена.**
Это уже существующее поведение (P5: частичный multi-СФ фейл), а не новая комбинация. ErrorDocsTab (frontend/src/components/projects/ErrorDocsTab.tsx:35, фильтр `status === "error" || has_issues`) показывает такие документы без правок, колонка «СФ» в таблице уже есть. Достаточно S0-7 (`last_error` в UI). Отдельный UI-режим не нужен.

**Q2. Бэкфилл существующих артефактов — да, отдельным data-migration шагом.**
Эвристика `status='parsed' AND doc_type='unknown' AND 0 СФ → error` валидна по коду: успешный путь всегда перезаписывает `doc_type` значением из результата (не «unknown» — unknown уходит в error-ветку, routers/invoices.py:321-327), значит «parsed + unknown» возможен только как артефакт оборванной обработки. `last_error='Разбор не был завершён (исторические данные)'`. Перед миграцией — SELECT по реальной БД для подсчёта; тем же SELECT'ом подсветить второй класс артефактов `parsed + doc_type='invoice' + 0 СФ` (пустой `invoices` от модели или все даты кривые — `continue` на pdf_parser.py:351) и решить по факту, трогать ли их.

**Q3. `rotations_applied` — не персистить, удалить из ответа.**
Фронт не читает (grep по frontend/src), тост генерический. Логирования достаточно. См. S1-2.

**Q4. `202 Accepted` — принято.**
Цена нулевая: axios принимает любой 2xx, MSW-хэндлеры статус не проверяют. Настоящий breaking change — тело без `invoices`, и он неизбежен при любом статус-коде.

**Q5. Sweep-таймаут на ступени 1 — не нужен.**
Однопроцессная модель + startup-sweep покрывают всё: на старте процесса живых тасок быть не может. Таймаут-детектор — только на ступени 2 (S2-4), где появляется второй процесс.

## 8. Открытые вопросы (актуально на round 3)

**Q6. `file_hash`-дедупликация — РЕШЕНО (2026-07-17): в скоуп S1, ответ на дубль — 200 + `duplicate: true`.**
Колонка `documents.file_hash` и unique constraint `(project_id, file_hash)` существуют с миграции d1e2f3a4 (models.py:261, 272), но upload её никогда не заполняет — дедупликация не реализована. В async-модели она особенно ценна: (а) sha256 считается в быстрой части эндпоинта, и дубль отбивается **до** трат на LLM; (б) без неё двойной клик по загрузке создаёт два документа и два параллельных LLM-вызова — guard S0-5 не спасает, это разные doc_id. Дёшево ложится в S1-1.
Семантика ответа на дубль — рекомендация: идемпотентный ответ (200 + существующий документ + флаг `duplicate: true` в теле; фронт показывает «Файл уже был загружен» и ведёт на существующий документ), а не 409 — двойной клик не должен выглядеть ошибкой. Идемпотентный ответ естественно ложится в S1-модель: фронт получает тот же сериализованный документ, что и при 202, polling подхватывает его статус без специальной ветки.
**Инвариант: `file_hash` — хэш байтов оригинальной загрузки, преднамеренно инвариантен к deskew.** После deskew хэш соответствует содержимому `{s3_key}.orig`, а не текущему `s3_key` — именно это даёт матч при повторной загрузке того же оригинала. НЕ «чинить» кажущееся расхождение пересчётом хэша после deskew — пересчёт молча ломает дедупликацию.
Race-safe алгоритм (round 3): пре-SELECT по хэшу — только fast-path; два параллельных upload одного файла проходят его одновременно, поэтому арбитр — unique constraint `uq_documents_project_file_hash` на INSERT. Порядок: sha256 → fast-path SELECT (дубль → 200 + `duplicate: true`) → S3 upload → INSERT документа; `IntegrityError` по constraint → rollback → прочитать победивший документ → удалить свой S3-объект (иначе orphan) → 200 + `duplicate: true` с документом победителя.
Решение зафиксировано: дедуп входит в S1 (часть S1-1, быстрая часть эндпоинта), семантика — идемпотентный 200 + `duplicate: true`; фронт показывает «Файл уже был загружен» и ведёт на существующий документ. AC: параллельная загрузка одного файла (тест на two-writer race) оставляет ровно один документ и ноль LLM-вызовов для проигравшего. Orphan-cleanup S3 — **best effort** (round 3.1): сбой `delete_file` не ломает 200-ответ пользователю, а логируется warning'ом; осиротевший объект в S3 — приемлемая цена (деньги на LLM не тратятся, документа-дубля нет), гарантия «ровно один S3-объект» не даётся.

**Q7. Форма no-commit варианта `get_or_create_material_class` (только он; suppliers уже flush-only).**
Параметр `commit: bool = True`, отдельная функция или перевод вызывающих на внешний commit — решить на реализации S0-2 по месту. Требование спеки только одно: внутри фазы B — flush, не commit.
