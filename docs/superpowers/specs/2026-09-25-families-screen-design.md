# Экран «Семьи и контексты»: переделка под работу оператора

**Гейт 1 закрыт 25.09.2026 в диалоге.** Дизайн — кликабельный макет
[`2026-09-25-families-screen/mockup.html`](2026-09-25-families-screen/mockup.html)
без вкладки «Предложения», блока «ИИ» карточки и строки «есть с чем сравнить» —
они принадлежат фиче 2 «Семантические предложения» и фиче 4 и здесь не делаются.

Фича **переделывает экран**, построенный фичей 1
([спека](2026-09-22-catalog-families-design.md) §2.10, PR #53). На бэкенде —
поля в двух существующих ответах, два эндпоинта чтения членств группы и **один
пакетный эндпоинт переноса**, составленный из существующей операции; из
ответа карточки удаляется плоский список членств `members[]` (§2.8).
Схема, миграции, существующие операции и их отказы, права, ИИ, парсер, каскад
матчинга — не трогаются.

**Редакция 2 — после ревью гейта 2 (Codex, 25.09.2026).** Приняты все
замечания: группа членств получила полный контракт — постраничный запрос группы и
полный список id (§2.5, §2.8 п. 3); позиции без раздела — группа «без раздела»
(`chapter_item_id: int | None`); работа имени-места считается от **сохранённой**
роли, а не повторной классификацией (§2.8 п. 2); путь классификатора — внутри
запроса страницы, без третьего запроса; клиентский цикл переноса заменён пакетным
эндпоинтом с результатом по каждой позиции (§2.6, §2.8 п. 4).

**Редакция 3 — сверка с макетом (27.09.2026, решение пользователя).** Группа
членств — **текст пути**, а не раздел одной сметы: одинаковые разделы разных
смет («Лифтовой холл МОП жилья / Стены») — одна группа. У «Шпатлевки в 2 слоя» ×
8.2.3 на стенде 27.09.2026 — 14 групп на 124 позиции вместо 124 строк (по числу
уникальных разделов, `chapter_item_id`) с повторяющимся текстом. Группа несёт
список разделов `chapter_item_ids`; эндпоинты группы и
пакетный перенос принимают этот список (§2.8 п. 2–4). Единица на экране —
символом, статус семьи — словами (§2.8, абзац после п. 2).

## 1. Проблема

Экран фичи 1 проверен пользователем на стенде 25.09.2026: «вообще не нравится».
Пять причин, каждая подтверждена разбором макета с пользователем 23–25.09.2026:

1. **Карточка контекста — на отдельной вкладке «Операции».** Выбор строки в
   «Контекстах» переключает вкладку; вернуться к списку — ещё один щелчок, и
   контекст рядом со списком не виден никогда.
2. **Подписи — коды спеки.** `LOCATION_ONLY`, «Роль имени», «Статья (id)»,
   `SUGGESTED`. Пользователь спросил, что значит «роль имени», и не отличил
   статью классификатора от раздела сметы («„Земляные работы“ — это всё-таки
   раздел?»).
3. **Не видно, откуда подпись: из классификатора или из сметы.** Статья СМР —
   общий классификатор (`work_categories`, 362 пункта, три уровня), разделы —
   свои у каждой сметы; на экране это две строки одного вида.
4. **Состояние членств не видно из списка.** Признаки «устаревшие / конфликт /
   пустой» есть только фильтрами; строка списка не говорит, что контекст требует
   действия. Число позиций в строке списка отсутствует.
5. **Нет выбора размера страницы; у «Семей» нет пагинации вовсе.** Размер
   страницы контекстов зашит (`PAGE_SIZE = 20`, `ContextsTab.tsx`).

Отдельно: пометка о событии печатает термин вместо события. Кнопку «Перенести в
статью 20» пользователь не понял — за ней «3 позиции из раздела „SHELL & CORE /
Стены“ после вашего ручного разноса относятся к статье СМР 20, а лежат здесь».

## 2. Решение

### 2.1. Раскладка

Вкладки верхнего уровня — **«Семьи» и «Контексты»**; вкладка «Операции»
упраздняется. «Контексты» — список слева, **карточка выбранного контекста панелью
справа** (та же страница, без смены вкладки). Выбор строки держит карточку; смена
фильтра или страницы не сбрасывает выбор, пока выбранный контекст есть в выдаче.

Карточка — шапка и **вкладки внутри карточки**: «Решения», «Членства N»,
«Журнал». Между шапкой и вкладками — **строки внимания** (§2.6).

«Семьи» — список слева, панель правки выбранной семьи справа (как сейчас по
составу действий).

Компоненты — только shadcn/ui (`Tabs`, `Table`, `Select`, `Pagination`,
`Badge`, `Dialog`, `Checkbox`); отсутствующие ставятся `npx shadcn add`.

### 2.2. Словарь подписей

Коды не печатаются нигде, кроме журнала по запросу (§2.5). Отображение — одна
таблица в коде фронтенда, её же читают тесты:

| Поле | Значение | Подпись |
|---|---|---|
| `name_role` | `WORK` / `LOCATION_ONLY` / `GENERIC_WORK` | «Наименование называет»: «работу» / «место» / «род изделия без состава» |
| `semantic_kind` | `WORK` / `SYSTEM` / `UNKNOWN` | «Вид»: «работа» / «система» / «не определён» |
| `semantic_state` | `SUGGESTED` / `CONFIRMED` / `NOT_APPLICABLE` | «предложен правилом» / «подтверждён» / «не применяется» |
| `*_source` | `rule` / `manual` | «правило» / «оператор» |
| `family_source` | `manual` / `suggestion` | «оператор» / «из предложения» |
| `work_category_source` | `file` / `manual` | «из „Статьи СМР“ в файле» / «ручной разнос» |
| `comparability_reason` | `insufficient_description` | «Состав описан: нет — сравнение ставок не производится»; `NULL` — «да» |

Подпись «Состав описан», а не «Сравнимость»: пустая причина значит только «сравнение
не запрещено», а не «есть с чем сравнить» (разбор 24.09.2026; строка «есть с чем
сравнить» — фича 4).

### 2.3. Источник подписи: классификатор или смета

Две плашки, одинаковые на всех вкладках, легенда под заголовком экрана:
- **«статья СМР»** — пункт классификатора (`work_categories`), общий для всех смет;
- **«в смете»** — раздел конкретной сметы (`position_items.job_title_in_proposal`
  строк-разделов).

Плашка ставится перед текстом везде, где он показан: строка списка, шапка
карточки, пути членств, работа имени-места.

### 2.4. Строка списка контекстов

Две строки текста и три колонки:
- наименование строки каталога (плашка «система» рядом, если `semantic_kind =
  SYSTEM`); ниже — «статья СМР» + код и название статьи в одну строку с
  многоточием, **полный путь классификатора — во всплывающей подсказке**;
- единица; семья (или «—»); **число позиций** (членств) и **точка «требует
  внимания»**, если у контекста есть устаревшие или конфликтные членства или
  членств нет — подсказка точки называет, что именно.

Колонки «Вид», «Роль имени», «Состояние» из списка уходят в карточку: фильтры по
ним остаются.

### 2.5. Карточка

**Шапка:** наименование · единица; «статья СМР» + код и название; ниже серым —
родители статьи в классификаторе («внутри: 8 Отделочные работы (паркинг,
надземная часть МОП) › 8.2 Отделка надземной части») и «ручной разнос», если
источник статьи `manual`.

**«Решения»:** вид (с источником и подтверждением), «Наименование называет» (у
сохранённой роли `LOCATION_ONLY` — строка «работа по разделу представительной
позиции: „в смете“ …», §2.8 п. 2), «Состав описан», семья (с источником).
Действия: подтвердить вид, назначить или снять семью, изменить «что называет» —
существующие операции фичи 1.

**«Членства N»:** позиции, **сгруппированные по тексту пути ближайшего раздела
сметы** (одинаковый путь в разных сметах — одна группа, редакция 3) —
строка группы «в смете» + путь сверху вниз + число позиций, по убыванию числа;
позиции без раздела (`chapter_item_id IS NULL` — схемой допустимо, на стенде 0) —
отдельная группа «без раздела», всегда последней. Группа раскрывается до своих
позиций **постраничным запросом группы** (§2.8 п. 3), а не из обрезанного списка
карточки. Галочка выбора — на группе и на позиции:
- галочка **группы** выбирает её позиции **целиком**, включая не загруженные на
  экран: при нажатии фронтенд получает полный список id группы (§2.8 п. 3) и
  передаёт его в существующие «Разделить…» / «Перенести…» — их тела уже принимают
  список произвольной длины (`SplitContextRequest`, `MoveMembersRequest`);
- галочка **позиции** — одну позицию.

Выбор хранится как набор id; счётчик «выбрано N» показывает размер набора, а не
число отмеченных строк на экране. Действия по состоянию строки (перенос
устаревшего, решение цели конфликтного) — у позиции, как в фиче 1. «Слить…», «В
архив…» — внизу вкладки.

**«Журнал»:** события словами по закрытому списку событий фичи 1 (спека фичи 1
§2.14) с временем и автором; код события — во всплывающей подсказке.

### 2.6. Строки внимания

Над вкладками карточки — по строке на каждое состояние, требующее действия, с
действием-ссылкой:
- **устаревшие членства** — «N позиций из раздела „в смете“ … после ручного
  разноса относятся к статье СМР C «…», а лежат здесь, в статье …» → «Перенести их
  в контекст «наименование × C»». Строк столько, сколько различных пар «раздел →
  целевая статья»;
- **конфликтные членства** — «N позиций пришли слиянием в Review с другим решением»
  → «Принять решение цели»;
- **пустой контекст** — «Позиций нет: смета заменена. Архивирует оператор.»

**Пакетное принятие переноса — новый эндпоинт** `POST
/contexts/{id}/stale-groups/transfer` (§2.8 п. 4). Клиентский цикл по позициям
отвергнут на гейте 2: у группы нет полного набора id на экране, список карточки
обрезан на 500, один перенос — два HTTP-вызова, размер группы не ограничен.
Эндпоинт принимает **группу**, а не список id: `chapter_item_ids` — разделы
группы (или `null` —
группа «без раздела») и `expected_category_id` — статью, которую оператор видел в
строке внимания. Сервер сам находит устаревшие членства этой группы и
переносит **каждое своей доменной операцией** `accept_transfer` (спека фичи 1
§2.8: блокировка, перечитывание, отказ при `fresh_effective !=
expected_category_id`), в своей точке сохранения. **Пачка не атомарна**: итог —
результат по каждой позиции («перенесено» либо отказ с кодом и текстом доменной
ошибки), экран печатает «перенесено N из M» и список отказов. Частичный успех —
законное состояние: атомарность пачки ничего не защищает, каждое принятие
самостоятельно.

«Принять решение цели» — существующая пакетная операция
(`POST /members/accept-target-decision`, список id) без изменений; id
конфликтных позиций экран берёт тем же запросом группы (§2.8 п. 3) с фильтром
состояния.

### 2.7. Пагинация

Во всех списках — «Семьи», «Контексты» — счётчик «21–30 из 43», выбор «На
странице: 10 / 20 / 50 / 100», переключатель страниц (первая, последняя, соседние,
многоточие между). По умолчанию 20. Смена фильтра или размера — на первую страницу.
- **«Контексты»** — серверная: `limit`/`offset` уже есть, потолок `MAX_PAGE_SIZE =
  100` уже равен верхнему варианту выбора.
- **«Семьи»** — на фронтенде: `GET /families` отдаёт весь список (десятки,
  после открытия семей — сотни строк), серверная пагинация не нужна.

Размер страницы запоминается в `localStorage` на экран (удобство одного
пользователя, при ошибке доступа — умолчание).

### 2.8. Бэкенд: поля, запрос группы и пакетный перенос

Добавки — поля в существующих ответах `GET /contexts` и `GET /contexts/{id}`,
два эндпоинта чтения членств группы и один пакетный эндпоинт переноса. Схема не
меняется. **Инварианты числа запросов фичи 1 сохраняются без правки порогов:**
`list_contexts` — ровно два запроса, счётчик и страница
(`test_list_contexts_query_count_independent_of_row_count`); карточка — число
запросов не растёт с числом членств
(`test_card_members_query_count_independent_of_member_count` — после удаления
`members[]` он проверяет то же свойство на `member_paths`, §2.8 п. 5).
**Инвариант карточки усиливается:** число запросов не растёт ни с числом членств,
ни с **числом уникальных путей, ни с их глубиной**. Нынешний тест сравнивает
контексты, где позиции не распределены по разным разделам, и N+1 по путям не
заметил бы; он переписывается — сравниваются контекст с одним путём глубины 2 и
контекст с двенадцатью разными путями глубины 4 (число членств тоже разное), и
число запросов карточки у них обязано совпасть.

**1. Строка списка (`GET /contexts`, `items[]`)** получает:
```
member_count: int
has_stale_members: bool
has_conflicting_members: bool
work_category_path: list[{code: str, title: str}]   # родители статьи, от корня, без неё самой
unit_symbol: str | None                             # символ единицы (units_of_measure.symbol): «м²», «шт»
```
Все четыре — **внутри запроса страницы**: число и два признака —
коррелированными подзапросами (`_stale_exists`, `_conflict_exists` уже есть в
`crud/semantic.py`), путь — **двумя внешними соединениями** `work_categories` на
родителя и прародителя статьи корзины. Глубина классификатора — три уровня
(замер стенда 25.09.2026: 362 пункта, максимум глубины 3), справочник без CRUD
(меняется только миграцией или seed). Предел держит тест: максимальная глубина
классификатора в данных `≤ 3`; поднимется глубина — тест красный, и соединения
дописываются, а не молча обрезают путь. Отдельного чтения справочника и
кэша процесса нет: третий запрос сломал бы инвариант «ровно два».

**2. Карточка (`GET /contexts/{id}`)** получает:
```
work_category_path: list[{code, title}]            # то же, что в списке
representative_work_title: str | None               # только при name_role = LOCATION_ONLY
member_paths: list[{chapter_item_ids: list[int], path: list[str], member_count: int,
                    stale_count: int, conflict_count: int}]
stale_groups: list[{chapter_item_ids: list[int], path: list[str], count: int,
                    target_category_id: int | None, target_category_code: str | None,
                    target_category_title: str | None}]
```

**Единица на экране — символом, а не кодом** (уточнено сверкой с макетом
27.09.2026): строка списка, карточка и строка `GET /families` получают
`unit_symbol` рядом с существующим `unit_code` тем же внешним соединением
`units_of_measure`, без нового запроса; экран печатает `unit_symbol`, код
`unit_code` на экран не выходит, как и коды таблицы §2.2. Статус семьи
(`draft` / `active` / `archived`) печатается словами «черновик» / «активна» /
«в архиве».
- **`representative_work_title`** считается **от сохранённой роли**, а не
  повторной классификацией. Ручная смена роли (`set_name_role`,
  `services/work_families.py`) записывает роль и ничего не пересчитывает, и
  классификатор после неё вправе вернуть другую роль — поэтому вызов
  `classify_name_role` дал бы подпись, противоречащую решению оператора. Правило:
  при `name_role = LOCATION_ONLY` — имя **ближайшего рабочего раздела** цепочки
  представительного членства тем же критерием рабочего раздела, что правило роли
  (`_is_working_chapter`, `services/semantic_rules.py`), вынесенным в публичную
  функцию `nearest_working_chapter(chain) -> str | None`; рабочего раздела нет —
  `None`; при любой другой сохранённой роли — `None`. Представитель —
  наименьший `position_item_id`, тот же, что фича 1 использует при пересчёте
  роли (докстрока `_classify_new_context_semantics`,
  `services/context_operations.py`). Контекст без членств — `None`. Подпись
  экрана: «работа по разделу представительной позиции».
- **`member_paths`** — все членства по ближайшему разделу позиции: один
  агрегирующий запрос `GROUP BY chapter_item_id`, путь сверху вниз; затем
  строки с ОДИНАКОВЫМ путём сливаются в одну группу в памяти (редакция 3):
  `chapter_item_ids` — её разделы по возрастанию, счётчики — суммы.
  **Пути строятся пакетно, ограниченным числом запросов, а не через
  `chapter_context()`:** та поднимается к корню через `db.get` на каждого
  предка (`services/context_routing.py`), и на карточке «Шпатлевки в 2 слоя» ×
  8.2.3 (81 путь, глубина до 6) это сотни запросов. Вместо неё — **один
  рекурсивный CTE** от множества уникальных `chapter_item_id` контекста (и
  раздела представительного членства, п. `representative_work_title`) вверх по
  `position_items.chapter_item_id`, отдающий `(start_id, depth, title)`; путь
  собирается в памяти. Защита от цикла разделов — в самом CTE (`CYCLE`,
  PostgreSQL ≥ 14; стенд — 16): найденный цикл даёт тот же доменный отказ, что
  `chapter_context()` для маршрутизации (`RoutingError` «цикл разделов»),
  переведённый роутером в доменную ошибку, а не бесконечную рекурсию и не
  молчаливо обрезанный путь. Порядок разделов в пути — тот же, что у
  `ChapterContext.chain` в обратном порядке (там снизу вверх), и это сверяется
  тестом на одной позиции: путь CTE = `reversed(chapter_context(...).chain)`.
  Текущая статья раздела для `stale_groups` (`work_category_id` строки-раздела)
  и её код и название берутся тем же агрегирующим запросом членств, не отдельно.
  Позиции без раздела — группа «без раздела»: `chapter_item_ids = []`,
  `path = []`. Порядок —
  `member_count DESC`, затем путь лексикографически; группа «без раздела»
  (`chapter_item_ids = []`) — последней.
  Сумма `member_count` групп равна `member_count` карточки **по построению**:
  группировка по допускающему `NULL` ключу теряет строк не больше, чем
  `COUNT(*)`.
- **`stale_groups`** — устаревшие членства по паре «ближайший раздел → текущая
  эффективная статья раздела» (та, по которой `transfer_proposal` ищет цель);
  ключ группы — пара «текст пути → целевая статья», `chapter_item_ids` — разделы
  этой пары, `[]` — без раздела. Источник текста строки
  внимания и `expected_category_id` для п. 4. `count` считает только
  ПЕРЕНОСИМЫЕ устаревшие членства (`membership_state=STALE AND conflict_at IS
  NULL`), не конфликтные — те сначала разрешаются действием «Принять решение
  цели» (п. 4); это то же множество, что берёт пакетный перенос группы, и
  группа без единого переносимого членства не даёт записи вовсе.

Число разных путей — `len(member_paths)`; отдельного поля нет.

**3. Членства группы — два эндпоинта чтения:**
```
GET /contexts/{id}/members?chapter_item_id=<int>[&chapter_item_id=<int>…]|no_chapter=true&state=<all|stale|conflict>&limit&offset
  -> {items: [{position_item_id, job_title, estimate_id, membership_state,
               conflict_at, conflict_from_context_id, routed_by}], total, limit, offset}
GET /contexts/{id}/member-ids?chapter_item_id=<int>[&chapter_item_id=<int>…]|no_chapter=true&state=<all|stale|conflict>
  -> {position_item_ids: list[int], total: int}
```
- форма строки — та же, что была у `members[]` карточки фичи 1; `limit` до
  `MAX_PAGE_SIZE`; порядок — `position_item_id`;
- `chapter_item_id` повторяется — группа из нескольких разделов (редакция 3),
  отбираются позиции ЛЮБОГО из них;
- без `chapter_item_id` и без `no_chapter` — по всему контексту (так экран берёт id
  всех конфликтных для «Принять решение цели»);
- `chapter_item_id` и `no_chapter=true` вместе — `422`;
- `member-ids` отдаёт **полный** список без обрезки: id — восемь байт, группа в
  тысячи позиций — десятки килобайт. Это тот же набор, который галочка группы
  передаёт в «Разделить» / «Перенести»;
- оба — ровно два запроса (счётчик и страница либо счётчик и список).

**5. Из карточки удаляются `members[]` и `members_truncated`** (решение
пользователя 25.09.2026). Единственный потребитель — экран фичи 1
(`ContextCard.tsx`), и после переделки их не читает никто; фронтенд и бэкенд
выкатываются вместе, держать совместимость не с кем. Уходит и
`CONTEXT_MEMBERS_PAGE_CAP` вместе с тестами обрезки, которые его подменяют
(`test_semantic_api.py`, три теста с `monkeypatch.setattr(... "CONTEXT_MEMBERS_PAGE_CAP" ...)`):
обрезать больше нечего — позиции идут постранично запросом группы (п. 3).
Свойство «число запросов карточки не растёт с числом членств» остаётся и
проверяется на `member_paths` и `stale_groups`.

**4. Пакетный перенос устаревшей группы:**
```
POST /contexts/{id}/stale-groups/transfer
  body: {chapter_item_ids: list[int] | null, expected_category_id: int | null}
  -> {results: [{position_item_id, outcome: "moved" | "refused",
                 target_context_id: int | null, error_code: str | null, message: str | null}],
      moved: int, refused: int}
```
- сервер находит устаревшие членства контекста в разделах `chapter_item_ids`
  (`null` — без раздела; пустой список — `422`) и для **каждого** вызывает существующий
  `accept_transfer(position_item_id, expected_category_id, actor_id)`
  (`services/context_operations.py`) в **своей точке сохранения**
  (`begin_nested`): доменный отказ одной позиции откатывает только её точку, не
  пачку;
- **пачка не вводит нового порядка захвата.** Все позиции группы идут из одной
  корзины (корзина контекста) в одну целевую (корзина «строка × текущая статья
  раздела»): каждый `accept_transfer` берёт те же две блокировки корзин тем же
  `lock_buckets` — по возрастанию `id` (`services/context_routing.py`, спека
  фичи 1 §2.8), — и они держатся до конца транзакции пачки; каждый вызов
  перечитывает состояние под своим (пере)захватом замка, поэтому следующая
  позиция никогда не работает с устаревшим в памяти состоянием. Откат точки
  сохранения снимает ТОЛЬКО замки, взятые ВПЕРВЫЕ внутри неё самой (свойство
  вложенных транзакций Postgres): если обе корзины отказанной позиции уже
  держал более ранний успешный `accept_transfer` той же пачки, эти замки
  переживают откат и остаются захваченными до конца транзакции пачки — иначе
  и быть не должно (уточнено при реализации). Целевой корзины может
  не быть до первого переноса: её создаёт первый `accept_transfer`, следующие
  находят. Порядок обхода позиций — `position_item_id`, ради воспроизводимости
  результата, а не блокировок;
- пустая группа (все уже перенесены или перестали быть устаревшими) — `200` с
  пустым `results`, не ошибка: состояние законно разошлось с экраном;
- журнал — события `members_moved` тех же операций, по одному на перенос;
  нового типа события нет;
- право `admin`, как у всех операций экрана.

### 2.9. Что не меняется

Операции фичи 1, их эндпоинты, тела, отказы и блокировки; права (`admin`);
схема; закрытый список событий журнала; `docs/reference/schema.md`. Новый
мутирующий эндпоинт один — п. 4, и он только композиция существующей операции.
`docs/reference/screens.md` `## 9.` переписывается под новую раскладку тем же
коммитом, что экран; заголовок раздела остаётся `## 9. Семьи и контексты`, и
`EXPECTED_SCREEN_ANCHORS` стража не трогается.

## 3. Отвергнутые альтернативы

**Переделка экрана внутри фичи 2.** Фича 2 смешала бы «ИИ-предложения» с правкой
экрана фичи 1, приёмка фронта ждала бы порога ИИ, а он ждёт разметки пользователя.
Экран нужен раньше: на нём пользователь будет активировать семьи из книги
открытия семей.

**Полный путь разделов под каждой строкой списка.** У одной строки каталога путей
бывает десятки: «Шпатлевка в 2 слоя» × 8.2.3 — 81 путь на стенде. Один путь в
списке лжёт о контексте, все — перегружают; пользователь сам предложил
ориентироваться на классификатор. Пути — во вкладке «Членства».

**Серверная пагинация семей.** Список — десятки и сотни строк, фильтры простые;
параметры `limit`/`offset` в `GET /families` добавили бы контракт без пользы.

**Пакетный перенос циклом на фронтенде** (редакция 1, отвергнуто на гейте 2).
Частичный успех законен, но клиентский цикл его не требует: у группы нет полного
набора id на экране, список карточки обрезан на 500, один перенос — два
HTTP-вызова, а размер группы не ограничен. Пакетный эндпоинт сохраняет частичный
успех (точка сохранения на позицию) и не обязан быть атомарным.

**Атомарный пакетный перенос.** Отвергнуто: одна позиция, чья статья разошлась с
`expected_category_id` после показа строки внимания, откатила бы перенос всей
группы, хотя остальные позиции законно переносимы.

**Серверные операции «разделить/перенести группу» по `chapter_item_id`.**
Отвергнуто: меняли бы тела существующих мутаций фичи 1. Полный список id группы
(§2.8 п. 3) даёт то же без правки операций.

**`work_title` повторной классификацией** (редакция 1, отвергнуто на гейте 2).
Ручная смена роли не пересчитывает классификатор, и подпись разошлась бы с
решением оператора.

**«Есть с чем сравнить: N владельцев в семье».** Подсчёт владельцев поперёк
контекстов семьи — вопрос сравнения, фича 4.

## 5. Definition of Done

1. Вкладки «Семьи» и «Контексты»; вкладки «Операции» нет; карточка — панелью
   справа от списка, выбор строки не меняет вкладку.
2. Ни один код из левой колонки таблицы §2.2 не печатается на экране вне
   подсказки журнала; каждое значение каждого поля таблицы имеет подпись —
   проверяется тестом по таблице, а не выборочно.
3. Плашки «статья СМР» и «в смете» стоят во всех местах §2.3; легенда под
   заголовком.
4. Строка списка — две строки текста, число позиций, точка при устаревших,
   конфликтных членствах и при нуле членств; при их отсутствии точки нет.
5. Вкладка «Членства» группирует по тексту пути ближайшего раздела (редакция 3), позиции без раздела —
   группой «без раздела» последней; суммы по группам равны `member_count`;
   галочка группы выбирает её позиции целиком, включая не загруженные на экран
   и сверх 500; «Разделить» и «Перенести» получают выбранный набор id.
6. Строки внимания §2.6 — по одной на пару «текст пути → целевая статья» устаревших,
   одна на конфликтные, одна на пустой; «Перенести их» — один вызов пакетного
   эндпоинта; экран сообщает «перенесено N из M» и перечисляет отказы.
7. Пагинация с выбором 10/20/50/100 в обоих списках; смена фильтра или размера —
   первая страница.
8. `GET /contexts` и `GET /contexts/{id}` отдают поля §2.8; инварианты числа
   запросов фичи 1 зелёные без правки порогов, а у карточки — независимо и от
   числа уникальных путей и их глубины (тест с 1 путём глубины 2 против 12 путей
   глубины 4); цикл разделов — доменный отказ, не зависание; эндпоинты группы — ровно два
   запроса.
8а. Пакетный перенос: частичный успех — отказ одной позиции не откатывает
   остальные; пустая группа — `200` с пустым `results`; события `members_moved`
   по одному на перенос.
8б. В ответе карточки нет `members[]` и `members_truncated`; `CONTEXT_MEMBERS_PAGE_CAP`
   в коде нет.
8в. `representative_work_title` следует сохранённой роли: после ручной смены роли
   на `LOCATION_ONLY` — имя рабочего раздела, после ручной смены с
   `LOCATION_ONLY` на другую роль — `None`.
9. `screens.md` `## 9.` описывает новую раскладку; страж зелёный.
10. `just ci` зелёный.
