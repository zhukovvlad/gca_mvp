# График отклонений: частичное покрытие базовой ценой

**Дата:** 2026-05-28
**Статус:** approved

## Контекст

В карточке проекта на вкладке «Обзор» график «Отклонения по классам бетона» (`DeviationChart`) показывает агрегированное отклонение по каждому материальному классу за выбранный период. Под графиком — баннер «N классов (…) без базовой цены — не учтены в расчёте».

Текущее поведение слишком строгое: класс попадает в баннер, если **хотя бы один** месяц в периоде не покрыт базовой ценой. На практике это даёт ложно-отрицательный результат — пользователь видит, что цена для класса задана, но класс всё равно объявляется «без базовой цены».

**Конкретный кейс (из обсуждения):** проект имеет инвойсы с декабря 2023 по март 2025. Базовая цена для класса B15 задана с 2024-01-01 по 2026-12-31 (`5 490 ₽`). Декабрь 2023 не покрыт → класс B15 уходит в баннер, хотя на 99 % периода цена есть.

Дополнительная путаница: верхняя плашка «Переплата: +X ₽» уже считается по покрытым месяцам (`compute_full_deviation` суммирует только непустые `deviation_amount`), а график — нет. Получается видимое рассогласование между двумя цифрами в одном UI-блоке.

## Решение

Изменение **только во фронте** — в логике агрегации `DeviationChart.displayCalcs` (ветка `periodFilterActive`). Бэкенд (`compute_calculations`) уже отдаёт корректные per-month строки с `reference_price = null` для непокрытых месяцев — фикс заключается в том, чтобы агрегация на клиенте перестала «всё или ничего» и начала считать по подмножеству покрытых месяцев.

**Правило:** если у класса есть **хотя бы один** покрытый месяц в выбранном периоде — показываем класс на графике с отклонением, посчитанным по покрытым месяцам. В баннер «без базовой цены» класс уходит только при **нулевом** покрытии.

Для прозрачности добавляем тултип на строку бара при частичном покрытии — пользователь должен понимать, что цифры считаны не по всему объёму.

## Изменения в `DeviationChart.tsx`

### Агрегация (ветка `periodFilterActive`)

Заменяем текущую `every`-проверку на разбиение по покрытию:

```ts
const coveredRows = rows.filter(r => r.reference_price !== null && r.reference_price > 0);

const totalQty = rows.reduce((s, r) => s + (r.total_qty ?? 0), 0);
const coveredQty = coveredRows.reduce((s, r) => s + (r.total_qty ?? 0), 0);

const deviationAmount = coveredRows.length === 0
  ? null
  : coveredRows.reduce((s, r) => s + (r.deviation_amount ?? 0), 0);

const refQtyTotal = coveredRows.length === 0
  ? null
  : coveredRows.reduce((s, r) => s + r.reference_price! * (r.total_qty ?? 0), 0);

const deviationPct = (deviationAmount !== null && refQtyTotal !== null && refQtyTotal > 0)
  ? (deviationAmount / refQtyTotal) * 100
  : null;

const referencePrice = (coveredRows.length === 0 || coveredQty <= 0)
  ? null
  : refQtyTotal! / coveredQty;
```

**Что не меняется:**

- `total_qty`, `material_total`, `delivery_total`, `avg_price` агрегата — считаются по **всем** строкам, чтобы общий объём и оборот совпадали с другими местами карточки.
- `period_start` / `period_end` агрегата — по всем строкам (минимум начала, максимум конца).
- Ветка без `periodFilterActive` (показывает только последний календарный месяц) — не меняется. В ней нет агрегации по нескольким месяцам, и частичное покрытие в одной строке невозможно.

**Что меняется (семантика):**

- `reference_price` — взвешенная средняя по покрытым месяцам (раньше — `null`, если хоть один не покрыт).
- `deviation_pct` — посчитан по покрытым месяцам (раньше — `null`).
- `deviation_amount` — формально такое же значение, как раньше (агрегация уже суммировала только непустые), но теперь явно выражено через `coveredRows`.

### Новое поле для тултипа

Локальный тип агрегированного объекта расширяем на frontend-стороне (без изменения общего типа `DashboardCalculation`):

```ts
type AggregatedCalc = DashboardCalculation & { covered_qty: number | null };
```

Поле `covered_qty` устанавливается:

- `coveredQty` — для частичного покрытия (`coveredRows.length > 0`).
- `null` — для нулевого покрытия (класс пойдёт в баннер).

Полное покрытие отличается от частичного по условию `covered_qty === total_qty`.

### Тултип на строке бара

При `covered_qty !== null && covered_qty < total_qty` оборачиваем строку бара в `Tooltip` из `@/components/ui/tooltip`:

> «Отклонение посчитано по {coveredQty} м³ из {totalQty} м³ — в остальных месяцах базовая цена не задана.»

`formatNumber` из `@/lib/format` для значений м³ (без тысячных).

При полном покрытии тултипа нет.

Для тестирования: строка-бар с частичным покрытием получает `data-testid="bar-partial-coverage"` (или `data-partial-coverage="true"` атрибут).

### Баннер «без базовой цены»

Текст и условие отображения не меняются. `withoutPrice = displayCalcs.filter(c => c.deviation_pct === null)` теперь автоматически ловит только классы с нулевым покрытием — это и есть «цена вообще не задана на пересечение с инвойсами».

## Edge cases

- **`coveredQty === 0` при `coveredRows.length > 0`** — невозможен по построению, т.к. `compute_calculations` пропускает строки с `total_qty == 0`. Тем не менее в `referencePrice` оставлен guard `coveredQty > 0` — защита от деления на ноль.
- **`reference_price === 0` или отрицательное** — строка считается непокрытой (поведение совпадает с текущим: `r.reference_price > 0`).
- **Один материальный класс, один месяц, не покрыт** — класс с нулевым покрытием → в баннер. Поведение не меняется.
- **Все месяцы класса покрыты** — `coveredQty === totalQty`, тултипа нет. Поведение для пользователя не отличается от текущего.

## Тестирование

Новый файл: `frontend/src/components/projects/DeviationChart.test.tsx` (component-level, тесты-соседи компонента согласно конвенции из `CLAUDE.md`).

**Кейсы:**

1. **Полное покрытие** — класс на графике, тултипа нет, в баннере отсутствует.
2. **Частичное покрытие** — класс на графике, `deviation_pct` посчитан только по покрытым месяцам, при hover на строку бара появляется тултип «X м³ из Y м³», в баннере отсутствует.
3. **Нулевое покрытие** — класс в баннере, на графике отсутствует.
4. **Смешанный набор** — три класса (полный / частичный / нулевой) — каждый в правильном блоке, числа сходятся.
5. **`periodFilterActive=false` (latest-month режим)** — поведение не меняется, тест-регрессия.

**Стек:** vitest + Testing Library. MSW не нужен — `DeviationChart` получает данные пропсом.

## Что не меняется

- Бэкенд: `compute_calculations`, `compute_full_deviation`, `compute_export_rows` — без изменений. Уже корректны.
- Excel-экспорт — не меняется. В нём расчёт идёт per-(invoice, class), без агрегации по нескольким месяцам, и непокрытые строки уже корректно показываются с пустыми deviation-полями.
- Верхняя плашка «Переплата» в графике — уже считается по покрытым месяцам, изменения не требует. После фикса агрегации цифра в плашке и сумма столбиков на графике сходятся.
- Тип `DashboardCalculation` в `frontend/src/types/` — не меняется. Расширение `covered_qty` локально в `DeviationChart.tsx`.

## Out of scope

- Backend-side подбор «ближайшей» базовой цены для месяцев без покрытия — методологически неверно (мешает разные периоды цен). Не делаем.
- Indicator «частично» в виде бейджа на строке бара — отказались в пользу тултипа на hover (см. обсуждение).
- Изменение текста баннера на что-то вроде «без базовой цены на весь период» — баннер теперь корректно описывает то, что показывает (нулевое покрытие), смысл уже соответствует.
