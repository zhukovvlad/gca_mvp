# Спецификация: направления материалов на странице объекта (мультикатегорийность)

**Дата:** 2026-06-11
**Статус:** принято · ревизия R5 (финальная перед реализацией)
**Scope:** страница объекта (frontend) + API страницы объекта; изменений схемы БД нет
**Зависимости:** применяется поверх units-рефакторинга (`e1f2a3b4c5d6`) — справочник
`material_types` и нормализация единиц уже в проде ветки main.

---

## 0. Изменения ревизии R2 (после обсуждения)

1. **§5.4 — разноска `calc_role='additive'` скоупится направлением.** Стоимость
   additive-класса пропорционально входит в avg_price base-классов **его
   `material_type`** внутри счёта, а не всех base-классов счёта (текущая
   реализация — упрощение моно-бетонной эпохи). Доставка остаётся общей на счёт.
   Это соответствует исходной интенции avg-price-рефакторинга («присадки
   к основному материалу», `rebar+additive` не создаём). Edge case: additive
   типа D в счёте без base-классов типа D → не входит ни в чей avg_price.
   Новые ADR #8, тест в §8.1, строка в §10. Для моно-направленных счетов
   (вся текущая история) поведение побитово прежнее.

## 0b. Изменения ревизии R3 (по ревью)

1. **§3.1 / §7.2 — дефолт моно-объекта = его направление** (ADR #10).
   `directions.length == 1` → страница открывается в режиме направления
   (привычные табы), сводка «Все» доступна через переключатель. Снимает
   UX-регрессию для 100% существующих объектов.
2. **§7.2 — гонка при мусорном `?direction=` закрыта гейтом.** Скоупнутые
   запросы не стартуют до прихода summary (`enabled`), невалидный code не
   уходит в API и не мигает 422-ошибками.
3. **§5.1 / §5.3 / §5.5 / §6.1 — тип `other` не образует направления** (ADR #9,
   решение владельца). Не в переключателе и не в `directions[]`; деньги его
   классов поглощает `other_total`; базовые цены классам типа `other` не
   назначаются (422); смешанность счетов считается только по направлениям
   (счёт «бетон + крепёж» — не смешанный). Цена: счета из одних «прочих»
   позиций недостижимы из UI — принятое ограничение MVP (§10).
4. **§3.2 / §7.3 — «Разобрать →» ведёт в `?view=errors`** при `direction=all`:
   тот же контент вкладки «Ошибки» с заголовком «Ошибки объекта» и ссылкой
   «← к сводке», без прыжка в контекст направления.
5. **§5.2 / §6.1 — недоучёт объёма видим:** `volume_excluded_count` в разбивке
   направления + сноска «без N позиций в других единицах» на фронте.
6. **§3.3 — копирайт якоря «N% оборота объекта»:** знаменатель включает
   доставку и прочее, доли направлений не складываются в 100% — подпись не
   должна провоцировать сложение.
7. **§13 — все открытые вопросы закрыты** (отступления §13.3/§13.4 приняты,
   `total_qty` — deprecated + TECH_DEBT; туда же — колонка «Направление»
   в полном экспорте).

## 0c. Изменения ревизии R4 (финальная вычитка ревью)

1. **§7.3 / §3.1 — пустой объект (без счетов) рендерит текущие табы без скоупа**
   (ADR #11, блокер воркфлоу). `directions[]` выводится из позиций, у нового
   объекта он пуст — без legacy-режима пользователь не добрался бы до вкладки
   «Базовые цены», чтобы задать эталонные цены из договора ДО прихода счетов
   (штатный первый шаг). Тест в §8.2, критерий в §11.
2. **§7.2 — сброс вкладки на «Обзор» — эффектом на смену `direction`**, а не в
   `onChange`: back/forward меняют direction мимо `onChange`, и вкладка не должна
   «переезжать» между направлениями при хождении по истории.
3. **§6.7 / §7.3 — формат имени файла канонизирован** (был расхождением даже в
   текущем коде: бэк `отчёт_…`, фронт `отчёт-…` и переопределяет через
   `a.download`). Канон один, бэкенд приводится к нему.
4. **§3.2 / §6.1 — подпись KPI «Счетов» дополнена хвостом «· N проч.»**
   (`other_invoice_count`): счета без единой direction-позиции входят в общее
   число, но не в разбивку — без хвоста цифры «не сходятся» для внимательного
   пользователя. Прямое следствие ADR #9, упомянуто там же.

## 0d. Изменения ревизии R5

1. **`sort_order` выкинут — изменений схемы БД в задаче НЕТ** (ADR #12).
   Его обоснование («кирпич должен встать перед „Прочее“») устарело после

   Правки: §2, §3.1, §4 (схлопнут), §6.1, §6.8, §8.1, §8.3, §11, ADR #1.

## 1. Контекст и цель

Система заточена под бетон: страница объекта показывает один плоский список классов
(B15, B30…), KPI «Объём м³», заголовок «Отклонения по классам бетона». Появилась
арматура (классы вида «А500С Ø12»), дальше — кирпич и т.д.

**Цель:** ввести «направление» (direction) как первоклассное измерение страницы
объекта: переключатель `Все направления | Бетон | Арматура | …`, режим сводки на
«Все», полный текущий состав страницы в скоупе конкретного направления. Визуальный
язык приложения не меняется.

**Главная находка инвентаризации:** справочник направлений **уже существует** —
это `material_types` (`code`, `name`, `default_unit_id`): `concrete → Бетон / м³`,
`rebar → Арматура / т`, `other → Прочее`. Все классы уже привязаны через
`material_classes.material_type_id` (NOT NULL). Денежные агрегаты **уже считаются
по позициям** (`InvoiceItem`), а не по счетам. Поэтому:

- новая таблица `material_categories` из ТЗ **не создаётся** — это дубль
  `material_types` (ADR #1);
- «миграция: все классы получают категорию Бетон» — уже выполнена units-рефакторингом;
- позиционный расчёт из ТЗ — уже текущая архитектура, переделка не нужна.

`direction` в API = `material_types.code`.

## 2. Scope

### В работе

- Изменений схемы БД нет (§4) — задача чисто кодовая
- Параметр `direction` в эндпоинтах страницы объекта: calculations, invoices,
  monthly-summary, project suppliers, reference-prices, export
- Summary: расширенный shape — totals объекта + массив разбивок по направлениям
- Поле `direction` в строках calculations (для группировки на фронте)
- Frontend: `DirectionSwitcher` (URL `?direction=`), режим сводки «Все направления»,
  скоуп табов направлением, чистка хардкодов бетона
- `KpiCard`: мультизначный вариант («Объёмы»); `DeviationChart`: секции по
  направлениям + top-N + нейтральный заголовок
- Экспорт: фильтр по направлению + суффикс направления в имени файла
- Тесты: инвариант сумм, смешанные счета, скоуп каждого эндпоинта, URL/режимы на фронте

### Осознанно за scope (backlog)

| Что | Почему отложено |
|---|---|
| Атрибутная модель арматуры (диаметр, класс стали) | Отдельная следующая задача (по ТЗ) |

| Перевод пог.м арматуры → т | Уже в backlog units-рефакторинга |

## 3. UX-модель страницы объекта

### 3.1. Переключатель направлений

Segmented control между шапкой (заголовок, «Экспорт», «Добавить счёт») и line-табами:
`Все направления | Бетон | Арматура | …`.

- Источник списка — `summary.directions[]` (см. §6.1): только направления с данными
  по объекту (тип `other` не входит — ADR #9), порядок — порядок добавления
  направлений (`ORDER BY material_types.id`, ADR #12). Отдельный запрос
  справочника не нужен.
- Дефолт зависит от объекта (ADR #10): `directions.length == 1` → дефолт = это
  направление (моно-объект сразу открывается с привычными табами, без лишнего
  клика); иначе — «Все направления». Сводка «Все» на моно-объекте остаётся
  доступной через переключатель (ради breakdown доставки/прочего).
- URL: отсутствие параметра = автодефолт (правило выше). Явный выбор пользователя
  пишется в URL всегда, включая `?direction=all`. Ссылки шарабельны, back/forward
  работают. Неизвестный code → фолбэк на автодефолт (URL не переписываем до
  действия пользователя).
- Объект только с бетоном → переключатель `Все | Бетон`, дефолт — «Бетон»
  (критерий приёмки #1).
- **Пустой объект (нет позиций → `directions.length === 0`):** переключатель не
  рендерится, страница работает как сегодня — текущие табы без скоупа
  (ADR #11, §7.3). Понятие направления к объекту без данных неприменимо, а путь
  «создал объект → задал базовые цены из договора до прихода счетов» обязан
  сохраниться.
- При переключении направления активная вкладка сбрасывается на «Обзор».
- Появление ряда табов при переходе «Все → направление» не дёргает layout: под
  ряд табов всегда зарезервирована высота (контейнер с `min-h`, на «Все» — пустой).

### 3.2. Режим «Все направления» (дефолт мульти-объекта)

Сводка для чтения сверху вниз. Line-табы **не рендерятся**. Состав:

1. **KPI-карточки ×4** (существующий `KpiCard`):
   - «Оборот, ₽ с НДС» — `total_amount` объекта; breakdown: строка на направление
     + «Доставка» + «Прочее».
   - «Объёмы» — мультизначная карточка: строка на направление в родной единице,
     имя в именительном падеже слева, значение справа («Бетон — 5 677,5 м³»,
     «Арматура — 124,8 т»; формат уточнён на ревью планов: без склонений в коде,
     масштабируется на любое будущее направление). Разные единицы НЕ суммируются.
   - «Счетов» — общее число; разбивка строками breakdown (как у «Оборота», не
     suffix-строкой — теснится): направления + «Смешанные» + «Прочие»
     (`other_invoice_count`, §6.1) — иначе общее число не сходится с разбивкой.
   - «Переплата за весь период» — `full_deviation_amount`; breakdown по направлениям.
2. **Алерт-строка** (если есть нераспознанные/проблемные документы):
   «N документов не распознаны и не учтены в цифрах · Разобрать →».
   Источник — уже загружаемый список документов (тот же счётчик, что бейдж «Ошибки»).
   Клик: `?view=errors` при `direction=all` — рендерится тот же контент вкладки
   «Ошибки» с заголовком «Ошибки объекта» и ссылкой «← к сводке» (сбрасывает
   `view`). Это не вторая система табов, а один флаг отображения; прыжка в
   контекст направления нет — пользователь не решит, что видит «ошибки бетона».
3. **Блок отклонений** — `DeviationChart` с группировкой секциями по направлениям:
   заголовок секции = название направления + подытог переплаты + ссылка «открыть →»
   (устанавливает `?direction=`). Внутри секции — топ-5 классов по |deviation_amount|.
   Фильтр по периоду (даты) — общий на блок, как сейчас.
4. **Сноска** (если применимо): «N классов без базовой цены — переплата может быть
   занижена» (логика уже есть в `DeviationChart`, остаётся; классы типа `other`
   в N не входят — им цены принципиально не назначаются, §6.2/§5.3).

На «Все» НЕТ: таблицы периодов, кнопки «Настроить базовые цены», полных списков позиций.

### 3.3. Режим конкретного направления

Полный текущий состав (табы: Обзор, Счета, Базовые цены, Коридоры, Поставщики,
По месяцам, Ошибки), всё содержимое в скоупе направления:

- **KPI**: «Оборот» = оборот направления, подпись-якорь «N% оборота объекта»
  (считается на фронте: `direction.turnover / total_amount`; знаменатель включает
  доставку и прочее, поэтому доли направлений в 100% не складываются — подпись
  именно «оборота объекта», не «материалов», сложение не провоцируем); «Объём» —
  в родной единице направления, при `volume_excluded_count > 0` — сноска/тултип
  «без N позиций в других единицах» (§5.2); «Счетов» — `«24 · 3 смешанных»`;
  «Переплата» направления.
- **Отклонения** — все классы направления, без группировки; таблица периодов и
  «Настроить базовые цены» — как сейчас.
- **Счётчики табов** пересчитаны под направление («Счета · 24», «Поставщики · 4»).
- **«Счета»** — счета, содержащие ≥1 позицию направления (смешанный счёт виден
  в обоих направлениях; деньги при этом не задваиваются — агрегаты по позициям).
- **«Коридоры»** — матрица фильтруется до типа направления и его классов.
- **«Ошибки»** — счётчик и содержимое всегда глобальные (у нераспознанного
  документа направления нет). Бейдж виден в любом направлении.
- **«Экспорт»** наследует контекст: отчёт по направлению, имя файла с суффиксом
  направления; на «Все» — полный отчёт, как сейчас.

## 4. Схема БД

**Изменений схемы НЕТ** — задача чисто кодовая (накат/откат/ревью без
прикосновений к БД).

- Справочник направлений (`material_types`) и привязка классов
  (`material_classes.material_type_id` NOT NULL) уже существуют
  (units-рефакторинг).
- Порядок направлений — `ORDER BY material_types.id` = порядок добавления
  (бетон, арматура, кирпич…): сиды (`MATERIAL_TYPES_SEED` в `crud/units.py`)
  создают типы в фиксированном порядке, id стабильны между окружениями.
  `sort_order` отвергнут (ADR #12): после ADR #9 «Прочее» в переключатель не
  попадает, упорядочивать вопреки хронологии нечего; при реальной нужде колонка
  вернётся однострочной аддитивной миграцией.
- Дефолтные единицы отображения уже есть: `material_types.default_unit_id`
  (M3 для бетона, TON для арматуры, NULL для other).

## 5. Семантика расчётов

### 5.1. Принадлежность денег направлению (по позициям)

Денежная принадлежность позиции направлению — через класс:
`invoice_item.material_class_id → material_class.material_type_id`.

| Позиция | Куда идёт в обороте |
|---|---|
| `item_type='material'`, класс типа D (направление) | оборот направления D (включая `calc_role='additive'`) |
| `item_type='material'`, класс типа `other` | `other_total` (тип `other` направления не образует — ADR #9) |
| `item_type='material'`, `material_class_id IS NULL` (аномалия) | `other_total` |
| `item_type='delivery'` | `delivery_total` (вне направлений) |
| `item_type='other'` | `other_total` (вне направлений) |

Таким образом `other_total` поглощает три случая: позиции `item_type='other'`,
material-позиции классов типа `other` и material-позиции без класса. В breakdown
оборота это одна строка «Прочее» — пользователю безразлично, какой случай внутри.

**Инвариант (покрывается тестом):**
`Σ directions[].turnover + delivery_total + other_total = total_amount`.
Все слагаемые — `SUM(amount + НДС)` по позициям, группировка не пересекается →
инвариант выполняется точно (без округленческих расхождений: округление только
при сериализации, как сейчас).

### 5.2. Объём направления

`volume` направления = `SUM(normalized_quantity)` по позициям направления, где:

- `item_type='material'`, класс направления, `calc_role='base'` (количества
  additive-классов в их единицах не мусорят объём — консистентно с расчётной
  логикой, где объёмная база — только base);
- `normalized_unit_id IS NOT NULL` и размерность совпадает с размерностью
  `default_unit` направления (пог.м арматуры в объём «т» не суммируются — честный
  недоучёт, не «попугаи»; ср. spec units §4.4).

`volume_unit` = символ `default_unit` направления.

**Недоучёт видим, а не молчалив:** `volume_excluded_count` направления — число
base-позиций направления, не вошедших в объём (другая размерность, например
арматура в пог.м, или `normalized_unit_id IS NULL`). При `> 0` фронт показывает
сноску/тултип «без N позиций в других единицах» — иначе «124,8 т» выглядит как
полный объём, и первый же снабженец, сверивший тонны с накладными, спишет
расхождение на баг.

### 5.3. Переплата направления

`overpayment` направления = `Σ deviation_amount` по классам направления из
`compute_calculations` за полный период (та же механика, что
`compute_full_deviation`). `null`, если ни у одного класса направления нет
базовой цены.

**Классам типа `other` базовые цены не назначаются** — иначе их deviation вошёл
бы в `full_deviation_amount`, но не в переплату ни одного направления, и разбивка
перестала бы сходиться. Обеспечение двухслойное: вкладка «Базовые цены» существует
только внутри направлений и классы типа `other` не предлагает (естественно), плюс
`POST/PUT /reference-prices` для класса типа `other` → 422 (целостность на уровне
API). Текущих данных не касается — все существующие классы concrete. При этом
правиле Σ переплат направлений = `full_deviation_amount` объекта точно
(расчёт per-class).

### 5.4. Смешанные счета: разноска доставки и additive-классов — КРИТИЧНО

Сейчас доставка (`item_type='delivery'`) и стоимость additive-классов
(`calc_role='additive'`) складываются в общий котёл `shared_per_invoice` и
разносятся по **всем** base-классам счёта (`compute_shared_shares`:
моно-размерность → по qty, микс → по amount). Пока счета были моно-бетонными,
«все base-классы счёта» совпадало с «классами бетона». В смешанном счёте это
ломается, поэтому правила расщепляются:

**Доставка — общая на счёт.** У строки «Доставка» в УПД направления нет
(физически это общий фрахт), привязать её не к чему. Разносится по всем
base-классам счёта, как сейчас. В смешанном счёте доля доставки достаётся
классам обоих направлений — осознанно.

**Additive — внутри своего направления.** Стоимость additive-класса
пропорционально входит в avg_price только base-классов **его `material_type`**
внутри счёта (доля — той же `compute_shared_shares`, но по подмножеству
base-строк этого типа). Это соответствует исходной интенции avg-price-рефакторинга:
additive — «присадки к основному материалу» (пластификатор → бетон), пара
`rebar+additive` сознательно не создаётся. Бонус: внутри одного направления
размерность обычно моно → разноска по объёму, а не fallback по деньгам.

- Edge case: additive типа D в счёте **без** base-классов типа D → стоимость
  не входит ни в чей avg_price (честный отказ вместо разноски на чужое
  направление). В обороте направления D она при этом остаётся (§5.1 — оборот
  по позициям, без разноски).
- Для моно-направленных счетов (вся текущая прод-история) результат побитово
  прежний — критерий приёмки #1 не затрагивается.
- Реализация: `shared_per_invoice` расщепляется на `delivery_per_invoice`
  (ключ — счёт) и `additive_per_invoice_by_type` (ключ — счёт × тип); та же
  правка зеркалится в `compute_export_rows` (колонки «Прочее» по классам)
  и `_compute_supplier_project_deviation` (`crud/suppliers.py`) — механика
  во всех трёх местах одна.

**Фильтр `direction` — на выходе расчёта**, точно так же, как сейчас работает
`material_class_id` (`calculations.py:287`, `:531`). Знаменатели разноски
(`base_rows`, `delivery_per_invoice`, `additive_per_invoice_by_type`) считаются
по **полному счёту** всегда — фильтр лишь отбирает готовые поклассовые строки.

Следствия:
- цифры класса (avg_price, deviation, compensation) идентичны при любом значении
  `direction` — покрывается тестом-стражем;
- «переплата направления» включает разнесённую на его классы долю доставки
  смешанного счёта — это производная метрика, инвариант оборота (§5.1) она
  не затрагивает (там доставка — отдельное слагаемое, без разноски).

### 5.5. Счётчики счетов

- `invoice_count` направления = число счетов с ≥1 позицией
  (`item_type='material'`) класса направления.
- `mixed_invoice_count` объекта = число счетов, чьи material-позиции охватывают
  ≥2 **направлений**. Классы типа `other` и позиции с `material_class_id IS NULL`
  смешанности не создают (тип `other` — не направление, ADR #9): счёт
  «бетон + крепёж на 3 тысячи» — НЕ смешанный, счётчик «· N смеш.» не раздувается
  шумом и сохраняет свой смысл (объясняет, почему счета направлений не складываются).
- `mixed_invoice_count` направления = число смешанных среди счетов направления
  (для подписи «24 · 3 смешанных»).
- Σ `invoice_count` направлений ≥ `invoice_count` объекта (смешанные считаются
  в каждом своём направлении) — это ожидаемо и документируется в типах.

## 6. API

Все изменения обратно совместимы: новые поля добавляются, старые не убираются;
`direction` — опциональный query-параметр, без него поведение прежнее («Все»).
Неизвестный code → 422. `?direction=other` → тоже 422: тип `other` направлением
не является (ADR #9), API-контракт не должен противоречить UI-модели
(уточнено по ревью PR #28).

### 6.1. `GET /dashboard/summary` — расширенный shape, БЕЗ параметра `direction`

Один ответ содержит и totals объекта, и разбивку по направлениям — фронт берёт
нужный срез сам. Это **намеренное отступление от ТЗ** («все эндпоинты принимают
direction»): один запрос обслуживает оба режима, переключение direction не
рефетчит summary, инвариант §5.1 виден в одном ответе. Принято ревью (§13.3).

```jsonc
{
  // существующие поля — без изменений (обратная совместимость):
  "doc_count": 12, "invoice_count": 88,
  "total_amount": 1234567.89, "material_amount": 1000000.0,
  "delivery_amount": 200000.0, "other_amount": 34567.89,
  "total_qty": 5677.5,                  // legacy, см. примечание ниже
  "first_invoice_date": "...", "last_invoice_date": "...",
  "full_deviation_amount": 123456.78,

  // новое:
  "directions": [                        // только направления с данными, без типа other (ADR #9); порядок — по id (ADR #12)
    {
      "code": "concrete", "name": "Бетон",
      "turnover": 900000.0,              // §5.1, по позициям, с НДС
      "overpayment": 110000.0,           // §5.3, null если нет базовых цен
      "volume": 5677.5,                  // §5.2
      "volume_unit": "м³",               // символ default_unit
      "volume_excluded_count": 0,        // §5.2, base-позиции вне объёма (размерность/нет нормализации)
      "invoice_count": 61,
      "mixed_invoice_count": 3
    },
    { "code": "rebar", "name": "Арматура", ... }
  ],
  "mixed_invoice_count": 3,              // §5.5, по направлениям, тип other смешанности не создаёт
  "other_invoice_count": 2,              // счета без единой direction-позиции (только delivery/прочее) — хвост «· N проч.» в KPI
  "delivery_total": 200000.0,            // = delivery_amount (алиас в новой терминологии)
  "other_total": 34567.89                // §5.1: item_type='other' + классы типа other + позиции без класса
}
```

Примечания:
- `total_qty` (сырое `SUM(quantity)` по всем material-позициям) остаётся для
  совместимости, но фронт перестаёт его использовать — при миксе единиц это
  «попугаи». Кандидат на удаление в TECH_DEBT.
- `overpayment` направлений и `full_deviation_amount` считаются из **одного**
  прогона `compute_calculations` за полный период (без дублирующего запроса):
  суммирование per-class строк с маппингом класс → тип.
- `unrecognized_count` в summary **не добавляется** — алерт-строка использует уже
  загружаемый список документов (та же логика, что бейдж «Ошибки»: `status ===
  "error" || has_issues`); числа алерта и бейджа гарантированно совпадают.

### 6.2. `GET /dashboard/calculations` — `?direction=` + поле `direction`

- Новый опциональный параметр `direction: str | None`. Фильтр на выходе (§5.4):
  строки классов, чей `material_type.code == direction`.
- В каждую строку добавляется поле `"direction": "concrete"` (code типа класса) —
  фронт группирует секции «Все направления» сам.
- Строки классов типа `other` получают `direction: "other"`; на фронте они не
  попадают ни в секции группировки «Все» (тип `other` — не направление), ни в
  сноску «N классов без базовой цены» (цены им принципиально не назначаются,
  §5.3 — считать их «ненастроенными» было бы ложной тревогой).
- **Группированный режим не выносится в отдельный эндпоинт**: подытоги и top-5 —
  это сортировка/срез уже возвращаемых per-class данных, фронт делает их из того
  же ответа, что питает текущий график. Те же числа в обоих режимах by construction.
  Отступление от ТЗ («эндпоинт возвращает группы») принято ревью (§13.4).
- `compute_calculations()` получает параметр `direction_type_id: int | None`
  (резолв code → id в роутере); `class_type_id_map` уже есть внутри.

### 6.3. `GET /dashboard/invoices` — `?direction=`

Фильтр: счета с ≥1 позицией (`item_type='material'`) класса направления
(EXISTS-подзапрос). Смешанный счёт возвращается в обоих направлениях целиком
(со всеми позициями — пользователь видит документ как есть).

### 6.4. `GET /dashboard/monthly-summary` — `?direction=`

С параметром: `total_amount` = только material-позиции направления (с НДС),
`total_qty` = `SUM(normalized_quantity)` base-классов направления с совпадающей
размерностью (§5.2), `invoice_count` = счета направления в месяце. Плюс поле
`volume_unit` в ответе. Без параметра — текущее поведение (вкладка «По месяцам»
на «Все» не рендерится, но контракт сохраняем).

### 6.5. `GET /projects/{id}/suppliers` — `?direction=`

Фильтр: поставщики, у которых есть ≥1 счёт по объекту с ≥1 позицией направления;
`invoice_count` — по счетам направления.

### 6.6. `GET /reference-prices` — `?direction=`

Фильтр по `material_class.material_type.code`. (Поле `material_type` уже есть
в ответе.) Селект класса в диалоге создания цены фильтруется на фронте до
классов направления. `POST` для класса типа `other` → 422 (§5.3, расширение
существующей `_validate_ref_unit`); `PATCH` существующей строки типа `other` —
тот же 422 (defense-in-depth для legacy-строк, по ревью PR #28).

### 6.7. `GET /export/excel` — `?direction=`

- `compute_export_rows()` и `compute_calculations()` получают фильтр направления
  (на выходе, §5.4).
- **Имя файла — канонический формат один** (сейчас бэк и фронт уже расходятся:
  бэк отдаёт `отчёт_…` в Content-Disposition, фронт переопределяет через
  `a.download` на `отчёт-…`):
  `отчёт-{имя}[-{Направление}][_{start}–{end}].xlsx`,
  например `отчёт-ЖК Радуга-Арматура_2026-01-01–2026-03-31.xlsx`.
  Источник видимого имени — фронт (`a.download`); бэкенд `Content-Disposition`
  приводится к тому же формату (заодно чинится существующее расхождение).
- В шапке отчёта — строка «Направление: Бетон» (под названием объекта).
- Без параметра — полный отчёт, как сейчас.

### 6.8. Без изменений

`/invoices/documents*` (ошибки глобальны), corridors API (фильтрация матрицы — на
фронте), suppliers detail/duplicates/merge, auth, material-classes CRUD,
`GET /api/material-types` (как есть; `sort_order` не вводится — ADR #12).

### 7.2. Состояние в URL

В `ProjectPage`:

```tsx
const [searchParams, setSearchParams] = useSearchParams();
const raw = searchParams.get("direction");          // null | 'all' | code
const directions = summaryQ.data?.directions;        // undefined пока грузится

// undefined = режим ещё не определён (summary не пришёл) — НЕ 'all'
const direction: string | undefined =
  directions === undefined ? undefined
  : raw === "all" ? "all"
  : directions.some((d) => d.code === raw) ? raw!
  : directions.length === 1 ? directions[0].code   // автодефолт моно-объекта (ADR #10)
  : "all";
```

- **Гейт от гонки (важно):** пока `direction === undefined`, скоупнутые запросы
  (invoices, calculations, monthly, suppliers, reference-prices) не стартуют
  (`enabled: direction !== undefined`); мусорный `?direction=` из URL не уходит
  в API → нет мигания 422-ошибок до фолбэка. Страница до прихода summary и так
  показывает скелетоны, UX не меняется.
- Автодефолт (нет параметра / неизвестный code) URL не переписывает; явный выбор
  пользователя пишется всегда, включая `?direction=all`.
- `onChange`: только `setSearchParams` (set `direction`, delete `view`).
- **Сброс вкладки на «Обзор» — эффектом на смену `direction`**, не в `onChange`:
  back/forward меняют direction мимо `onChange`, и вкладка не должна «переезжать»
  между направлениями при хождении по истории. Один `useEffect` по `direction`
  (срабатывание на маунте безвредно — дефолтная вкладка и так «Обзор»).
- `?view=errors` читается только при `direction === 'all'` (§7.3); при любом
  другом режиме игнорируется/удаляется.
- back/forward работают из коробки (состояние выводится из URL, не дублируется).

### 7.3. Условный рендер ProjectPage

```
direction === undefined              → скелетоны (summary грузится)
directions.length === 0              → текущие <Tabs> БЕЗ скоупа (legacy-режим, как сегодня; ADR #11)
direction === 'all', view=errors     → контент вкладки «Ошибки» («Ошибки объекта», «← к сводке»)
direction === 'all'                  → KPI×4 (сводные) + алерт-строка + DeviationChart (grouped, top-5)
direction === <code>                 → текущие <Tabs> (контент скоупнут direction)
```

В legacy-режиме скоупнутые хуки вызываются без `direction` (полные данные) —
поведение и контракты идентичны сегодняшним; переключатель скрыт (§7.1).

- Под рядом табов — контейнер фиксированной высоты в обоих режимах (§3.1).
- `direction` прокидывается в `useDashboardInvoices`, `useDashboardCalculations`,
  `useDashboardMonthlySummary`, `useProjectSuppliers`, `useReferencePrices` и в
  `handleExport` (query-параметр + суффикс направления в имени файла по
  каноническому формату §6.7).
- `useDashboardSummary` — без direction (один ответ на оба режима, §6.1); срез
  направления выбирается на фронте: `summary.directions.find(d => d.code === direction)`.
- Счётчики табов — из скоупнутых запросов; бейдж «Ошибки» — из `useDocuments`
  (глобален, как сейчас).

  поклассово **идентичны** соответствующим строкам без параметра (avg_price,
  deviation_amount, compensation) — фильтр не меняет знаменатели разноски.

**Разноска additive по направлению (§5.4, unit + integration):**
- смешанный счёт: бетон (base) + арматура (base) + пластификатор
  (`calc_role='additive'`, тип concrete) + доставка → стоимость additive входит
  только в avg_price бетонных классов; в строках арматуры — лишь доля доставки;
- моно-бетонный счёт с additive: avg_price не изменился относительно текущей
  логики (регрессия — побитовое равенство);
- edge case: additive типа concrete в счёте только с base-классами rebar →
  ни в чей avg_price не входит; в `directions[].turnover` бетона — учтена;
- та же пара проверок для `compute_export_rows` (колонка «Прочее») и
  `_compute_supplier_project_deviation`.

**Скоуп эндпоинтов:** `calculations` (только классы направления + поле `direction`),
`monthly-summary` (суммы/объёмы/счета направления, `volume_unit`),
`projects/{id}/suppliers` (только поставщики направления), `reference-prices`,
`export` (строки только направления; имя файла с суффиксом; «Направление: …» в шапке);
неизвестный `direction` → 422.

**Миграций нет** — миграционные тесты не нужны (ADR #12).

## 10. Риски и митигация

| Риск | Митигация |
|---|---|
| Фильтр направления, влезший в знаменатели разноски, тихо меняет цифры классов | Правило §5.4 «фильтр на выходе» + тест-страж идентичности поклассовых строк |
| Скоуп additive по типу меняет цифры существующих моно-счетов | Регрессионный тест побитового равенства на моно-направленном счёте (§8.1); правка зеркалится во все 3 места разноски одинаково |
| Инвариант сумм ломается на позициях с NULL-классом | Явное правило §5.1 (→ `other_total`) + тест |
| «Попугаи» в объёмах направления (пог.м в тоннах) | Фильтр по размерности default_unit (§5.2), честный недоучёт |
| Расхождение алерта и бейджа «Ошибки» | Один источник данных (список документов), без дублирования логики на бэке |
| Сломать глобальный дашборд изменением `DashboardSummary` | Только аддитивные поля; старые поля сохраняются |
| Мусорный `?direction=` до загрузки summary роняет скоупнутые запросы в 422 | Гейт `enabled: direction !== undefined` (§7.2) + тест на отсутствие запросов с невалидным code |
| `?direction=rebar` на объекте без арматуры | Валидация против `summary.directions` → фолбэк на автодефолт (без редиректа, URL не трогаем до действий пользователя) |
| Layout-дёргание при появлении табов | Зарезервированная высота ряда табов в обоих режимах |
| Счета из одних «прочих» позиций недостижимы из UI (вкладки «Счета» на «Все» нет) | Принятое ограничение MVP (ADR #9): такие счета — мелочёвка или недоклассифицированный документ; второе закроет атрибутная задача. Запасной выход — кликабельная KPI «Счетов» с плоским списком |
| Базовая цена классу типа `other` рассинхронизирует разбивку переплаты | Запрет на двух уровнях: UI не предлагает + 422 в API (§5.3) |

## 11. Критерии приёмки (из ТЗ, уточнённые)

- [ ] Пустой объект (без счетов): табы видны как сегодня, «Базовые цены» достижимы, переключатель скрыт
- [ ] Объект только с бетоном: дефолт — режим «Бетон» (привычные табы сразу); цифры сводки «Все» совпадают с текущей версией; переключатель `Все | Бетон`
- [ ] Объект с бетоном и арматурой: дефолт «Все»; `total_amount = Σ turnover направлений + delivery_total + other_total` (тест, точное равенство)
- [ ] Смешанный счёт виден в счетах обоих направлений, деньги не задваиваются; счёт «направление + классы типа other» смешанным не считается
- [ ] `?direction=rebar` открывает страницу в контексте арматуры; back/forward работают; мусорный code не порождает запросов к API
- [ ] На «Все»: нет табов, таблицы периодов, кнопки настройки цен; есть алерт при нераспознанных; «Разобрать →» открывает «Ошибки объекта» без смены направления
- [ ] KPI объёма при недоучёте показывает сноску «без N позиций в других единицах»
- [ ] Счётчики табов и KPI направления — только его данные; счётчик «Ошибки» глобален
- [ ] Поклассовые цифры (avg_price, deviation, compensation) идентичны с фильтром direction и без него
- [ ] Экспорт с направления — отчёт по направлению, суффикс в имени файла
- [ ] Изменений схемы БД нет; существующие тесты зелёные
- [ ] `just lint` и `just test` зелёные

## 12. Ключевые решения (ADR)

1. **`material_types` — и есть справочник направлений.** Новая таблица
   `material_categories` не создаётся: дублировала бы code/name/default_unit
   один в один и потребовала бы синхронизации двух справочников. Используем
   существующий как есть (после R5 — без расширений схемы, ADR #12).
   Direction в API = `material_types.code`.
2. **Фильтр направления — на выходе расчёта, не во входных запросах.** Знаменатели
   разноски доставки/добавок всегда считаются по полному счёту; направление
   отбирает готовые поклассовые строки (как `material_class_id` сейчас). Иначе
   смешанные счета меняли бы avg_price классов в зависимости от выбранного режима.
3. **Summary — один ответ для обоих режимов** (totals + `directions[]`), без
   параметра `direction`. Срез направления выбирает фронт. Меньше API-поверхности,
   нет рефетча при переключении, инвариант виден в одном ответе.
4. **Группировка отклонений — на фронте** из тех же per-class строк calculations
   (+ поле `direction` в строке). Сервер не дублирует логику «top-N + подытог»,
   оба режима гарантированно показывают одни числа.
5. **Объём направления — только base-классы с совпадающей размерностью.**
   Присадки и «не та» единица не попадают в KPI; недоучёт честный и видимый
   (та же философия, что dimension guard units-спеки).
6. **Оборот направления — все material-позиции его классов (base + additive), без
   разноски.** Разноска доставки — инструмент расчёта avg_price/переплаты, а не
   принадлежности денег: в обороте доставка остаётся отдельным слагаемым.
7. **Ошибки/нераспознанные — глобальны для объекта**, у документа без распознанных
   позиций направления нет. Алерт и бейдж питаются одним источником.
8. **Стоимость additive-класса входит в avg_price только base-классов своего
   `material_type`; доставка — общая на счёт.** Текущая разноска additive по всем
   base-классам счёта — упрощение моно-бетонной эпохи; в смешанном счёте она
   удорожала бы чужое направление (пластификатор → avg_price арматуры).
   У additive-класса направление есть (`material_type_id` NOT NULL), у строки
   доставки — нет, отсюда разные правила. Additive без base-классов своего типа
   в счёте — не разносится никому (честный отказ). Для моно-направленных счетов
   поведение побитово прежнее.
9. **Тип `other` не образует направления** (решение владельца, R3). Не показывается
   в переключателе и не входит в `directions[]`; деньги его классов поглощает
   `other_total` (одна строка «Прочее» в breakdown — §5.1); базовые цены его
   классам не назначаются (UI + 422, §5.3); смешанность счетов считается только
   по направлениям (§5.5). Смысл «Прочего» для пользователя остаётся один.
   Принятая цена: счета из одних «прочих» позиций недостижимы из UI (§10);
   бэкенду не нужно решать, есть ли у `other` «данные» — он просто никогда
   не направление. Следствие для KPI «Счетов»: такие счета входят в общее число,
   но не в разбивку по направлениям — подпись дополняется хвостом «· N проч.»
   (`other_invoice_count`, §3.2/§6.1), чтобы цифры сходились на глаз.
10. **Дефолт моно-объекта — его направление, не «Все»** (ревью R3).
    `directions.length == 1` → страница открывается в режиме направления:
    пользователь существующих объектов сразу видит привычные табы, без
    обязательного клика. Сводка «Все» доступна через переключатель (breakdown
    доставки/прочего). Снимает скрытую UX-регрессию для всей текущей базы.
11. **Пустой объект — legacy-режим: текущие табы без скоупа** (ревью R4).
    `directions[]` выводится из позиций, у нового объекта он пуст; без этого
    режима исчезал бы штатный первый шаг «создал объект → задал базовые цены
    из договора до прихода счетов». Понятие направления к объекту без данных
    неприменимо; переключатель скрыт, поведение и контракты — сегодняшние.
12. **`sort_order` не вводится — порядок направлений = `ORDER BY id`** (R5).
    Единственная мотивация колонки («кирпич перед „Прочее“») умерла с ADR #9:
    `other` в переключатель не попадает, а для реальных направлений порядок
    добавления (бетон, арматура, кирпич…) — ровно нужный; сиды создают типы в
    фиксированном порядке, id стабильны между окружениями. В результате задача
    вообще не трогает схему БД — ценное свойство, когда главный риск — тихо
    испортить расчётные цифры. Ручная перестановка, если когда-нибудь
    понадобится, вернётся однострочной аддитивной миграцией без потерь.

## 13. Закрытые вопросы (ревью R3)

1. **Направление «Прочее» (тип `other`)** → НЕ направление (решение владельца).
   Не в переключателе, не в `directions[]`; деньги — в `other_total`; базовые
   цены запрещены; смешанность без `other`. Подробности — ADR #9. Недостижимость
   счетов из одних «прочих» позиций — принятое ограничение MVP (§10).
2. **Алерт «Разобрать →» на «Все»** → `?view=errors` при `direction=all`:
   тот же контент вкладки «Ошибки» с заголовком «Ошибки объекта» и «← к сводке».
   Прыжок в «первое направление + вкладка Ошибки» отвергнут: визуальный контекст
   направления лгал бы о скоупе ошибок (§3.2, §7.3).
3. **Summary без параметра `direction`** (ADR #3) → принято ревью: один shape
   лучше для UX переключения, инвариант виден в одном ответе.
4. **Группированные отклонения на фронте** (ADR #4) → принято ревью: серверная
   группировка top-N без второго потребителя — мёртвый код.
5. **`total_qty` в summary** → остаётся deprecated-полем, запись в TECH_DEBT.
   Туда же (по ревью): полный экспорт на «Все» — плоский список классов без
   колонки «Направление»; добавить колонку при реальной потребности смешанных
   объектов. И `SupplierPage.tsx:304` («Объём, м³») — из §7.6.
