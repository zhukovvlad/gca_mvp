# План: фаза предъявления — первый продукт ревью задачи

**Спека:** `docs/superpowers/specs/2026-09-12-review-presentation-phase-design.md`
**Ветка:** `docs/step-four`

## Global Constraints

- **Скрипты остаются read-only.** Ни один скрипт фичи не пишет в файлы, не
  трогает индекс гита (`git add -N` запрещён), не импортирует приложение, не
  меняет `pyproject`, лок, `justfile` и `.github`, не касается БД и схемы.
  Выход за эту границу **нарушает утверждённый дизайн** и требует возврата на
  гейт 3 с пересмотром плана. Исключение §9.1 здесь ни при чём — оно к фиче не
  применяется (спека, врезка о плане).
- **Продуктовый код не меняется ни одной строкой.** `backend/` вне `scripts/` и
  `tests/`, `frontend/src/` — не трогаются.
- **Тесты гита живут только во временном репозитории.** Любое тестовое
  состояние — staged, unstaged, неотслеживаемый файл, двоичное содержимое —
  создаётся в отдельном временном репозитории (`tmp_path`, свой `git init`).
  **Рабочий репозиторий тесты не изменяют ни на одном шаге**, ни дерево, ни
  индекс: тест, правящий его, однажды уронит чужую работу и будет выглядеть
  флейком. Проверяется сохранением исходного статуса либо конкретной строки
  `??`, а не утверждением о пустоте статуса.
- **Ветка зелёная после каждой задачи.** Порядок задач подчинён этому:
  маршрутизатор заводится после файла, на который ведёт; проверка стража — после
  маршрутизатора.
- **Инварианты домена не меняются.** Ревизия `AGENTS.md` объявляется врезкой с
  явной пометкой «инварианты домена НЕ меняются, меняется процесс §9».
- **Фаза не применяется к самой себе задним числом.** Перечислитель заводится
  задачами 1–2 и до их завершения не существует; задачи этой фичи ревьюируются
  по действующему сегодня порядку. Это названо здесь, а не обнаруживается в
  процессе.
- **Роли фичи не заводятся.** Ни одного нового участника процесса; правится
  только порядок работы существующего ревьюера и область личных проверок
  оркестратора.

## Структура файлов

```

  scripts/enumerate_review_units.py          СОЗДАЁТСЯ (задачи 1, 2)
  scripts/check_agents_index.py              ПРАВИТСЯ (задача 5)
  tests/unit/test_enumerate_review_units.py  СОЗДАЁТСЯ (задачи 1, 2)
  tests/unit/test_check_agents_index.py      ПРАВИТСЯ либо СОЗДАЁТСЯ (задача 5)
docs/
  process/implementation.md                  СОЗДАЁТСЯ (задача 3)
  superpowers/plans/TEMPLATE.md              ПРАВИТСЯ (задача 4)
  devlog/2026-09-12-review-presentation-phase.md  СОЗДАЁТСЯ на финале
AGENTS.md                                    ПРАВИТСЯ (задача 4)
```

## Решения плана, которых нет в спеке

1. **Скрипт разделён на две задачи по подкомандам, а не по слоям.** `assertions`
   разбирает markdown, `hunks` разбирает вывод гита; общего у них — разрешение
   корня репозитория и печать строк. Резать по «каркас отдельно» значило бы
   завести задачу, чья зелень ничего не доказывает.
2. **Тесты обеих подкоманд живут в одном файле.** Подкоманды делят формат
   вывода, и расхождение формата обязано падать в одном месте.
3. **Семнадцатая проверка стража лепится по образцу `check_15`.** У §4 и §10
   маршрут стережётся тремя ветвями; наш случай той же природы, и заводить
   четвёртую форму проверки незачем.
4. **§9.2 чинится попутно.** Строка «План фичи» обещает «задачи с чекбоксами»,
   но `TEMPLATE.md` и план `2026-09-09-price-predicate` их не несут: практика
   сменилась вместе с правилом утверждений, а таблица осталась. Задача 4 правит
   эту ячейку всё равно — чинить отдельной фичей дороже, чем одной строкой здесь.
5. **Порядок 1→2→3→4→5 сквозной.** Задачи 1 и 2 независимы от документных и
   могли бы идти после них; поставлены первыми, потому что их утверждения самые
   содержательные, а документные задачи по §3.6 спеки вырождаются.

## Задачи

### Task 1: Перечислитель утверждений плана

**Files**
- Create: `backend/scripts/enumerate_review_units.py`
- Create: `backend/tests/unit/test_enumerate_review_units.py`

**Interfaces**
- Потребляет: `argparse`, `hashlib`, `pathlib`, `subprocess` (stdlib);
  `git rev-parse --show-toplevel`.
- Производит:

```python
# backend/scripts/enumerate_review_units.py
def repo_root() -> Path
def task_block(lines: list[str], task: int) -> list[str]
def assertion_items(block: list[str]) -> list[tuple[str, str]]
def emit(rows: Iterable[Sequence[str]]) -> None
def main() -> int
```

**Утверждения**
- команда `assertions --plan <путь> --task N` печатает по строке на пункт
  раздела «Утверждения» задачи N; поля разделены табуляцией; отметок времени в
  выводе нет — два прогона подряд дают побайтно равный вывод;
- блок задачи ограничен `### Task N:` и ближайшим следующим `### ` либо `---`;
  пункт соседней задачи в вывод не попадает — предъявлено планом, где у задачи
  N+1 есть свои утверждения;
- берётся список после строки `**Утверждения**` и до следующего жирного
  заголовка; пункты разделов «Files», «Interfaces», «Имена» и «Проверка» в
  вывод не попадают — четыре отрицательных входа;
- идентификатор верхнего пункта — `A<задача>.<номер>`, нумерация с единицы;
- вложенный пункт получает букву: `A4.3b`; буква считается внутри своего
  верхнего пункта, а не сквозно по задаче;
- строка с отступом, не начинающаяся с `- `, дописывается к тексту текущего
  пункта, а не заводит новый: пункт из двух строк даёт **одну** строку вывода;
- путь `--plan` разрешается от корня репозитория независимо от текущего
  каталога: прогон из `backend/` и из корня дают одинаковый вывод;
- отсутствующая задача N и отсутствующий раздел «Утверждения» — разные отказы с
  разными сообщениями, оба с кодом возврата, отличным от нуля; пустой вывод с
  кодом 0 не выдаётся ни на одном из двух;
- скрипт не пишет в файлы и не меняет состояние дерева: `git status
  --porcelain` **до и после прогона совпадает посимвольно**. Утверждать
  пустоту статуса нельзя — штатный момент запуска перечислителя это ГРЯЗНОЕ
  дерево незакоммиченной задачи, и пустой статус там не норма, а исключение.

**Имена**
- Заводятся этой задачей: `enumerate_review_units`, `repo_root`, `task_block`,
  `assertion_items`, `emit`, подкоманда `assertions`.
- Существуют, проверено `grep`-ом: `backend/scripts/` с `__init__.py`;
  `docs/superpowers/plans/TEMPLATE.md`; прецедент скрипта-читателя без записи —
  `backend/scripts/count_plan_edits.py`.

**Проверка**
- `just test-unit-k enumerate_review_units` — зелёная; в разделе назвать выбор
  ДО задачи (ноль тестов, класса ещё нет) и ПОСЛЕ.
- `just lint-backend` — зелёная.

### Task 2: Перечислитель hunk'ов и схема `H:`

**Files**
- Edit: `backend/scripts/enumerate_review_units.py`
- Edit: `backend/tests/unit/test_enumerate_review_units.py`

**Interfaces**
- Потребляет: `repo_root`, `emit` (заведены задачей 1); `git diff HEAD`,
  `git status --porcelain`.
- Производит:

```python
# backend/scripts/enumerate_review_units.py
@dataclass(frozen=True)
class Hunk:
    path: str
    context: str
    body: str
    added: int
    removed: int

def diff_hunks() -> list[Hunk]
def untracked_hunks() -> list[Hunk]
def hunk_id(path: str, body: str) -> str
```

**Утверждения**
- команда `hunks` печатает по строке на hunk: идентификатор, путь, контекст
  `@@`, счётчик вида `+N/-M`; поля разделены табуляцией, отметок времени нет;
- в область попадают И staged, И unstaged правки: файл, часть которого
  добавлена в индекс, а часть нет, даёт hunk'и обоих видов;
- неотслеживаемый неигнорируемый файл даёт **один** hunk «добавлен целиком» с
  `-0`; игнорируемый файл не даёт ни одного — два входа;
- индекс гита не изменяется, и проверяется это **следствием, а не временем
  файла**: во временном репозитории с неотслеживаемым файлом после прогона
  `git status --porcelain` показывает его по-прежнему как `??`, а не как `A `.
  Сверка `mtime` у `.git/index` для этого не годится — его обновляет и сам `git
  status`, то есть проверка краснела бы по причине, к скрипту не относящейся;
- **точное правило `hunk_id` — первые восемь hex от
  `sha256(path + "\n" + body)`**, где `body` — строки `+` и `-` (первый символ
  сохранён, заголовок `@@` отброшен, хвостовые пробелы сняты), склеенные через
  `\n` **без хвостового перевода строки**;
- правило предъявлено **известным входом с известным ответом**, а не пересказом
  алгоритма: путь `backend/money/price.py` и тело из трёх строк
  `+    if not value.is_finite():`, `+        return False`,
  `-    return value > 0` дают ровно **`H:c81dd3dd`**; тот же текст при пути
  `backend/money/other.py` — ровно **`H:2292efa1`**. Оракул считан независимо от
  реализации и держит разделитель, порядок склейки и алгоритм;
- три входа на нормализацию: тот же hunk со сдвинутыми номерами строк даёт ТОТ
  ЖЕ ID; тот же текст в другом файле — ДРУГОЙ (см. вектор выше); добавленный
  хвостовой пробел — ТОТ ЖЕ;
- форма идентификатора — `H:` и восемь шестнадцатеричных знаков;
- **двоичное содержимое даёт детерминированный синтетический hunk, а не
  пропуск.** Там, где `git diff` печатает «Binary files … differ», тело
  строится **симметрично текстовому — обеими сторонами правки**, а не одной:

  | Правка | Тело | Счётчик |
  |---|---|---|
  | добавление | `+binary <sha256(new)>` | `+1/-0` |
  | удаление | `-binary <sha256(old)>` | `+0/-1` |
  | изменение | `-binary <sha256(old)>` и `+binary <sha256(new)>` | `+1/-1` |

  Контекст у всех трёх фиксированный — `@@ binary @@`; ID считается тем же
  правилом, что у текстового hunk'а. Старая сторона берётся из `git show
  HEAD:<путь>`, новая — из рабочего дерева;
- **две разные правки к одному содержимому дают разные ID:** `A → B` и `C → B`
  различаются, потому что тело несёт и старый хэш. Односторонняя форма
  `+binary <sha256 текущего>` их отождествляла бы, а удалённый файл при ней не
  имел бы тела вовсе — текущего содержимого у него нет;
- три независимых входа: добавление, изменение и удаление двоичного файла;
  молчаливый пропуск запрещён — инструмент строит знаменатель, и невидимый
  элемент в нём опаснее лишнего. Двоичные файлы в репозитории есть
  (`fixtures/gp_estimate_fixture.xlsx`), то есть вход не надуман;
- два hunk'а с одинаковым нормализованным телом в одном файле различаются
  позиционными суффиксами `.2`, `.3` в порядке перечисления; при появлении
  третьего такого hunk'а РАНЬШЕ по порядку суффиксы соседей сдвигаются — это
  предъявляется, а не обходится, потому что обещание стабильности внутри группы
  дубликатов не действует (спека §3.10);
- порядок вывода: по пути файла, внутри файла — по положению в `diff`; на
  дереве с тремя правленными файлами вывод совпадает с сортировкой путей;
- пустое дерево (`git diff HEAD` пуст, неотслеживаемых нет) даёт пустой вывод и
  код возврата 0 — это не отказ.

**Имена**
- Заводятся этой задачей: `Hunk`, `diff_hunks`, `untracked_hunks`, `hunk_id`,
  подкоманда `hunks`.
- Существуют, проверено `grep`-ом: `repo_root`, `emit` (задача 1).

**Проверка**
- `just test-unit-k enumerate_review_units` — зелёная; назвать выбор ДО и ПОСЛЕ
  (прирост за счёт классов этой задачи).
- `just lint-backend` — зелёная.

  вместе с объяснявшим его комментарием и предъявление действующего пути — и
  прямо говорит, что ссылка на ненаблюдаемость третьим исходом не является

- файл задаёт объём повтора после правок: дефолт — вся таблица задачи, сужение
  допустимо только при явном сопоставлении файлов, тестов, фикстур и

- файл описывает поисковый журнал зависимых текстов пятью графами и называет
  приём «искать по утверждению, а не по имени механизма», не обещая полноты
  (§3.8);
- файл требует называть выбор команды проверки ДО и ПОСЛЕ задачи (§3.9);
- файл несёт контракт перечислителя в объёме, который нужен ревьюеру на месте:
  обе команды буквально, схему `A…` и `H:…`, область `diff`, правило
  many-to-many и место с сроком жизни отчёта (§3.10);
- **состав файла сверяется с §3 спеки подразделом к подразделу**: у каждого из
  подразделов §3.1–§3.11 есть соответствующее место в файле. Сверка перечнем, а
  не впечатлением: обещание «переносит §3 целиком» иначе выполняется частично и
  выглядит выполненным;
- блок для брифа отделён от обязанностей оркестратора заголовком, и его границы
  названы явно — иначе в бриф уедет весь файл;
- разделы файла **не нумерованы**: исполнитель процитирует номер в докстроке, и
