# Полезная площадь объекта — Implementation Plan

> **Для исполнителей:** задачи идут по порядку, каждая заканчивается коммитом.
> Шаги помечены чекбоксами (`- [ ]`). **Все коммиты делает оркестратор.**

**Goal:** завести на объекте третью площадь — полезную, — которая хранится, вводится
и показывается, но **не входит** в общую и ни в один расчёт. Нужна следующей фиче
(стартовый дашборд), где показывается разбивка площадей по базе.

**Architecture:** миграция `0013` добавляет одну колонку на `objects` и два `CHECK`'а.
`area_total_sp` не трогается — остаётся `GENERATED ALWAYS AS (надземная + подземная)`.
Ограничение «полезная ≤ общей» дублируется судьёй итогового состояния в CRUD ради
`422`; самодостаточные проверки (`float`, отрицательное) — в Pydantic. Фронтенд получает
третье поле в диалоге объекта и показ полезной площади на **двух** поверхностях, где
площади уже видны, — в карточке договора и в шапке паспорта проекта.

**Обе поверхности несут один и тот же дефект, который вносит эта фича:** пустое
состояние ТЭП у них висит на `area_total_sp === null`, поэтому объект с одной лишь
полезной площадью получит надпись «ТЭП не заведены» про заведённые данные. Чинит их
эта же фича — задачи 4 и 5.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy 2.x sync ORM, Alembic, psycopg3,
PostgreSQL 16; React + TS, Vite, shadcn/ui, TanStack Query, vitest + MSW.

**Спека:** [2026-08-15-object-useful-area-design.md](../specs/2026-08-15-object-useful-area-design.md)
(гейт 2 закрыт 2026-08-15). **Ветка:** `feat/object-useful-area` (создана от `main` = `a07c6cd`).

## Global Constraints

Требования этого раздела входят в **каждую** задачу неявно.

**Процесс**

- В `main` не коммитить. Ветка одна — `feat/object-useful-area`.
- **Перед пушем — `just ci`**, шагами и в форме CI. Правки только в `docs/` от него
  освобождены (`AGENTS.md` §9.3).
- Коммиты делает **оркестратор**, не исполнитель задачи.
- Субагентам **запрещено печатать кириллицу в терминал**: вердикты ASCII, русский текст —
  в файл отчёта, `rg -c` вместо `rg`, `Read` вместо `Get-Content`.

**Оболочка — PowerShell 5.1, не bash**

- После **каждой** нативной команды внутри `try` обязательно
  `if ($LASTEXITCODE -ne 0) { throw "<что> failed: $LASTEXITCODE" }`. После блока
  `try/finally` `$?` равен `True` при ненулевом `$LASTEXITCODE` — падение маскируется
  ([silent-test-runs](../../insights/silent-test-runs.md)).
- **Вердикт читается по напечатанным числам, а не по коду возврата:** `rg` без совпадений
  возвращает `1` и портит код блока, где всё верно.
- Не работают: `env -u`, `VAR=value` префикс, `&&`, `||`, `grep`, `wc`, heredoc, перенос
  строки обратным слэшем. Многострочный текст в `git commit` — here-string `@'…'@` с
  закрывающей меткой в **нулевой** колонке.
- Разовые скрипты — в `$env:TEMP\gca-useful-area`.
- Один раз на сессию: `$env:PYTHONIOENCODING='utf-8'; $env:PYTHONUTF8='1'`.
- Команды бэкенда — из `backend/` через `uv run`; `git` — из корня; `vitest` — **только из
  `frontend/`** (в корне лежит другая установка, она не разрешает алиас `@/`, `AGENTS.md` §11).

**Домен**

- **Площади:** `Numeric` в БД ↔ `Decimal` в Python ↔ **строки в JSON**. На входе — строка
  или точное целое; `float` отвергается явно. В тестах сравнивать `Decimal` с `Decimal`.
- `decimal_json` обязателен для **любого** ответа, несущего `Decimal`.
- `area_total_sp` — генерируемая колонка, её выражение **не меняется** (спека §2.2).
- Полезная площадь не участвует ни в одном расчёте: ₽/м² везде считается от общей.

**Проверки**

- Тест, доказывающий защиту, обязан быть проверен **снятием защиты**
  ([verifying-guards](../../insights/verifying-guards.md)): снять — увидеть красный —
  вернуть из побайтовой копии, не через `git checkout --`. Защит несколько и они
  маскируют друг друга, поэтому снятия — **порознь**, список у каждой задачи.
- **Снятие защиты, живущей в схеме, требует реального переналожения.** Правка уже
  накатанного файла миграции в PostgreSQL не меняет **ничего**: `CHECK` остаётся на
  месте, прогон остаётся зелёным, и это прочитается как «защиты нет», хотя она есть.
  Ослабленную миграцию применять через `downgrade`/`upgrade` или на свежей базе.
- **`prepare_threshold = 5` считает ПОВТОРНЫЕ ИСПОЛНЕНИЯ одной формы запроса, а не
  строки.** Один `INSERT` с десятью строками порога не достигает и дефект не
  воспроизводит ([batch-larger-than-five](../../insights/batch-larger-than-five.md)).
  Схема проверки: **6–10 валидных исполнений одной формы**, затем нарушающее исполнение
  **той же формы**.
- На финале строить соответствие «требование DoD спеки → тест» списком
  ([replaying-new-rules](../../insights/replaying-new-rules.md)).

## Task 1: Миграция 0013, модель, ограничения схемы

**Цель:** колонка и оба `CHECK`'а существуют и работают; `downgrade` снимает их начисто.

- [ ] **Шаг 1: написать падающие тесты схемы** — `test_schema_constraints.py`.

  Псевдокод — **эскиз**, имена хелперов сверить с файлом перед написанием:

  ```
  · полезная > суммы слагаемых  → IntegrityError
  · полезная = сумме слагаемых  → проходит (граница включена)
  · полезная < 0                → IntegrityError
  · полезная задана, пара NULL  → ПРОХОДИТ (граница §2.4 спеки — закрепляется намеренно)
  · полезная NULL               → проходит

  ужесточили мимоходом.

  значениями, по одному исполнению каждое, — затем нарушающее исполнение **той же
  формы**. Один `INSERT` с десятью строками порога не достигает и дефект не
  воспроизводит.

- [ ] **Шаг 6: круговой рейс** — `upgrade head` → `downgrade -1` → `upgrade head`.
      Проверить, что после `downgrade` колонки и обоих `CHECK`'ов нет.

- [ ] **Шаг 7: снять обе защиты схемы — ПОРОЗНЬ и с реальным переналожением.**

      (а) ослабить `ck_objects_area_useful_sp_within_total` до `true`;
      (б) вернуть, ослабить `ck_objects_area_useful_sp_non_negative` до `true`.

      Каждый раз: **`downgrade -1` → `upgrade head`** (или свежая база) — правка файла
      уже накатанной миграции в PostgreSQL не меняет ничего, и зелёный прогон после неё
      означал бы только то, что защита осталась на месте. Вернуть из побайтовой копии и
      переналожить.

      **Ожидаемый результат каждого снятия — четыре утверждения, а не одно.** Ослабление
      меняет и поведение, и текст ограничения в базе, поэтому красных будет два:

      | Что | Ожидание |
      |---|---|
      | негативный тест **этого** ограничения | КРАСНЫЙ |
      | сравнение `DB_OBJECT_CHECKS` целиком | КРАСНЫЙ — снимок берётся из PostgreSQL, а выражение изменилось |
      | негативный тест **соседнего** ограничения | зелёный — иначе снятие задело не то, что задумано |
      | сравнение `ORM_OBJECT_CHECKS` | зелёный — `models.py` не менялся |

      Красный DB-снимок здесь не помеха, а часть вердикта: если он остался зелёным,
      значит ослабленная миграция в базу **не доехала** и весь прогон недействителен.

## Task 2: Прикладной слой — `422` вместо `500`

**Цель:** оба валидатора `_AreaMixin` охватывают три поля; правило «полезная ≤ общей»
судит итоговое состояние; отказ человекочитаемый.

- [ ] **Шаг 1: написать падающие тесты API** — `test_references_api.py`.

  **Параметризация по именам полей обязательна** (DoD спеки): два независимых
  набора, каждый по трём полям.

  ```
  @parametrize field in (area_aboveground_sp, area_underground_sp, area_useful_sp)
      · float на входе        → 422, текст про строку
      · отрицательное значение → 422

  Итоговое состояние — ОБЕ ветви:
    A. объект: слагаемые 60 + 40 (общая 100), полезная 80
       PATCH area_aboveground_sp = 30  (общая станет 70 < 80)
       → 422 человекочитаемый
       → GET возвращает ПРЕЖНИЕ значения (60/40/80) — доказательство отката
    B. тот же объект
       PATCH area_useful_sp = 120  (> существующей общей 100)
       → 422

  СОЗДАНИЕ — своя ветвь, не покрытая двумя предыдущими:
    C. POST объекта: слагаемые 60 + 40, полезная 120
       → 422 человекочитаемый (а НЕ сырая ошибка целостности)

  Позитив: POST и PATCH с полезной площадью строкой; полезная без пары сохраняется.
  ```

  Ветвь **A** — та, которой нет в наивной реализации: нарушение вносит слагаемое, а не
  полезная. Ветвь **B** стережёт вырождение правила в проверку только «своего» поля.
  Ветвь **C** — отдельный путь `create_object`: без неё судья может стоять только в
  `update_object`, и создание уходило бы на `CHECK` с сырой пятисоткой.

**Дефект вносит эта фича, поэтому чинит его она же.**

а иначе печатает «ТЭП не заведены». По границе §2.4 полезная площадь может быть заведена
**без** пары — и тогда карточка утверждает «не заведены» про заведённые данные.

- [ ] **Шаг 1: расширить хелпер** `renderCard` — ключ `useful` в `objectAreas` рядом с
      `above`/`under`/`total`.

- [ ] **Шаг 2: написать падающие тесты** `ContractCardPage.test.tsx`:

  ```
  1. пара и полезная заданы      → видны четыре строки, включая полезную
  2. пара задана, полезная NULL  → полезная строка НЕ показывается (не «—», а отсутствует)
  3. пара NULL, полезная задана  → «ТЭП не заведены» НЕ печатается; видна полезная
  4. всё NULL                    → «ТЭП не заведены»

## Task 5: Паспорт проекта — тот же дефект, та же починка

**Дефект тот же, что в задаче 4, и найден тем же способом.** `PassportHeader.tsx:182`
объявляет `noTep = object.area_total_sp === null`, и этот флаг управляет тремя местами:
значением метрики «Площадь общая», её подписью и метрикой ₽/м² с подписью. При заведённой
полезной и незаведённой паре паспорт скажет «ТЭП не заведены» про заведённые данные.

**Правило целевого состояния** (согласовано на гейте 3): если общей нет, метрика площади
говорит **«Общая площадь не заведена»**, полезная при этом **показывается**, а удельная
стоимость **не считается** — знаменатель ₽/м² не меняется никогда (спека §2.2, §4).

**У метрики ₽/м² состояний ТРИ, а не два.** Прежняя редакция плана оставляла ей
дословное «нет ТЭП», и это ложь ровно того же рода, что и в метрике площади: ТЭП
заведены, не заведена общая. Разбиение:

| Состояние | Значение ₽/м² | Подпись |
|---|---|---|
| все площади `NULL` | «нет ТЭП» — **как сейчас, дословно** | как сейчас |
| полезная есть, общей нет | «не считается» | «нет общей площади» |
| общая есть | значение — **как сейчас** | «по общей площади» |

Средняя строка — новая; крайние обязаны остаться посимвольно прежними.

- [ ] **Шаг 1: бэкенд** — поле в `object_dict` (`project_passport.py:1223-1229`) и тест
      в `test_project_passport_api.py`, что оно доезжает до ответа. `per_sqm` (строка
      1352) **не трогать**: он берётся из `area_total_sp` и остаётся таким.

- [ ] **Шаг 2: написать падающие тесты** `ProjectPassportPage.test.tsx`:

  ```
  1. пара и полезная заданы     → в подписи метрики площади видна полезная;
                                   ₽/м² считается как раньше (значение не изменилось),
                                   подпись «по общей площади»
  2. пара задана, полезная NULL → полезной в подписи НЕТ — не «—», не «undefined»,
                                   отсутствует; общая площадь, её подпись и ₽/м² —
                                   дословно прежние
  3. пара NULL, полезная задана → «Общая площадь не заведена»; полезная ВИДНА;
                                   ₽/м² — «не считается», подпись «нет общей площади»
                                   (НЕ «нет ТЭП»: ТЭП заведены)
  4. всё NULL                   → «ТЭП не заведены» и «нет ТЭП» — дословно как сейчас
  ```

  Случаи **2 и 4 — контроль неизменности**: оба обязаны быть зелёными до правки и

  стережёт самый вероятный побочный эффект правки подписи — полезную площадь, которая
  начнёт печататься как «—» или `undefined` там, где её просто нет.

  Случай 3 проверяет **обе** метрики сразу — площадь и ₽/м²: правка одной из них при
  забытой второй и есть тот дефект, ради которого он написан.

- [ ] **Шаг 3: прогнать, увидеть красное** — красные **1 и 3**; **2 и 4 зелёные**. Если
      красен хотя бы один из контрольных, предпосылка неверна — разбираться до

- [ ] **Шаг 4: реализация.** Флаг `noTep` расщепляется на два смысла: «нет общей»

      (управляет текстами «ТЭП не заведены» и «нет ТЭП»).

      **Полезная площадь показывается в ПОДПИСИ существующей метрики**, рядом с

      не добавляет строк в сетку метрик.

- [ ] **Шаг 5: ЗАМЕР ПЕЧАТИ ПОЛНОГО ПАСПОРТА В БРАУЗЕРЕ.** Обязателен, и утверждать
      что-либо о печати **до** него нельзя. Прежняя редакция плана заявляла, что
      расширение подписи высоты сетки не меняет, — это предположение, а не факт: более
      длинная подпись переносится на вторую строку и высоту как раз увеличивает.
      `AGENTS.md` §11 требует браузерный замер при **любой** правке печатной формы, и
      расчёт «на бумаге» там уже ошибался (284 мм при доступных 277).

      Замер на **максимальном** составе паспорта: нет выхода за правый край, нет
      разрывов внутри строк, шапка таблицы повторяется на каждом листе. Проверять оба
      состояния подписи — с полезной площадью и без неё, — потому что удлиняется именно
      она. Если подпись переносится и раскладка ломается, полезная площадь уезжает в
      отдельную строку или сокращается — решение принимается **по замеру**, а не заранее.
