## 5. Контракты, которые уже есть (фаза 4)

`POST /api/v1/estimates/upload` — multipart: `file`, `contract_id`,
`amendment_no?`, `replace?`. Ответы:

| Код | Когда |
|---|---|
| `202` | задание создано, тело — задание в статусе `pending` |
| `200` | идемпотентно: текущая смета пары уже загружена ЭТИМ файлом |
| `400` | не `.xlsx`/`.xlsm`, не ZIP внутри, пустой файл |
| `403` | `replace=true` без роли `admin` |
| `404` | договора нет |
| `409` | смета уже есть (нужен `replace=true`) либо импорт пары уже идёт |
| `413` | больше `UPLOAD_MAX_SIZE_MB` |
| `422` | `amendment_no <= 0` |

`GET /api/v1/import-jobs/{id}` — поллинг. Тело (то же и у upload):

```jsonc
{
  "id": 1, "contract_id": 7, "amendment_no": null,
  "filename": "смета.xlsx", "file_sha256": "…",
  "status": "pending|parsing|importing|matching|done|error",
  "error_text": null, "warnings": ["…"],
  "counters": { "positions_total": 1830, "matched_cache": 0,
                "matched_exact": 0, "matched_nonposition": 0, "to_review": 1830 },
  "estimate_id": 42,          // смета ТЕКУЩЕЙ пары, а не «этого задания»
  "created_at": "…", "started_at": "…", "finished_at": "…"
}
```

`GET /api/v1/import-jobs/{id}/file` — исходник: `200`, `404` (нет задания),
**`410`** (файл удалён ретенцией §8 — запись задания жива, это аудит). Экран
обязан различать 404 и 410.

**Сервис Review** (`backend/services/review.py`) — готов и покрыт тестами:

```python
merge_into_position(db, *, to_review_id, target_id, resolver=None) -> int  # перенесено позиций
set_kind(db, *, to_review_id, kind, resolver=None) -> CatalogPosition      # POSITION|HEADER|TRASH
# ReviewError — доменный отказ с человекочитаемым текстом; транслировать в 409/404/422
# MANUAL_KINDS — что оператор вправе ставить; LOT_HEADER туда НЕ входит
```

Обе функции блокируют строки `FOR UPDATE` и требуют, чтобы транзакцией управлял
вызывающий. При пакетной обработке передавать общий `resolver` — иначе справочник
единиц перечитывается на каждое решение.

## 6. Решения, которые фаза 5 должна принять явно

Выбранное и обоснование записать в итоговый отчёт `docs/phase5-crud-review.md`.

### 6.1. Отдельные экраны справочников или заведение по месту

§7.1 называет один экран «Договоры/Объекты». Объект, подрядчик и класс — три
отдельные сущности, которые надо где-то создавать. Варианты: (а) отдельные
экраны-справочники; (б) создание по месту в форме договора (комбобокс
«выбрать или создать»); (в) гибрид. Рекомендация: (б) для подрядчика и объекта
(их заводят в момент договора), отдельный простой экран для классов (их мало,
меняются редко, право `admin`). Решить и обосновать.

### 6.2. Права на CRUD договоров и справочников

§3 распределяет роли явно **не полностью**: `admin` — пользователи, классы,
нормативы, замена/удаление смет; `member` — чтение, загрузка смет, ручной
матчинг. Про создание и правку **договоров, объектов, подрядчиков** не сказано.
Это **вопрос к пользователю** — задать его в начале фазы, не в середине.
Рекомендация как отправная точка: заведение и правка карточек — `admin`,
`member` читает и грузит сметы (тогда §3 не расширяется по смыслу: «управление»
остаётся у admin).

### 6.3. Судьба осиротевших TO_REVIEW-строк

Долг фазы 4 (`docs/phase4-import.md` §13.5): после `replace` позиции старой
сметы удаляются каскадом, а созданные ею TO_REVIEW-строки остаются — в очереди
появляется строка, на которую не ссылается ни одна позиция. Обычно её тут же
переиспользует следующий импорт. Варианты: (а) не показывать строки с нулём
ссылок; (б) показывать с пометкой и кнопкой «удалить»; (в) чистить фоном.
Рекомендация: (а) плюс счётчик ссылок в API — это гигиена экрана, а не
целостности.

### 6.4. Поиск цели при слиянии: FTS или ILIKE

§5 допускает «поиск FTS/ILIKE». В схеме есть `catalog_positions.fts_vector`
(GIN, `to_tsvector('simple', standard_job_title)`) и обычный индекс по
`standard_job_title`. Есть и `prepare_for_fts_query` в
`parser/sanitize_text.py` — готовит строку лемм для `to_tsquery('simple', …)`.
Выбрать одно и обосновать; помнить, что оператор ищет по человеческому названию,
а не по нормализованному.

### 6.5. Размер очереди Review

На реальной смете первый импорт создаёт **~1100** TO_REVIEW-строк разом. Экран
обязан это выдержать: пагинация серверная, фильтр по единице/тексту, сортировка
по числу ссылающихся позиций (сначала самые «тяжёлые» работы — их разбор даёт
наибольший прирост метрики §10). Решить, нужны ли пакетные действия
(«пометить выбранные как TRASH») — это резко ускоряет первичный разбор, но
усложняет UI и требует пакетного эндпоинта.

### 6.6. Валидация алиасов единиц

Долг фазы 4 (`docs/phase4-import.md` §12.2.1): добавление алиаса, чья
нормализованная форма занята другой единицей, должно отклоняться **на входе**.
Сейчас дефект справочника только гасится при чтении (`UnitResolver` не применяет
конфликтующую форму и логирует). §7 экрана единиц не предусматривает. Решить:
делать ли CRUD единиц в фазе 5 (тогда с валидацией) или отложить, оставив
только серверную защиту чтения. Рекомендация: отложить, записав долг явно.

## 7. Известные грабли

**Backend:**

- `baseURL` axios-клиента — `"/api"`, а эндпоинты фазы 4 живут на `/api/v1/…`.

  `/api`.
- `DecimalJSONResponse` (main.py) умеет `Decimal → строка`, но **не умеет

  в ответах приводить к ISO явно, как это делает `routers/estimates.job_response`.
- Деньги — `Decimal` end-to-end, в JSON строками (§3). В тестах сравнивать
  `Decimal` с `Decimal`, без `pytest.approx`.

  констрейнта и отдавать 400 с человеческим текстом (§7.3), как это сделано для

- Роли проверяются зависимостью `require_admin` (`auth.py`), CSRF — middleware
  плюс `require_csrf`; для новых POST/PATCH/DELETE ничего вручную не нужно.
- `caplog` в проекте **ненадёжен** (`setup_logging()` чистит root-хендлеры) —
  ловить логи собственным хендлером, образец:
  `tests/integration/test_unit_resolution.py::captured_warnings`.
- Тесты, которым нужны настоящие коммиты (пайплайн, конкуренция), используют

## 10. Процесс

Как в фазах 0–4: коммиты по шагам (§4), остановка после фазы, итоговый отчёт по
образцу `docs/phase4-import.md`. Пользователь прогоняет внешнее ревью; замечания
проверять по фактам, а не принимать на веру.

Реальные данные из `samples/` — **никуда**: ни в код, ни в доки, ни в сообщения
коммитов, включая суммы (политика `docs/phase0-input-data.md`).

**Правило, выстраданное фазой 4** (`docs/phase4-import.md` §12.4, §13.1): тест,
который якобы доказывает защиту — от гонки, от потери ресурса, от попадания мимо
индекса, — обязан быть проверен **снятием защиты**: временно откатить правку,
убедиться, что тест падает, вернуть. Дважды за фазу тесты проходили по чужой
причине. И помнить продолжение: снятие защиты доказывает только тот путь, который
тест исполняет.

При противоречии этого документа с `AGENTS.md` побеждает `AGENTS.md` — и об этом
надо сказать вслух.
