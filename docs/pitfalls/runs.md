**Когда читать:** запускаешь тесты, линтеры и инструменты (`npx`, `pytest`, `vitest`, `tsc`) или пишешь файлы из Python.

- **`npx tsc --noEmit` во фронтенде проверяет НОЛЬ файлов.** `frontend/tsconfig.json` —
  references-only (`"files": []`), поэтому голому вызову компилировать нечего: замерено
  `--listFiles` — 0 строк против 1346 у `-p tsconfig.app.json`. Шаг проверки типов в такой
  форме пуст и на фиче разноса спрятал настоящую ошибку компиляции. Гонять `npx tsc -b
  --force`; `just ci` использует `tsc -b --noEmit` и слепым не был — слепыми были ручные
  прогоны.
- **`npx vitest` из КОРНЯ репозитория поднимает другой vitest.** В корне лежит своя
  установка (4.1.10 против 4.1.6 во `frontend/`), она не разрешает алиас `@/`, и весь
  набор падает на сборке с «Cannot find package '@/components/ui/button'», печатая
  «Tests no tests». Выглядит в точности как сломанный импорт в проверяемом коде. Гонять
  только из `frontend/`.
- **Случайный `npx <инструмент>` из каталога БЕЗ этого инструмента уносит
  `node_modules/.bin` соседнего проекта.** Один вызов `npx tsc` из корня
  репозитория (TypeScript стоит только во `frontend/`) заставил npm поставить из
  реестра пакет-обманку `tsc@2.0.4` — заглушку с сообщением «This is not the tsc
  command you are looking for», — и установка снесла `frontend/node_modules/.bin`
  целиком. После этого `npx` В ПРАВИЛЬНОМ КАТАЛОГЕ начал тянуть инструменты из
  реестра вместо локальных: `npx vitest --version` дал `4.1.11` вместо проектных
  `4.1.6`. Это опаснее двух граблей выше: там неверный каталог виден в самой
  команде, здесь каталог верный, и подмена не видна вовсе — прогон просто идёт
  другой установкой. Признак: строка `npm warn exec The following package was not
  found and will be installed`. Увидел её у `npx tsc`/`npx vitest` — локальной
  установки не нашли, и прогону нельзя верить ни в какую сторону. Лечится `npm
  install` в каталоге проекта (`npm ci` на этой машине упирается в занятый файл).
- **Перезапись файла целиком из Python переводит его в LF, и `git status`
  считает файл изменённым при пустом `git diff`.** Рабочее дерево здесь CRLF.
  Само расхождение безобидно, опасна его непрозрачность: `snapshot_parse_samples.py`
  пишет в манифест флаг `dirty`, читая `git status --porcelain -- backend/parser`,
  а `compare_parse_snapshots.py` отказывается сравнивать снимок с `dirty=true`.
  Проверка происхождения при этом срабатывает ПРАВИЛЬНО — она честно отказывает,
  — но причина отказа выглядит необъяснимой: файл «изменён», хотя diff пуст.
  Правки в существующих файлах вносить точечным редактированием, а не
  перезаписью; увидел отказ по `dirty` при пустом `git diff` — смотри на
  окончания строк.
- **Дата внутри ZIP имеет гранулярность 2 секунды, поэтому «тот же файл» из
  тестового помощника два раза подряд — это РАЗНЫЕ байты и разный sha256.**
  `zipfile.writestr(str, ...)` штампует запись текущим временем, а формат DOS
  внутри ZIP хранит его с точностью до двух секунд. Помощник, собирающий
  «тот же» xlsx по одному и тому же маркеру, даёт совпадающие байты, только
  пока оба вызова укладываются в одно двухсекундное окно. Замер: тест
  идемпотентности загрузки раунда («тот же файл — тот же sha, ответ 200»)
  падал ТОЛЬКО на полном прогоне и проходил на своём файле в одиночку — под
  нагрузкой разрыв между двумя вызовами регулярно превышал порог. Ни одно
  подмножество набора его не воспроизводило, потому что течи между тестами не
  было вовсе: подводил сам помощник. Две правдоподобные гипотезы (незаметённые
  таблицы в списке TRUNCATE и незакрытый патч модуля) стоили полутора часов и
  обе оказались неверны. Лечится `ZipInfo` с фиксированной `date_time`.
  Правило шире ZIP: **если тест зависит от ТОЖДЕСТВА порождённого файла, у
  порождающей функции не должно быть источника недетерминизма** — ни часов, ни
  случайности, ни порядка словаря. И проверять такую правку надо в обе стороны:
  одинаковый вход обязан дать одинаковые байты, а РАЗНЫЙ — разные, иначе
  детерминизм куплен ценой того, что помощник перестал различать входы.
- **Два прогона pytest против одной тестовой БД одновременно портят оба.**
  Схема пересоздаётся на сессию, и второй процесс сносит её из-под первого:
  падения расходятся по несвязанным файлам, а время растёт в разы. Замер:
  полный интеграционный набор, запущенный параллельно с агентом, который тоже
  трогал базу, дал 14 падений и 34 минуты вместо 6,5. Признак — падения в
  файлах, которых правка не касалась. Прогон против `gca_test` — один за раз.
- **Вывод дочернего процесса на Windows приходит с CRLF, и якорь `$` в разборе
  молча перестаёт совпадать.** `subprocess.run(..., capture_output=True)` отдаёт
  байты как есть, а `re.search(r"^Лишних: (\d+)$", out, re.MULTILINE)` требует,
  чтобы за цифрой сразу шёл `\n`: `\r` перед ним совпадение ломает. Замерено на
  обвязке снятий фичи §11 — не разобралось НИ ОДНОГО счётчика из пяти. Спасло
  только то, что обвязка обязана требовать разбора и падать, если его нет
  (`docs/insights/verifying-guards.md`): иначе все мутанты отрапортовались бы
  убитыми, потому что «счётчик не найден» неотличим от «счётчик нулевой».
  Лечится `.replace("\r\n", "\n")` сразу после `decode("utf-8")`.
- **Строка команды, отданная Bash-инструменту, теряет УДВОЕННЫЕ обратные слэши
  ДО того, как её увидит шелл: `\\` приезжает как `\`.** Одиночный слэш цел,
  поэтому регулярки вроде `r"\d+"` работают, и дефект вылезает только там, где
  слэш нужен ПАРОЙ: `"\\r\\n"` в патч-скрипте становится литералом с НАСТОЯЩИМ
  переводом строки внутри, то есть синтаксически битым Python.

  Границу надо знать точно, иначе лечат не то. **Heredoc и Git Bash здесь ни при
  чём.** Замер без python и без внешних кавычек — один `cat <<'EOF'` с телом
  `a\nb` / `a\\nb` / `a\\\\nb`: тот же heredoc, положенный В ФАЙЛ и запущенный
  `bash файл.sh`, печатает тело байт-в-байт, а отданный строкой команды печатает
  `a\nb` / `a\nb` / `a\\nb`. Значит, преобразование происходит в ДОСТАВКЕ строки
  команды, а не в разборе heredoc'а, и кавычки `<<'EOF'` от него не защищают,
  потому что защищать нечего — шелл получает уже изменённый текст. Через
  PowerShell-инструмент той же потери нет.

  Отсюда правило: правки кода и любые тексты с экранированием подавать ФАЙЛОМ
  (записать файл, затем `python файл.py` / `bash файл.sh`), а не строкой
  команды. Если файл почему-то нельзя — проверить доехавшее печатью `repr()`
  перед тем, как что-то этим текстом править.
- **Код возврата после конвейера принадлежит последней команде, а не проверке.**
  `just check-agents-index | grep Итог` и `python verify_move.py | tail -3`
  печатают то, что нужно, и возвращают ноль даже когда сама проверка упала:
  выход берётся у `grep`/`tail`. Гейт, поставленный так, зеленеет всегда.
  Замер: на фиче «история наружу» я прогнал разовый сверщик через `| tail -3`,
  увидел «код: 0» и объявил переезд сверенным — при том что сверщик вернул 1 и
  назвал шесть лишних единиц. Разошлось на первом же прогоне без конвейера. В
  фиче §11 та же грабля стоила записи «код возврата 1 здесь ожидаем», после
  которой вердикт скрипта перестал что-либо означать. Правило: **команду,
  чей код возврата и есть предмет, запускать без конвейера** — вывод при
  необходимости писать в файл и читать отдельно (`cmd > out.txt; echo $?`).
