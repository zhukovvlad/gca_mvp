**Когда читать:** трогаешь домен и приложение бэкенда: деньги на `Decimal`, схемы Pydantic, знаки и направления величин, конфигурацию uvicorn.

- Деньги: Decimal end-to-end; в JSON — строки; в тестах сравнивать Decimal с Decimal.
- **Pydantic ключует `field_validator`-ы по имени метода.** Два миксина с
  одноимёнными валидаторами схлопываются в **один** слот: побеждает первый по
  MRO, второй исчезает молча — защита читается как живая, будучи мёртвой.
  Замерено в Ф5 фазы 7: схема, наследующая `_MoneyMixin` и `_PercentMixin`, где
  оба метода назывались `_reject_float`, отвергала `float` в сумме договора и
  **принимала** его в проценте условия. Имена методов-валидаторов обязаны быть
  уникальными по всему дереву наследования схемы; проверяется прогоном по
  конкретному входу, а не чтением — по коду оба валидатора выглядят живыми.
- Один uvicorn worker — не «дефолт, который можно поменять», а условие корректности recovery; при переходе на несколько workers понадобится лизинг jobs (за скоупом MVP).
- **`Decimal.//` усекает частное К НУЛЮ, а не вниз, поэтому «потолок» через
  `-(-a // b)` ЗАНИЖАЕТСЯ.** Приём верен для `int`, где `//` округляет вниз, и
  неверен для `Decimal`: на отрицательном делимом усечение к нулю и округление
  вниз расходятся. Замер: `205 879` при шаге `50 000` дало 4 интервала вместо 5,
  верх оси диаграммы оказался НИЖЕ самого высокого столбца, и столбец рисовался
  на 10 % короче собственной подписи — во всех состояниях сразу. Ошибку нашло
  измерение высот, а не проверка глазами: картинка выглядела правдоподобной.
  Потолок писать явным сравнением (`n = floor(a / b)`, затем `+1`, если
  `b * n < a`), а у любой «вмещающей» величины держать проверку вида
  `assert max(pool) <= top` — она ловит целый класс ошибок округления, а не эту
  одну.
- **Минус, приклеенный к строке, — не вычитание.** `addDecimalStrings(a, `-${b}`)`
  на отрицательном `b` даёт `--100`, разбор отказывает, функция возвращает `null`,
  и вызывающий получает «не смог посчитать» ровно там, где считать важнее всего.
  Замер: подсказка диаграммы теряла направление приведения и для роста
  (−100 → −80), и для снижения (−100 → −120). Для сравнения есть
  `compareDecimalStrings` — знак там внутри целого `BigInt`, ломаться нечему.
  Отрицательные суммы в проекте хранимы: `position_items.total_cost_total` —
  `Numeric NULL` без `CheckConstraint` снизу.
- **У величины, чей ЗНАК участвует в решении, тест обязан покрыть ОБА знака.** Не
  тот, что стоит на стенде, а оба. Выстрадано дважды в одной строке: правка,
  которая ввела разбор знака, сама же не проверила отрицательный вход, и внешнее
  ревью нашло это вторым кругом по уже исправленному коду. Проверять такое надо и
  снятием «наоборот» — сравнением по модулю: на неотрицательных фикстурах оно
  проходит как верное.
- **Булево на направление — это два состояния там, где достижимо три.** Множитель
  ровно 1, дельта ровно 0, разность ровно 0 — законные состояния, и в
  `down: boolean` им места нет: всё, что «не down», красится и подписывается как
  рост. Замер: чип печатал нейтральное «поправка 0,0%» жёлтым тоном роста, тогда
  как подсказка на тех же данных уже говорила нейтральное «Приведено». Различитель
  — строка (`"up" | "down" | "flat"`), а не второй флаг: два булева умеют
  оказаться в невозможной паре. И проверять надо в обе стороны: третье состояние
  не должно съесть два первых.
