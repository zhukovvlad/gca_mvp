## 1. Что случилось и зачем фаза

Фазы 0–6 формально закрыты: тесты зелёные, DoD выполнен, три круга внешнего ревью
пройдены. Но пользователь посмотрел на результат и сказал прямо: **паспорт,
матрица и отчёты в текущем виде не устраивают**.

Корень — в гранулярности, и его важно понять до любого кода. MVP построил всю
аналитику вокруг **каталожных позиций** (атомов): паспорт = топ-15 позиций сметы,
матрица = 1932 работы × договоры, нормативы = ставка на работу. А бизнес мыслит
**иерархическим классификатором видов работ** (крупные статьи: котлован, монолит,
фасад, отделка МОП, инженерка…) и **удельными показателями — руб/м² от ТЭП**.
Уровень MVP — торг по конкретной расценке; уровень, который нужен, — анализ
стоимости проекта. Примечательно, что `AGENTS.md` §1.1 всегда говорил «по объектам
и **крупным статьям**» — статьи в MVP потерялись.

Фундамент не выброшен: позиции смет, детерминированный парсер, матчинг, каталог —
это сырьё, из которого статьи **агрегируются**.

## 2. Образец

`samples/260429_*.xlsx` («Анализ стоимости ДГП») — упрощённый паспорт проекта от
пользователя. **Наш должен быть «немного другим, но суть такая же»** (формулировка
пользователя; что именно «немного другим» — выяснять по ходу, не досочинять).

Структура образца (лист «Проекты» — паспорт одного проекта):

1. **Шапка с ТЭП:** проект, год подписания договора, предполагаемая сдача (РНВ),
   класс здания, генподрядчик; площади — подземная / надземная / общая / полезная.
2. **Свод стоимости:** базовый ДГП + доп. соглашения (раздельно **подписанные** и
   **на рассмотрении МРГ**), везде две колонки — «Общая стоимость» и **«Стоимость
   за м²»** (делитель — общая площадь из ТЭП). Ниже — крупные блоки (СМР,
   Монолит+МК, Фасад, Отделка МОП, Благоустройство, ВИС, РД, MR Base, MR Ready,
   нулевой цикл) и коммерческие условия (аванс %, банковская гарантия %,
   гарантийное удержание).
3. **Главная таблица — иерархический классификатор видов работ**, ~100 строк в
   3 уровня (`5 → 5.2 → 5.2.1`): разработка стадии Р, подготовительные работы,
   котлован (сваи/земляные/ограждение/водопонижение), гидроизоляция подземной
   части, монолит+МК, перегородки и стены, фасад (СПК/НВФ/СОФ), кровли, отделка
   МОП/двери/ворота, лифты, инженерные системы (механика 7 подсистем,
   электрика/слаботочка 8 подсистем), благоустройство, технологические решения,
   другие. Колонки: № | вид работ | **объём** | стоимость за ед. | ГП/базовый
   договор | ДС подписанные | предполагаемые удорожания | итого | **руб/м²**.
4. **Натуральные показатели:** расход арматуры кг/м³, бетон м³ и руб/м³, S фасада
   и руб/м² фасада, цены ресурсов, курсы валют.

Скрытый лист «Сводная» — сравнение **нескольких проектов бок о бок** по тем же
крупным статьям с руб/м². Это и есть целевая «матрица»: проекты колонками, статьи
строками — не каталожные работы.

**Политика samples/ прежняя и строгая:** файл не коммитить, реальные данные
(суммы, названия ЖК, имена контрагентов из скрытых листов) — никуда, включая доки
и сообщения коммитов.

## 3. Решения пользователя (зафиксированы, не пересматривать молча)

1. **Классификатор везде более-менее одинаков** → фиксированный справочник
   компании (иерархия ~3 уровня, коды как в образце).
2. **Привязка позиций → статьи через каталожные работы — ОТЛОЖЕНА.** Не строить.
3. **MR Base / MR Ready / РД / нулевой цикл — блоки внутри ДГП**, т.е.
   верхнеуровневые статьи того же классификатора, а не отдельные сущности.
4. **Старые экраны (паспорт/матрица/отчёты фазы 6) не выкидывать — просто
   убрать.** Скрыть из навигации; код, эндпоинты и тесты живут. Позже могут
   вернуться «нижним этажом» (drill-down из статьи в расценки).
5. **Ключевые объёмы по разделам добывает LLM** — механизм из
   `parser_tender_xlsx`, но осовремененный (см. §4).

## 4. LLM-механизм: что согласовано точно

Референс — `C:\Users\zhukov_v\Projects\_gca_sources\parser_tender_xlsx`:
`app/gemini_module/` (TenderProcessor: ретраи на 429 с jitter, промпты по
категориям из `constants.py` — `pit_specs`, `slurry_wall_specs`,
`sheet_pile_wall_specs`, `strut_system_specs`, «Отделка») и
`app/markdown_utils/` (`json_to_markdown`, `positions_report` — MD генерировался
из уже РАСПАРСЕННОГО JSON, не из сырого файла).

Как это работало там: в LLM передавался **текстовый MD с видами работ и
объёмами, БЕЗ денег, на всю смету целиком**; модель извлекала ключевые параметры.

Как делаем здесь (уточнения согласованы с пользователем):

- **Вход** — MD-выжимка **одного раздела** сметы (не всей): наименования работ,
  единицы, количества. **Денег во входе нет вообще.** Генерируется из
  `position_items` (иерархия разделов уже в БД: `is_chapter`,
  `chapter_number_in_proposal`, `chapter_ref_in_proposal`) — переносить
  `markdown_utils` не нужно.
- **Задача LLM — семантическая**: из десятков строк раздела понять, какие и есть
  «ключевой объём», и вернуть его. Условно: «Монолит» → бетон м³, арматура т;
  «Фасад» → S м² по типам (СПК/НВФ); «Котлован» → выемка м³, сваи шт.
  Детерминированный код эту задачу не решает — потому и LLM.
- **Деньги в LLM-контур не попадают в принципе.** Суммы по разделам/статьям —
  SQL-агрегация `position_items` (§3 AGENTS: Decimal end-to-end — не трогается).
- **Чанкование по разделам** — маленькие промпты: точнее (модель не теряется в
  2576 строках), дешевле, ошибка локализована одним разделом.
- **Транспорт — OpenRouter** (не прямой Gemini SDK, как в исходнике):
  `response_format` с JSON-схемой + `require_parameters: true`; ZDR-политика и
  ограничение провайдеров без обучения на данных (сметы коммерческие); ключ —
  в `.env`/настройках.
- **Формат выхода — фиксированная схема показателей на статью классификатора**
  (как категории в старом `constants.py`): сводная сравнивает проекты, и
  сравнивать можно только одинаковые показатели; свободный список «что нашла
  модель» несравним. **Черновик набора показателей на статью предлагает агент**
  (по образцу и по содержимому реальных смет), пользователь правит — договорённость
  последнего обмена.
- Результат разметки — с **версией промпта+модели** (аналог `norm_version`;
  смена модели = осознанный перевыпуск, не тихий дрейф), с кэшем (повторная
  загрузка сметы LLM не дёргает) и с **очередью подтверждения** (паттерн Review
  готов). Обязательна статья/корзина «Прочее/нераспределённое» — видимая, не
  размазанная.

**Модели (рекомендация агента, знание на май 2026 — свериться с актуальным прайсом
OpenRouter перед стартом):** рабочая — `anthropic/claude-sonnet-5`; дешёвый
массовый тир — `anthropic/claude-haiku-4.5` или `google/gemini-3-flash`;
арбитр для сложных случаев — `anthropic/claude-opus-5` или
`google/gemini-3-pro`. Схема «дешёвая модель + эскалация к арбитру при низкой
уверенности». **Выбор подтвердить замером на трёх реальных офертах** (они в
`samples/`, точные объёмы для eval уже есть в БД из детерминированного парсера) —
по образцу замера §6.3 фазы 6: решение фактами, не вкусом.

## 7. Процесс

Как в фазах 0–6: решения записывать с обоснованием; коммиты по шагам; **прогон на
живом стенде с реальными сметами — часть DoD, планировать после первого
работающего экрана** (фаза 6 нашла живьём пять дефектов, которых не поймал ни
один тест, — на LLM-контуре это будет ещё важнее); правило проверки защит — три
слоя (§10 брифинга фазы 6: снятие защиты, `assert` факта снятия, команды в форме
CI по отдельности); внешнее ревью пользователь прогоняет сам — замечания
проверять по фактам, тестом до правки.

Для LLM-контура к DoD добавится своё: детерминированные тесты без сети (LLM-клиент
мокается), отдельный eval-прогон на реальных офертах с записанными ответами,
замер стоимости запроса на смету.
