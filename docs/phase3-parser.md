# Фаза 3 — парсер: что перенесено, что изменено, что замерено

Результат фазы 3 (AGENTS.md §9). Документ фиксирует отступления
`backend/parser/` от исходника `parser_tender_xlsx@0e178c097d80`, замеры, на
которых эти отступления основаны, и оставшиеся риски.

Порядок работ был задан `docs/phase3-start.md` §4: сначала прогон исходного
парсера как есть, потом адаптация. Ниже — результаты этого прогона и то, что
из них следует.

## 1. Прогон исходного парсера «как есть» (шаг 3 брифинга)

Исходный `app/excel_parser/` запущен без единой правки на обезличенном fixture
и на реальном образце из `samples/`.

| | fixture | реальный образец |
|---|---|---|
| `load_workbook(data_only=True)` | 2,2 с | 2,9 с |
| `ws.max_row` / `ws.max_column` | 2600 / 24 | 2600 / **16384** |
| объединённых диапазонов | 2613 | 2613 |
| `read_headers` | 0,01 с | 0,20 с |
| `read_contractors` | 0,03 с | 0,09 с |
| `read_lots_and_boundaries` | **207,7 с** | не дождались (оценка 4–5 мин) |

Выявлено четыре дефекта. Три из них — расхождение допущений исходника с
раскладкой сметы ГП, четвёртый — производительность.

### 1.1. Шапка терялась целиком (`tender_id`, `tender_title`)

`read_headers` сканировал строки 3–5. В смете ГП шапка на строку выше:
«Предмет тендера» в строке 2, «Объект» в 3, «Адрес объекта» в 4. Объект и адрес
попадали в диапазон случайно, а предмет тендера — нет:

```
tender_id    = None
tender_title = None
```

Одинаково на обоих файлах.

### 1.2. Терялись две первые строки позиций

`get_lot_positions` начинал обход с `max(START_INDEXING_POSITION_ROW=13,
lot_start_row)`. Лот в смете ГП начинается со строки 11, поэтому константа
съедала строки 11 и 12 — строку-раздел лота и первый раздел сметы.
Исходник давал **2574** позиции вместо 2576.

Граница лота найдена по реальному маркеру «Лот №» в колонке D, а константа —
угадана под другой формат файла. Авторитетна граница лота, константа убрана.

### 1.3. Стоимость проверок: 207 секунд на fixture

Два места обходили лист несоразмерно объёму данных:

* признак «ячейка колонки A объединена» (досрочный выход из блока позиций,
  AGENTS.md §11) вычислялся **линейным перебором всех 2613 объединённых
  диапазонов на каждой из ~2576 строк** — 6,7 млн проверок вхождения, замерено
  4,7 с на сотню строк;
* проверка «строка пустая» бралась как `all(... for cell in ws[row])`, а `ws[row]`
  разворачивается до `ws.max_column`.

На реальном файле второе особенно дорого: `max_column` там 16384 (фаза 0),
и openpyxl материализовал бы по 16 тыс. объектов ячеек на строку — 0,061 с на
строку, около 157 с только на проверки пустоты.

Заметим: фаза 0 нашла только явный `max_col=ws.max_column` в
`read_contractors.py:72` и оценила риск как гипотетический. Неявный `ws[row]`
в `get_lot_positions`, `get_summary` и `get_additional_info` она пропустила —
он и оказался главным.

### 1.4. Что, наоборот, заработало сразу

* **Один подрядчик → одно предложение.** Отдельной ветки не понадобилось:
  `read_contractors` находит маркер «Наименование контрагента» (G6) и ровно один
  заголовок подрядчика (J6), обход с индекса 1 даёт одно `contractor_1`.
* **Отсутствие baseline.** `normalize_lots_json_structure` штатно подставляет
  «Расчетная стоимость отсутствует» и вычищает поля отклонений.
* **Раскладка колонок сошлась точно.** Блок подрядчика J6:T6 — 11 колонок, и
  ветка `colspan == 11` в `parse_contractor_row` описывает ровно ту раскладку,
  которую замерила фаза 0: J — предлагаемое количество, K–N — цена за единицу,
  O–R — стоимость всего, S — стоимость за объёмы заказчика, T — комментарий
  участника.
* **Досрочный выход по merged-ячейке** остановил позиции перед строкой «ИТОГО»,
  и блок «Дополнительная информация» (где в колонке J лежит текст «Представлено»,
  «К обсуждению») в позиции не попал — негативный сценарий фазы 0 закрыт.

## 2. Отступления `backend/parser/` от исходника

### 2.1. Структура

| Исходник | Здесь |
|---|---|
| `app/excel_parser/*` (14 модулей) | `backend/parser/*` |
| `app/constants.py` | `backend/parser/constants.py` (внутрь пакета) |
| `app/parse.py` (оркестратор + Go-сервер + markdown + архивация) | `backend/parser/estimate.py` — только разбор |
| — | `backend/parser/sheet.py` — границы сканирования |
| — | `backend/parser/layout.py` — проверка раскладки колонок |

Пакет самодостаточен: импортов из слоя БД и FastAPI нет. `app/utils/file_validation.py`
не переносился — он завязан на FastAPI `UploadFile` и относится к эндпоинту
загрузки, то есть к фазе 4.

### 2.2. Публичный API пакета сокращён — и это не косметика

Исходный `excel_parser/__init__.py` реэкспортировал все функции. Здесь наружу
выходят только `parse_estimate`, `parse_worksheet`, `ParseResult`,
`EstimateParseError`, `PARSER_VERSION` и функции нормализации.

Причина не в стиле. Почти каждый модуль назван по своей главной функции
(`read_headers.read_headers`, `get_summary.get_summary`, …), и реэкспорт
**затирает атрибут-модуль**: после `from .read_headers import read_headers`
выражение `parser.read_headers` означает функцию, а не модуль. Это ломается
молча — `import parser.read_headers as m; m.sanitize_text` падает с
AttributeError. Шаги разбора берутся полным путём:
`from parser.read_headers import read_headers`.

### 2.3. Изменения логики

| Модуль | Изменение | Основание |
|---|---|---|
| `read_headers` | диапазон 3–5 → 2–5, вынесен в константы | §1.1 |
| `get_lot_positions` | обход от `lot_start_row`, константа `START_INDEXING_POSITION_ROW` убрана | §1.2 |
| `get_summary` | начало поиска итогов передаётся аргументом `search_start_row` (строка начала позиций) вместо той же константы | следствие §1.2: с floor’ом ниже 9 поиск наткнулся бы на объединённую шапку таблицы A9:A10 |
| `get_lot_positions`, `get_summary` | индекс объединённых строк колонки A строится один раз | §1.3 |
| `get_lot_positions`, `get_summary`, `get_additional_info` | пустота строки проверяется в пределах блока подрядчика | §1.3 |
| `read_contractors` | ширина скана ограничена `MAX_HEADER_SCAN_COLUMN = 256` вместо `ws.max_column` | §1.3 |
| `build_merged_shape_map` | карта строится по границам диапазонов, без обхода `ws[coord]` | не материализует ячейки |
| `sanitize_text` | ленивая загрузка модели, отказ вместо тихого фолбэка | §2.4 |
| `parse_contractor_row` | денежные колонки отдаются десятичными строками, не `float` | §2.6 |
| `postprocess` | гасятся все литералы ошибок Excel, не только DIV/0; даты/время переводятся в ISO-строки | §2.6 |
| `read_executer_block` | без изменений | §4.1 |

**Расширение диапазона шапки безопасно для тендерных таблиц.** При дублировании
ключа побеждает нижняя строка, поэтому шапка в строках 3–5 перекрывает то, что
нашлось в строке 2. Закреплено тестом
`test_read_headers_duplicate_key_uses_last_one`.

**Цена ограничения сканов** — строка, где данные лежат правее блока подрядчика,
считается пустой. Для сметы это верно: читать там нечего. Закреплено тестом
`test_row_with_data_only_right_of_contractor_block_counts_as_empty`.

### 2.4. Нормализация: отказ вместо тихого фолбэка

В исходнике модель spaCy грузилась на import, а при её отсутствии
`normalize_job_title_with_lemmatization` печатала предупреждение и возвращала
**нелемматизированный** текст.

Для GCA это недопустимо. `normalized_job_title` — идентичность работы в каталоге
(AGENTS.md §4), на ней же строится `cache_key` матчинга. Тихая деградация
записала бы в каталог другую строку, и каталог, кэш и матчер разъехались бы
незаметно — ровно то, от чего предостерегает §11.

Поэтому:

* модель грузится **лениво**, при первом вызове (импорт пакета остаётся дешёвым
  — важно для юнит-тестов, не трогающих нормализацию; загрузка стоит ~1,5–3 с);
* отсутствие spaCy или модели — `NormalizationUnavailableError`, а не фолбэк;
* базовая очистка вынесена в `basic_clean_job_title` и тестируется напрямую,
  без подмены флагов;
* результат кэшируется (`lru_cache` по очищенной строке). Кэш безопасен, потому
  что функция чистая; смысл чисто экономический — на реальном образце 2576
  наименований дают 1070 уникальных. Независимость результата от прогретости
  кэша закреплена тестом.

**Версии закреплены точно** — `spacy==3.8.14`, `ru-core-news-sm==3.8.0`. Смена
любой из них меняет результат нормализации, то есть требует инкремента
`norm_version`, миграции перевыпуска ключей `source='manual'` и пересчёта
`catalog_positions.normalized_job_title` (AGENTS.md §11). Это отдельная задача,
а не «обновление зависимости».

Модель ставится обычной зависимостью через `[tool.uv.sources]` (колесо с
GitHub-релиза), а не командой `spacy download`, — чтобы версия попадала в
`uv.lock` и была одинаковой у всех и в CI.

**Уточнение к `docs/phase3-start.md` §3.** Там сказано, что pymorphy3 не
используется. Прямых импортов действительно нет, но `ru_core_news_sm` 3.8.0
объявляет pymorphy3 своей зависимостью — русский лемматизатор spaCy работает
через него. Так что pymorphy3 в окружении есть и он «реально используемый»
в смысле §11; natasha и razdel — нет.

### 2.5. Новое: проверка раскладки колонок (`layout.py`)

Парсер определяет смысл колонок подрядчика **по ширине его объединённого блока**,
а не по тексту заголовков. Пока файл выглядит как замеренный — всё верно; если
раскладка поедет, та же ячейка молча начнёт читаться как другое поле.

Опаснее всего первая колонка блока — `suggested_quantity`: на ней держится вес
позиции в средневзвешенной ставке (AGENTS.md §6), то есть вся сквозная матрица.
Поэтому `check_estimate_layout` сверяет: один подрядчик, ширина блока 11,
заголовок первой колонки блока — «Предлагаемое количество», один лот.
Расхождения возвращаются в `ParseResult.warnings` и в фазе 4 лягут в
`import_jobs.warnings` (AGENTS.md §5) — они не блокируют импорт, но видны
человеку.

Это и есть механизм отслеживания главного непокрытого риска — вариативности
шапки (один образец, `docs/phase0-input-data.md`).

Константа заголовка написана по реальному тексту файла — «**Предлагаемое**
количество», не «Предполагаемое» (AGENTS.md §4).

**Где проходит граница между предупреждением и отказом.** Предупреждение
обещает импорт, поэтому его нельзя выдавать там, где импорта не будет. Смысл
колонок задаётся шириной блока, и раскладка известна только для ширин 8, 9, 10
и 11 (`parse_contractor_row.SUPPORTED_CONTRACTOR_COLSPANS`):

* ширина известна, но не 11 — файл разбирается, расхождение уходит
  предупреждением. Например, при colspan 8/9 колонки «Предлагаемое количество»
  нет вовсе, и весом позиции станет `quantity` через `COALESCE` (AGENTS.md §6);
* ширина неизвестна (или заголовок подрядчика вообще не объединён с колонками
  своего блока) — `EstimateParseError` из `estimate._validate_contractor_blocks`,
  до начала разбора. Разбирать блок неизвестной ширины нечем: стоимости молча
  легли бы не в те поля.

Раньше второй случай кончался необработанным `ValueError` из
`parse_contractor_row` (а необъединённый заголовок — `KeyError` по
`merged_shape`): `ParseResult` не создавался, и сформированное
`check_estimate_layout` предупреждение до `import_jobs.warnings` не доезжало.
Закреплено тестами `test_raises_on_unsupported_contractor_colspan`,
`test_raises_when_contractor_header_is_not_merged` и
`test_supported_but_non_gp_colspan_is_a_warning_not_an_error`.

### 2.6. Деньги: десятичные строки, ни одного `float`

`openpyxl` отдаёт числовую ячейку как `float`, а AGENTS.md §3 и §11 требуют
`numeric` в БД ↔ `Decimal` в Python ↔ **строки в JSON**, без `float`. Результат
парсера — не промежуточное представление: это JSON, который ложится в
`estimate_raw_data.raw_data`. Поэтому конвертация делается на границе чтения
файла, в `parse_contractor_row.money_to_json`.

Дело не только в букве контракта. Получив `float`, импорт фазы 4 естественным
образом сделал бы `Decimal(14998746.74)` — а это
`Decimal("14998746.74000000022351741790771484375")`. Преобразование через
`str()` берёт кратчайшее представление double, которое round-trip'ится точно.

| | значение |
|---|---|
| в ячейке | `14998746.74` (`float`) |
| в `raw_data` | `"14998746.74"` |
| в фазе 4 | `Decimal("14998746.74")` — простым `Decimal(value)` |

Границы правила:

* строками отдаются только деньги — `unit_cost.*`, `total_cost.*`,
  `total_cost_for_organizer_quantity` (набор зафиксирован в
  `parse_contractor_row.MONEY_KEYS`); блок итогов идёт через ту же функцию;
* **количества остаются числами** — `quantity` и `suggested_quantity`
  под требование §3 не подпадают;
* пустая ячейка → `null`, не `0` (AGENTS.md §3); `nan`/`inf` и `bool` тоже
  `null` — ни то, ни другое не сумма, а `Decimal(True)` дал бы 1 тихо;
* **все литералы ошибок Excel** (`#DIV/0!`, `#N/A`, `#REF!`, `#VALUE!`, …) →
  `null`: `postprocess.replace_excel_errors_with_null` (расширение исходного
  `replace_div0_with_null`, который знал только деление на ноль). После
  перевода денег в строки фаза 4 не отличила бы `#REF!` от суммы по типу;
* **даты и время** (`datetime`/`date`/`time`/`timedelta` — openpyxl отдаёт
  date-форматированные ячейки объектами) → ISO-строки:
  `postprocess.stringify_temporal_values`. Без этого `json.dumps` падал бы
  на первом же файле с датой в комментарии;
* прочий нечисловой мусор в денежной колонке (произвольный текст) проходит
  как есть — raw_data архивен; валидация сумм остаётся на фазе 4, и
  `Decimal(value)` на таком значении упадёт громко.

`ParseResult.data` при этом остаётся напрямую сериализуемым в `jsonb`: своего
энкодера фазе 4 не нужно. Обратная сторона — SQL-анализ по `raw_data` требует
`::numeric`; для архивного слоя это приемлемо, доменные суммы живут в
`position_items`.

Смежное следствие для нормализации: фактическую лемматизацию выполняют
pymorphy3 и его словари, поэтому в `pyproject.toml` точно запинены и они
(`pymorphy3==2.0.6`, `pymorphy3-dicts-ru==2.4.417150.4580142`), а не только
spacy и модель, — иначе `uv lock --upgrade` молча менял бы
`normalized_job_title` при нетронутых пинах spacy (граница «смена версии =
инкремент `norm_version`» из §2.4 включает словари).

Тесты денежного контракта — `test_parse_contractor_row.py::TestMoneyToJson` и
`test_estimate.py::TestMoneyContract`; сравнения стоимостей в тестах ведутся в
`Decimal`, без `pytest.approx` (AGENTS.md §11).

### 2.7. Оркестратор и контракт с фазой 4

`parse_estimate(source) -> ParseResult` возвращает:

* `data` — полная JSON-структура для `estimate_raw_data.raw_data`, деньги в ней
  десятичными строками (§2.6);
* `parser_version` — для `estimate_raw_data.parser_version` (сейчас `"1.0.0"`);
* `warnings` — список строк для `import_jobs.warnings`.

`PARSER_VERSION` — это **не** `norm_version` из AGENTS.md §4: версия
нормализации живёт отдельно и вводится в фазе 4 вместе с матчингом, потому что
её инкремент требует миграции.

Структурно непригодный файл поднимает `EstimateParseError` с внятной причиной
(нет строки заголовков контрагентов / нет самого подрядчика / нет маркера лота).
Всё, что читается с оговорками, читается и попадает в `warnings`.

Оставшиеся ~19 с — почти целиком лемматизация 1070 уникальных наименований.

## 4. Что осталось незакрытым

### 4.1. `data_prepared_on_date` в смете ГП всегда NULL

Блок исполнителя (`Исполнитель:` / `Телефон:` / `Дата составления:`) —
источник `estimates.data_prepared_on_date` (AGENTS.md §4). **В полученном
образце его нет**: проверено и на реальном файле, и на fixture, все три поля
пустые. Ниже блока позиций идут только итоги и «Дополнительная информация».

Следствие: датой сравнения с нормативом станет `contracts.signed_date` —
штатный фолбэк §4, который именно поэтому и требует `signed_date NOT NULL`.
Схема к этому готова, но стоит понимать, что фолбэк будет не исключением,
а нормой.

`read_executer_block` намеренно перенесён без изменений: расширять окно поиска
не на чем — файлов с этим блоком у нас пока нет.

### 4.2. Один образец

Всё выше замерено на одном реальном файле (ограничение фазы 0). До пилотной
приёмки парсера нужны ещё 1–2 сметы других объектов и лет. Пока их нет,
раскладку сторожит `check_estimate_layout` (§2.5).

### 4.3. Протухшие тесты исходника

`app/tests/excel_parser/test_get_items_dict.py` на зафиксированной ревизии
описывает более раннюю версию кода: валидный `colspan 12` и поле
`deviation_from_baseline_cost` у colspan 9/10/11. Фактический код исходника так
себя не ведёт — эти тесты в исходном репозитории падали. При переносе они
приведены к реальному поведению; проверяемые свойства сохранены, плюс добавлен
тест `test_template_matches_parse_contractor_row_keys`, который ловит именно
такое расхождение шаблона и разбора строки.

### 4.4. Побочная находка: `fileConfig` в Alembic гасил логгеры приложения

`alembic/env.py` вызывал `fileConfig(config.config_file_name)`, а он по
умолчанию отключает все логгеры, созданные до вызова и не перечисленные в
`alembic.ini`, — то есть все логгеры backend. Когда Alembic исполняется в том же
процессе (conftest накатывает миграции один раз на сессию тестов), приложение
после этого замолкает до конца процесса.

Обнаружено на тесте, который проверял предупреждение `annotate_structure_fields`:
он проходил в одиночку и падал в полном прогоне. Добавлен
`disable_existing_loggers=False`.

Второй, независимый источник той же проблемы — `logging_config.setup_logging()`
делает `root.handlers.clear()` и сносит хендлер фикстуры `caplog`. Это не
трогали (правка меняла бы логгирование всего приложения, а это за скоупом фазы
3), но знать стоит: **`caplog` в этом проекте ненадёжен**, если в прогоне
участвуют тесты, импортирующие `main`. Тест парсера ловит лог собственным
хендлером.

### 4.5. Решения, отложенные на фазу 4 (по итогам внутреннего ревью)

* **Несколько подрядчиков.** Парсер разберёт каждый блок (`contractor_1..N`) и
  предупредит, но AGENTS.md §4 фиксирует «ровно одно proposal на лот». Что
  делать со вторым блоком — импортировать оба или отвергать файл — решить до
  написания импорта; текст предупреждения в `layout.py` сознательно не обещает
  ни того, ни другого. Смежный side effect: любая непустая необъединённая
  ячейка в строке заголовков правее маркера считается «подрядчиком» и роняет
  файл с `EstimateParseError` (координата в сообщении есть; исходник на таком
  файле тоже падал).
* **Формулы без кэша.** `data_only=True` читает кэшированные значения формул;
  файл, сохранённый без пересчёта (например, сгенерированный библиотекой), даст
  смету со сплошными NULL-стоимостями и нулём предупреждений. Дёшево ловится
  эвристикой «непустые позиции при полностью пустых деньгах → warning» — на
  парсере или на импорте.
* **Скрытый первый лист.** `_select_worksheet` берёт `wb.sheetnames[0]`, не
  проверяя видимость; книга со скрытым служебным первым листом распарсится не
  оттуда (предупреждение о нескольких листах при этом будет). При появлении
  таких файлов — брать первый видимый.
