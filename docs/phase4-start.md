3. **Go делал UPSERT повсюду** (повторная загрузка обновляла тендер на месте).
   У нас повторная загрузка регулируется правилами §5 (идемпотентность по
   sha256 / 409 / replace с удалением старой сметы) — внутри транзакции
   импорта достаточно **INSERT**: смета либо новая, либо только что удалена
   replace-ом.
4. **Baseline-предложение не импортируется.** Парсер всегда отдаёт
   `baseline_proposal` с заглушкой «Расчетная стоимость отсутствует»

   ровно одно предложение на лот. Если title baseline-а вдруг НЕ заглушка —
   это неожиданный формат: warning, baseline всё равно не импортировать
   (колонка `proposals.is_baseline` существует для будущего возврата тендеров,
   в MVP всегда false).
5. В tenders-go ключ позиции назывался `comment_organazier` (опечатка); наша

## 4. Что делает фаза 4

Дословно из AGENTS.md §9:

> **Импорт+матчинг:** две сессии, транзакция, каскад, recovery,
> идемпотентность, replace-флоу, эндпоинты. Интеграционные тесты, включая:
> повторный импорт того же файла (идемпотентность); другой файл без replace
> (409); replace=true (замена + аудит); два miss с одинаковой нормализованной
> парой (один TO_REVIEW, не конфликт); ручное решение переживает истечение
> auto-TTL; рестарт с зависшим job; смета и `done`-статус коммитятся атомарно
> (симуляция падения между матчингом и финалом не оставляет сметы без
> done-job); слияние TO_REVIEW удаляет строку и не оставляет кэш-записей на
> TO_REVIEW.

Разумный порядок работ:

1. **Хранилище** (§8): `Storage` (save/get/delete) + `LocalStorage`,
   uuid-ключи, путь из настроек; ретенция error-jobs при старте.
2. **Сервис импорта** (порт `ImportFullTender`): чистая функция
   «`ParseResult.data` + `contract_id` → строки БД» в одной транзакции,
   тестируемая без HTTP. Сверка шапки с карточкой → warnings.
3. **Сервис матчинга** (§5 шаг 4): нормализованная пара, cache_key,
   каскад, счётчики. `norm_version = 1` — константа рядом с cache_key.
4. **Оркестратор джоба**: две сессии (A — статусы/warnings, B — домен+done),
   мягкий таймаут, recovery на startup (один uvicorn worker — условие
   корректности, §3).
5. **Эндпоинты**: `POST /api/v1/estimates/upload` (multipart, лимит 25 МБ из
   настроек; право загрузки — `member`, `replace=true` — `admin`),
   `GET /api/v1/import-jobs/{id}` (поллинг статуса),
   `GET /api/v1/import-jobs/{id}/file` (выдача исходника, §8).
6. **Интеграционные тесты** — минимум список §9.4 (выше) плюс хвосты из
   фаз 2–3 (§7 ниже).

Фронтенд-части у фазы 4 нет (загрузка/поллинг — экран «Договоры», фаза 5).

## 5. Контракт парсера (итог фазы 3)

`from parser import parse_estimate, EstimateParseError, PARSER_VERSION`:

- `parse_estimate(source) -> ParseResult(data, parser_version, warnings)`;
  `source` — путь или двоичный поток. Структурно непригодный файл →
  `EstimateParseError` с человекочитаемым сообщением (в `error_text` джоба).
- `data` — готовый JSON для `estimate_raw_data.raw_data`, сериализуется
  `json.dumps` без своего энкодера. `warnings: list[str]` — добавить к
  `import_jobs.warnings`.
- **Деньги в `data` — десятичные строки** (`"14998746.74"`) либо `null`.
  В `Numeric`-колонки: `Decimal(value)` напрямую. Все литералы ошибок Excel
  уже превращены в `null`, даты — в ISO-строки (`docs/phase3-parser.md` §2.6).
- **Количества (`quantity`, `suggested_quantity`) — числа** (int/float).
  ЛОВУШКА: в `Numeric` их конвертировать только как `Decimal(str(v))` —
  `Decimal(float)` даст двоичный хвост, ровно то, от чего §3 защищается.
  Но прежде оглянуться: возможно, правильнее одним движением перевести и
  количества на строки в парсере (решение пользователя от 2026-08-03
  требовало строк только для денег) — тогда импорт станет однороден. Если
  менять контракт — инкремент `PARSER_VERSION` и правка
  `docs/phase3-parser.md` §2.6.
- Структура `data`: `tender_id`, `tender_title`, `tender_object`,
  `tender_address`, `executor` (всегда пустой), `lots.lot_N.{lot_title,
  proposals.contractor_N, baseline_proposal}`; у предложения — `title`,
  `inn`, `address`, `accreditation`, `contractor_width`,
  `contractor_coordinate`, `contractor_items.{positions, summary}`,
  `additional_info`. Ключи позиций — строки «1», «2», …; поля — §4
  (`is_chapter`, `chapter_ref`, `job_title_normalized` уже посчитан парсером).
- `parser_version` → `estimate_raw_data.parser_version`. Это НЕ
  `norm_version`.

## 6. Решения, которые фаза 4 должна принять явно

Зафиксированы в `docs/phase3-parser.md` §4.5; в начале фазы выбрать и
записать в итоговый отчёт (`docs/phase4-import.md`):

1. **Несколько подрядчиков в файле.** Парсер разберёт все блоки с warning, но
   §4 требует ровно одно предложение на лот (и индекс это закрепляет).
   Рекомендация: на импорте отвергать такой файл с внятной ошибкой — «смета ГП
   с несколькими подрядчиками не поддерживается»; молча импортировать первого
   нельзя (какого из них считать договорным — неизвестно).
2. **Формулы без кэша.** Файл, сохранённый без пересчёта, даёт сплошные
   NULL-стоимости и ноль предупреждений. Дешёвая эвристика на импорте:
   «позиции есть, все денежные поля NULL → warning».
3. **Неизвестная единица измерения.** `units_of_measure` + алиасы приехали из
   фазы 1 (там же нормализация, `tests/unit/test_unit_normalization.py`).
   Каскад матчинга требует `unit_norm` — каноническое имя после разрешения
   алиаса, `''` если единицы нет. Что делать с единицей, которой нет ни в
   канонах, ни в алиасах (в реальных файлах видели `m3` латиницей)?
   Варианты: (а) get-or-create новой единицы + warning (так делал tenders-go);
   (б) `unit_id = NULL` + warning. Выбрать и обосновать; помнить, что единица —
   часть идентичности каталожной работы, и тихая порча здесь разъедает каталог.

## 7. Известные грабли (§11 + фазы 2–3)

- **Инвариант «`matching_cache` никогда не ссылается на `kind='TO_REVIEW'`»**
  схемой не выражается — закрепить тестом (условие безопасности DELETE при
  слиянии в Review; `docs/phase2-schema.md` §5).
- `updated_at` обновляется только через ORM — raw-SQL UPDATE метку не тронет.
- Три raw-SQL индекса невидимы для `alembic check` (`RAW_SQL_INDEXES` в
  `alembic/env.py`); их поведение держат интеграционные тесты — не ослаблять.
  Арбитр get-or-create — `uq_catalog_positions_norm_unit`, `ON CONFLICT`
  должен целиться ровно в него.
- Деньги: Decimal end-to-end, в тестах сравнивать Decimal с Decimal (никакого
  `pytest.approx` на деньгах).
- `caplog` в проекте ненадёжен (`setup_logging()` чистит root-хендлеры) —
  ловить логи собственным хендлером, как в тестах парсера.
- Нормализация грузит spaCy лениво (~1,5–3 с при первом вызове) и **отказывает**
  (`NormalizationUnavailableError`) при недоступной модели — матчинг обязан
  дать джобу упасть в `error`, а не деградировать. Версии
  spacy/модели/pymorphy3 запинены точно; их смена = инкремент `norm_version`
  миграция (§11).
- Один uvicorn worker — условие корректности recovery; не «дефолт».
- PG16 обязателен (UNIQUE NULLS NOT DISTINCT); интеграционные тесты гонять
  на локальном кластере 5459, он PG16.
- В `import_jobs.counters` — пять счётчиков §4; метрика DoD (§10) считается
  по ним, не по логам.
