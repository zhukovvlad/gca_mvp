## 4. Что делает фаза 3

Дословно из `AGENTS.md` §9:

> **Парсер:** перенос `excel_parser` → `backend/parser/`, чистка импортов,
> адаптация один-подрядчик-без-baseline, юнит-тесты на fixtures из фазы 0.

Порядок работ, продиктованный §5.2 (главный технический риск — «отсутствие
baseline-блока не должно ронять `read_contractors.py` / детекцию шапки»):

1. Перенос модулей как есть, чистка импортов (`from app.` → относительные или
   `from parser.`), выкинуть неиспользуемое.
2. Перенос юнит-тестов исходника, зелёный прогон — фиксируем, что перенос
   эквивалентен.
3. **Тест на реальном файле ДО адаптации** (§5.2): прогнать парсер на смете ГП
   из `samples/` и на fixture, зафиксировать фактическое поведение (что падает /
   что парсится неверно). Только потом писать адаптацию.
4. Адаптация: один подрядчик → один proposal; нет колонки «Расчётная стоимость»
   (baseline); `suggested_quantity` парсится штатно.
5. Константы детекции шапки — по реальному заголовку **«Предлагаемое
   количество»** (не «Предполагаемое»; закрыто фазой 0, §4).

## 6. Definition of done фазы 3

- `backend/parser/` — самодостаточный модуль без импортов из БД/FastAPI-слоя;
- юнит-тесты парсера зелёные на fixture; тест на реальном файле проходит локально;
- адаптация один-подрядчик-без-baseline покрыта тестом, написанным до неё (п. 4.3);

- `just test-backend` (весь suite, не только unit) и `just lint-backend` зелёные;
- существующие 205 тестов не тронуты.

## 7. Известные грабли (§11 + фазы 0–2)

- Парсер опирается на объединённые ячейки (`build_merged_shape_map`); **не
  ломать досрочный выход по merged-ячейке в первой колонке** — это признак
  конца позиций / начала summary.
- spaCy грузит модель на import модуля — для юнит-тестов без NLP это
  медленно; смотреть, можно ли отложить загрузку до первого вызова
  нормализации, не ломая детерминизм.
- В tenders-go ключ назывался `comment_organazier` (опечатка); в нашей схеме
  колонка — `comment_organizer`, как в JSON парсера (`constants.py`). При
  порте импорта (фаза 4) маппинг прямой, ничего переименовывать не надо.
- Ruff в проекте строже, чем в исходнике (`select E,F,I,B,UP,SIM`); исходник
  писан под black/isort — будет волна механических правок, делать их отдельным
  коммитом от смысловых.
