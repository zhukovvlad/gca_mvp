## 1. Бизнес-задача

Свести расценки всех договоров генподряда (ГП) 2024–2027 в единую базу:

1. **Единая база расценок** — по объектам и крупным статьям, со сквозным сравнением одной и той же работы между объектами и годами.
2. **Паспорт объекта на одной странице** — договор, подписант, дата, ключевые расценки, отклонения. Печатная форма.
3. **Нормативы расценок по классам объектов** — превышения подсвечиваются автоматически; переутверждение нормативов с учётом инфляции, с историей по периодам действия.
4. **Применение** — предметный торг с подрядчиками, защита цифр перед банком и партнёрами (выгрузки в Excel).

Анализ текстов самих договоров — **вне скоупа MVP** (отдельный модуль позже).

## 3. Ключевые решения (зафиксированы, не пересматривать)

- **Single-tenant.** Внутренний инструмент одной компании. `organizations` и все `org_id` выпиливаются. Роли: `admin` — управление пользователями, классами, нормативами, замена/удаление смет; `member` — чтение, загрузка смет, ручной матчинг (Review).
- **Стек:** Python 3.12, FastAPI, SQLAlchemy 2.x sync ORM, Alembic, psycopg3; PostgreSQL 16 + pgvector (extension включить первой миграцией, векторный матчинг — фаза 2); React + TS, Vite, shadcn/ui, Tailwind, TanStack Query, TanStack Table, Recharts.
- **Без брокеров:** никаких Celery/Redis. Длинные операции — FastAPI `BackgroundTasks` + таблица `import_jobs`. **MVP запускается строго с одним worker-процессом uvicorn** — это условие корректности startup-recovery (§6); зафиксировать в конфиге запуска и README. Таймаут парсинга — **мягкий**: проверка прошедшего времени между этапами пайплайна, не жёсткое прерывание.
- **Деньги:** `numeric` в БД ↔ `Decimal` в Python ↔ строки в JSON. Никаких float. Пустая стоимость в смете → `NULL`, не `0`.
- **Источник истины при импорте — карточка договора.** `contract_id` передаётся в запросе; объект, подрядчик и реквизиты договора НЕ апсертятся из XLSX. Реквизиты из шапки файла сохраняются в raw_data; при расхождении с карточкой — записи в `import_jobs.warnings`.
- **Каталог работ общий.** Единица «идентичности» работы в каталоге — **нормализованное название + единица измерения** (§4).

## 4. Доменная модель

Ключевой факт: **смета к договору ГП структурно = тендерная таблица**, но с одним подрядчиком, без колонки «Расчётная стоимость» (baseline) и с заполненным `suggested_quantity`.

**Уточнено по итогам фазы 0** (замер — `docs/phase0-input-data.md`): в реальном файле колонка называется **«Предлагаемое количество»** (не «Предполагаемое», как в ранних редакциях этого документа) — это количество, предложенное подрядчиком. ## 5. Пайплайн импорта

`POST /api/v1/estimates/upload` (multipart: файл + `contract_id` + `amendment_no?` + `replace?=false`). Лимиты: размер ≤ 25 МБ (настройка), мягкий таймаут 10 мин (§3).

**Правила повторной загрузки для той же пары (contract_id, amendment_no):**

1. **Текущая** смета этой пары загружена **тем же** файлом (`estimates.import_job_id` ведёт на `done`-job с тем же `file_sha256`) → идемпотентно вернуть этот job, не импортировать. Идемпотентность привязана к текущей смете, а не к любому историческому `done`-job: иначе после замены (правило 3) повторная загрузка **вытесненного** файла отвечала бы «уже загружено», хотя в БД лежит другая смета. Такой случай идёт по правилу 2 и требует `replace=true`.
2. Уже существует estimate, файл **другой**, `replace` не передан → **`409 Conflict`** с понятным сообщением («смета уже загружена; для замены повторите с replace=true»).
3. `replace=true` (право: `admin`) → в доменной транзакции: удалить существующий estimate (CASCADE на lots/proposals/positions/raw_data), импортировать новый. Старые `import_jobs` и их файлы **не удаляются** — это аудит; в новом job зафиксировать warning «заменена смета estimate_id=N от <дата>».

Транзакционная модель — **две разные сессии**:

- **Сессия A (промежуточные статусы и ошибки):** переходы `pending→parsing→importing→matching` и запись предупреждений **парсера** — отдельные короткие транзакции с немедленным commit (фронт видит прогресс). Статус `error` пишется сессией A **после** rollback домена и потому его переживает.
- **Сессия B (домен + финал):** шаги 3–4, предупреждения, **описывающие доменное состояние**, и **финальный переход в `done` вместе с итоговыми счётчиками** — одна атомарная транзакция. Смета и её `done`-статус коммитятся неразделимо: не существует состояния «смета в БД, а job не done» (crash window закрыт). При исключении — полный rollback (домена и финального статуса), затем сессия A пишет `error` + текст.

**Предупреждения делятся по тому, о чём они говорят, а не по этапу.** Предупреждение парсера относится к файлу — оно обязано пережить откат домена и быть видно во время прогресса, поэтому его пишет сессия A. Предупреждение о замене сметы, расхождении шапки с карточкой, неизвестной единице или сработавшей эвристике **описывает состояние домена** — оно не должно существовать, если домен откатился, поэтому его пишет сессия B в той же транзакции. Это тот же аргумент, которым выше требуется атомарность `done` со счётчиками. Дописывание в оба конца делается SQL-конкатенацией (`warnings || :items`), а не «прочитать-изменить-записать»: иначе одна сессия теряла бы то, что дописала другая.

Шаги:

1. Валидация, сохранение файла (§8), sha256, создание `import_job` (сессия A), ответ `job_id`. **Сохранённый файл удаляется во всех путях, где новый job не создан:** идемпотентный возврат существующего done-job (правило 1), ответ `409` (правило 2), любая ошибка создания job. Файл остаётся только у реально созданного job. Тяжёлая часть — в `BackgroundTasks`.
2. **Парсинг** (`backend/parser/` = перенесённый `excel_parser`). Адаптация под смету ГП: один подрядчик → один proposal; отсутствие baseline-блока не должно ронять `read_contractors.py` / детекцию шапки (главный технический риск — покрыть тестом на реальном файле ДО написания адаптации); `suggested_quantity` парсится штатно.
3. **Импорт** (сессия B, порт логики `ImportFullTender`): [replace: удаление старого estimate] → estimate → raw_data (+parser_version) → lots → proposal → position_items. Реквизиты из шапки сравнить с карточкой договора → расхождения в `warnings` (не блокируют).
4. **Матчинг** (та же сессия B), каскад для каждой позиции кроме `is_chapter`; везде используется одна и та же нормализованная пара `(normalize(job_title), unit_norm)`:
   1. `cache_key` в `matching_cache` → hit: проставить `catalog_position_id`; продлить TTL только для `source='auto'`; счётчик — по `kind` целевой каталожной строки: `POSITION` → `matched_cache`, `HEADER`/`TRASH` → `matched_nonposition`;
   2. SQL-поиск точного совпадения `(normalized_job_title, unit_id)` среди `kind='POSITION'` → проставить + записать кэш (`source='auto'`);
   3. miss: **атомарный get-or-create** `catalog_positions` — `INSERT ... ON CONFLICT (normalized_job_title, COALESCE(unit_id,-1)) DO NOTHING` + повторный SELECT. По `kind` найденной строки: `TO_REVIEW` → привязаться; `POSITION` → это hit ветки 2 (дубль не создавать, записать кэш); `HEADER`/`TRASH` → привязаться (строка уже вручную размечена как не-работа), позиция не попадает ни в очередь Review, ни в VIEW отклонений; учитывать отдельным счётчиком `matched_nonposition`.
   Нормализация — `sanitize_text.normalize_job_title_with_lemmatization` из парсера; `norm_version` — константа, входит в cache_key.
5. Финальный статус `done` + итоговые счётчики — **последняя операция сессии B**, в той же транзакции, что и домен (см. транзакционную модель выше).

**Recovery при рестарте** (корректно при одном worker, §3): на startup все jobs в статусах `pending|parsing|importing|matching` переводятся в `error` («прерван перезапуском, повторите загрузку»). Повторная загрузка идемпотентна/разрешена по правилам выше.

Recovery — **условие запуска, а не удобство**: незавершённый job держит частичный уникальный индекс `uq_import_jobs_active_pair` (§4), поэтому без recovery повторная загрузка той же пары вечно отвечает `409` до следующего перезапуска. Не выполнившийся recovery обязан ронять старт приложения. Ретенция файлов (§8) — наоборот, best-effort: она выполняется **отдельной транзакцией**, и её ошибка не откатывает recovery и не мешает работе (файл, не удалённый сегодня, удалится при следующем запуске).

**Ручной матчинг (экран Review):** очередь позиций, привязанных к `kind='TO_REVIEW'`. Действия: «слить с существующей POSITION» (поиск FTS/ILIKE), «утвердить как новую POSITION», «пометить HEADER/TRASH». Решение применяется **ко всем** position_items, ссылающимся на данную TO_REVIEW-строку. При слиянии, в одной транзакции: `UPDATE position_items SET catalog_position_id = <target>` → запись в `matching_cache` c **`source='manual'`, `expires_at = NULL`** (ручные решения не истекают) → **`DELETE` TO_REVIEW-строки** (после переноса ссылок она пуста; удаление освобождает её уникальную нормализованную пару, иначе она перехватывала бы будущие get-or-create). «Утвердить как POSITION» / «пометить HEADER/TRASH» — смена `kind` той же строки, без удаления. Инвариант: **записи `matching_cache` никогда не указывают на строки `kind='TO_REVIEW'`** (кэш пишется только в ветках 2/HEADER/TRASH и при ручных решениях) — это условие безопасности DELETE, закрепить тестом. Векторные подсказки по embedding — фаза 2, в MVP не делать.

## 6. Семантика сквозной матрицы (зафиксировано)

- По каждому договору участвует **только последняя смета** (максимальный `amendment_no`, NULL — минимальный). Предыдущие — история в карточке договора, в матрицу не попадают.
- Вес позиции: `w = COALESCE(suggested_quantity, quantity)`. **Подтверждено на реальном файле в фазе 0** (`docs/phase0-input-data.md`), развилка закрыта: авторитетно `suggested_quantity` — колонка «Предлагаемое количество». На 1828 из 1828 расценённых строк `Стоимость всего = цена за единицу × suggested_quantity`, тогда как `quantity` («Общее кол-во») точно так же на 1828 из 1828 строк даёт справочную колонку «Стоимость всего за объемы заказчика». Строк, где `quantity` и осмысленно (≠1), и отличается от `suggested_quantity`, не найдено ни одной — то есть `quantity` в сметах ГП либо заглушка `1`, либо равен `suggested_quantity`, и `COALESCE` даёт верный вес в обоих случаях. Ограничение: проверено на одном образце (§9, фаза 0).
- Работа встречается в смете несколько раз → ячейка = средневзвешенная ставка:
  `SUM(unit_cost_total * w) / SUM(w)` **только по строкам, где `unit_cost_total IS NOT NULL` и `w > 0`**; если таких строк нет — ячейка пустая. Drill-down в позиции по клику.
- Строки = `catalog_positions (kind='POSITION')`, колонки = договоры (группировка по объекту), в ячейке ставка + `deviation_pct` цветом. Фильтры: класс, период, текстовый поиск по названию работы. Фильтр «статья/раздел» — не в MVP (у него нет формального источника: разделы специфичны для каждой сметы, а строки матрицы — каталожные). Закрепление первой колонки. Min/max/разброс — не в MVP.

2. **Ручной матчинг** (на базе Review) — очередь TO_REVIEW, действия из §5.
3. **Нормативы** (на базе ReferencePrices/handbook, право `admin`) — классы, ставки, периоды, форма переутверждения с коэффициентом инфляции (предзаполнение: новая ставка = старая × индекс, редактируемо); ошибки EXCLUDE (пересечение периодов) — человекочитаемый 400.
4. **Паспорт проекта** — страница `/contracts/:id/passport`, **свод по статьям фиксированного классификатора компании** с рублями на квадратный метр: шапка с ТЭП и коммерческими условиями, кольцо структуры стоимости, таблица по статьям. Считается по **исходной** смете договора (`amendment_no IS NULL`). Печать — `@media print`, PDF в MVP = Ctrl+P, **раскладка многостраничная**.

   **Обещание «одна страница А4» снято** (фаза 7, Ф6; обоснование — спека `docs/superpowers/specs/2026-08-10-project-passport-design.md` §2.11 и замер §1.3). Причина: на лист входит порядка 45–50 плотных строк, а непустых ветвей дерева статей замерено 103–178 на смету. Свести их к одному листу можно было либо потеряв второй и третий уровни классификатора — а именно в них живёт разбивка, которую аналитик расписывает руками, — либо показав на бумаге меньше, чем на экране, то есть той самой обрезкой при печати, которую прежняя редакция этого пункта запрещала. Выбран третий вариант: состав полный, печать многостраничная. «Одна страница» в §1 пункт 2 читается после этого как **деловая цель «один свод»**, а не как ограничение печати.

   **Обязательство печатной раскладки осталось, изменилась его формулировка:** замером в браузере проверяется, что **нет обрезки по правому краю и нет разрывов внутри строк**, шапка таблицы повторяется на каждом листе (§11 — `@media print` в jsdom не наблюдаем).

   **`passport_top_n` — история, а не действующий инвариант.** Настройка (таблица настроек, экран Settings) и её `CHECK` 1–20 в миграции 0004 остаются в БД и управляют **экраном фазы 6**, который убран из навигации и вернётся drill-down'ом из статьи. Верхняя граница подобрана замером печатной раскладки **того** экрана (`docs/phase6-analytics.md` §1.5, §3.2) и на паспорт проекта не влияет.
5. **Сквозная матрица** — новая страница на TanStack Table, семантика §6.
6. **Отчёты** (на базе Reports) — Excel через openpyxl: (а) свод расценок по договору с отклонениями; (б) сравнение с нормативами «для банка». Два отчёта — **два файла**: у них разный охват и разные параметры (свод берёт один договор, «для банка» — выборку).

   **Макет «для банка» согласован с пользователем 2026-08-04** (вопрос задан первым сообщением фазы 6, как и требовал прежний текст этого пункта):

   | Что | Решение |
   |---|---|
   | Разрез | **класс → работа**: секции по `rate_class`, внутри — каталожные `POSITION` |
   | Колонки | работа, единица, объём, ставка, норматив, стоимость, отклонение %, **отклонение в деньгах** |
   | Итоги | **по каждому классу и общий** |
   | Шапка | название, период, состав выборки, дата формирования; снизу — блок подписей «Составил / Утвердил» |

   Отклонение в деньгах = `(ставка − норматив) × объём`. Итоги: деньги суммой; отклонение — **средневзвешенное по объёму**, то есть `(факт − норматив) / норматив` по суммам, а не среднее арифметическое процентов (последнее завышает вклад мелких работ и в разговоре с банком даёт неверную цифру). Позиции без норматива в расчёт отклонения **не входят** и показываются отдельным счётчиком в каждом итоге; когда сравнимых работ нет вовсе, отклонение пусто и в процентах, и в деньгах — ноль там читался бы как «сошлось с нормативом». Счётчиков исключённого два, и они образуют **разбиение**: «с объёмом, но без норматива» и «с ценой, но без объёма» — позиция без объёма и без норматива считается один раз, в счётчике объёма (это блокирующая причина: норматив без объёма не помог бы), и суммы сходятся **по файлу**: строка отчёта агрегирует работу (несколько позиций → одна строка), поэтому по числу видимых строк позиции не сосчитать — в итогах печатается счётчик «Сравнимых позиций», а в сноске — независимо посчитанное «Всего расценённых позиций» (`count(*)` по VIEW, не сумма счётчиков), и сравнимые + два счётчика исключённого = всего. Секции строятся от **классов выборки** (договоров с последней сметой), а не от строк с положительным объёмом: класс, все позиции которого без объёма, остаётся секцией со счётчиками, иначе шапка говорила бы «Классов: N», а секций было бы меньше.

## 8. Хранилище файлов

Локальная директория за абстракцией `Storage` (`save/get/delete`, реализация `LocalStorage`, путь из настроек). Требования: имя на диске = непрозрачный ключ (uuid), оригинальное имя — только в БД; никаких путей от клиента; выдача только через авторизованный `GET /api/v1/import-jobs/{id}/file`, не через статику. Ретенция: файлы jobs со статусом `error` старше 30 дней (настройка) удаляются проверкой при старте приложения — т.е. при первом запуске после истечения срока, не ровно в срок; файлы `done`-jobs хранятся бессрочно (аудит). S3-реализация — потом, без правки вызывающих мест.

## 9. Процесс разработки

### 9.1. Цикл фичи (единица работы)

Единица работы — **фича**: связное изменение, которое можно спроектировать,
реализовать и принять целиком. Пять шагов, три гейта:

1. **Брейншторм** — разведка контекста, вопросы по одному, 2–3 варианта с
   trade-off. **Гейт 1: дизайн одобрен в диалоге.**
2. **Спека** → `docs/superpowers/specs/ДАТА-тема-design.md`. **Гейт 2.**
3. **План** → `docs/superpowers/plans/ДАТА-тема.md`. **Гейт 3.**
4. **Реализация** — TDD, коммиты по задачам плана.
5. **Финал** — `docs/devlog/ДАТА-тема.md`, затем PR. Если фича выстрадала правило
   работы — завести инсайт и строку в указателе (§12).

**Гейт — остановка, а не уведомление:** следующий шаг не начинается, пока
предыдущий не одобрен. Гейты проходят в диалоге; отдельных PR под спеку и план
нет — спека, план и реализация живут в одной ветке фичи.

Сокращения: дизайн уже зафиксирован и проверен фактами → спека тонкая (ссылка
на источник + дельта); правка только документации → без плана; тривиальная
механика (опечатка, версия зависимости) → без цикла, но если правка тянет за
собой поведение — это фича. **Гейт 1 не пропускается никогда.**

### 9.2. Таксономия документов

| Документ | Где | Что в нём |
|---|---|---|
| Инварианты и процесс | `AGENTS.md` | архитектурные решения навсегда, процесс, грабли (§11) |
| Рамка фазы | `docs/phaseN-frame.md` | скоуп / вне скоупа / DoD фазы / состав фич |
| Спека фичи | `docs/superpowers/specs/` | проблема с замерами, решение, отвергнутые альтернативы |
| План фичи | `docs/superpowers/plans/` | задачи с чекбоксами, файлы, интерфейсы, Global Constraints, ветка |
| Devlog фичи | `docs/devlog/` | что сделано, замеры, отступления от плана, найденные грабли |
| Инсайт | `docs/insights/` | одно выстраданное правило работы: чем выстрадано, как теперь, чего не ловит (§12) |

**Факт живёт в одном месте.** Спека ссылается на рамку, план — на спеку,
devlog — на план; дублировать текст нельзя. При противоречии побеждает документ,
который ближе к инварианту: `AGENTS.md` → спека → план.

Фазового отчёта в новом процессе нет: при приёмке фазы в её рамку добавляется
врезка «принята, дата» со ссылками на devlog'и фич. Отчёты фаз 0–6
(`docs/phaseN-*.md`) остаются как исторические.

### 9.3. Ветвление, проверки, PR

- Ветка на фичу; префиксы `feat/`, `fix/`, `chore/`, `docs/`, `build/`, `ci/`,
  `perf/`. Имя ветки прописывается в плане.
- Спека, план и реализация — отдельными коммитами **в одной ветке**; PR один,
  со ссылками на спеку и план в описании.
- В `main` напрямую не коммитить. `main` держим зелёным.
- **Перед пушем — `just ci`** (ruff + pytest + eslint + tsc + vitest, шаги по
  отдельности). Правки только в `docs/` от `just ci` освобождены — ни одна
  проверка их не касается.
- Ветки после мержа удаляем.

### 9.4. Фазы (вехи приёмки)

Фаза — граница приёмки и крупная арка, а не единица работы: у неё рамка (§9.2),
состав фич и свой DoD. Приёмка = DoD фазы + прогон на живом стенде + ревью
пользователя. Внешнее ревью пользователь гоняет сам; замечания проверяются по
фактам, тестом до правки.

0. **Входные данные:** получить у пользователя 2–3 реальных XLSX-сметы ГП **до начала работ**. На них же: сверить семантику quantity vs suggested_quantity (§6). **Реальные файлы не коммитить**: каталог `samples/` в `.gitignore`; для тестов подготовить обезличенные fixtures (заменить наименования контрагентов/объектов, сохранить структуру и типы данных).
   **Статус: выполнено условно** (`docs/phase0-input-data.md`) — получен один образец вместо 2–3, сверка §6 проведена и вывод внесён в §4/§6. Дополнительные образцы (другие объекты и годы) нужны **до пилотной приёмки парсера**: вариативность шапки — главный риск фазы 3.
1. **Инициализация и чистка:** в `gca_mvp` — этот документ как `AGENTS.md`, рядом однострочный `CLAUDE.md` с указателем на `AGENTS.md`, `.gitignore` (включая `samples/`), затем перенос кода `udp-tenders@98fb676` **одним коммитом без чужой git-истории**, с текстом коммита вида `import udp-tenders @ 98fb67667c44 as boilerplate` и упоминанием источника в README. На зафиксированной ревизии udp-tenders файла LICENSE нет, а все три исходных репозитория принадлежат автору проекта; если LICENSE/copyright notices появятся в источниках — перенести их файлами, ссылки в README недостаточно. После переноса: удалить LLM/PDF/MinIO/organizations/УПД-домен, привести названия (пакеты, `application_name` в database.py, заголовки фронта) к проекту, зелёные оставшиеся тесты, запуск пустого приложения одним worker.
2. **Схема:** Alembic — pgvector + btree_gist extensions; перенос таблиц tenders-go (raw SQL через `op.execute()` для COALESCE-уникальных, частичных, EXCLUDE-индексов; проверить корректный downgrade); contracts, rate_classes, rate_standards, import_jobs, estimate_raw_data, `normalized_job_title`; VIEW отклонений; слияние units. SQLAlchemy-модели поверх.
3. **Парсер:** перенос `excel_parser` → `backend/parser/`, чистка импортов, адаптация один-подрядчик-без-baseline, юнит-тесты на fixtures из фазы 0.
4. **Импорт+матчинг:** две сессии, транзакция, каскад, recovery, идемпотентность, replace-флоу, эндпоинты. Интеграционные тесты, включая: повторный импорт того же файла (идемпотентность); другой файл без replace (409); replace=true (замена + аудит); два miss с одинаковой нормализованной парой (один TO_REVIEW, не конфликт); ручное решение переживает истечение auto-TTL; рестарт с зависшим job; смета и `done`-статус коммитятся атомарно (симуляция падения между матчингом и финалом не оставляет сметы без done-job); слияние TO_REVIEW удаляет строку и не оставляет кэш-записей на TO_REVIEW.
5. **CRUD и Review:** договоры, нормативы, ручной матчинг, роли.
6. **Аналитика:** паспорт, матрица, Excel (после согласования макета).
   **Статус: выполнено** (`docs/phase6-analytics.md`). Макет «для банка» согласован до начала работ по §7.6 и внесён в §7.6 этого документа; шесть решений §6 брифинга приняты и обоснованы. Метрика §10 перепроверена после наполнения каталога: 4091/4092 на трёх контрольных договорах с новыми `contract_id`.
7. **Паспорт проекта по статьям классификатора** — рамка и состав фич:

## 10. Definition of Done

DoD ниже — **проектный**. У каждой фичи свой DoD в её спеке, у фазы — в её рамке (§9.2).

- Реальная смета проходит конвейер целиком. Метрика матчинга: после первичного наполнения каталога и ручной обработки очереди Review те же файлы фазы 0 загружаются для **специально созданных контрольных договоров с новыми `contract_id`** (иначе сработает идемпотентность и вернутся старые jobs); по счётчикам этих новых jobs `(matched_cache + matched_exact) / positions_total ≥ 90%`, где `positions_total` = число позиций, допущенных к каскаду матчинга (`is_chapter = false`; `matched_nonposition` в знаменатель входит, в числитель — нет).
- Паспорт проекта показывает **все** поля §1 пункт 2 (номер договора, подписант, дата, ключевые расценки в разрезе статей классификатора, отклонения) и печатается **без обрезки по правому краю и без разрывов внутри строк**, с повторением шапки таблицы на каждом листе; состав тот же в §7.4. Печать многостраничная — обещание «одна страница А4» снято фазой 7 с обоснованием (§7.4). Проверяется **только замером в браузере**: `@media print` в jsdom не наблюдаем (§11). Прежняя редакция ссылалась на «§1.2» — подраздела с таким номером в документе нет.
- Превышение норматива видно в матрице и паспорте без ручных действий; «нет норматива» отличим от «0%».
- Переутверждение норматива не меняет отклонения старых смет (сравнение по дате сметы).
- Прерванный рестартом импорт не оставляет ни зависшего job, ни половины сметы в БД.
- Ручное решение из Review продолжает матчить ту же позицию спустя >30 дней (тест с подменой времени).
- Загрузка исправленного файла даёт 409 без replace и корректную замену с replace.
- `pytest` и `vitest` зелёные; критический путь покрыт интеграционными тестами.

## 11. Известные грабли

- COALESCE-уникальные, частичные и EXCLUDE-индексы — только raw SQL в миграциях; `alembic downgrade` должен их корректно снимать.
- Парсер опирается на объединённые ячейки (`build_merged_shape_map`); не ломать досрочный выход по merged-ячейке в первой колонке (признак конца позиций / начала summary).
- `normalize_job_title_with_lemmatization` тянет NLP-зависимости (pymorphy3/natasha) — оставить только реально используемые; spaCy-модель не тащить, если не используется. Нормализация должна быть **детерминированной** (одна строка → всегда один результат) — иначе разъедутся кэш, каталог и матчер.
- Инкремент `norm_version` — это не «поменял константу»: обязательная миграция перевыпуска ключей `source='manual'` (§4) и пересчёт `normalized_job_title` в каталоге.
- `UNIQUE NULLS NOT DISTINCT` — PG16-синтаксис; в тестах та же мажорная версия PG, что и в проде.
- **Откат приложения ниже миграции 0003 не поддерживается после первой сметы с многокилобайтовым наименованием.** Индексы версии 0002 такие значения не проиндексируют, поэтому `alembic downgrade` упрётся в те же `ProgramLimitExceeded`; downgrade сам это проверяет и отказывается с объяснением, а не сырой ошибкой PostgreSQL. Вернуться на 0002 можно только удалив или сократив эти строки — это потеря данных и решение человека, не миграции. Схема откатывается, данные нет.
- **btree не индексирует значения длиннее 2704 байт**, а наименование работы приходит из ячейки XLSX и бывает многокилобайтовым (реальный файл: 5077 символов). Любой новый индекс по тексту из сметы — только по `sha256`/GIN, иначе импорт падает `ProgramLimitExceeded` и смета не сохраняется целиком. Две тонкости, обе проверены замером: индексный кортеж перед проверкой предела **сжимается**, поэтому фикстура из повторяющейся фразы дефект не воспроизводит (нужен несжимаемый текст); и `text::bytea` разбирает вход как escape-формат — «C:\temp» приводится с ошибкой, а «\x41» молча даёт тот же байт, что «A», поэтому обратные слэши удваиваются перед приведением (`replace(x,'\','\\')`), а `convert_to` не годится вовсе — она `stable`.
- Деньги: Decimal end-to-end; в JSON — строки; в тестах сравнивать Decimal с Decimal.
- **Pydantic ключует `field_validator`-ы по имени метода.** Два миксина с
  одноимёнными валидаторами схлопываются в **один** слот: побеждает первый по
  MRO, второй исчезает молча — защита читается как живая, будучи мёртвой.
  Замерено в Ф5 фазы 7: схема, наследующая `_MoneyMixin` и `_PercentMixin`, где
  оба метода назывались `_reject_float`, отвергала `float` в сумме договора и
  **принимала** его в проценте условия. Имена методов-валидаторов обязаны быть
  уникальными по всему дереву наследования схемы; проверяется прогоном по
  конкретному входу, а не чтением — по коду оба валидатора выглядят живыми.
- Один uvicorn worker — не «дефолт, который можно поменять», а условие корректности recovery; при переходе на несколько workers понадобится лизинг jobs (за скоупом MVP).
- **Печатную раскладку А4 проверяет только замер в браузере.** `@media print` в jsdom не наблюдаем, и расчёт «на бумаге» ошибается: паспорт с экранными KPI-карточками занимал 284 мм при доступных 277, а таблица с ширинами колонок в rem выходила за правый край листа больше чем на 1100 px, то есть на бумаге правые колонки просто обрезались бы. Ни один тест этого не поймал. Любая правка печатной формы требует замера высоты листа и выхода за край при **максимальном** N (`docs/phase6-analytics.md` §3.2).
- **Наименование работы надо зажимать по высоте всюду, где оно попадает в таблицу.** В каталоге есть работа с наименованием на 5077 символов, и без зажима её ячейка вырастает до 1323 px — одна строка выше листа А4, остальные уезжают за экран. Тонкость: класс `block` рядом с `line-clamp` отменяет `display: -webkit-box`, без которого зажим не работает вовсе; первая правка из-за этого сделала хуже (2201 px), и увидеть это можно только замером.
- **Точность денег в xlsx ограничена форматом, а не кодом.** Формат хранит числа как IEEE-754 double: до ~15 значащих цифр значение доезжает точно, дальше теряет младшие разряды (замер: `12345678901234567.89` → `1.234567890123457e+16`). Писать деньги текстом нельзя — банк складывает колонку, а `СУММ` по тексту даёт ноль. То есть §3 выполняется до файла включительно по величинам договоров ГП, но «полная точность» в xlsx — неправда, и обещать её не надо.

## 12. Выстраданные правила работы (инсайты)

§11 — про то, где укусит стек и домен. Здесь — про то, **как работать и как
проверять**. Каждое правило заведено потому, что его отсутствие уже стоило
проекту дефекта или ложно-зелёного прогона; в файле указано, чем именно
выстрадано и **чего правило не ловит**.

- **[Тест, доказывающий защиту, обязан быть проверен снятием защиты](docs/insights/verifying-guards.md)** — восемь слоёв, каждый добавлен после того, как предыдущего не хватило: снять и увидеть красный; убедиться, что снятие применилось; контрольный прогон до снятия; форма CI и по отдельности; эталон не должен ехать вместе с проверяемым; снятие доказывает только исполняемый путь; не валит ничего → защиты нет; защита бывает не одна — снятие одной дефект не воспроизводит, а соседняя защита маскирует снятую, и вход негативного теста обязан нарушать ровно одно ограничение, иначе маскировку создаёт сам выбор входа.
- **[Предпосылка теста бывает ложной, и видно это только замером](docs/insights/false-test-premises.md)** — лемма, которой модель не даёт; выборочный промах float; вакуозный тест метки времени в транзакции. Предпосылку, способную тихо измениться, проверять внутри самого теста.
- **[Прогон, который молчит вместо того чтобы упасть](docs/insights/silent-test-runs.md)** — успех читается по числу прошедших, а не по коду возврата: файл без `pytestmark` (молча пропало 65 тестов), integration без `TEST_DATABASE_URL`, `&&` с `grep` вместо отдельных шагов, невзлетевший раннер, снесённый `caplog`, `try/finally` в PowerShell (после блока `$?` равен `True` при ненулевом `$LASTEXITCODE`).
- **[Дефект, который просыпается только на партии](docs/insights/batch-larger-than-five.md)** — `prepare_threshold = 5` в psycopg3: партия из 5 проходит, из 10 падает. Raw-SQL объекты схемы проверять партией >5, а не одной строкой.
- **[Новое правило надо прогнать, а не описать](docs/insights/replaying-new-rules.md)** — три слоя, все оплачены в Ф2: свойство проверки утверждалось, не будучи прогнанным по конкретному входу (неисполнимый тест колонки A, ложно-зелёный тест денег); новое правило не прогонялось по **уже существующим** входам (строка лота в общем хелпере, моки в чужом файле, лист без A/B); и — отдельно — покрытие спеки сверялось по памяти, поэтому три её поведенческих требования остались без исполняющего теста при верной реализации, и нашли это ревьюеры. На финале строить соответствие «требование спеки → тест» списком; требование без теста либо получает тест, либо объявляется границей в devlog.

Новый инсайт заводится на финале фичи (§9.1 шаг 5) и **только** если отсутствие
правила уже стоило дефекта — со ссылкой на случай. Положительные приёмы и общие
соображения сюда не попадают: документ читается целиком в начале каждой сессии,
и его ценность держится на том, что каждая строка оплачена.
